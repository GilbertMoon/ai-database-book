# Chapter 09 실습 발표 강의안

## 트랜잭션으로 좌석·수강신청·결제 정합성 검증하기

> 목적: `transaction_lab` 스키마에서 좌석 차감, 수강신청 생성, 결제 생성을 트랜잭션으로 실행하고 COMMIT·ROLLBACK·SAVEPOINT·Lock 결과를 기록한다.  
> 기준: 초보자가 “무엇을 실행하고, 어떤 결과가 나와야 하며, 다르면 무엇을 확인해야 하는지”를 직관적으로 이해할 수 있어야 한다.

트랜잭션에서 중요한 것은 변경 전 상태를 알고 시작하는 것입니다. 그래야 변경 후 결과가 맞는지 판단할 수 있습니다.

## 8. FOR UPDATE, 조건부 UPDATE, RETURNING을 함께 봅니다

**화면 구성**

| 기능 | 역할 | 확인할 결과 |
|---|---|---|
| `FOR UPDATE` | 좌석 행 잠금 | 대상 행 확인 |
| `remaining_seats > 0` | 좌석 있을 때만 차감 | UPDATE 1행 |
| `RETURNING` | 변경 결과 반환 | course_id, price |
| CTE | 좌석 성공 결과로 신청·결제 연결 | 후속 INSERT 1건 |

**발표 스크립트**

성공 트랜잭션의 핵심 구문은 세 가지입니다.

`FOR UPDATE`는 좌석 행을 잠급니다. 조건부 UPDATE는 좌석이 실제로 남아 있을 때만 차감합니다. `RETURNING`은 그 변경이 성공했는지 증거를 보여 줍니다.

CTE는 좌석 확보 결과가 있을 때만 신청과 결제가 생성되도록 연결합니다.

따라서 단순히 SQL이 실행되었다가 아니라, 각 단계에서 몇 행이 영향을 받았는지를 확인해야 합니다.

## 10. ROLLBACK 실습은 임시 상태와 복구 상태를 비교합니다

**화면 구성**

| 대상 | 트랜잭션 전 | 트랜잭션 내부 | ROLLBACK 후 |
|---|---:|---:|---:|
| course 302 remaining | 1 | 0 | 1 |
| enrollment 9002 | 0행 | 1행 | 0행 |
| payment 9902 | 0행 | 1행 | 0행 |

**발표 스크립트**

04 파일은 실패를 가정한 ROLLBACK 실습입니다.

트랜잭션 내부에서는 좌석이 줄고 신청과 결제가 생깁니다. 하지만 외부 결제 승인 실패를 가정하면 이 변경을 확정하면 안 됩니다.

`ROLLBACK`을 실행한 뒤에는 좌석, 신청, 결제가 모두 원래 상태로 돌아왔는지 확인합니다.

이 비교를 통해 ROLLBACK이 “아직 확정하지 않은 변경”을 취소한다는 것을 직접 확인합니다.

## 11. ROLLBACK과 IDENTITY 번호를 구분합니다

**화면 구성**

| 문장 | 판단 |
|---|---|
| ROLLBACK 후 명시적 ID를 다시 직접 입력할 수 있다 | 가능 |
| IDENTITY 자동 번호도 항상 회수된다 | 아님 |
| 명시적 ID 입력이 다음 자동값을 이동시킨다 | 아님 |

**발표 스크립트**

이 실습에서는 비교를 쉽게 하려고 ID를 직접 입력합니다.

직접 입력한 9002 행이 ROLLBACK으로 사라졌다면, 같은 번호를 다시 직접 입력할 수 있습니다.

하지만 자동 IDENTITY 번호는 다릅니다. 자동으로 발급된 번호는 트랜잭션이 취소되어도 회수되지 않을 수 있습니다.

또 명시적 ID를 넣었다고 해서 다음 자동값이 자동 조정되는 것도 아니므로 마지막에는 필요한 경우 `RESTART WITH`를 확인합니다.

## 13. 좌석 부족은 0행 결과로 확인합니다

**화면 구성**

| 질문 | 기대 |
|---|---|
| 좌석 UPDATE 결과 | 0행 |
| 신청 INSERT | 0행 |
| 결제 INSERT | 0행 |
| SQL 문법 오류 | 아님 |
| 업무상 성공 | 아님 |
| 종료 | ROLLBACK |

**발표 스크립트**

강의 302의 좌석이 0인 상태에서 다시 신청을 시도합니다.

이때 `remaining_seats > 0` 조건을 만족하지 않으므로 UPDATE는 0행입니다. 이것은 SQL 오류가 아니라 조건에 맞는 행이 없다는 뜻입니다.

중요한 것은 업무 판단입니다. 좌석을 확보하지 못했으므로 신청과 결제를 만들면 안 됩니다.

따라서 이 트랜잭션은 COMMIT하지 않고 ROLLBACK으로 종료합니다.

## 15. 좌석 사용량 공식으로 다시 검산합니다

**화면 구성**

```text
활성 수강신청 수 = capacity - remaining_seats
```

| course_id | active enrollment | used seats | 일치 |
|---:|---:|---:|---|
| 301 | 1 | 1 | 예 |
| 302 | 1 | 1 | 예 |
| 303 | 0 | 0 | 예 |

**발표 스크립트**

최종 검증에서 특히 중요한 것은 좌석과 신청 수가 맞는지입니다.

좌석이 줄었다면 그만큼 활성 수강신청이 있어야 합니다. 반대로 활성 수강신청이 있는데 좌석이 줄지 않았다면 정합성이 깨진 것입니다.

그래서 `capacity - remaining_seats`와 실제 수강중 신청 수를 비교합니다.

이 값이 모두 맞으면 좌석과 신청의 의미가 일치한다고 볼 수 있습니다.

```text
enrollment 9001: 수강중 → 취소
course 301 remaining: 1 → 2

```

**발표 스크립트**

하지만 이 선택 실습은 주 실습 최종 상태를 보존하기 위해 마지막에 ROLLBACK합니다.

실습 목적은 “취소와 좌석 복구도 같은 트랜잭션이어야 한다”는 구조를 이해하는 것입니다.

## 17. SAVEPOINT는 일부 단계만 되돌릴 때 사용합니다

**화면 구성**

```text
BEGIN
→ SAVEPOINT
→ 좌석 임시 차감
→ 중복 활성 신청 오류
→ ROLLBACK TO SAVEPOINT
→ 좌석 복구 확인
→ ROLLBACK
```

**발표 스크립트**

09 선택 실습은 오류와 SAVEPOINT를 다룹니다.

트랜잭션 안에서 오류가 발생하면 일반적으로 전체 트랜잭션을 ROLLBACK해야 합니다.

하지만 오류가 날 수 있는 구간 앞에 SAVEPOINT를 만들어 두면, 전체가 아니라 특정 지점까지만 되돌릴 수 있습니다.

이 실습에서는 좌석을 임시로 차감한 뒤 중복 활성 신청 오류를 발생시키고, SAVEPOINT로 돌아가 좌석 차감까지 되돌리는 흐름을 확인합니다.

## 18. 두 세션 Lock 실습은 별도 연결에서 진행합니다

**화면 구성**

- 세션 A
  - `BEGIN`
  - course 303 `FOR UPDATE`
- 세션 B
  - 다른 연결에서 `BEGIN`
  - `lock_timeout = 5s`
  - 같은 course 303 `FOR UPDATE`

**발표 스크립트**

07 선택 실습은 두 개의 SQL Editor와 서로 다른 연결 세션이 필요합니다.

세션 A가 강의 303의 좌석 행을 `FOR UPDATE`로 잠그면, 세션 B는 같은 행을 잠그려고 할 때 기다릴 수 있습니다.

이 실습은 Lock 대기를 확인하기 위한 것입니다. B가 기다리거나 timeout이 발생하면 반드시 ROLLBACK으로 종료합니다.

READ COMMITTED에서는 A가 끝난 뒤 B가 최신 상태를 다시 확인해야 합니다.

## 19. AI 트랜잭션 SQL을 실패 경로 중심으로 검토합니다

**화면 구성**

```sql
UPDATE transaction_lab.course_inventory
SET remaining_seats = remaining_seats - 1
WHERE course_id = 302;

INSERT INTO transaction_lab.enrollments (...);
COMMIT;
INSERT INTO transaction_lab.payments (...);
```

- 문제 찾기: 좌석 조건, 결제 분리, 검증 없음, COMMIT 위치, 중복 처리

**발표 스크립트**

AI가 만든 SQL은 실행될 수 있어도 안전하지 않을 수 있습니다.

예시 SQL은 `remaining_seats > 0` 조건이 없습니다. 좌석이 없어도 음수로 줄어들 수 있습니다.

또 신청을 COMMIT한 뒤 결제를 따로 INSERT합니다. 결제 INSERT가 실패하면 신청만 남게 됩니다.

COMMIT 전 검증도 없고, 중복 활성 신청이나 오류 복구도 고려하지 않습니다.

트랜잭션 SQL을 검토할 때는 정상 경로보다 실패 경로를 먼저 확인해야 합니다.

## 20. 최종 점검: 안전한 트랜잭션을 한 문장으로 설명합니다

**화면 구성**

- 체크리스트
  - 사전 조건 검사
  - 같은 세션 실행
  - 조건부 UPDATE
  - 영향 행 수 확인
  - COMMIT 전 검증
  - ROLLBACK·SAVEPOINT 복구
  - 최종 검증 통과

**발표 스크립트**

실습의 마지막에는 안전한 트랜잭션을 한 문장으로 설명해 봅니다.

안전한 트랜잭션은 관련 변경을 같은 경계 안에 묶고, 조건과 영향 행 수를 확인하며, 최종 상태가 맞을 때만 COMMIT하는 처리입니다.

예상과 다르거나 오류가 나면 ROLLBACK해야 합니다. 일부 복구가 필요하면 SAVEPOINT를 사용할 수 있습니다.

이 습관이 실제 서비스에서 데이터 정합성을 지키는 기본입니다.
