# Chapter 09 실습 발표 강의안

## 트랜잭션으로 좌석·수강신청·결제 정합성 검증하기

> 목적: `transaction_lab` 스키마에서 좌석 차감, 수강신청 생성, 결제 생성을 트랜잭션으로 실행하고 COMMIT·ROLLBACK·SAVEPOINT·Lock 결과를 기록한다.  
> 기준: 초보자가 “SQL을 실행했다”가 아니라 “업무 단위, 실행 전 상태, 영향 행 수, COMMIT 전 검증, 실패 시 복구 방법을 확인했다”라고 말할 수 있어야 한다.

---

## 1. 이번 실습은 조회가 아니라 변경을 다룹니다

**화면 구성**

```text
01 schema
→ 02 seed
→ 03 성공 COMMIT
→ 04 실패 ROLLBACK
→ 05 두 번째 COMMIT과 좌석 부족
→ 06 최종 검증
```

**발표 스크립트**

챕터 09 실습은 실제 데이터를 변경합니다. 따라서 파일을 빠르게 실행하는 것보다 각 단계가 어떤 상태를 만들고, 무엇을 확인한 뒤 다음 단계로 넘어가야 하는지가 더 중요합니다.

이번 실습의 주 흐름은 스키마 생성, 초기 데이터 입력, 성공 커밋, 실패 롤백, 좌석 부족 처리, 최종 검증입니다.

---

## 2. 같은 연결 세션에서 실행해야 합니다

**화면 구성**

- 같은 DBeaver SQL Editor
- 같은 연결 세션
- `BEGIN`과 `COMMIT`을 다른 연결에서 실행하지 않음
- 객체는 `transaction_lab.` 또는 `course_project.`로 명시

**발표 스크립트**

트랜잭션은 현재 연결 세션 안에서 유지됩니다. `비긴`을 실행한 연결과 `커밋` 또는 `롤백`을 실행하는 연결이 달라지면 같은 트랜잭션을 제어하는 것이 아닙니다.

따라서 주 실습은 같은 에스큐엘 Editor와 같은 연결에서 순서대로 실행합니다. 현재 스키마가 `트랜잭션 랩`일 필요는 없지만, 테이블 이름은 스키마까지 명시해 사용합니다.

## 3. 실행 전 사전 조건을 확인합니다

**화면 구성**

```sql
SELECT current_database();
SELECT current_schema();
SHOW search_path;
```

기대:

```text
ai_database_book
course_project.enrollments = 5행
transaction_lab 기존 없음
```

**발표 스크립트**

먼저 현재 데이터베이스가 `ai_database_book`인지 확인합니다. 챕터 09는 챕터 07의 학생과 강의 데이터를 참조하므로 `코스 프로젝트` 테이블도 존재해야 합니다.

또한 `트랜잭션 랩`이 이미 있으면 이전 실습 상태가 남아 있을 수 있습니다. 보존할 데이터가 없다면 초기화 후 다시 시작합니다.

## 4. 스키마 생성도 하나의 트랜잭션입니다

**화면 구성**

```text
BEGIN
→ 사전 조건 검사
→ CREATE SCHEMA
→ CREATE TABLE
→ CREATE INDEX
→ COMMIT
```

**발표 스크립트**

`01_transaction_lab_schema.sql`은 실습 스키마와 테이블을 만듭니다. 이 작업도 하나의 트랜잭션으로 구성되어 있습니다.

중간에 테이블 생성이 실패하면 일부 객체만 남는 상황을 줄이기 위해 전체 생성 단위를 함께 확정하거나 중단합니다.

실행 후에는 `트랜잭션 랩.코스 인벤토리`, `트랜잭션 랩.인롤먼츠`, `트랜잭션 랩.페이먼츠`가 만들어졌는지 확인합니다.

## 5. 초기 데이터는 좌석 검증의 기준입니다

**화면 구성**

| course_id | capacity | remaining_seats |
|---:|---:|---:|
| 301 | 2 | 2 |
| 302 | 1 | 1 |
| 303 | 1 | 1 |

```text
enrollments = 0행
payments = 0행
```

**발표 스크립트**

`02_transaction_lab_seed.sql`은 좌석 초기 상태를 만듭니다. 강의 301은 좌석 2개, 302와 303은 좌석 1개입니다.

실습용 수강신청과 결제는 0건이어야 합니다. 이 상태를 기준으로 이후 좌석 차감, 롤백, 좌석 부족을 판단합니다.

---

## 6. 성공 COMMIT 실습의 업무 단위를 먼저 말합니다

**화면 구성**

```text
학생 101이 강의 301을 신청한다.

1. 좌석 1개 차감
2. enrollment 9001 생성
3. payment 9901 생성
4. 결과 검증
5. COMMIT
```

**발표 스크립트**

성공 실습에서는 학생 101이 강의 301을 신청한다고 가정합니다. 이 업무는 좌석 차감, 수강신청 생성, 결제 생성으로 구성됩니다.

세 작업 중 하나만 성공하면 안 됩니다. 따라서 한 트랜잭션 안에서 실행하고, 커밋 전에 결과를 확인합니다.

---

## 7. `FOR UPDATE`는 좌석 행을 잠급니다

**화면 구성**

```sql
SELECT ...
FROM transaction_lab.course_inventory
WHERE course_id = 301
FOR UPDATE OF ci;
```

- 잠금 대상: course 301 좌석 행
- 아직 좌석 차감 아님

**발표 스크립트**

먼저 좌석 행을 `포 업데이트`로 조회합니다. 이 문장은 다른 트랜잭션이 같은 행을 동시에 수정하지 못하도록 잠그는 역할을 합니다.

하지만 이 시점에는 좌석이 줄어든 것이 아닙니다. 잠금은 최신 상태를 확인하고 안전하게 변경할 준비를 하는 단계입니다.

---

## 8. 좌석 확보는 UPDATE 1행으로 확인합니다

**화면 구성**

```text
UPDATE ... remaining_seats > 0
RETURNING ...
```

| 결과 | 의미 |
|---|---|
| 1행 | 좌석 확보 성공 |
| 0행 | 좌석 부족 |

**발표 스크립트**

좌석 확보의 성공 여부는 조건부 업데이트가 몇 행을 바꾸었는지로 판단합니다.

`remaining_seats > 0` 조건이 있으므로 좌석이 남아 있으면 1행이 변경됩니다. 좌석이 없으면 0행입니다.

0행은 에스큐엘 오류가 아니라 업무상 실패입니다. 이 차이를 반드시 구분해야 합니다.

---

## 9. 신청과 결제는 좌석 성공 결과에 연결됩니다

**화면 구성**

```text
seat CTE
→ new_enrollment CTE
→ payments INSERT
```

기대:

```text
enrollment 9001 = 1행
payment 9901 = 1행
```

**발표 스크립트**

성공 파일은 씨티이를 이용해 좌석 업데이트 결과를 신청 인서트와 결제 인서트로 연결합니다.

좌석 업데이트 결과가 비어 있으면 후속 인서트도 실행 대상이 없습니다. 이렇게 해야 좌석 없이 신청이나 결제가 만들어지는 상태를 줄일 수 있습니다.

---

## 10. COMMIT 전 검증 결과를 기록합니다

**화면 구성**

| 확인 항목 | 기대 |
|---|---:|
| enrollment 9001 | 1행 |
| payment 9901 | 1행 |
| recorded_amount | 100000 |
| payment amount | 100000 |
| course 301 remaining | 1 |

**발표 스크립트**

커밋 전에 결과를 확인합니다. 신청과 결제가 각각 1행인지, 두 금액이 100000으로 일치하는지, 강의 301의 잔여 좌석이 1인지 봅니다.

이 조건이 모두 맞아야 커밋합니다. 하나라도 다르면 커밋하지 않고 원인을 확인해야 합니다.

---

## 11. ROLLBACK 실습은 실패 상황을 안전하게 확인합니다

**화면 구성**

```text
학생 102, 강의 302
좌석 차감 + 신청 9002 + 결제 9902
→ 외부 결제 실패 가정
→ ROLLBACK
```

**발표 스크립트**

`04_rollback_transaction.sql`은 일부러 실패를 가정하는 실습입니다. 트랜잭션 내부에서는 좌석이 줄고 신청과 결제가 보일 수 있습니다.

하지만 외부 결제 실패라고 판단하면 커밋하지 않습니다. 롤백을 실행해 미확정 변경을 모두 취소합니다.

---

## 12. ROLLBACK 전후 상태를 비교합니다

**화면 구성**

| 대상 | 트랜잭션 내부 | ROLLBACK 후 |
|---|---:|---:|
| course 302 remaining | 0 | 1 |
| enrollment 9002 | 있음 | 없음 |
| payment 9902 | 있음 | 없음 |

**발표 스크립트**

롤백 후에는 강의 302의 좌석이 다시 1이어야 합니다. 신청 9002와 결제 9902도 없어야 합니다.

트랜잭션 내부에서 보였던 값이 확정되지 않았다는 점을 확인하는 것이 이 장의 핵심 경험입니다.

---

## 13. 두 번째 COMMIT으로 좌석 302를 소진합니다

**화면 구성**

```text
학생 103이 강의 302 신청
→ enrollment 9002 생성
→ payment 9902 생성
→ course 302 remaining = 0
→ COMMIT
```

**발표 스크립트**

다음 실습에서는 강의 302의 남은 좌석 1개를 정상적으로 사용합니다. 이번에는 신청과 결제를 만들고 커밋합니다.

이후 강의 302의 잔여 좌석은 0이 됩니다. 이 상태에서 같은 강의에 추가 신청을 시도하면 좌석 부족 상황을 확인할 수 있습니다.

---

## 14. 좌석 부족은 ROLLBACK으로 종료합니다

**화면 구성**

```text
course 302 remaining = 0
추가 신청 시도
→ 좌석 UPDATE 0행
→ 신청 0행
→ 결제 0행
→ ROLLBACK
```

**발표 스크립트**

강의 302의 좌석이 이미 0인 상태에서 추가 신청을 시도하면 좌석 업데이트는 0행입니다.

이것은 문법 오류가 아니라 좌석이 없다는 업무 결과입니다. 신청과 결제가 만들어지면 안 되므로 트랜잭션은 롤백으로 종료합니다.

---

## 15. 최종 검증 파일로 정합성을 확인합니다

**화면 구성**

```text
course_project.enrollments = 5
lab enrollments = 2
payments = 2
course 301 remaining = 1
course 302 remaining = 0
course 303 remaining = 1
```

**발표 스크립트**

`06_transaction_validation.sql`은 주 실습의 최종 상태를 검증합니다.

챕터 07의 수강신청 5건은 그대로 유지되어야 하고, 실습용 신청과 결제는 각각 2건이어야 합니다.

또 좌석 범위 위반, 결제 누락, 금액 불일치, 고아 payment, 중복 활성 신청이 모두 0행인지 확인합니다.

## 16. 취소와 좌석 복구도 하나의 트랜잭션입니다

**화면 구성**

```text
수강중 → 취소
+ remaining_seats 1 증가
```

- 선택 실습
- 기본적으로 마지막에 ROLLBACK

**발표 스크립트**

신청을 취소할 때 상태만 취소로 바꾸면 좌석 사용량이 맞지 않을 수 있습니다. 취소와 좌석 복구도 함께 처리해야 합니다.

`08_cancel_and_restore.sql`은 이 상황을 보여 주는 선택 실습입니다. 주 실습의 최종 상태를 보존하기 위해 기본적으로 마지막에 롤백합니다.

---

## 17. 오류와 SAVEPOINT 실습은 조심해서 진행합니다

**화면 구성**

```text
BEGIN
SAVEPOINT before_optional_step
오류 가능 SQL
ROLLBACK TO SAVEPOINT
계속 진행
COMMIT 또는 ROLLBACK
```

**발표 스크립트**

트랜잭션 안에서 오류가 나면 이후 정상 에스큐엘도 실행되지 않고 `커런트 트랜잭션 이즈 어보티드`가 나올 수 있습니다.

기본 대응은 전체 롤백입니다. 일부 선택 단계만 되돌리고 계속 진행하려면 오류가 나기 전에 세이브포인트를 만들어야 합니다.

이 실습은 주석을 한 구간씩 해제해 천천히 진행합니다.

---

## 18. 두 세션 Lock 실습은 연결을 분리해야 합니다

**화면 구성**

```text
세션 A: BEGIN → course 303 FOR UPDATE
세션 B: BEGIN → 같은 행 FOR UPDATE
→ 대기 또는 lock_timeout
```

**발표 스크립트**

동시성 실습은 두 개의 에스큐엘 Editor 또는 서로 다른 연결 세션이 필요합니다. 같은 세션에서 실행하면 락 대기 상황을 제대로 볼 수 없습니다.

세션 A가 course 303 행을 잠그고 있으면 세션 B는 같은 행을 잠그려 할 때 기다릴 수 있습니다.

오류가 나거나 timeout이 나면 해당 트랜잭션을 롤백으로 종료합니다.

## 19. 초기화는 `transaction_lab`만 대상으로 합니다

**화면 구성**

```text
reset_transaction_lab.sql
→ 현재 DB 확인
→ transaction_lab 객체만 삭제
→ course_project 보호
```

**발표 스크립트**

실습을 처음부터 다시 시작할 때는 초기화 파일을 사용합니다. 하지만 초기화는 실제 데이터를 삭제하는 작업입니다.

챕터 09 초기화는 `트랜잭션 랩`만 대상으로 해야 합니다. 챕터 07과 08에서 사용하는 `코스 프로젝트` 데이터는 유지되어야 합니다.

실행 전 삭제 대상과 현재 데이터베이스를 반드시 확인합니다.

## 20. 최종 완료 기준은 성공·실패·복구를 모두 설명하는 것입니다

**화면 구성**

- 성공 COMMIT 결과 설명
- 실패 ROLLBACK 전후 비교
- 좌석 부족 0행 처리
- 최종 정합성 검증 통과
- 오류 후 ROLLBACK 또는 SAVEPOINT 설명
- Lock 대기와 Deadlock 구분
- AI SQL 실패 경로 검토

**발표 스크립트**

챕터 09 실습의 완료 기준은 커밋이 한 번 성공했다는 것이 아닙니다.

성공한 트랜잭션은 왜 확정했는지, 실패한 트랜잭션은 왜 되돌렸는지, 좌석 부족이 왜 에스큐엘 오류가 아닌지, 오류 후 어떤 복구가 필요한지 설명할 수 있어야 합니다.

에이아이가 만든 트랜잭션 에스큐엘도 같은 기준으로 검토합니다. 정상 경로뿐 아니라 실패 경로와 복구 경로까지 있어야 안전한 트랜잭션 설계라고 볼 수 있습니다.
