# Chapter 09 이론 발표 강의안

## 트랜잭션으로 데이터 정합성 지키기

> 목적: 좌석 차감, 수강신청 생성, 결제 기록처럼 함께 성공해야 하는 여러 변경을 트랜잭션으로 묶어 정합성을 지키는 사고방식을 설명한다.  
> 기준: 초보자가 각 장표를 보며 “왜 BEGIN이 필요하고, 언제 COMMIT·ROLLBACK해야 하는지” 직관적으로 이해할 수 있어야 한다.

---

## 1. 여러 변경을 하나의 업무 단위로 묶습니다

**화면 구성**

- 큰 제목: 트랜잭션으로 데이터 정합성 지키기
- 흐름: 좌석 차감 → 수강신청 생성 → 결제 기록 → 검증 → COMMIT 또는 ROLLBACK
- 키워드: 업무 단위 / 함께 성공 / 함께 취소

**발표 스크립트**

이번 장은 조회가 아니라 변경을 안전하게 처리하는 방법을 배웁니다.

온라인 강의 신청을 생각해 보겠습니다. 학생이 강의를 신청하면 남은 좌석이 줄어야 하고, 수강신청 행이 생겨야 하며, 결제 행도 함께 생겨야 합니다.

이 셋 중 하나만 성공하면 데이터가 이상해집니다. 좌석만 줄었는데 신청이 없거나, 신청은 있는데 결제가 없거나, 결제는 있는데 연결된 신청이 없을 수 있습니다.

트랜잭션은 이런 여러 변경을 하나의 업무 단위로 묶어 “모두 성공하면 확정, 하나라도 문제면 취소”하도록 만드는 장치입니다.

---

## 2. 트랜잭션은 SQL 묶음이 아니라 업무 경계입니다

**화면 구성**

- 강조 문장: 트랜잭션 = 업무가 시작되고 확정되는 범위
- 비교 카드
  - 단순 SQL 묶음: 여러 문장을 차례로 실행
  - 업무 트랜잭션: 함께 성공해야 할 변경과 검증을 포함

**발표 스크립트**

초보자가 자주 하는 오해는 트랜잭션을 단순히 여러 SQL을 묶는 문법으로 보는 것입니다.

하지만 더 중요한 것은 업무 경계입니다. 어느 시점부터 좌석, 신청, 결제를 하나의 작업으로 보고, 어느 시점에 이 작업을 확정할지 정하는 것입니다.

예를 들어 좌석 차감은 성공했지만 결제 저장이 실패했다면 이 업무는 성공했다고 볼 수 없습니다. 그래서 중간 결과를 남기지 않고 되돌려야 합니다.

따라서 트랜잭션을 설계할 때는 “어떤 변경들이 반드시 함께 움직여야 하는가?”를 먼저 정해야 합니다.

## 4. 실행 전 사전 조건을 검사해야 합니다

**화면 구성**

- 체크리스트
  - 현재 DB가 `ai_database_book`인가?

  - `course_project.enrollments`가 5행인가?

**발표 스크립트**

초보자에게 중요한 습관은 실행 전에 현재 위치와 기준 상태를 먼저 확인하는 것입니다.

## 5. BEGIN, COMMIT, ROLLBACK의 역할을 구분합니다

**화면 구성**

| 명령 | 의미 | 사용 시점 |
|---|---|---|
| `BEGIN` | 트랜잭션 시작 | 관련 변경 전 |
| `COMMIT` | 변경 확정 | 검증이 모두 맞을 때 |
| `ROLLBACK` | 변경 취소 | 오류 또는 예상과 다른 결과 |

**발표 스크립트**

`BEGIN`은 이제부터 하나의 업무 단위가 시작된다는 표시입니다.

`COMMIT`은 그동안의 변경을 확정합니다. 확정한 뒤에는 같은 트랜잭션의 `ROLLBACK`으로 되돌릴 수 없습니다.

`ROLLBACK`은 아직 확정하지 않은 변경을 취소합니다. 오류가 났거나, 조회 결과가 예상과 다르거나, 외부 결제 실패처럼 업무상 성공이 아니라고 판단되면 `ROLLBACK`해야 합니다.

따라서 `COMMIT`은 빨리 실행하는 명령이 아니라, 확인이 끝난 뒤 마지막에 실행하는 명령입니다.

## 6. 정합성은 여러 안전장치가 함께 지킵니다

**화면 구성**

| 안전장치 | 담당 역할 |
|---|---|
| 제약조건 | 한 행의 값과 참조 오류 차단 |
| 고유 인덱스 | 중복 활성 신청 차단 |
| 트랜잭션 | 여러 변경의 확정·취소 경계 |
| 업무 조건 | 변경 가능 여부 판단 |
| 검증 SELECT | 최종 의미 확인 |

**발표 스크립트**

트랜잭션만 쓰면 데이터가 자동으로 올바르게 되는 것은 아닙니다.

제약조건은 음수 금액이나 존재하지 않는 부모 참조 같은 오류를 막습니다. 고유 인덱스는 같은 학생이 같은 강의에 중복으로 수강중 상태가 되는 것을 막습니다.

하지만 모든 수강중 신청에 결제가 반드시 하나 있어야 한다는 규칙은 여러 테이블을 함께 봐야 합니다. 이런 규칙은 트랜잭션 흐름과 검증 SQL이 함께 확인해야 합니다.

즉, 제약조건·업무 조건·트랜잭션·검증은 서로 역할이 다릅니다.

## 7. ACID는 수강신청 사례로 이해합니다

**화면 구성**

| 특성 | 쉬운 의미 | 사례 |
|---|---|---|
| Atomicity | 모두 반영 또는 모두 취소 | 좌석·신청·결제 |
| Consistency | 전후 상태가 규칙을 만족 | 좌석 범위·결제 연결 |
| Isolation | 동시 작업의 간섭 제어 | 마지막 좌석 경쟁 |
| Durability | 확정된 변경 유지 | COMMIT된 신청 |

**발표 스크립트**

ACID는 외워야 할 영어 약자가 아니라 트랜잭션이 지켜야 할 성질입니다.

Atomicity는 좌석, 신청, 결제가 함께 성공하거나 함께 취소되는 성질입니다.

Consistency는 트랜잭션 전후의 데이터가 정해진 규칙을 만족해야 한다는 뜻입니다. 단, 업무 규칙이 저절로 생기는 것은 아니므로 제약조건과 검증이 필요합니다.

Isolation은 동시에 여러 사용자가 신청할 때 서로 간섭하지 않도록 제어하는 성질이고, Durability는 COMMIT된 변경이 유지되는 성질입니다.

이 상태에서 신청을 성공시키면 좌석은 줄고, 신청과 결제 행이 함께 생겨야 합니다.

## 9. 성공 트랜잭션은 좌석·신청·결제를 함께 확정합니다

**화면 구성**

```text
BEGIN
→ 좌석 행 잠금
→ remaining_seats > 0 조건으로 좌석 차감
→ 신청 행 생성
→ 결제 행 생성
→ COMMIT 전 검증
→ COMMIT
```

**발표 스크립트**

성공 트랜잭션의 핵심은 변경 순서와 검증입니다.

먼저 대상 강의의 좌석 행을 확인하고 잠급니다. 그다음 `remaining_seats > 0` 조건으로 좌석을 차감합니다.

좌석 차감 결과가 있을 때만 신청과 결제 INSERT가 이어집니다. 이 연결을 위해 CTE와 `RETURNING`을 사용합니다.

마지막으로 COMMIT 전에 신청 1행, 결제 1행, 금액 일치, 잔여 좌석 변화가 모두 맞는지 확인합니다.

## 10. FOR UPDATE와 조건부 UPDATE는 역할이 다릅니다

**화면 구성**

| 구문 | 역할 |
|---|---|
| `SELECT ... FOR UPDATE` | 대상 행을 잠그고 현재 상태를 확인 |
| `UPDATE ... WHERE remaining_seats > 0` | 실제로 변경 가능한 경우만 좌석 차감 |
| `RETURNING` | 변경 성공 증거 확인 |

**발표 스크립트**

`FOR UPDATE`를 사용했다고 신청이 성공한 것은 아닙니다.

`FOR UPDATE`는 다른 트랜잭션이 같은 좌석 행을 동시에 바꾸지 못하도록 잠그고, 현재 상태를 확인하는 역할입니다.

실제 업무 성공 여부는 조건부 UPDATE가 결정합니다. 좌석이 남아 있을 때만 `remaining_seats`를 1 줄입니다.

그리고 `RETURNING`이나 영향 행 수를 통해 정말 1행이 바뀌었는지 확인해야 합니다.

## 11. ROLLBACK은 확정 전 변경을 되돌립니다

**화면 구성**

```text
트랜잭션 내부 임시 상태
- course 302 remaining_seats = 0
- enrollment 9002 존재
- payment 9902 존재

ROLLBACK 후
- course 302 remaining_seats = 1
- enrollment 9002 없음
- payment 9902 없음
```

**발표 스크립트**

ROLLBACK 실습은 실패 상황을 이해하기 위한 실습입니다.

트랜잭션 안에서는 좌석이 줄고 신청과 결제가 생긴 것처럼 보일 수 있습니다. 하지만 외부 결제 승인 실패 같은 문제가 발생했다고 가정하면 이 변경을 확정하면 안 됩니다.

`ROLLBACK`을 실행하면 아직 COMMIT되지 않은 좌석 차감, 신청 생성, 결제 생성이 모두 취소됩니다.

이때 중요한 점은 ROLLBACK 후 실제 테이블 상태를 다시 조회해 원래 상태로 돌아왔는지 확인하는 것입니다.

## 12. ROLLBACK과 IDENTITY 번호는 다릅니다

**화면 구성**

- 비교 카드
  - 명시적 ID: ROLLBACK 후 같은 숫자를 직접 다시 사용할 수 있음
  - 자동 IDENTITY: 할당된 번호가 ROLLBACK으로 회수되지 않을 수 있음
  - 명시적 ID 입력: 다음 자동값을 자동 이동시키지 않음

**발표 스크립트**

트랜잭션을 배울 때 ID 번호를 함께 오해하기 쉽습니다.

이번 실습에서는 비교를 쉽게 하려고 `9002`, `9902` 같은 ID를 직접 입력합니다. 이 명시적 ID로 만든 행이 ROLLBACK되면 행 자체가 사라지므로 같은 숫자를 다시 직접 사용할 수 있습니다.

하지만 IDENTITY가 자동으로 발급한 번호는 다르게 생각해야 합니다. 자동 번호는 트랜잭션이 취소되어도 회수되지 않을 수 있습니다.

또 직접 ID를 넣었다고 해서 다음 자동값이 자동으로 이동하는 것도 아닙니다. 필요하면 `RESTART WITH`로 조정해야 합니다.

## 13. 좌석 부족은 SQL 오류가 아니라 0행 결과일 수 있습니다

**화면 구성**

```text
UPDATE ... WHERE remaining_seats > 0
→ 0행 반환
→ 문법 오류 아님
→ 자동 ROLLBACK 아님
→ 업무상 좌석 확보 실패
```

**발표 스크립트**

좌석이 없는 강의에 신청을 시도하면 PostgreSQL이 항상 오류를 내는 것은 아닙니다.

`WHERE remaining_seats > 0` 조건을 만족하는 행이 없으면 UPDATE 결과가 0행이 됩니다. 이것은 문법 오류가 아니라 조건을 만족하는 대상이 없다는 정상 실행 결과입니다.

하지만 업무적으로는 신청 실패입니다. 좌석을 확보하지 못했으므로 신청과 결제를 만들면 안 됩니다.

따라서 0행을 “성공”으로 처리하지 말고, 정원 마감 같은 업무 결과로 처리해야 합니다.

## 14. SQL 오류 상태에서는 ROLLBACK 또는 SAVEPOINT가 필요합니다

**화면 구성**

```text
current transaction is aborted

기본 대응: ROLLBACK
부분 복구: SAVEPOINT → ROLLBACK TO SAVEPOINT
```

**발표 스크립트**

조건 불충족으로 0행이 나온 것과 SQL 오류는 다릅니다.

트랜잭션 안에서 제약조건 오류나 문장 오류가 발생하면 PostgreSQL은 현재 트랜잭션을 오류 상태로 둘 수 있습니다. 이 상태에서는 다음 SQL도 계속 실패할 수 있습니다.

기본 대응은 전체 트랜잭션을 `ROLLBACK`하는 것입니다.

일부 단계만 되돌리고 트랜잭션을 계속 진행하고 싶다면 오류가 발생하기 전에 `SAVEPOINT`를 만들어 두고, 문제가 생겼을 때 `ROLLBACK TO SAVEPOINT`를 사용합니다.

## 15. 취소와 좌석 복구도 같은 트랜잭션이어야 합니다

**화면 구성**

```text
수강중 → 취소
+ remaining_seats 1 증가
```

**발표 스크립트**

신청 취소도 단순히 상태만 바꾸면 안 됩니다.

수강중 신청을 취소하면 사용 중이던 좌석도 다시 풀려야 합니다. 상태는 취소인데 좌석이 복구되지 않으면 활성 신청 수와 사용 좌석 수가 맞지 않습니다.

따라서 취소 상태 변경과 좌석 복구는 같은 트랜잭션 안에서 처리해야 합니다.

결제 행은 신청 당시 기록으로 남을 수 있습니다. 실제 환불은 별도의 금액, 상태, 승인 ID가 필요한 다른 업무입니다.

---

## 16. Lock 대기와 Deadlock은 다릅니다

**화면 구성**

| 구분 | 의미 |
|---|---|
| Lock 대기 | 다른 트랜잭션의 잠금 해제를 기다림 |
| Deadlock | 서로가 가진 잠금을 기다리는 순환 대기 |

**발표 스크립트**

두 사용자가 마지막 좌석을 동시에 신청하면 한 트랜잭션이 먼저 좌석 행을 잠글 수 있습니다.

다른 트랜잭션은 잠금이 풀릴 때까지 기다릴 수 있습니다. 이것은 일반적인 Lock 대기입니다.

Deadlock은 더 복잡합니다. A는 301을 잠그고 302를 기다리고, B는 302를 잠그고 301을 기다리는 식으로 서로 빠져나가지 못하는 순환 대기가 생기는 상황입니다.

Deadlock을 줄이려면 여러 행을 잠글 때 항상 같은 순서로 접근하고, 트랜잭션을 짧게 유지해야 합니다.

## 17. 트랜잭션은 너무 짧아도, 너무 길어도 문제입니다

**화면 구성**

- 같은 트랜잭션에 포함
  - 좌석 확보
  - 신청 생성
  - 결제 성공 결과 저장
  - 내부 검증
- 오래 기다리지 말 것
  - 사용자 추가 입력
  - 느린 외부 API
  - 대용량 파일 처리

**발표 스크립트**

트랜잭션 경계는 적절해야 합니다.

너무 짧으면 좌석만 확정되고 신청이 실패하는 식의 부분 확정이 생깁니다. 반대로 너무 길면 잠금을 오래 잡아 다른 사용자의 작업을 막을 수 있습니다.

데이터베이스 안에서 함께 확정해야 하는 변경과 검증은 트랜잭션에 포함합니다.

하지만 사용자가 카드번호를 다시 입력할 때까지 기다리거나, 외부 API가 오래 응답하지 않는 시간을 DB 트랜잭션 안에 넣는 것은 위험합니다.

## 18. AI가 만든 트랜잭션 SQL은 실패 경로까지 검토합니다

**화면 구성**

- 검토 체크리스트
  - 좌석 0행 확인
  - 신청·결제 연결
  - COMMIT 전 검증
  - 오류 후 ROLLBACK
  - 중복 활성 신청 차단
  - `course_project` 변경 금지

**발표 스크립트**

AI는 정상 경로의 SQL을 그럴듯하게 만들어 줄 수 있습니다. 하지만 트랜잭션에서는 실패 경로가 더 중요합니다.

좌석 UPDATE가 0행일 때도 신청을 넣는지, 신청과 결제가 서로 다른 트랜잭션으로 분리되는지, COMMIT 전에 검증이 있는지 확인해야 합니다.

또 실습용 `transaction_lab`만 바꿔야 하는데 기존 `course_project` 데이터를 건드리는지도 확인해야 합니다.

좋은 트랜잭션 SQL은 성공했을 때뿐 아니라 실패했을 때도 데이터가 모순되지 않도록 설계된 SQL입니다.

## 19. 핵심 정리

**화면 구성**

```text
관련 변경은 같은 트랜잭션 안에서 실행한다.
영향 행 수와 검증 결과가 맞을 때만 COMMIT한다.
문제나 오류가 있으면 ROLLBACK한다.
```

**발표 스크립트**

이번 장의 핵심은 간단합니다.

좌석, 신청, 결제처럼 함께 움직여야 하는 변경은 같은 트랜잭션 안에서 실행합니다.

그러나 트랜잭션만으로 업무가 자동으로 옳아지는 것은 아닙니다. 조건부 UPDATE, 영향 행 수, 제약조건, 검증 SELECT가 함께 필요합니다.

마지막으로 COMMIT은 검증 후에 실행합니다. 예상과 다르면 ROLLBACK해야 합니다. 이 습관이 데이터 정합성을 지키는 가장 기본적인 출발점입니다.
