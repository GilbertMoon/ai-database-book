# Chapter 09 이론 발표 강의안

## 트랜잭션으로 데이터 정합성 지키기

> 목적: 좌석 차감, 수강신청 생성, 결제 기록처럼 함께 성공해야 하는 여러 변경을 하나의 업무 단위로 묶어 데이터 정합성을 지키는 사고방식을 설명한다.  
> 기준: 초보자가 “BEGIN을 썼다”가 아니라 “어떤 변경을 함께 확정해야 하고, 무엇을 확인한 뒤 COMMIT해야 하는지”를 말할 수 있어야 한다.

---

## 1. Chapter 09는 여러 변경을 안전하게 확정하는 장입니다

**화면 구성**

```text
좌석 차감
→ 수강신청 생성
→ 결제 기록
→ COMMIT 전 검증
→ COMMIT 또는 ROLLBACK
```

**발표 스크립트**

지금까지는 주로 데이터를 만들고 조회하고 검증했습니다. 챕터 09에서는 실제 서비스에서 자주 발생하는 여러 변경을 하나의 업무 단위로 묶는 방법을 배웁니다.

온라인 강의 신청에서는 좌석만 줄고 신청이 없거나, 신청은 있는데 결제가 없는 상태가 생기면 안 됩니다. 그래서 관련 변경을 같은 트랜잭션 안에서 실행하고, 결과가 모두 맞을 때만 확정합니다.

---

## 2. 트랜잭션은 SQL 묶음이 아니라 업무 경계입니다

**화면 구성**

- 업무 단위: 하나로 성공하거나 하나로 실패해야 하는 작업
- 예: 좌석 + 신청 + 결제
- 핵심 질문: 어디서 시작하고 어디서 확정할 것인가?

**발표 스크립트**

트랜잭션은 단순히 에스큐엘 여러 줄을 감싸는 문법이 아닙니다. 하나의 업무가 어디에서 시작하고 어디에서 끝나는지 정하는 경계입니다.

예를 들어 좌석 차감, 수강신청 생성, 결제 기록은 각각 다른 테이블을 바꾸지만 사용자가 보기에는 하나의 수강신청 확정 업무입니다. 따라서 이 세 변경은 함께 성공하거나 함께 취소되어야 합니다.

---

## 3. 부분 성공은 정합성 문제를 만듭니다

**화면 구성**

| 남은 상태 | 문제 |
|---|---|
| 좌석만 감소 | 신청자가 없음 |
| 신청만 생성 | 좌석과 결제가 맞지 않음 |
| 결제만 생성 | 연결된 신청이 없음 |
| 신청·결제 생성, 좌석 미차감 | 초과 신청 가능 |

**발표 스크립트**

세 작업을 따로 확정하면 중간 실패가 그대로 데이터베이스에 남을 수 있습니다.

좌석만 줄고 신청이 없으면 사용자도 없는데 좌석이 사라집니다. 신청은 있는데 결제가 없으면 유료 강의 신청의 의미가 불분명합니다. 결제만 있고 신청이 없으면 결제가 어떤 신청의 결과인지 알 수 없습니다.

트랜잭션의 첫 번째 목적은 이런 부분 성공을 막는 것입니다.

## 4. Chapter 09는 별도 실습 스키마를 사용합니다

**화면 구성**

```text
course_project

transaction_lab

```

**발표 스크립트**

학생과 강의 마스터는 `코스 프로젝트`를 참조하지만, 좌석과 실험용 수강신청, 결제는 `트랜잭션 랩`에 따로 만듭니다.

이렇게 하면 앞 장의 기준 데이터는 보호하면서 트랜잭션 실험만 독립적으로 초기화할 수 있습니다.

## 5. 실행 전 사전 조건 검사가 필요합니다

**화면 구성**

```text
현재 DB = ai_database_book
course_project = 3 / 2 / 3 / 5행
recorded_amount = NUMERIC(12,0)
상태 = 신청2 / 수강중1 / 완료1 / 취소1
전체 = 590000 / 활성 = 3·340000 / 취소 제외 = 4·440000
학생 101~103·강의 301~303 기준값 일치
transaction_lab 기존 없음
```

**발표 스크립트**

트랜잭션 실습은 기준 데이터가 맞아야 의미가 있습니다. 학생과 강의가 없거나 챕터 07·08의 행 수, 상태 범위, `recorded_amount` 기준값이 달라져 있으면 좌석·신청·결제 실습 결과도 달라집니다.

따라서 챕터 09의 스키마 생성 파일은 단순히 현재 상태를 출력만 하지 않고, 조건이 맞지 않으면 예외를 발생시켜 중단하도록 설계되어 있습니다.

초보자에게 중요한 습관은 “일단 실행”이 아니라 “실행할 수 있는 상태인지 먼저 확인”입니다.

## 6. BEGIN, COMMIT, ROLLBACK의 역할

**화면 구성**

| 명령 | 의미 | 사용 시점 |
|---|---|---|
| `BEGIN` | 트랜잭션 시작 | 관련 변경 전 |
| `COMMIT` | 변경 확정 | 검증 완료 후 |
| `ROLLBACK` | 미확정 변경 취소 | 오류·검증 실패 시 |

**발표 스크립트**

`비긴`은 지금부터 하나의 트랜잭션으로 처리하겠다는 시작 표시입니다. `커밋`은 그 안의 변경을 확정합니다.

반대로 `롤백`은 아직 확정되지 않은 변경을 취소합니다. 이미 `커밋`한 변경은 같은 트랜잭션의 `롤백`으로 되돌릴 수 없습니다.

따라서 중요한 변경은 커밋 전에 반드시 상태를 확인해야 합니다.

---

## 7. 트랜잭션만으로 정합성이 자동 보장되지는 않습니다

**화면 구성**

| 안전장치 | 담당 역할 |
|---|---|
| 제약조건 | 한 행의 값·참조 오류 차단 |
| 고유 인덱스 | 조건부 중복 차단 |
| 트랜잭션 | 여러 변경의 확정·취소 경계 |
| 업무 조건 | 변경 가능 여부 판단 |
| 검증 SELECT | 최종 의미 확인 |

**발표 스크립트**

트랜잭션을 사용하면 여러 변경을 함께 확정하거나 함께 취소할 수 있습니다. 하지만 잘못된 에스큐엘을 트랜잭션 안에서 실행하고 커밋하면 잘못된 상태도 확정될 수 있습니다.

그래서 제약조건, 업무 조건, 영향 행 수 확인, 검증 셀렉트가 함께 필요합니다.

트랜잭션은 정합성을 지키는 도구 중 하나이지, 업무 규칙을 자동으로 판단하는 마법이 아닙니다.

## 8. ACID는 업무 사례로 이해합니다

**화면 구성**

| 특성 | 입문 수준 의미 | 사례 |
|---|---|---|
| Atomicity | 모두 반영 또는 모두 취소 | 좌석·신청·결제 |
| Consistency | 전후 상태가 규칙을 만족 | 좌석 범위·결제 연결 |
| Isolation | 동시 작업 간섭 제어 | 마지막 좌석 경쟁 |
| Durability | 확정 변경 유지 | COMMIT된 신청 |

**발표 스크립트**

에이씨아이디는 트랜잭션의 네 가지 특성입니다. 초보자 단계에서는 용어를 외우기보다 온라인 강의 신청 사례로 이해하면 됩니다.

아토미시티는 좌석·신청·결제가 모두 되거나 모두 취소되는 성질입니다. 컨시스턴시는 트랜잭션 전후 데이터가 규칙을 만족해야 한다는 뜻입니다.

아이솔레이션은 두 사람이 마지막 좌석을 동시에 신청할 때의 간섭 문제와 관련되고, 듀러빌리티는 커밋된 결과가 유지된다는 의미입니다.

## 9. 초기 상태는 좌석·신청·결제 검증의 기준입니다

**화면 구성**

| course_id | 강의 | capacity | remaining_seats |
|---:|---|---:|---:|
| 301 | 데이터베이스 입문 | 2 | 2 |
| 302 | 정규화 실습 | 1 | 1 |
| 303 | 파이썬 데이터 분석 | 1 | 1 |

```text
lab enrollments = 0
payments = 0
```

**발표 스크립트**

트랜잭션 실습의 시작 상태는 명확해야 합니다. 강의 301은 좌석 2개, 강의 302와 303은 각각 좌석 1개입니다.

실습용 수강신청과 결제는 처음에는 0건입니다. 이 기준을 알아야 이후 커밋, 롤백, 좌석 부족 상황이 맞게 처리되었는지 판단할 수 있습니다.

## 10. 성공 트랜잭션은 좌석을 먼저 확보합니다

**화면 구성**

```sql
SELECT ...
FROM transaction_lab.course_inventory
WHERE course_id = 301
FOR UPDATE;
```

```text
행 잠금
→ 최신 좌석 확인
→ 조건부 UPDATE 준비
```

**발표 스크립트**

성공 트랜잭션에서는 먼저 신청하려는 강의의 좌석 행을 확인하고 잠급니다.

`셀렉트 ... 포 업데이트`는 해당 행을 수정 대상으로 잠그는 역할을 합니다. 하지만 잠금만으로 좌석 확보가 성공한 것은 아닙니다.

실제 성공 여부는 이후 `remaining_seats > 0` 조건이 있는 업데이트가 1행을 바꾸었는지로 확인해야 합니다.

---

## 11. 조건부 UPDATE의 영향 행 수가 핵심입니다

**화면 구성**

```sql
UPDATE course_inventory
SET remaining_seats = remaining_seats - 1
WHERE course_id = 301
  AND remaining_seats > 0
RETURNING course_id, remaining_seats;
```

- 1행 반환: 좌석 확보 성공
- 0행 반환: 좌석 없음

**발표 스크립트**

좌석 차감 에스큐엘에서 가장 중요한 부분은 `remaining_seats > 0` 조건입니다. 좌석이 남아 있을 때만 차감해야 하기 때문입니다.

이 업데이트가 1행을 반환하면 좌석을 확보한 것입니다. 0행이면 에스큐엘 문법 오류가 아니라 업무상 좌석 확보 실패입니다.

이 차이를 구분해야 좌석 부족 상황을 정확하게 처리할 수 있습니다.

---

## 12. CTE로 좌석 성공 결과에 신청·결제를 연결합니다

**화면 구성**

```text
seat UPDATE 결과
→ new_enrollment INSERT
→ payment INSERT
```

- seat가 1행이면 후속 INSERT 실행
- seat가 0행이면 후속 INSERT도 0건

**발표 스크립트**

이 장의 성공 에스큐엘은 씨티이를 사용해 좌석 업데이트 결과를 다음 인서트로 연결합니다.

좌석 확보가 성공했을 때만 수강신청을 만들고, 수강신청이 만들어졌을 때만 결제를 만듭니다.

이렇게 하면 좌석이 없는데 신청이나 결제만 생기는 상태를 줄일 수 있습니다. 그래도 마지막에는 반드시 검증해야 합니다.

## 13. COMMIT 전 검증이 확정 기준입니다

**화면 구성**

```text
신청 9001 = 1행
결제 9901 = 1행
두 금액 = 100000
강의 301 remaining_seats = 1
```

**발표 스크립트**

커밋은 마지막에 한 번 누르는 저장 버튼처럼 생각하면 됩니다. 저장하기 전에 결과가 맞는지 확인해야 합니다.

성공 트랜잭션에서는 신청 1건, 결제 1건, 금액 일치, 좌석 감소가 모두 맞아야 합니다.

하나라도 맞지 않으면 커밋하지 않고 롤백해야 합니다.

---

## 14. ROLLBACK은 미확정 변경만 되돌립니다

**화면 구성**

| 상태 | course 302 | enrollment 9002 | payment 9902 |
|---|---:|---:|---:|
| 트랜잭션 내부 | 0 | 있음 | 있음 |
| ROLLBACK 후 | 1 | 없음 | 없음 |

**발표 스크립트**

롤백 실습에서는 트랜잭션 안에서 좌석을 줄이고 신청과 결제를 만든 뒤 외부 결제 실패를 가정합니다.

트랜잭션 내부에서는 변경이 보일 수 있지만 롤백하면 모두 취소됩니다. 좌석은 원래대로 돌아오고, 신청과 결제 행도 없어집니다.

단, 이미 커밋된 변경은 롤백으로 되돌릴 수 없다는 점을 분명히 해야 합니다.

---

## 15. ROLLBACK과 IDENTITY 번호는 다릅니다

**화면 구성**

```text
명시적 ID 9002
→ ROLLBACK 후 직접 재사용 가능

IDENTITY 자동 번호
→ 할당 후 일반적으로 회수되지 않음
```

**발표 스크립트**

이 실습에서는 비교를 쉽게 하기 위해 9001, 9002 같은 아이디를 명시적으로 입력합니다. 명시적으로 입력한 값은 롤백 후 다시 직접 사용할 수 있습니다.

하지만 아이덴티티가 자동으로 발급한 번호는 트랜잭션이 취소되어도 일반적으로 회수되지 않습니다. 그래서 자동 아이디에는 빈 번호가 생길 수 있습니다.

자동 아이디를 학생 수나 주문 수처럼 해석하면 안 됩니다.

---

## 16. 좌석 부족은 SQL 오류가 아니라 업무 실패일 수 있습니다

**화면 구성**

```text
UPDATE ... WHERE remaining_seats > 0
→ 0행 반환

의미:
문법 오류 아님
자동 ROLLBACK 아님
업무상 좌석 확보 실패
```

**발표 스크립트**

좌석이 0개인 강의에 추가 신청을 시도하면 조건부 업데이트가 0행을 반환할 수 있습니다.

이것은 에스큐엘이 틀렸다는 뜻이 아닙니다. 좌석이 없다는 업무 결과입니다.

이 경우 후속 신청과 결제를 만들면 안 되고, 트랜잭션은 롤백으로 종료하는 것이 안전합니다.

---

## 17. SQL 오류 후에는 트랜잭션 상태를 확인합니다

**화면 구성**

```text
트랜잭션 안에서 오류 발생
→ current transaction is aborted
→ ROLLBACK
```

선택 복구:

```text
SAVEPOINT
→ 오류 발생
→ ROLLBACK TO SAVEPOINT
→ 계속 진행
```

**발표 스크립트**

조건이 맞지 않아 업데이트가 0행인 것과 에스큐엘 오류는 다릅니다. 제약조건 위반이나 문장 오류가 발생하면 포스트그레스큐엘 트랜잭션이 오류 상태가 될 수 있습니다.

이 상태에서는 정상 에스큐엘도 계속 실패할 수 있으므로 기본 대응은 롤백입니다.

일부 단계만 되돌리고 싶다면 오류가 나기 전에 세이브포인트를 만들어 두어야 합니다.

---

## 18. Lock 대기와 Deadlock을 구분합니다

**화면 구성**

```text
Lock 대기
A가 잠근 행을 B가 기다림

Deadlock
A는 B를 기다리고 B는 A를 기다림
```

**발표 스크립트**

동시에 같은 좌석 행을 바꾸려 하면 한 세션이 다른 세션을 기다릴 수 있습니다. 이것은 일반적인 락 대기입니다.

데드락은 서로가 가진 잠금을 기다리는 순환 구조입니다. 포스트그레스큐엘은 데드락을 감지하면 한 트랜잭션을 오류로 종료할 수 있습니다.

여러 행을 잠글 때는 같은 순서로 접근하고, 트랜잭션을 짧게 유지하는 것이 중요합니다.

---

## 19. 트랜잭션은 너무 길어도 위험합니다

**화면 구성**

같은 트랜잭션에 포함:

```text
좌석 확보
신청 생성
결제 성공 결과 저장
COMMIT 전 내부 검증
```

오래 기다리면 안 되는 작업:

```text
사용자 입력
느린 외부 API
대용량 파일 처리
```

**발표 스크립트**

트랜잭션이 너무 짧으면 하나의 업무가 부분 확정될 수 있습니다. 반대로 너무 길면 잠금을 오래 잡아 다른 사용자의 작업을 막을 수 있습니다.

특히 외부 결제창 응답이나 느린 에이피아이를 기다리면서 데이터베이스 트랜잭션을 오래 열어 두면 위험합니다.

실제 시스템에서는 결제 승인 아이디, 재시도, 멱등성, 보상 처리 같은 별도 설계가 필요합니다.

## 20. AI 트랜잭션 SQL은 실패 경로까지 검토합니다

**화면 구성**

- BEGIN·COMMIT 경계가 맞는가?
- 좌석 UPDATE 0행을 확인하는가?
- 신청·결제가 좌석 성공에 연결되는가?
- COMMIT 전 검증이 있는가?
- 오류 후 ROLLBACK 또는 SAVEPOINT를 고려하는가?
- 외부 작업을 트랜잭션 안에 오래 두지 않는가?

**발표 스크립트**

에이아이는 트랜잭션 에스큐엘 초안을 빠르게 만들 수 있지만, 정상 경로만 작성하고 실패 경로를 빠뜨릴 수 있습니다.

좌석 업데이트가 0행인데도 신청을 인서트하거나, 신청을 커밋한 뒤 결제를 별도 트랜잭션으로 넣는 구조는 위험합니다.

트랜잭션 에스큐엘은 성공했을 때뿐 아니라 좌석 부족, 오류, 재실행, 취소, 동시 실행 상황까지 검토해야 합니다.
