# Chapter 10 실습 발표 강의안

## 실행 계획을 기록하고 인덱스 전후를 비교하기

> 목적: `performance_lab`에서 대량 데이터를 만들고, 같은 SQL의 인덱스 생성 전후 실행 계획과 결과 행을 비교해 인덱스 판단 근거를 기록한다.  
> 기준: 초보자가 “인덱스를 만들었다”가 아니라 “무엇을 측정했고, 결과가 같았고, 읽기 이점과 비용을 비교했다”라고 말할 수 있어야 한다.


> **검증 기준 버전**
>
> 이 장의 자동 검증 기준은 **PostgreSQL 16**입니다. PostgreSQL 16의 다중 컬럼 B-tree에서는 선두 컬럼 제약이 없으면 후행 컬럼 조건만으로 탐색 범위를 줄이기 어렵습니다. **B-tree Skip Scan은 PostgreSQL 18에서 추가**되었으므로, PostgreSQL 18 이상에서는 동일 SQL의 계획이 달라질 수 있습니다. 실습 결과에는 서버 버전을 함께 기록합니다.

**Chapter 07·08 시작 기준**

`course_project`의 `students / instructors / courses / enrollments = 3 / 2 / 3 / 5`, 상태는 `신청 2 / 수강중 1 / 완료 1 / 취소 1`이어야 합니다.  
`course_project.enrollments.recorded_amount`는 `NUMERIC(12,0)`이며, 전체 기록 금액은 `590000`, 활성 신청은 `3건 / 340000`, 취소 제외 이력은 `4건 / 440000`입니다.  
기준 신청은 `1001 = 완료 / 100000`, `1004 = 취소 / 150000`, `1005 = 신청 / 120000`이고 `uq_course_enrollments_active`가 존재해야 합니다. Chapter 10은 이 상태를 읽기만 하고 변경하지 않습니다.

## 5. 자동 인덱스를 먼저 확인합니다

**화면 구성**

```sql
SELECT schemaname, tablename, indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'performance_lab';
```

- PK·UNIQUE 자동 인덱스
- FK 자식 컬럼은 자동 인덱스 아님

**발표 스크립트**

인덱스 후보를 만들기 전에 현재 인덱스 목록을 먼저 봅니다.

기본키와 유니크 제약조건은 자동 인덱스를 만듭니다. 따라서 이미 유니크가 있는 이메일 컬럼에 같은 인덱스를 또 만들 필요가 없습니다.

반면 `인롤먼츠.student_id`, `인롤먼츠.course_id` 같은 외래키 자식 컬럼은 자동 인덱스가 아닙니다. 그래서 실제 조회 패턴을 보고 후보로 검토합니다.

## 7. EXPLAIN ANALYZE 결과에서 볼 항목을 정합니다

**화면 구성**

| 항목 | 기록 이유 |
|---|---|
| 주요 계획 노드 | 찾는 방식 |
| Index Cond | 인덱스 탐색 조건 |
| Filter | 읽은 뒤 제거 조건 |
| rows / actual rows | 예상과 실제 차이 |
| Buffers | 읽기 작업량 |
| Execution Time | 관찰 시간 |

**발표 스크립트**

실행 계획은 길기 때문에 모든 글자를 같은 비중으로 읽으면 어렵습니다.

초보자는 먼저 어떤 Scan을 사용했는지, 인덱스 조건이 있는지, 예상 행 수와 실제 행 수가 맞는지, 읽은 블록 수가 줄었는지를 봅니다.

실행 시간은 캐시와 PC 상태의 영향을 받으므로 단독 판단 근거로 쓰지 않습니다.

## 8. 이메일 검색은 자동 인덱스 사용을 확인합니다

**화면 구성**

```sql
WHERE email = 'performance5000@example.com'
```

- 기대 결과: 1행
- 새 수동 인덱스 생성 없음
- UNIQUE 자동 인덱스 확인

**발표 스크립트**

이메일 검색은 인덱스가 필요한 전형적인 조건처럼 보입니다. 하지만 `스튜던츠.email`에는 유니크 제약조건이 있으므로 자동 인덱스가 이미 있습니다.

따라서 이 실습의 목적은 새 인덱스를 만드는 것이 아니라 기존 자동 인덱스를 확인하는 것입니다.

에이아이가 `스튜던츠(email)` 인덱스를 추천하면 중복 가능성을 먼저 검토해야 합니다.

## 9. 강의 제목 검색은 전후 비교 대상입니다

**화면 구성**

```sql
WHERE title = '성능 테스트 강의 00500'
```

| 항목 | 생성 전 | 생성 후 |
|---|---|---|
| 주요 계획 노드 | 기록 | 기록 |
| Buffers | 기록 | 기록 |
| 결과 행 수 | 1 | 1 |

**발표 스크립트**

강의 제목은 유니크가 아니고 자동 인덱스도 없습니다. 정확히 한 강의를 찾는 선택도 높은 조건이므로 후보 인덱스로 실험합니다.

인덱스 생성 전후에 같은 에스큐엘을 실행하고, 계획 노드와 Buffers가 어떻게 바뀌는지 기록합니다.

결과 행 수는 생성 전과 후 모두 1이어야 합니다.

## 10. 학생별 신청 JOIN은 FK 자식 인덱스를 검토합니다

**화면 구성**

```sql
WHERE e.student_id = 5000
```

- 기대 결과: 10행
- 후보: `enrollments(student_id)`
- JOIN 경로 유지

**발표 스크립트**

학생 한 명의 신청 목록은 실제 서비스에서 자주 필요한 조회입니다.

`스튜던츠.id`는 기본키라 자동 인덱스가 있지만, `인롤먼츠.student_id`는 외래키 자식 컬럼이므로 자동 인덱스가 아닙니다.

인덱스 생성 전후로 신청 테이블 접근 방식이 어떻게 달라지는지 확인합니다.

## 11. 복합 인덱스는 세 조건을 나누어 봅니다

**화면 구성**

후보 인덱스:

```text
(course_id, status)
```

| 조건 | 기대 행 수 |
|---|---:|
| course_id = 1500 | 50 |
| course_id + status | 15 |
| status = '수강중' | 30001 |

**발표 스크립트**

복합 인덱스는 하나의 에스큐엘만 보고 판단하지 않습니다.

`course_id`만 있는 조건, `course_id`와 `status`가 함께 있는 조건, `status`만 있는 조건을 나누어 봅니다.

선두 컬럼인 `course_id`가 있는 조건은 잘 맞을 가능성이 높고, `status` 단독 조건은 반환 행이 많아 시퀀셜 스캔이 더 합리적일 수 있습니다.

## 12. ORDER BY와 LIMIT 계획을 비교합니다

**화면 구성**

| SQL | 확인할 점 |
|---|---|
| `ORDER BY title` | 전체 정렬 |
| `ORDER BY title LIMIT 20` | 앞부분만 필요 |

**발표 스크립트**

같은 `오더 바이 title`이라도 전체 행을 다 반환하는지, 앞 20개만 필요한지에 따라 계획이 달라질 수 있습니다.

LIMIT이 있으면 인덱스 순서대로 필요한 만큼만 읽는 계획이 유리할 수 있습니다.

정렬 실습에서는 Sort 노드가 있는지, 인덱스 스캔이 사용되는지, Buffers가 어떻게 달라지는지 기록합니다.

```text
실습 판단
→ 후보 인덱스 효과 확인

운영 적용
→ 잠금·소요 시간·디스크·CONCURRENTLY·실패 처리 검토
```

**발표 스크립트**

실습에서 효과가 있었다고 운영 DB에 바로 적용하는 것은 위험합니다.

운영 테이블은 크고 사용자가 동시에 쓰고 있을 수 있습니다. 일반 `CREATE INDEX`가 적절한지, `CREATE INDEX CONCURRENTLY`가 필요한지, 실패 후 invalid 인덱스를 어떻게 처리할지 검토해야 합니다.

운영 반영은 성능 튜닝이면서 변경 작업입니다.

## 20. 최종 완료 기준은 측정 기록과 판단 근거입니다

**화면 구성**

- `performance_lab`만 변경
- 기준 행 수 일치
- 후보 인덱스 3개 확인
- 전후 실행 계획 기록
- 결과 행 수 동일
- Buffers·시간 비교
- 중복·비용 검토
- AI 추천 검증 가능

**발표 스크립트**

챕터 10 실습의 완료 기준은 인덱스 3개를 만든 것이 아닙니다.

기준 데이터가 맞고, 후보 인덱스가 없는 계획과 있는 계획을 같은 에스큐엘로 비교했고, 결과 행 수가 동일하며, 읽기 이점과 쓰기 비용을 함께 판단했는지가 중요합니다.

이 과정을 거치면 에이아이가 추천한 인덱스도 그대로 믿지 않고 근거를 가지고 적용·보류·제거를 결정할 수 있습니다.
