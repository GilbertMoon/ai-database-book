# Chapter 10 실습 발표 강의안

## 실행 계획을 기록하고 인덱스 전후를 비교하기

> 목적: `performance_lab`에서 대량 데이터를 생성한 뒤, 같은 SQL의 인덱스 생성 전후 실행 계획과 결과를 비교해 인덱스 적용 판단 근거를 기록한다.  
> 기준: 초보자가 “무엇을 실행하고, 어떤 결과가 나와야 하며, 계획이 달라졌을 때 어떻게 해석해야 하는지”를 직관적으로 이해할 수 있어야 한다.

---

## 1. 이번 실습은 인덱스 효과를 증거로 확인합니다

**화면 구성**

- 큰 제목: 실행 계획으로 인덱스 효과 검증하기
- 흐름: 기준 데이터 생성 → 인덱스 전 계획 → 후보 인덱스 생성 → 인덱스 후 계획 → 검증·판단
- 강조 문장: 인덱스 적용은 느낌이 아니라 증거로 판단합니다

**발표 스크립트**

이번 실습은 인덱스를 만들고 끝내는 실습이 아닙니다. 같은 SQL을 인덱스 생성 전과 후에 실행 계획으로 비교하고, 실제로 읽기 방식이 달라졌는지 확인하는 실습입니다.

먼저 `performance_lab`에 성능 실험용 데이터를 만듭니다. 그다음 후보 인덱스가 없는 상태에서 기준 실행 계획을 기록합니다.

후보 인덱스를 만든 뒤 같은 SQL을 다시 측정합니다. 결과 행 수는 같아야 하고, 실행 계획과 Buffers, 실제 시간은 비교 대상이 됩니다.

## 2. 실습 파일 순서를 정확히 지킵니다

**화면 구성**

| 순서 | 파일 | 역할 |
|---:|---|---|
| 1 | `01_performance_lab_schema.sql` | 스키마·테이블 생성 |
| 2 | `02_performance_lab_seed.sql` | 대량 데이터 생성·ANALYZE |
| 3 | `03_baseline_explain.sql` | 후보 인덱스 없는 기준 계획 기록 |

| 6 | `06_index_review.sql` | 인덱스 목록·크기·사용 통계 검토 |
| 7 | `07_result_validation.sql` | 결과 행과 데이터 상태 검증 |

**발표 스크립트**

이 실습은 순서가 매우 중요합니다. 03 파일은 후보 인덱스가 없는 상태에서 실행해야 합니다. 05 파일은 후보 인덱스 3개가 만들어진 뒤 실행해야 합니다.

순서를 바꾸면 비교 실험이 깨집니다. 예를 들어 인덱스를 먼저 만든 뒤 기준 계획을 보면 더 이상 ‘인덱스 전’ 계획이 아닙니다.

각 SQL 파일에는 상태 보호 구문이 들어 있습니다. 조건이 맞지 않으면 예외가 발생하는데, 이는 오류라기보다 잘못된 비교를 막는 안전장치입니다.

실습용 PC에 따라 데이터 생성 시간이 다를 수 있습니다. 하지만 데이터를 줄이면 기대 행 수와 검증 SQL도 함께 바뀌어야 하므로 임의로 줄이지 않는 것이 좋습니다.

워크북에는 이 기준값을 먼저 적어 두고, 각 SQL 실행 후 실제 결과와 비교합니다.

## 6. 자동 인덱스를 먼저 확인합니다

**화면 구성**

```sql
SELECT schemaname, tablename, indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'performance_lab'
ORDER BY tablename, indexname;
```

- PRIMARY KEY 자동 인덱스
- UNIQUE 자동 인덱스
- FK 자식 컬럼은 자동 생성 아님

**발표 스크립트**

후보 인덱스를 만들기 전에 현재 인덱스 목록을 확인합니다. 이미 있는 인덱스를 모르고 같은 역할의 인덱스를 다시 만들면 불필요한 중복이 됩니다.

`students.email`은 UNIQUE이므로 이미 자동 인덱스가 있습니다. 따라서 이메일 검색을 위해 같은 컬럼에 수동 인덱스를 다시 만들지 않습니다.

반면 `enrollments.student_id`, `enrollments.course_id`는 외래키 자식 컬럼이지만 PostgreSQL이 자동으로 인덱스를 만들지는 않습니다. 실제 조회 패턴에 따라 후보가 됩니다.

## 7. EXPLAIN ANALYZE 결과를 워크북에 기록합니다

**화면 구성**

- 기록 항목
  - 주요 계획 노드
  - 예상 rows
  - actual rows
  - Buffers
  - Execution Time
  - Index Cond
  - 결과 행 수

**발표 스크립트**

실행 계획은 화면에 한 번 보고 지나가면 의미가 없습니다. 기준 계획과 사후 계획을 비교하려면 핵심 항목을 워크북에 기록해야 합니다.

처음에는 모든 줄을 다 해석하지 않아도 됩니다. 어떤 Scan이 사용되었는지, 예상 행 수와 실제 행 수가 맞는지, Buffers와 Execution Time이 어떻게 달라졌는지부터 봅니다.

그리고 `Index Cond`가 있는지 확인합니다. 이는 인덱스가 조건 검색에 실제로 사용되었는지 판단하는 중요한 단서입니다.

## 8. 이메일 검색은 자동 인덱스 사용을 확인합니다

**화면 구성**

```sql
SELECT id, name, email
FROM performance_lab.students
WHERE email = 'performance5000@example.com';
```

- 기대 결과: 학생 ID 5000, 1행
- 확인: 사용된 인덱스와 `Index Cond`

**발표 스크립트**

첫 번째 조회는 이메일로 학생 한 명을 찾는 SQL입니다. 이 컬럼에는 UNIQUE 제약조건이 있으므로 자동 인덱스가 이미 있습니다.

따라서 이 실습의 목적은 새 인덱스를 만드는 것이 아니라, 자동 인덱스가 실행 계획에서 어떻게 보이는지 확인하는 것입니다.

결과는 1행이어야 하고, 학생 ID는 5000이어야 합니다. 실행 계획에서는 이메일 조건이 인덱스 탐색에 사용되는지 확인합니다.

## 9. 강의 제목 검색은 인덱스 전후를 비교합니다

**화면 구성**

```sql
SELECT id, title, level, price
FROM performance_lab.courses
WHERE title = '성능 테스트 강의 00500';
```

- 생성 전: 기준 계획 기록
- 생성 후: `idx_performance_courses_title` 사용 여부 확인
- 결과 행 수: 1행 유지

**발표 스크립트**

강의 제목은 자동 인덱스가 없는 일반 컬럼입니다. 정확히 한 강의를 제목으로 찾는 조회가 반복된다면 인덱스 후보가 될 수 있습니다.

03 파일에서는 인덱스가 없는 상태의 계획을 기록합니다. 04 파일에서 title 인덱스를 만든 뒤, 05 파일에서 같은 SQL을 다시 실행합니다.

이때 결과 행 수는 전후 모두 1행이어야 합니다. 달라지는 것은 결과가 아니라 PostgreSQL이 행을 찾는 경로입니다.

## 10. 학생별 신청 조회는 FK 자식 컬럼 인덱스를 검토합니다

**화면 구성**

```text
조건: e.student_id = 5000
기대 결과: 10행
후보 인덱스: idx_performance_enrollments_student_id
```

**발표 스크립트**

학생 한 명의 신청 목록을 자주 조회한다면 `enrollments.student_id`가 중요한 조건이 됩니다. 이 컬럼은 학생 테이블을 참조하는 외래키지만, PostgreSQL이 자동 인덱스를 만들어 주지는 않습니다.

그래서 이번 실습에서는 `student_id` 인덱스 생성 전후를 비교합니다. 결과는 항상 10행이어야 합니다.

계획에서 `enrollments`를 어떻게 접근하는지, 인덱스 생성 후 Buffers와 실행 시간이 어떻게 달라졌는지 기록합니다.

## 11. 복합 인덱스는 세 조건으로 나누어 봅니다

**화면 구성**

- 후보 인덱스: `(course_id, status)`
- 비교 조건
  - `course_id = 1500` → 50행
  - `course_id = 1500 AND status = '수강중'` → 15행
  - `status = '수강중'` → 30001행

**발표 스크립트**

복합 인덱스는 하나의 SQL만 보고 판단하지 않습니다. 선두 컬럼 조건이 있는 경우와 없는 경우를 나누어 봐야 합니다.

`course_id = 1500`은 선두 컬럼을 사용합니다. `course_id`와 `status`가 모두 있는 조건은 두 컬럼을 함께 활용할 수 있습니다.

하지만 `status = '수강중'`만 있는 조건은 반환 행이 30001건으로 많고 선두 컬럼도 빠져 있습니다. 인덱스 사용 가능성이 제한적일 수 있습니다. 이 차이를 실행 계획으로 확인합니다.

## 12. ORDER BY와 LIMIT 계획을 비교합니다

**화면 구성**

- SQL 1: `ORDER BY title` 전체 정렬
- SQL 2: `ORDER BY title LIMIT 20`
- 기록: `Sort` 노드, Index Scan, Buffers, 실행 시간

**발표 스크립트**

정렬도 인덱스의 영향을 받을 수 있습니다. 전체를 정렬해야 하는 경우와 앞의 20개만 필요한 경우는 계획이 달라질 수 있습니다.

`LIMIT 20`이 있으면 PostgreSQL은 전체를 다 정렬하는 대신 인덱스를 따라 앞부분만 가져오는 방법을 선택할 수 있습니다.

그래서 실습에서는 `Sort` 노드가 있는지, title 인덱스가 정렬에 사용되는지 확인합니다.

## 13. 통계 조건을 섞지 않습니다

**화면 구성**

```text
02: 데이터 생성 + ANALYZE
03: 기준 계획
04: 인덱스만 생성
05: 같은 SQL 재측정
```

- 강조: 04 이후 `ANALYZE` 재실행 없음

**발표 스크립트**

이번 실험에서는 후보 인덱스의 효과만 비교하고 싶습니다. 그래서 데이터 생성 후 한 번만 `ANALYZE`를 실행하고, 인덱스 생성 뒤에는 다시 `ANALYZE`하지 않습니다.

운영 환경에서는 통계 갱신이 중요합니다. 하지만 비교 실험에서는 통계 표본까지 바뀌면 차이가 인덱스 때문인지 통계 변화 때문인지 구분하기 어렵습니다.

초보자에게 중요한 포인트는 “비교할 때는 바뀌는 조건을 최소화한다”입니다.

## 14. 예상 rows와 actual rows를 비교합니다

**화면 구성**

| SQL | 기대 actual rows |
|---|---:|
| 제목 검색 | 1 |
| 학생별 신청 | 10 |
| 강의 단독 | 50 |
| 강의+상태 | 15 |
| 상태 단독 | 30001 |

**발표 스크립트**

실행 계획에서 `rows`는 PostgreSQL의 예상이고, `actual rows`는 실제 실행 결과입니다.

두 값이 비슷하면 통계가 비교적 잘 맞는다고 볼 수 있습니다. 크게 다르면 데이터 분포, 통계 수집 여부, 조건 값의 빈도, 컬럼 간 상관관계를 의심해 볼 수 있습니다.

이번 장에서는 고급 통계 튜닝까지 다루지는 않습니다. 다만 예상과 실제가 크게 다를 수 있고, 그 차이가 계획 선택에 영향을 줄 수 있다는 점을 이해하면 충분합니다.

## 16. 인덱스 목록과 크기를 검토합니다

**화면 구성**

```sql
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
```

- 실험 후보 인덱스 3개
- 크기와 사용 통계

**발표 스크립트**

후보 인덱스를 만들고 나면 인덱스 목록과 크기를 확인합니다. 인덱스는 저장 공간을 사용하기 때문에 크기도 판단 자료가 됩니다.

사용 통계도 참고할 수 있습니다. 하지만 `idx_scan = 0`이라고 바로 삭제하면 안 됩니다. 아직 해당 SQL을 실행하지 않았거나, 통계가 초기화되었을 수도 있습니다.

이번 실습의 후보 인덱스는 전후 측정을 위한 실험 대상입니다. 아직 최종 운영 적용 인덱스라고 부르면 안 됩니다.

---

## 17. 적용·보류·제거 판단을 기록합니다

**화면 구성**

- 판단 표
  - 조회 패턴
  - 전후 계획 변화
  - Buffers 변화
  - 결과 동일성
  - 쓰기 비용
  - 최종 판단: 적용 / 보류 / 제거

**발표 스크립트**

인덱스 실습의 마지막은 판단 기록입니다. “빨라진 것 같다”가 아니라 어떤 SQL에서, 어떤 계획이, 어떤 수치로 달라졌는지 남겨야 합니다.

읽기 이점이 분명하고 반복 조회에 중요하다면 적용 후보가 됩니다. 효과가 작거나 중복 가능성이 크다면 보류하거나 제거할 수 있습니다.

이 기록은 나중에 AI 추천이나 운영 적용 여부를 검토할 때 중요한 근거가 됩니다.

## 18. AI 추천 인덱스를 검토합니다

**화면 구성**

- AI SQL 검토 체크리스트
  - 기존 인덱스 확인
  - 컬럼 순서 근거
  - 전후 EXPLAIN
  - 결과 검증
  - 쓰기 비용
  - 운영 생성 방식

**발표 스크립트**

AI가 제안한 인덱스를 그대로 만들면 중복 인덱스가 생기거나 효과가 없는 인덱스를 추가할 수 있습니다.

AI에게 요청할 때는 실제 SQL과 현재 인덱스 목록, 데이터 규모, 기대 결과를 함께 제공해야 합니다. 그리고 AI가 추천한 뒤에도 반드시 실행 계획과 결과 검증으로 확인합니다.

인덱스는 권위 있는 답변으로 승인하는 것이 아니라, 실험 증거로 승인합니다.
