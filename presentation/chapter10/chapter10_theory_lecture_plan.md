# Chapter 10 이론 발표 강의안

## 실행 계획으로 인덱스 효과 검증하기

> 목적: 데이터가 많아졌을 때 PostgreSQL이 어떤 방법으로 행을 찾는지 이해하고, 인덱스가 실제로 도움이 되는지를 실행 계획으로 판단한다.  
> 기준: 초보자가 각 장표를 보며 “왜 인덱스가 필요한지, 실행 계획에서 무엇을 봐야 하는지, 언제 인덱스를 만들지 말아야 하는지” 직관적으로 이해할 수 있어야 한다.

---

## 1. 데이터가 많아지면 찾는 방법이 중요해집니다

**화면 구성**

- 큰 제목: 실행 계획으로 인덱스 효과 검증하기
- 흐름: 조회 질문 → 기준 계획 → 인덱스 생성 → 사후 계획 → 적용 판단
- 키워드: 대량 데이터 / 인덱스 / 실행 계획 / 검증

**발표 스크립트**

Chapter 07에서는 작은 온라인 강의 데이터베이스를 만들었고, Chapter 08에서는 JOIN과 집계로 질문에 답했습니다. 작은 데이터에서는 전체 테이블을 읽어도 금방 끝납니다.

하지만 데이터가 많아지면 이야기가 달라집니다. 학생이 3명이 아니라 1만 명이고, 수강신청이 5건이 아니라 10만 건이라면 PostgreSQL이 어떤 경로로 데이터를 찾는지가 중요해집니다.

이번 장의 핵심은 인덱스를 많이 만드는 것이 아닙니다. 실제로 자주 쓰는 조회가 무엇인지 정하고, 인덱스 전후 실행 계획을 비교해 도움이 되는지 확인하는 것입니다.

---

## 2. 작은 프로젝트 데이터와 성능 실험 데이터는 분리합니다

**화면 구성**

- 비교 카드 3개
  - `course_project`: 앞 장의 작은 프로젝트 데이터
  - `transaction_lab`: 트랜잭션 실습 데이터
  - `performance_lab`: Chapter 10 성능 실험 데이터
- 강조 문장: 기존 프로젝트는 변경하지 않습니다

**발표 스크립트**

성능 실험을 하기 위해 기존 프로젝트 데이터를 대량 데이터로 덮어쓰면 안 됩니다. Chapter 07과 08의 결과가 깨지고, 이전 장과 연결해서 검증할 수 없게 됩니다.

그래서 Chapter 10에서는 `performance_lab`이라는 별도 스키마를 사용합니다. 도메인은 온라인 강의 수강신청과 같지만, 성능 관찰을 위해 더 많은 학생, 강의, 신청 데이터를 만듭니다.

초보자 입장에서는 스키마를 분리한다는 말이 어렵게 느껴질 수 있습니다. 간단히 말하면 실험용 방을 따로 만드는 것입니다. 기존 방은 그대로 두고, 새 방에서 마음껏 인덱스 실험을 하는 구조입니다.

## 3. 실습 데이터는 크지만 의미 없는 데이터는 아닙니다

**화면 구성**

- 표: students 10003 / instructors 2 / courses 2003 / enrollments 100005
- 기준값 카드
  - 학생 5000 신청 10건
  - 강의 1500 신청 50건
  - 강의 1500 수강중 15건
  - 전체 수강중 30001건

**발표 스크립트**

성능 실험 데이터는 단순히 아무 숫자나 많이 넣은 데이터가 아닙니다. 학생마다 신청 10건, 강의마다 신청 50건처럼 결과를 예측할 수 있도록 만들어져 있습니다.

이렇게 기준값이 정해져 있어야 실행 계획이 바뀌어도 결과의 의미가 같다는 것을 확인할 수 있습니다. 인덱스 전후로 결과 행 수가 달라지면 성능 개선이 아니라 SQL이나 데이터가 달라진 것입니다.

따라서 이번 장에서는 실행 계획을 보기 전에 먼저 기준 데이터와 기대 행 수를 고정합니다.

## 4. 인덱스는 빠른 검색을 돕는 보조 구조입니다

**화면 구성**

- 왼쪽: 테이블 전체를 위에서 아래로 읽는 그림
- 오른쪽: 인덱스 키에서 위치를 찾아가는 그림
- 예시 SQL: `WHERE email = 'performance5000@example.com'`

**발표 스크립트**

인덱스는 책 뒤의 찾아보기와 비슷합니다. 책 전체를 한 페이지씩 넘기지 않고, 키워드가 있는 위치를 먼저 찾은 뒤 해당 페이지로 이동합니다.

데이터베이스에서도 비슷합니다. 조건에 맞는 행이 아주 적다면 테이블 전체를 읽는 것보다 인덱스를 통해 위치를 찾는 것이 유리할 수 있습니다.

다만 인덱스가 있다고 무조건 빠른 것은 아닙니다. 대부분의 행을 읽어야 하는 조건이라면 인덱스를 왔다 갔다 하는 것보다 테이블을 순서대로 읽는 것이 더 나을 수 있습니다.

---

## 5. 자동 인덱스와 수동 인덱스를 구분합니다

**화면 구성**

- 표
  - PRIMARY KEY: 자동 인덱스 생성
  - UNIQUE: 자동 인덱스 생성
  - FOREIGN KEY 자식 컬럼: 자동 생성 아님
  - 일반 컬럼: 자동 생성 아님

**발표 스크립트**

인덱스를 만들기 전에 이미 있는 인덱스를 확인해야 합니다. PostgreSQL은 기본키와 유니크 제약조건을 유지하기 위해 인덱스를 자동으로 만듭니다.

예를 들어 `students.email`이 UNIQUE라면 이미 이메일 검색을 도울 수 있는 고유 인덱스가 있습니다. 여기에 같은 컬럼으로 수동 인덱스를 또 만들면 중복일 가능성이 큽니다.

반대로 외래키 자식 컬럼에는 자동으로 인덱스가 만들어지지 않습니다. `enrollments.student_id`나 `enrollments.course_id`는 JOIN과 조회 패턴에 따라 수동 인덱스를 검토해야 합니다.

---

## 6. 인덱스 후보는 실제 SQL에서 찾습니다

**화면 구성**

- 질문 카드 5개
  - 자주 실행되는가?
  - 테이블이 충분히 큰가?
  - 적은 행을 선택하는가?
  - 기존 인덱스와 중복되지 않는가?
  - 쓰기 비용을 감수할 가치가 있는가?

**발표 스크립트**

인덱스 후보는 컬럼 이름만 보고 고르지 않습니다. 실제로 반복 실행되는 SQL을 봐야 합니다.

예를 들어 강의 제목으로 정확히 한 강의를 찾는 조회가 자주 있다면 `courses.title` 인덱스를 검토할 수 있습니다. 학생 한 명의 신청 목록을 자주 본다면 `enrollments.student_id` 인덱스를 검토할 수 있습니다.

반대로 WHERE에 등장했다는 이유만으로 모든 컬럼에 인덱스를 만들면 저장 공간과 쓰기 비용만 늘어날 수 있습니다.

---

## 7. EXPLAIN은 PostgreSQL의 실행 계획을 보여 줍니다

**화면 구성**

- 코드 2개
  - `EXPLAIN SELECT ...`
  - `EXPLAIN (ANALYZE, BUFFERS) SELECT ...`
- 비교: 예상 계획 vs 실제 실행 측정

**발표 스크립트**

`EXPLAIN`은 PostgreSQL이 이 쿼리를 어떻게 실행하려고 하는지 보여 줍니다. 실제 결과를 보여 주는 것이 아니라 실행 경로를 보여 줍니다.

`EXPLAIN ANALYZE`는 쿼리를 실제로 실행한 뒤 실제 행 수와 시간까지 보여 줍니다. 여기에 `BUFFERS`를 붙이면 데이터 블록을 얼마나 읽었는지도 관찰할 수 있습니다.

중요한 주의점이 있습니다. `EXPLAIN ANALYZE`는 실제로 실행합니다. 이번 장에서는 SELECT에만 사용합니다. UPDATE나 DELETE에 무심코 사용하면 실제 데이터가 변경될 수 있습니다.

---

## 8. 실행 계획에서 먼저 볼 항목

**화면 구성**

- 표: 계획 노드 / rows / actual rows / Buffers / Index Cond / Filter / Sort
- 강조: cost는 밀리초가 아닙니다

**발표 스크립트**

실행 계획을 처음 보면 숫자가 많아서 어렵습니다. 처음부터 모든 항목을 완벽하게 해석하려 하지 않아도 됩니다.

먼저 어떤 방법으로 읽었는지 봅니다. `Seq Scan`인지, `Index Scan`인지, `Bitmap Heap Scan`인지 확인합니다. 그다음 예상 rows와 실제 actual rows가 크게 다른지 봅니다.

`Index Cond`가 보이면 인덱스가 조건 검색에 실제로 사용되었다는 중요한 근거입니다. `Filter`는 행을 읽은 뒤 조건으로 걸러냈다는 뜻이므로 많이 제거되면 비효율을 의심할 수 있습니다.

---

## 9. Seq Scan이 항상 나쁜 것은 아닙니다

**화면 구성**

- 3개 카드
  - 작은 테이블
  - 대부분의 행을 반환하는 조건
  - 전체 집계
- 강조 문장: 인덱스가 있어도 Seq Scan이 합리적일 수 있습니다

**발표 스크립트**

초보자가 자주 하는 오해는 `Seq Scan`을 보면 무조건 나쁘다고 생각하는 것입니다. 그렇지 않습니다.

테이블이 작거나, 조건에 맞는 행이 너무 많거나, 대부분의 행을 읽어야 하는 집계라면 순차적으로 읽는 것이 더 합리적일 수 있습니다.

인덱스를 쓰는 것도 비용이 있습니다. 인덱스에서 키를 찾고 다시 원본 테이블 행을 찾아가는 과정이 필요합니다. 그래서 PostgreSQL은 상황에 따라 전체 읽기를 선택할 수 있습니다.

---

## 10. Index Scan과 Bitmap Scan을 구분합니다

**화면 구성**

- 비교 카드
  - Index Scan: 적은 행을 바로 찾기
  - Bitmap Scan: 여러 위치를 모아 블록 단위로 읽기
- 예시: 정확 일치 / 중간 정도의 선택도

**발표 스크립트**

`Index Scan`은 인덱스에서 조건에 맞는 키를 찾고 원본 행으로 이동합니다. 보통 아주 적은 행을 찾을 때 유리합니다.

`Bitmap Index Scan`과 `Bitmap Heap Scan`은 조건에 맞는 위치를 비트맵으로 모은 뒤 필요한 테이블 블록을 묶어서 읽습니다. 한두 행보다는 많지만 전체 테이블을 읽을 정도는 아닐 때 선택될 수 있습니다.

중요한 것은 노드 이름 하나만 보고 정답을 외우는 것이 아닙니다. 반환 행 수, Buffers, 실제 시간과 함께 봐야 합니다.

## 11. 복합 인덱스는 컬럼 순서가 중요합니다

**화면 구성**

- 인덱스: `(course_id, status)`
- 조건별 활용 가능성 표
  - `course_id = 1500`
  - `course_id = 1500 AND status = '수강중'`
  - `status = '수강중'`

**발표 스크립트**

복합 인덱스는 여러 컬럼을 묶은 인덱스입니다. 이때 왼쪽부터 이어지는 선두 컬럼이 중요합니다.

`(course_id, status)` 인덱스가 있다면 `course_id = 1500` 조건은 선두 컬럼을 사용합니다. `course_id = 1500 AND status = '수강중'`은 두 컬럼을 함께 활용할 가능성이 큽니다.

반면 `status = '수강중'`만 있으면 선두 컬럼이 빠져 있어 일반적으로 활용 가능성이 제한적입니다. 다만 PostgreSQL이 비용상 유리하다고 판단하면 Skip Scan 같은 방식이 선택될 수 있으므로 절대 사용 불가라고 단정하지는 않습니다.

## 12. ORDER BY와 LIMIT도 인덱스 후보가 될 수 있습니다

**화면 구성**

- 비교
  - 전체 정렬: `ORDER BY title`
  - 앞 20개만 필요: `ORDER BY title LIMIT 20`
- 강조: LIMIT은 계획을 바꿀 수 있습니다

**발표 스크립트**

인덱스는 WHERE 조건에만 관련되는 것이 아닙니다. 정렬에도 영향을 줄 수 있습니다.

예를 들어 강의 제목순으로 모든 강의를 정렬해야 한다면 별도 Sort가 필요할 수 있습니다. 하지만 제목순 앞 20개만 필요하다면 title 인덱스를 따라가며 앞부분만 가져오는 계획이 유리할 수 있습니다.

그래서 `ORDER BY`와 `LIMIT`이 있는 쿼리도 인덱스 후보를 판단할 때 함께 봐야 합니다.

---

## 13. 인덱스 전후 비교는 조건을 통제해야 합니다

**화면 구성**

- 흐름: 데이터 생성 + ANALYZE → 기준 계획 → 인덱스 생성 → 같은 SQL 재측정
- 강조: 바뀌는 것은 후보 인덱스 존재 여부 하나

**발표 스크립트**

인덱스 효과를 비교하려면 공정한 실험이어야 합니다. 데이터도 같고, SQL도 같고, 가능한 통계 조건도 같아야 합니다.

이 장에서는 대량 데이터를 만든 뒤 `ANALYZE`로 통계를 수집합니다. 그다음 인덱스가 없는 기준 계획을 기록하고, 후보 인덱스를 만든 뒤 같은 SQL을 다시 실행합니다.

인덱스를 만든 뒤 데이터를 바꾸거나 통계를 다시 수집하면 차이가 인덱스 때문인지 다른 조건 때문인지 판단하기 어려워집니다.

## 14. 결과 행 동일성은 실행 계획과 별도로 확인합니다

**화면 구성**

- 좌측: 실행 계획 비교
- 우측: 결과 행 수 검증
- 예시 기대값: 이메일 1행, 학생 5000 신청 10행, 강의 1500 수강중 15행

**발표 스크립트**

실행 계획이 바뀌었다고 해서 결과가 맞다는 뜻은 아닙니다. 인덱스 전후에도 SQL이 같은 의미를 가져야 하고 결과 행 수도 같아야 합니다.

예를 들어 강의 1500의 수강중 신청은 15건이어야 합니다. 인덱스를 만든 뒤 계획이 빨라졌더라도 결과가 14건이나 16건이면 잘못된 것입니다.

그래서 Chapter 10의 마지막에는 `07_result_validation.sql`로 기준 결과를 자동 검증합니다.

## 15. 인덱스는 읽기 이점과 쓰기 비용을 함께 봅니다

**화면 구성**

- 비용 카드
  - 저장 공간
  - INSERT 비용
  - UPDATE 비용
  - DELETE 비용
  - 유지보수와 운영 복잡성

**발표 스크립트**

인덱스는 읽기를 빠르게 할 수 있지만 무료가 아닙니다. 인덱스도 별도의 데이터 구조이므로 저장 공간을 사용합니다.

새 행을 INSERT하면 테이블뿐 아니라 관련 인덱스에도 키가 추가됩니다. 인덱스 키 컬럼을 UPDATE하면 인덱스도 갱신해야 합니다.

따라서 읽기 성능이 조금 좋아진다고 무조건 인덱스를 유지하는 것은 아닙니다. 실제로 반복되는 중요한 조회인지, 쓰기 비용을 감수할 가치가 있는지 함께 판단해야 합니다.

---

## 16. 실습 CREATE INDEX와 운영 CREATE INDEX는 다릅니다

**화면 구성**

- 비교 카드
  - 실습 DB: 일반 `CREATE INDEX`
  - 운영 DB: 잠금 영향, 소요 시간, 디스크 공간, `CONCURRENTLY` 검토

**발표 스크립트**

이번 장은 독립된 실험 스키마에서 진행하므로 일반 `CREATE INDEX`를 사용합니다. 실습에서는 데이터 규모와 실행 환경이 통제되어 있습니다.

하지만 운영 중인 큰 테이블에서는 일반 인덱스 생성이 쓰기 작업에 영향을 줄 수 있습니다. 이 경우 `CREATE INDEX CONCURRENTLY`를 검토할 수 있습니다.

다만 `CONCURRENTLY`는 트랜잭션 블록 안에서 실행할 수 없고, 실패하면 invalid 인덱스가 남을 수도 있습니다. 운영 적용은 실습과 다르게 잠금과 복구 계획까지 고려해야 합니다.

---

## 17. 중복 인덱스와 미사용 통계는 조심해서 해석합니다

**화면 구성**

- 예시
  - UNIQUE 자동 인덱스 + 같은 수동 인덱스
  - `(course_id)` + `(course_id, status)`
- 주의: `idx_scan = 0`만으로 삭제하지 않기

**발표 스크립트**

인덱스가 많아지면 비슷한 역할을 하는 인덱스가 생길 수 있습니다. 예를 들어 이미 UNIQUE 자동 인덱스가 있는 이메일에 같은 수동 인덱스를 만들면 중복일 가능성이 큽니다.

또 `(course_id)` 단일 인덱스와 `(course_id, status)` 복합 인덱스는 일부 역할이 겹칠 수 있습니다. 하지만 복합 인덱스가 단일 인덱스를 항상 완전히 대체한다고 단정하면 안 됩니다.

`pg_stat_user_indexes`에서 `idx_scan = 0`이라고 바로 삭제하는 것도 위험합니다. 통계가 방금 초기화되었거나, 아직 해당 워크로드가 실행되지 않았을 수 있습니다.

## 18. AI 추천 인덱스는 실행 계획으로 검증합니다

**화면 구성**

- 검토 체크리스트
  - 실제 워크로드
  - 기존 인덱스와 중복 여부
  - 컬럼 순서
  - 전후 실행 계획
  - 결과 동일성
  - 쓰기 비용
  - 운영 생성 방식

**발표 스크립트**

AI에게 “인덱스 추천해 주세요”라고만 묻는 것은 위험합니다. AI는 WHERE에 나온 컬럼마다 단일 인덱스를 추천하거나, 이미 자동 인덱스가 있는 컬럼에 중복 인덱스를 제안할 수 있습니다.

좋은 요청은 실제 SQL, 현재 인덱스 목록, 데이터 규모, 기대 결과, 운영 조건을 함께 제공합니다.

그리고 최종 판단은 AI의 설명이 아니라 실행 계획 전후 비교와 결과 검증으로 해야 합니다. 인덱스는 추천이 아니라 증거로 결정합니다.

  - 전후 비교는 같은 조건으로 수행
  - 읽기 이점과 쓰기 비용을 함께 판단
