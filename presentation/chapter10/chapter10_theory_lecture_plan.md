# Chapter 10 이론 발표 강의안

## 실행 계획으로 인덱스 효과 검증하기

> 목적: 인덱스를 “빠르게 해 주는 마법”이 아니라 실제 조회 패턴을 더 적은 비용으로 처리하기 위한 선택으로 이해시킨다.  
> 기준: 초보자가 “인덱스를 만들었다”가 아니라 “같은 데이터·같은 통계·같은 SQL로 전후 계획과 결과를 비교했다”라고 말할 수 있어야 한다.

---

## 1. Chapter 10은 빠른 조회를 증거로 검증하는 장입니다

**화면 구성**

```text
조회 질문 정의
→ 기준 실행 계획 측정
→ 후보 인덱스 생성
→ 같은 SQL 재측정
→ 결과 동일성 확인
→ 적용·보류·제거 판단
```

**발표 스크립트**

이번 장의 핵심은 인덱스를 많이 만드는 것이 아닙니다. 데이터가 많아졌을 때 PostgreSQL이 어떤 경로로 행을 찾는지 보고, 인덱스가 실제로 도움이 되는지 증거로 판단하는 것입니다.

그래서 먼저 실제 조회 질문을 정합니다. 그다음 인덱스가 없는 기준 상태에서 실행 계획을 기록하고, 후보 인덱스를 만든 뒤 같은 SQL을 다시 측정합니다.

인덱스 적용 여부는 느낌이 아니라 계획 노드, 반환 행 수, Buffers, 실행 시간, 결과 동일성으로 판단합니다.

## 2. 작은 프로젝트 데이터와 성능 실험 데이터는 분리합니다

**화면 구성**

```text
course_project     → Chapter 07·08 기준 데이터
transaction_lab    → Chapter 09 트랜잭션 실습
performance_lab    → Chapter 10 성능 실험
```

**발표 스크립트**

Chapter 07의 데이터는 학생 3명, 신청 5건입니다. 이 정도 크기에서는 전체 테이블을 읽어도 빠르기 때문에 인덱스 효과를 보기 어렵습니다.

하지만 기존 프로젝트 데이터를 대량 데이터로 덮어쓰면 앞 장의 검증 기준이 깨집니다. 그래서 Chapter 10은 `performance_lab`이라는 별도 스키마에서 실험합니다.

성능 실험은 독립적으로 만들고 독립적으로 초기화해야 합니다.

## 3. 합성 데이터도 검증 가능한 업무 의미를 가져야 합니다

**화면 구성**

| 테이블 | 최종 예상 행 |
|---|---:|
| students | 10003 |
| instructors | 2 |
| courses | 2003 |
| enrollments | 100005 |

**발표 스크립트**

성능 실험용 데이터라고 해서 아무 값이나 무작위로 넣으면 안 됩니다. 그래야 결과 행 수를 예측하고 실행 계획이 맞는지 확인할 수 있습니다.

이 장에서는 학생별 신청 10건, 강의별 신청 50건처럼 검증 가능한 규칙을 둡니다.

예를 들어 학생 5000의 신청은 10건, 강의 1500의 신청은 50건, 강의 1500의 수강중 신청은 15건이어야 합니다. 이 숫자가 기준값입니다.

## 4. 인덱스는 검색을 돕는 별도 구조입니다

**화면 구성**

```text
인덱스 키 값
→ 원본 테이블 행을 찾는 위치 정보
```

- 기본 `CREATE INDEX`: B-tree
- 정확 일치, 범위 조건, 정렬에 자주 사용

**발표 스크립트**

인덱스는 테이블 자체가 아니라 테이블을 더 빨리 찾기 위한 별도 구조입니다.

예를 들어 이메일로 학생 한 명을 찾는다면 모든 학생을 처음부터 끝까지 읽는 것보다, 이메일 값이 정렬된 인덱스에서 위치를 찾는 것이 유리할 수 있습니다.

PostgreSQL의 기본 인덱스는 B-tree입니다. 정확 일치, 범위 조건, 정렬 같은 일반적인 조회에 많이 사용됩니다.

## 5. 자동 인덱스와 수동 인덱스를 먼저 구분합니다

**화면 구성**

| 구조 | 자동 인덱스 | 판단 |
|---|---|---|
| PRIMARY KEY | 생성됨 | 중복 생성 금지 |
| UNIQUE | 생성됨 | 중복 생성 금지 |
| FOREIGN KEY 자식 컬럼 | 자동 생성 안 됨 | 조회 패턴 보고 판단 |
| 일반 컬럼 | 자동 생성 안 됨 | 실제 SQL 보고 판단 |

**발표 스크립트**

인덱스를 만들기 전에 이미 존재하는 인덱스를 먼저 확인해야 합니다.

기본키와 UNIQUE 제약조건은 PostgreSQL이 자동으로 인덱스를 만듭니다. 그래서 `students.email`에 UNIQUE가 있다면 같은 이메일 컬럼에 일반 인덱스를 또 만드는 것은 중복일 수 있습니다.

반면 외래키 자식 컬럼에는 자동 인덱스가 생기지 않습니다. 하지만 모든 외래키에 기계적으로 인덱스를 만드는 것도 답은 아닙니다. 실제 JOIN과 조회 패턴을 봐야 합니다.

## 6. ANALYZE와 EXPLAIN ANALYZE는 다릅니다

**화면 구성**

```text
ANALYZE table
→ 옵티마이저 통계 수집

EXPLAIN ANALYZE query
→ 쿼리 실제 실행 + 실행 계획 측정
```

**발표 스크립트**

`ANALYZE`라는 단어가 둘 다 들어가지만 역할은 다릅니다.

`ANALYZE table`은 PostgreSQL이 계획을 세울 때 참고할 통계를 수집합니다. 반면 `EXPLAIN ANALYZE`는 실제 쿼리를 실행하고 계획과 실제 행 수, 시간을 보여 줍니다.

이 실험에서는 데이터 생성 후 통계를 한 번 수집하고, 인덱스 전후 비교에서는 같은 데이터와 같은 통계를 유지합니다.

---

## 7. 실행 계획은 결과표가 아니라 처리 경로입니다

**화면 구성**

| 항목 | 의미 |
|---|---|
| cost | 상대 예상 비용 |
| rows | 예상 행 수 |
| actual rows | 실제 행 수 |
| Buffers | 읽은 블록 정보 |
| Filter | 읽은 뒤 거른 조건 |
| Index Cond | 인덱스 탐색 조건 |

**발표 스크립트**

실행 계획은 일반 SELECT 결과가 아닙니다. PostgreSQL이 어떤 방식으로 데이터를 찾고, 걸러내고, 정렬하는지 보여 주는 처리 경로입니다.

`cost`는 시간이 아니라 상대 비용입니다. `rows`는 예상 행 수이고, `actual rows`는 실제 행 수입니다.

특히 `Index Cond`가 보이면 해당 조건이 인덱스 탐색에 사용되었다는 중요한 근거가 됩니다.

---

## 8. Seq Scan은 항상 나쁜 계획이 아닙니다

**화면 구성**

```text
Seq Scan
→ 테이블을 순서대로 읽음

Index Scan
→ 인덱스에서 찾고 원본 행 접근

Bitmap Scan
→ 여러 위치를 모아 블록 단위 접근
```

**발표 스크립트**

초보자는 `Seq Scan`이 보이면 무조건 느리고 나쁜 계획이라고 생각하기 쉽습니다. 그렇지 않습니다.

작은 테이블이거나 대부분의 행을 읽어야 하는 조건이라면 전체 테이블을 순서대로 읽는 것이 더 합리적일 수 있습니다.

인덱스는 소수 행을 찾거나 정렬과 LIMIT 조건에 맞을 때 특히 유리할 수 있습니다. 계획 노드는 정답표가 아니라 비용 판단의 결과입니다.

---

## 9. WHERE 조건은 인덱스 후보의 출발점입니다

**화면 구성**

```text
자주 실행되는가?
테이블이 충분히 큰가?
적은 행을 선택하는가?
기존 인덱스와 중복되지 않는가?
쓰기 비용을 감수할 가치가 있는가?
```

**발표 스크립트**

WHERE에 등장한다고 모두 인덱스 후보가 되는 것은 아닙니다.

실제로 자주 실행되는 조회인지, 테이블이 충분히 큰지, 조건이 전체 중 적은 행만 선택하는지 먼저 확인합니다.

예를 들어 강의 제목 정확 일치 검색은 2,003개 강의 중 1개를 찾으므로 후보가 될 수 있습니다. 하지만 이미 UNIQUE 인덱스가 있는 이메일에는 중복 인덱스를 만들 필요가 없습니다.

---

## 10. JOIN에서는 외래키 자식 컬럼을 검토합니다

**화면 구성**

```text
students.id      → PK 자동 인덱스
courses.id       → PK 자동 인덱스

enrollments.student_id → 수동 검토
enrollments.course_id  → 수동 검토
```

**발표 스크립트**

JOIN에서 부모 테이블의 기본키는 이미 인덱스가 있습니다. 하지만 자식 테이블의 외래키 컬럼에는 자동 인덱스가 생기지 않습니다.

학생 한 명의 신청 목록을 자주 조회한다면 `enrollments(student_id)` 인덱스를 검토할 수 있습니다.

하지만 모든 외래키에 자동으로 인덱스를 만드는 것이 아니라, 실제 조회와 부모 삭제·변경 패턴을 함께 봐야 합니다.

## 11. 복합 인덱스는 컬럼 순서가 중요합니다

**화면 구성**

```sql
CREATE INDEX idx_performance_enrollments_course_status
ON performance_lab.enrollments(course_id, status);
```

| 조건 | 활용 가능성 |
|---|---|
| course_id = 1500 | 선두 컬럼 사용 |
| course_id + status | 두 컬럼 사용 |
| status 단독 | 제한적 가능성 |

**발표 스크립트**

복합 인덱스는 여러 컬럼을 하나의 순서로 묶은 인덱스입니다. 이때 왼쪽, 즉 선두 컬럼이 중요합니다.

`(course_id, status)` 인덱스는 `course_id = 1500` 조건이나 `course_id = 1500 AND status = '수강중'` 조건에 잘 맞을 수 있습니다.

반면 `status = '수강중'`만 있는 조건은 선두 컬럼이 없고 반환 비율도 높기 때문에 제한적입니다. 다만 PostgreSQL은 비용에 따라 Skip Scan을 선택할 수 있으므로 실행 계획으로 확인해야 합니다.

---

## 12. ORDER BY와 LIMIT도 계획에 영향을 줍니다

**화면 구성**

```sql
ORDER BY title
ORDER BY title LIMIT 20
```

- 전체 반환: `Seq Scan + Sort` 가능
- 일부 반환: 인덱스 순서 활용 가능

**발표 스크립트**

인덱스는 WHERE 조건뿐 아니라 정렬에도 영향을 줄 수 있습니다.

전체 2,003행을 모두 정렬해서 반환한다면 순차 읽기 후 정렬이 합리적일 수 있습니다. 하지만 정렬 결과의 앞 20개만 필요하다면 인덱스 순서대로 조금만 읽는 계획이 유리할 수 있습니다.

인덱스가 있다고 정렬이 항상 사라지는 것은 아닙니다. 반환 행 수와 비용을 함께 봐야 합니다.

---

## 13. 인덱스 전후 비교는 조건을 통제해야 합니다

**화면 구성**

```text
같은 데이터
+ 같은 통계
+ 같은 SQL
+ 인덱스 존재 여부만 변경
```

**발표 스크립트**

인덱스 효과를 비교하려면 실험 조건을 통제해야 합니다.

기준 계획을 측정한 뒤 데이터를 바꾸거나 통계를 다시 수집하거나 SQL을 수정하면 무엇 때문에 계획이 바뀌었는지 알기 어렵습니다.

그래서 이 장에서는 데이터 생성 후 `ANALYZE`를 한 번 실행하고, 인덱스 생성 후에는 같은 SQL을 그대로 다시 측정합니다.

---

## 14. 결과 행 동일성은 실행 계획과 별도로 확인합니다

**화면 구성**

```text
EXPLAIN ANALYZE
→ 실행 계획 출력

SELECT COUNT(*)
→ 결과 행 수 검증
```

**발표 스크립트**

`EXPLAIN ANALYZE`는 쿼리를 실제로 실행하지만 일반 조회 결과를 보여 주는 것이 아니라 실행 계획을 보여 줍니다.

따라서 인덱스 전후 계획이 달라졌더라도 결과 행이 같은지는 별도 SQL로 확인해야 합니다.

이 장의 검증 기준은 이메일 검색 1행, 학생 5000 신청 10행, 강의 1500 신청 50행, 강의 1500 수강중 15행입니다.

## 15. 예상 rows와 actual rows 차이를 봅니다

**화면 구성**

```text
rows        → 옵티마이저 예상
actual rows → 실제 실행 결과
```

확인 질문:

```text
통계가 최신인가?
데이터 분포가 치우쳤는가?
조건 값이 흔한가, 드문가?
컬럼 간 상관관계가 큰가?
```

**발표 스크립트**

옵티마이저는 통계를 보고 행 수를 예상합니다. 그런데 예상 행 수와 실제 행 수가 크게 다르면 계획 선택에도 영향을 줄 수 있습니다.

입문 단계에서는 먼저 `ANALYZE`가 실행되었는지, 데이터 분포가 지나치게 치우쳐 있지 않은지 확인합니다.

정확한 통계 튜닝은 고급 주제이지만, 예상과 실제를 비교하는 습관은 지금부터 필요합니다.

## 16. 인덱스에는 읽기 이점과 쓰기 비용이 함께 있습니다

**화면 구성**

| 이점 | 비용 |
|---|---|
| 적은 행 탐색 | 저장 공간 증가 |
| 정렬 보조 | INSERT 비용 증가 |
| JOIN 탐색 보조 | UPDATE·DELETE 유지 비용 |
| 일부 조회 개선 | 관리 복잡성 증가 |

**발표 스크립트**

인덱스는 조회를 빠르게 만들 수 있지만 무료가 아닙니다.

행을 새로 넣거나 수정하거나 삭제할 때 테이블만 바꾸는 것이 아니라 인덱스 구조도 함께 유지해야 합니다.

그래서 읽기가 드문 컬럼이나 반환 비율이 높은 상태 컬럼마다 인덱스를 만들면 오히려 비용만 늘어날 수 있습니다.

## 17. 운영 환경의 CREATE INDEX는 잠금을 고려해야 합니다

**화면 구성**

```text
실습 DB
→ 일반 CREATE INDEX

운영 DB
→ 잠금 영향·시간·디스크 검토
→ 필요 시 CREATE INDEX CONCURRENTLY
```

**발표 스크립트**

실습에서는 독립된 스키마에서 일반 `CREATE INDEX`를 사용합니다. 하지만 운영 중인 큰 테이블에서는 인덱스 생성이 쓰기 작업에 영향을 줄 수 있습니다.

이때 `CREATE INDEX CONCURRENTLY`를 검토할 수 있습니다. 다만 더 오래 걸릴 수 있고, 트랜잭션 블록 안에서 실행할 수 없으며, 실패 후 invalid 인덱스 확인도 필요합니다.

운영 인덱스 생성은 SQL 한 줄이 아니라 작업 계획입니다.

## 18. 중복 인덱스와 미사용 인덱스를 조심합니다

**화면 구성**

```text
students.email UNIQUE 자동 인덱스
+ students(email) 수동 인덱스
→ 중복 가능성

(course_id)
+ (course_id, status)
→ 역할 중복 가능성
```

**발표 스크립트**

비슷한 인덱스가 많으면 저장 공간과 쓰기 비용이 늘어납니다.

하지만 복합 인덱스가 단일 인덱스를 항상 완전히 대체한다고 단정할 수도 없습니다. 인덱스 크기, 쿼리 형태, 정렬 요구, 실제 계획을 비교해야 합니다.

`idx_scan = 0`도 즉시 삭제 근거가 아닙니다. 통계 기간이 짧거나 아직 해당 워크로드가 실행되지 않았을 수 있습니다.

---

## 19. AI 추천 인덱스는 실행 계획으로 검토합니다

**화면 구성**

- 기존 인덱스와 중복되는가?
- 실제 반복 SQL인가?
- 선택도가 충분한가?
- 컬럼 순서 근거가 있는가?
- 전후 계획·Buffers·결과 행을 확인했는가?
- 운영 잠금과 쓰기 비용을 검토했는가?

**발표 스크립트**

AI에게 “인덱스 추천해 주세요”라고만 요청하면 WHERE에 등장하는 모든 컬럼마다 인덱스를 제안할 수 있습니다.

AI 추천은 출발점일 뿐입니다. 실제 SQL, 현재 인덱스 목록, 데이터 규모, 기준 실행 계획, 전후 측정 결과를 함께 검토해야 합니다.

특히 UNIQUE 자동 인덱스 중복, 복합 인덱스 순서 근거 부족, 작은 테이블의 Seq Scan을 무조건 문제로 보는 오류를 조심해야 합니다.

## 20. 핵심 정리: 인덱스의 가치는 측정으로 판단합니다

**화면 구성**

```text
인덱스의 가치는 존재 여부가 아니라,
통제된 실험에서 줄인 읽기 비용과
추가한 유지 비용으로 판단한다.
```

**발표 스크립트**

Chapter 10에서 가장 중요한 문장은 이것입니다. 인덱스의 가치는 존재 여부가 아니라 측정으로 판단합니다.

실제 조회 질문을 정하고, 기존 인덱스를 확인하고, 같은 데이터와 같은 SQL로 전후 실행 계획을 비교합니다.

그리고 결과 행이 동일한지 검증한 뒤, 읽기 이점이 쓰기·저장·운영 비용보다 큰지 판단합니다. 이 기준을 지킬 때 AI가 추천한 인덱스도 안전하게 검토할 수 있습니다.
