# Chapter 11 이론 발표 강의안

## 데이터베이스를 안전하게 지키고 복구하는 방법

> 목적: 데이터베이스 보안을 단순한 비밀번호 문제가 아니라 인증, 권한, 소유권, 비밀 보호, 백업·복원 검증까지 이어지는 운영 절차로 설명한다.  
> 기준: 초보자가 “권한을 줬다”가 아니라 “필요한 작업만 허용하고, 실제 차단 결과와 복원 가능성을 검증했다”라고 말할 수 있어야 한다.

---

## 1. Chapter 11은 빠른 DB보다 안전한 DB를 다룹니다

**화면 구성**

```text
보호 대상 식별
→ 최소 권한 설계
→ 실제 허용·차단 검증
→ 비밀 정보 보호
→ 백업 생성
→ 별도 DB 복원 검증
```

**발표 스크립트**

챕터 10에서는 인덱스와 실행 계획을 통해 빠르게 조회하는 방법을 배웠습니다. 하지만 데이터베이스가 아무리 빨라도 권한이 과도하거나, 접속 정보가 노출되거나, 백업을 복원할 수 없다면 안전한 시스템이라고 할 수 없습니다.

이번 장의 핵심은 두 가지입니다. 첫째, 필요한 작업만 허용하고 나머지는 차단합니다. 둘째, 백업은 파일을 만드는 데서 끝내지 않고 별도 데이터베이스에 복원해서 실제로 사용할 수 있는지 검증합니다.

## 2. 보안은 여러 통제가 함께 작동해야 합니다

**화면 구성**

| 영역 | 핵심 질문 |
|---|---|
| 인증 | 누가 접속했는가? |
| 권한 부여 | 무엇을 할 수 있는가? |
| 소유권 | 누가 객체를 관리하는가? |
| 입력 보호 | 입력값이 SQL 구조를 바꾸는가? |
| 비밀 보호 | 접속 정보와 백업 파일이 노출되는가? |
| 감사·기록 | 누가 무엇을 했는가? |
| 복구 | 장애 후 되돌릴 수 있는가? |

**발표 스크립트**

보안은 비밀번호 하나로 끝나지 않습니다. 접속하는 사람이 누구인지 확인하는 인증이 있고, 인증된 사람이 어떤 테이블에서 어떤 작업을 할 수 있는지 정하는 권한 부여가 있습니다.

또 객체를 누가 소유하고 관리하는지, 사용자 입력이 에스큐엘 명령으로 변하지 않게 막는지, 접속 정보와 백업 파일을 어떻게 보호하는지도 함께 봐야 합니다.

마지막으로 장애나 실수가 발생했을 때 복구할 수 있어야 합니다. 그래서 보안과 백업은 분리된 주제가 아니라 안전한 운영을 위한 하나의 흐름입니다.

## 3. Chapter 11은 별도 `security_lab`에서 진행합니다

**화면 구성**

```text
변경 금지: course_project / transaction_lab / performance_lab / public
이번 장 실습: security_lab
```

- Role 생성·삭제와 GRANT·REVOKE 예시는 기본 주석 상태
- 필요한 문장만 테스트 환경에서 선택 실행

**발표 스크립트**

이번 장은 역할과 권한, 백업과 복원을 다루기 때문에 실수의 영향이 큽니다. 그래서 앞 장의 스키마는 변경하지 않고 `security_lab`이라는 별도 스키마를 사용합니다.

특히 포스트그레스큐엘 Role은 데이터베이스 하나가 아니라 클러스터 전체에 영향을 줄 수 있습니다. 따라서 역할 생성, 삭제, 권한 부여 문장은 무조건 전체 실행하지 않고, 관리자 권한이 있는 테스트 환경에서 필요한 문장만 선택 실행합니다.

## 4. 먼저 보호할 자산과 위험을 정합니다

**화면 구성**

| 보호 자산 | 대표 위험 |
|---|---|
| 개인정보 | 과도한 조회·외부 유출 |
| 업무 데이터 | 무단 변경·삭제 |
| 비밀 정보 | 계정 탈취 |
| 데이터 구조 | 잘못된 ALTER·DROP |
| 로그 | 접속 URL·토큰 기록 |
| 백업 파일 | 전체 데이터 사본 노출 |
| 복구 절차 | 장애 시 복구 지연 |

**발표 스크립트**

보안 설계는 “무엇을 지켜야 하는가”에서 시작합니다. 이름과 이메일은 개인정보이고, 수강 상태와 금액은 업무 데이터입니다. 접속 유알엘, 비밀번호, 토큰, 백업 파일도 모두 보호 대상입니다.

위험은 외부 공격만이 아닙니다. 개발 계정으로 운영 DB에 접속하거나, 공개 저장소에 `.env`나 백업 파일을 올리거나, 에이아이가 만든 `DROP` 명령을 검토 없이 실행하는 것도 큰 위험입니다.

## 5. 인증·권한·소유권을 구분합니다

**화면 구성**

```text
인증       → 누가 접속했는가?
권한 부여  → 무엇을 할 수 있는가?
소유권     → 객체를 변경·삭제·권한 부여할 수 있는가?
역할 멤버십 → 다른 역할의 권한을 쓸 수 있는가?
감사       → 누가 무엇을 했는가?
```

**발표 스크립트**

초보자가 자주 헷갈리는 부분은 인증과 권한입니다. 인증은 접속 주체를 확인하는 일입니다. 하지만 접속에 성공했다고 해서 모든 테이블을 읽거나 수정할 수 있는 것은 아닙니다.

권한은 `셀렉트`, `인서트`, `업데이트`, `딜리트` 같은 작업 허용 범위입니다. 소유권은 더 강합니다. 객체 소유자는 객체 구조와 권한 관리에 큰 영향을 줄 수 있습니다.

그래서 애플리케이션 접속 계정을 테이블 소유자로 두지 않고, 소유 역할과 실행 역할을 분리하는 것이 안전합니다.

## 6. LOGIN 역할과 NOLOGIN 권한 역할을 분리합니다

**화면 구성**

| 역할 종류 | LOGIN | 목적 |
|---|---|---|
| owner role | NOLOGIN | 객체 소유·권한 관리 |
| report role | NOLOGIN | 조회 권한 묶음 |
| app role | NOLOGIN | 앱 실행 권한 묶음 |
| backup role | NOLOGIN | 백업용 읽기 권한 묶음 |
| login user | LOGIN | 실제 접속 |

**발표 스크립트**

포스트그레스큐엘 Role은 실제로 로그인하는 계정으로도 사용할 수 있고, 권한 묶음으로도 사용할 수 있습니다.

로그인 역할과 권한 역할을 분리하면 관리가 쉬워집니다. 보고용 사용자는 보고 권한 역할의 멤버가 되고, 앱 사용자는 앱 권한 역할의 멤버가 됩니다.

이렇게 하면 여러 사용자에게 같은 권한을 반복 부여하지 않고, 권한 역할 하나를 조정해 공통 정책을 관리할 수 있습니다.

## 7. 권한은 객체 범위별로 다릅니다

**화면 구성**

| 범위 | 대표 권한 | 의미 |
|---|---|---|
| 데이터베이스 | CONNECT | DB 접속 허용 |
| 스키마 | USAGE | 스키마 안 객체 이름 사용 |
| 스키마 | CREATE | 스키마 안 객체 생성 |
| 테이블 | SELECT, INSERT, UPDATE, DELETE | 행 조회·변경 |
| 컬럼 | SELECT, INSERT, UPDATE | 특정 컬럼 작업 |
| 시퀀스 | USAGE, SELECT, UPDATE | 자동 번호 사용·조회·설정 |

**발표 스크립트**

권한은 한 번에 끝나지 않습니다. 데이터베이스에 접속할 수 있어도 스키마 안 객체를 사용할 수 없을 수 있고, 스키마를 사용할 수 있어도 테이블을 조회할 수 없을 수 있습니다.

또 아이덴티티 자동값을 사용해 인서트하려면 테이블 인서트뿐 아니라 연결된 시퀀스 권한도 필요할 수 있습니다.

이 장의 앱 역할은 시퀀스 번호를 직접 조회할 필요가 없으므로 기본적으로 `USAGE`만 부여하고 `셀렉트`는 부여하지 않는 최소 권한 예시를 사용합니다.

## 8. 최소 권한은 작업 행렬로 설계합니다

**화면 구성**

| 작업 | 읽기 역할 | 앱 역할 |
|---|---|---|
| 학생·강의·신청 SELECT | 허용 | 허용 |
| 신청 INSERT | 불허 | 허용 |
| 신청 status UPDATE | 불허 | 허용 |
| paid_amount UPDATE | 불허 | 불허 |
| DELETE, TRUNCATE | 불허 | 불허 |
| schema CREATE | 불허 | 불허 |

**발표 스크립트**

권한을 부여하기 전에 역할별로 해야 할 작업을 표로 정리합니다. 읽기 역할은 보고용이므로 조회만 허용합니다.

앱 역할은 수강신청을 추가하고 상태를 바꿀 수 있어야 합니다. 하지만 결제 금액을 수정하거나 삭제할 수 있으면 위험합니다. 스키마 생성 권한도 필요하지 않습니다.

이 작업 행렬이 `그랜트`, `REVOKE`, 권한 테스트의 기준이 됩니다. 표 없이 권한을 주면 나중에 왜 허용했는지 설명하기 어렵습니다.

## 9. GRANT·REVOKE 후에는 유효 권한과 경로를 모두 봅니다

**화면 구성**

```text
has_*_privilege
→ 최종적으로 작업 가능한가?

ACL / PUBLIC / 멤버십 / 소유권
→ 그 권한이 어떤 경로로 생겼는가?
```

**발표 스크립트**

`그랜트`를 했는지, `REVOKE`를 했는지만 보면 충분하지 않습니다. 같은 권한이 직접 부여, 다른 역할 멤버십, 퍼블릭 권한, 객체 소유권을 통해 여전히 남아 있을 수 있습니다.

그래서 `has_table_privilege` 같은 유효 권한 함수로 최종 결과를 보고, 동시에 에이씨엘과 퍼블릭 권한, 역할 멤버십과 소유권 경로도 확인해야 합니다.

특히 데이터베이스에는 기본적으로 퍼블릭 CONNECT가 있을 수 있으므로, CONNECT가 true라고 해서 내가 직접 그랜트했기 때문이라고 단정하면 안 됩니다.

## 10. 현재 객체 권한과 미래 객체 권한은 다릅니다

**화면 구성**

```text
GRANT ON TABLE
→ 지금 존재하는 테이블에 적용

ALTER DEFAULT PRIVILEGES
→ 특정 역할이 앞으로 만들 객체의 기본 권한
```

**발표 스크립트**

현재 존재하는 테이블에 `그랜트 셀렉트`를 했다고 해서 앞으로 새로 만들어질 테이블에도 자동으로 같은 권한이 적용되는 것은 아닙니다.

미래 객체의 기본 권한은 `ALTER 디폴트 PRIVILEGES`로 설정합니다. 여기서 중요한 것은 “어떤 역할이 앞으로 객체를 생성하는가”입니다.

Default Privileges는 기존 객체의 권한을 바꾸지 않으므로, 현재 객체와 미래 객체 권한을 따로 확인해야 합니다.

## 11. 권한은 실제 허용·차단 동작으로 검증합니다

**화면 구성**

| 역할 | 성공해야 함 | 실패해야 함 |
|---|---|---|
| 읽기 계정 | SELECT | INSERT, UPDATE, DELETE |
| 앱 계정 | SELECT, INSERT, status UPDATE | paid_amount UPDATE, DELETE, schema CREATE |

**발표 스크립트**

권한 조회 결과가 맞아 보여도 실제 동작을 확인해야 합니다. 읽기 계정은 셀렉트가 성공해야 하지만 인서트, 업데이트, 딜리트는 실패해야 합니다.

앱 계정은 신청 인서트와 status 업데이트는 성공해야 합니다. 하지만 결제 금액인 `paid_amount` 수정, 딜리트, 스키마 CREATE는 실패해야 합니다.

실패 테스트는 오류가 정상 결과일 수 있으므로 한 문장씩 실행하고, 오류 후에는 `롤백 투 세이브포인트` 또는 `롤백`으로 상태를 복구합니다.

## 12. PUBLIC과 소유권은 과소평가하면 안 됩니다

**화면 구성**

```text
확인 경로:
직접 GRANT
PUBLIC 권한
역할 멤버십
객체 소유권
Default Privileges
```

**발표 스크립트**

`REVOKE`를 했는데도 권한이 남아 있다면 다른 경로가 있을 수 있습니다. 퍼블릭에게 부여된 권한, 다른 권한 역할의 멤버십, 객체 소유권이 대표적입니다.

그렇다고 무조건 `REVOKE ALL FROM 퍼블릭`을 실행하면 다른 계정이나 애플리케이션에 영향을 줄 수 있습니다. 테스트 DB에서 의존성을 먼저 확인해야 합니다.

소유 역할을 삭제할 때도 조심해야 합니다. 소유권을 다른 역할로 이전하고, 남은 권한과 의존성을 검토한 뒤 정리해야 합니다.

## 13. 비밀 정보는 저장소와 로그에 남기지 않습니다

**화면 구성**

```text
.env.example → 변수 이름만
실제 .env     → 저장소 밖 또는 ignore
PGPASSWORD   → 예제에 저장하지 않음
PGPASSFILE   → 보호된 경로 사용
백업 파일    → 원본 데이터 수준으로 보호
```

**발표 스크립트**

접속 유알엘, 비밀번호, 토큰, 백업 파일은 모두 민감 정보입니다. `.env.example`에는 변수 이름만 두고 실제 값은 넣지 않습니다.

`PGPASSWORD`를 명령어나 예제 파일에 남기면 쉘 기록이나 로그에 노출될 수 있습니다. 가능한 경우 저장소 밖의 password file을 사용하고 OS 접근 권한을 제한합니다.

비밀 정보가 이미 노출되었다면 깃에서 파일을 삭제하는 것만으로 충분하지 않습니다. 먼저 비밀번호나 토큰을 폐기하고 회전해야 합니다.

## 14. SQL Injection은 값과 SQL 구조를 분리해 막습니다

**화면 구성**

```text
위험: SQL 문자열 + user_input
안전: SQL 구조 + 파라미터 값
```

- 값: 파라미터 바인딩
- 테이블명·컬럼명·정렬 방향: 허용 목록
- 피해 범위 축소: 최소 권한 계정

**발표 스크립트**

사용자 입력을 문자열로 이어 붙이면 입력값이 에스큐엘 구조를 바꿀 수 있습니다. 그래서 값은 파라미터로 바인딩해야 합니다.

하지만 테이블명, 컬럼명, 정렬 방향은 보통 값 파라미터로 처리할 수 없습니다. 이런 식별자는 애플리케이션에서 허용 목록으로 제한해야 합니다.

또 최소 권한 계정을 사용하면 Injection이 발생하더라도 피해 범위를 줄일 수 있습니다. 입력 검증 하나만으로 끝나는 것이 아니라 파라미터 바인딩, 허용 목록, 최소 권한을 함께 사용합니다.

---

## 15. 백업·복제·고가용성은 같은 말이 아닙니다

**화면 구성**

| 방식 | 목적 | 주의점 |
|---|---|---|
| 논리 백업 | 구조·데이터 복원·이관 | 복원 시간·의존성 검증 필요 |
| 물리 백업·PITR | 클러스터·특정 시점 복구 | WAL·보관 정책 필요 |
| 복제 | 가용성·읽기 분산 | 삭제도 복제될 수 있음 |
| 스냅샷 | 스토리지 시점 사본 | DB 일관성·복원 시험 필요 |

**발표 스크립트**

백업, 복제, 고가용성은 목적이 다릅니다. 복제 서버가 있다고 해서 실수로 삭제한 데이터를 자동으로 되돌릴 수 있는 것은 아닙니다. 삭제도 그대로 복제될 수 있습니다.

이 장에서는 입문 수준에서 논리 백업과 복원 검증에 집중합니다. 중요한 것은 백업 파일을 만들었다는 사실이 아니라, 필요한 시점에 복원할 수 있음을 확인하는 것입니다.

---

## 16. 백업 전에는 버전·계정·의존성을 확인합니다

**화면 구성**

```text
도구 버전: pg_dump / pg_restore / psql
서버 버전: SHOW server_version
백업 계정: CONNECT + USAGE + SELECT
의존성: FK, 타입, 함수, 확장, Large Object, RLS
```

**발표 스크립트**

백업 명령을 실행하기 전에 도구 버전과 서버 버전을 확인합니다. 일반적으로 오래된 `피지 덤프`로 더 새로운 서버를 백업하려 하면 문제가 될 수 있습니다.

또 백업 계정이 모든 데이터를 자동으로 우회해서 읽는다고 생각하면 안 됩니다. 필요한 스키마와 테이블을 읽을 권한이 있어야 하며, 행-Level Security가 있다면 백업 결과에도 영향을 줄 수 있습니다.

특정 스키마만 백업할 때는 외부 의존성도 확인해야 합니다. 실습의 `security_lab`은 단독 복원 가능하도록 설계되어 있습니다.

---

## 17. 백업 파일은 생성 후 바로 검증합니다

**화면 구성**

```text
종료 코드·경고 확인
파일 크기·생성 시각 기록
pg_restore --list 확인
SHA-256 해시 기록
저장 위치·접근 권한 확인
```

**발표 스크립트**

`피지 덤프`가 끝났다고 백업이 완료된 것은 아닙니다. 명령이 성공했는지, 경고가 없는지, 파일 크기가 비정상적으로 작지 않은지 확인해야 합니다.

사용자 정의 형식 백업은 `피지 리스토어 --list`로 내부 목록을 확인할 수 있습니다. 해시를 기록하면 파일이 나중에 바뀌었는지 확인하는 데 도움이 됩니다.

하지만 해시는 복원 가능성을 증명하지 않습니다. 파일이 변하지 않았다는 근거일 뿐이고, 실제 복원 시험은 따로 해야 합니다.

---

## 18. 복원은 원본이 아니라 별도 DB에서 검증합니다

**화면 구성**

```text
createdb ai_database_book_restore
→ pg_restore --single-transaction
→ 06_restore_validation.sql
→ 권한 재적용
→ 허용·차단 재검증
```

**발표 스크립트**

복원 검증은 원본 데이터베이스에 덮어쓰지 않습니다. 깨끗한 별도 데이터베이스를 만들고 그곳에 복원합니다.

작은 실습 백업은 `--single-transaction`으로 복원해 중간 오류가 있을 때 부분 복원 객체가 남는 위험을 줄입니다. 다만 대규모 운영 복원에서는 긴 트랜잭션의 잠금과 자원 사용을 별도로 검토해야 합니다.

복원 후에는 구조와 데이터만 보지 않습니다. 소유권, 시퀀스, 제약조건, 부분 고유 인덱스, 그리고 권한 재적용 후 허용·차단 동작까지 확인합니다.

---

## 19. RPO·RTO는 백업 전략의 목표입니다

**화면 구성**

| 기준 | 질문 | 예 |
|---|---|---|
| RPO | 어느 시점까지의 데이터 손실을 허용하는가? | 최대 1시간 |
| RTO | 장애 후 얼마 안에 재개해야 하는가? | 2시간 |

**발표 스크립트**

RPO는 허용 가능한 데이터 손실 시간입니다. RPO가 1시간인데 하루 한 번만 백업하면 목표를 만족할 수 없습니다.

RTO는 장애 후 서비스를 다시 시작해야 하는 시간입니다. 백업 파일은 있어도 복원 시간이 너무 오래 걸리면 RTO를 만족하지 못할 수 있습니다.

그래서 백업 주기, 복원 시간, 검증 결과, 다음 복원 시험 날짜를 Runbook에 기록해야 합니다. 복구 절차는 담당자의 기억이 아니라 반복 실행 가능한 문서여야 합니다.

---

## 20. 핵심 정리: 보안은 허용·차단·복원으로 증명합니다

**화면 구성**

```text
최소 권한
→ 유효 권한과 경로 확인
→ 실제 허용·차단 테스트
→ 비밀 정보 보호
→ 백업 파일 검증
→ 별도 DB 복원 검증
→ RPO·RTO 기록
```

**발표 스크립트**

챕터 11의 핵심은 보안을 추상적인 구호가 아니라 확인 가능한 결과로 만드는 것입니다.

필요한 권한만 주고, 실제로 허용되어야 할 작업은 성공하는지, 차단되어야 할 작업은 실패하는지 확인합니다.

그리고 백업은 파일 생성에서 끝나지 않습니다. 별도 DB에 복원하고 구조, 데이터, 소유권, 권한을 다시 검증해야 비로소 복구 가능한 백업이라고 할 수 있습니다.
