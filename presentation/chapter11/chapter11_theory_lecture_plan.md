# Chapter 11 이론 발표 강의안

## 데이터베이스를 안전하게 지키고 복구하는 방법

> 목적: 데이터베이스 보안을 단순한 비밀번호 문제가 아니라 인증, 권한, 소유권, 비밀 보호, 백업·복원 검증까지 이어지는 운영 설계로 설명한다.  
> 기준: 초보자가 각 장표를 보며 “누가 무엇을 할 수 있어야 하는지, 백업이 왜 복원 검증까지 포함해야 하는지” 직관적으로 이해할 수 있어야 한다.

---

## 1. 빠른 DB보다 안전하게 지킬 수 있는 DB가 중요합니다

**화면 구성**

- 큰 제목: 데이터베이스를 안전하게 지키고 복구하는 방법
- 흐름: 보호 대상 파악 → 최소 권한 → 비밀 보호 → 백업 → 복원 검증
- 키워드: 보안 / 권한 / 복구 가능성

**발표 스크립트**

앞 장에서는 인덱스와 실행 계획을 보며 데이터베이스를 빠르게 조회하는 방법을 배웠습니다. 그런데 데이터베이스가 아무리 빨라도 권한이 과도하거나, 접속 정보가 노출되거나, 백업을 복원할 수 없다면 안전한 시스템이라고 보기 어렵습니다.

이번 장에서는 PostgreSQL을 기준으로 데이터베이스를 안전하게 지키는 방법을 봅니다. 핵심은 필요한 사람에게 필요한 작업만 허용하고, 백업은 파일 생성이 아니라 실제 복원 검증까지 확인하는 것입니다.

---

## 2. 보안은 여러 통제가 함께 작동해야 합니다

**화면 구성**

- 7개 영역 카드: 인증, 권한 부여, 소유권, 입력 보호, 비밀 보호, 감사·기록, 복구
- 강조 문장: 인증 성공 ≠ 모든 데이터 접근 가능

**발표 스크립트**

보안은 “비밀번호를 설정했다”에서 끝나지 않습니다. 먼저 접속하는 사람이 누구인지 확인하는 인증이 있고, 인증된 사람이 무엇을 할 수 있는지 정하는 권한 부여가 있습니다.

또 테이블을 누가 소유하고 관리할지, 사용자가 입력한 값이 SQL 구조를 바꾸지 못하게 할지, 백업 파일과 접속 URL을 어떻게 보호할지도 함께 생각해야 합니다.

마지막으로 장애나 실수가 발생했을 때 복구할 수 있어야 합니다. 보안과 복구는 따로 떨어진 주제가 아니라 운영 안정성을 만드는 하나의 흐름입니다.

## 3. Chapter 11은 별도 security_lab에서 실습합니다

**화면 구성**

```text
앞 장 데이터: course_project / transaction_lab / performance_lab
이번 장 실습: security_lab
```

- 안내: 기존 프로젝트 객체는 삭제하거나 변경하지 않음

**발표 스크립트**

이번 장은 역할과 권한, 백업·복원을 다루기 때문에 기존 실습 데이터를 함부로 건드리면 위험합니다. 그래서 `security_lab`이라는 별도 스키마를 사용합니다.

또 PostgreSQL의 Role은 특정 데이터베이스 하나가 아니라 클러스터 전체에 영향을 줄 수 있습니다. 그래서 역할 생성, 삭제, 권한 부여 예시는 기본적으로 주석 상태로 제공하고, 필요한 문장만 선택 실행하는 방식으로 진행합니다.

## 4. 먼저 보호할 자산과 위험을 정합니다

**화면 구성**

| 자산 | 위험 |
|---|---|
| 개인정보 | 과도한 조회·유출 |
| 업무 데이터 | 무단 변경·삭제 |
| 비밀 정보 | 계정 탈취 |
| 백업 파일 | 전체 데이터 노출 |
| 복구 절차 | 장애 시 복구 지연 |

**발표 스크립트**

보안 설계는 “무엇이 위험한가”를 먼저 정해야 합니다. 이름과 이메일은 개인정보입니다. 수강 상태와 결제 금액 같은 업무 데이터는 잘못 수정되면 서비스 의미가 깨집니다.

백업 파일도 매우 중요합니다. 백업은 원본 데이터의 사본이므로 공개 저장소에 올라가면 원본 DB가 노출된 것과 비슷한 위험이 생깁니다.

위험은 외부 해킹만이 아닙니다. 개발 계정으로 운영 DB에 접속하거나, AI가 만든 `DROP` 명령을 검토 없이 실행하는 것도 중요한 위험입니다.

## 5. 인증·권한·소유권을 구분합니다

**화면 구성**

- 비교 표
  - 인증: 누가 접속했는가
  - 권한 부여: 무엇을 할 수 있는가
  - 소유권: 객체를 관리할 수 있는가
  - 감사: 누가 무엇을 했는가

**발표 스크립트**

초보자가 자주 헷갈리는 부분이 인증과 권한입니다. 인증은 “누가 접속했는가”입니다. 하지만 접속에 성공했다고 해서 모든 테이블을 읽거나 수정할 수 있는 것은 아닙니다.

권한 부여는 접속한 역할이 어떤 테이블에서 `SELECT`, `INSERT`, `UPDATE`, `DELETE`를 할 수 있는지 정합니다. 소유권은 한 단계 더 강합니다. 객체 소유자는 테이블 정의 변경이나 권한 관리에 큰 영향을 줄 수 있습니다.

그래서 실제 접속 계정을 테이블 소유자로 쓰지 않고, 소유 역할과 실행 역할을 분리하는 것이 좋습니다.

## 6. 로그인 역할과 권한 역할을 분리합니다

**화면 구성**

| 역할 | LOGIN | 목적 |
|---|---|---|
| owner role | NOLOGIN | 객체 소유 |
| report role | NOLOGIN | 조회 권한 묶음 |
| app role | NOLOGIN | 앱 작업 권한 묶음 |
| login user | LOGIN | 실제 접속 |

**발표 스크립트**

PostgreSQL Role은 실제 접속 계정으로도 사용할 수 있고, 권한 묶음으로도 사용할 수 있습니다. 이 둘을 분리하면 관리가 쉬워집니다.

예를 들어 보고용 사용자는 로그인은 하지만 직접 여러 테이블 권한을 하나씩 받지 않고, 보고 권한 역할의 멤버가 됩니다. 앱 사용자도 마찬가지로 앱 권한 역할을 통해 필요한 권한만 받습니다.

이 방식은 권한을 개인 계정마다 흩뿌리지 않고 역할 단위로 관리하게 해 줍니다.

## 7. 권한은 범위별로 다릅니다

**화면 구성**

| 범위 | 대표 권한 | 의미 |
|---|---|---|
| 데이터베이스 | CONNECT | 접속 가능 |
| 스키마 | USAGE | 객체 이름 접근 |
| 테이블 | SELECT, INSERT, UPDATE | 행 작업 |
| 컬럼 | UPDATE(status) | 특정 컬럼 변경 |
| 시퀀스 | USAGE | IDENTITY 번호 사용 |

**발표 스크립트**

권한은 한 번에 전부 주는 것이 아니라 범위별로 나뉩니다. 데이터베이스 `CONNECT` 권한이 있어도 테이블을 읽을 수 있는 것은 아닙니다. 스키마 `USAGE`가 있어도 테이블 `SELECT`가 없으면 조회할 수 없습니다.

또 자동 ID를 사용하는 `IDENTITY` 컬럼은 내부 시퀀스를 사용하므로, 앱 역할이 ID를 생략하고 INSERT하려면 필요한 시퀀스 권한도 확인해야 합니다.

최소 권한을 설계할 때는 데이터베이스, 스키마, 테이블, 컬럼, 시퀀스 권한을 따로 보아야 합니다.

---

## 8. 최소 권한은 작업 행렬로 설계합니다

**화면 구성**

| 작업 | 보고 역할 | 앱 역할 |
|---|---|---|
| SELECT | 허용 | 허용 |
| enrollments INSERT | 불허 | 허용 |
| status UPDATE | 불허 | 허용 |
| paid_amount UPDATE | 불허 | 불허 |
| DELETE | 불허 | 불허 |
| schema CREATE | 불허 | 불허 |

**발표 스크립트**

최소 권한은 감으로 정하지 않습니다. “이 역할이 어떤 작업을 해야 하는가”를 표로 작성합니다.

보고 역할은 조회만 하면 됩니다. 수강신청 앱 역할은 신청을 추가하고 상태를 바꿀 수는 있지만, 결제 금액을 임의로 바꾸거나 행을 삭제해서는 안 됩니다.

이렇게 작업 행렬을 만들면 `ALL PRIVILEGES`처럼 과도한 권한을 주지 않아도 됩니다. 중요한 것은 허용할 작업뿐 아니라 차단해야 할 작업도 함께 적는 것입니다.

## 9. GRANT·REVOKE 후에는 유효 권한을 확인합니다

**화면 구성**

- 흐름: GRANT/REVOKE → has_*_privilege 확인 → ACL 확인 → 실제 동작 테스트
- 경로 카드: 직접 권한, 멤버십, PUBLIC, 소유권

**발표 스크립트**

`GRANT`를 실행했다고 설계가 끝나는 것이 아닙니다. 실제 로그인 역할이 최종적으로 어떤 작업을 할 수 있는지 확인해야 합니다.

반대로 `REVOKE`를 실행해도 다른 경로로 권한이 남아 있을 수 있습니다. 직접 받은 권한, 다른 역할 멤버십, `PUBLIC` 권한, 객체 소유권 같은 경로를 확인해야 합니다.

그래서 권한 검증은 함수 결과와 ACL 조회, 실제 성공·실패 동작 테스트를 함께 봐야 합니다.

## 10. 현재 객체 권한과 미래 객체 권한은 다릅니다

**화면 구성**

```text
현재 객체 GRANT
→ 지금 존재하는 테이블에 적용

ALTER DEFAULT PRIVILEGES
→ 앞으로 생성될 객체의 기본 권한
```

**발표 스크립트**

현재 이미 존재하는 테이블에 `GRANT`를 주는 것과 앞으로 생성될 테이블의 기본 권한을 정하는 것은 다릅니다.

`ALTER DEFAULT PRIVILEGES`는 미래 객체에 대한 설정입니다. 기존 테이블의 권한을 자동으로 바꿔 주지 않습니다. 또한 어떤 역할이 객체를 생성하는지에 따라 적용 결과가 달라질 수 있습니다.

운영에서는 현재 객체와 미래 객체 권한을 모두 관리해야 새 테이블이 생겼을 때 권한 누락이나 과다 부여가 생기지 않습니다.

## 11. 권한은 실제 허용·차단 동작으로 확인합니다

**화면 구성**

| 역할 | 성공해야 함 | 실패해야 함 |
|---|---|---|
| 읽기 계정 | SELECT | INSERT, UPDATE, DELETE |
| 앱 계정 | SELECT, INSERT, status UPDATE | paid_amount UPDATE, DELETE, CREATE |

**발표 스크립트**

권한 검증은 “권한이 있을 것 같다”로 끝나면 안 됩니다. 읽기 계정은 조회만 성공해야 하고, 삽입이나 수정은 실패해야 합니다.

앱 계정은 수강신청을 추가할 수 있고 상태만 바꿀 수 있어야 합니다. 하지만 결제 금액 수정, 삭제, 스키마 생성은 실패해야 합니다.

성공 테스트는 마지막에 `ROLLBACK`해서 기준 데이터를 보존하고, 실패 테스트는 한 문장씩 실행해 어떤 권한 때문에 막혔는지 확인합니다.

## 12. 비밀 정보와 로그도 보호 대상입니다

**화면 구성**

- 금지 예: `.env`에 비밀번호 저장, 백업 파일 커밋, 전체 접속 URL 로그 출력
- 권장 예: `.env.example`에는 변수명만, password file은 저장소 밖, 토큰 노출 시 회전

**발표 스크립트**

비밀 정보는 데이터베이스 안에만 있는 것이 아닙니다. 접속 URL, 비밀번호, 토큰, 백업 파일, 오류 로그도 보호해야 합니다.

저장소에는 실제 비밀번호가 들어간 `.env`를 올리지 않습니다. 예제 파일에는 변수 이름만 둡니다. 실제 암호 파일은 저장소 밖에 두고 OS 권한으로 보호합니다.

비밀 정보가 노출되면 파일을 삭제하는 것만으로 끝나지 않습니다. 비밀번호나 토큰을 폐기하고 새로 발급해야 하며, 로그와 배포 환경까지 확인해야 합니다.

## 13. SQL Injection은 구조와 값을 분리해 막습니다

**화면 구성**

```text
위험: SQL 문자열 + 사용자 입력
안전: SQL 구조 + 파라미터 값
```

- 추가: 테이블명·컬럼명·정렬 방향은 허용 목록으로 제한

**발표 스크립트**

SQL Injection은 사용자가 입력한 값이 SQL 구조의 일부로 해석될 때 발생합니다. 예를 들어 이메일 검색 SQL을 문자열 결합으로 만들면 사용자가 입력한 값이 조건을 바꿀 수 있습니다.

안전한 방향은 SQL 구조와 값을 분리하는 것입니다. 값은 파라미터로 바인딩합니다.

다만 테이블명, 컬럼명, 정렬 방향은 일반적인 값 파라미터로 처리하기 어렵습니다. 이런 경우에는 애플리케이션에서 허용 목록을 만들고 그 안에서만 선택하게 해야 합니다.

## 14. 백업·복제·고가용성은 목적이 다릅니다

**화면 구성**

| 방식 | 목적 | 주의점 |
|---|---|---|
| 논리 백업 | 복원·이관 | 복원 시험 필요 |
| 물리 백업·PITR | 특정 시점 복구 | WAL 정책 필요 |
| 복제 | 가용성·읽기 분산 | 삭제도 복제될 수 있음 |
| 스냅샷 | 시점 사본 | DB 일관성 확인 필요 |

**발표 스크립트**

백업, 복제, 고가용성은 비슷해 보이지만 목적이 다릅니다. 복제는 서비스 중단을 줄이거나 읽기 부하를 나누는 데 도움이 되지만, 실수로 삭제한 데이터도 그대로 복제될 수 있습니다.

백업은 특정 시점으로 돌아가기 위한 준비입니다. 이 장에서는 입문 수준에서 논리 백업과 복원 검증에 집중합니다.

중요한 점은 백업 파일이 있다고 해서 복구 가능하다고 말할 수 없다는 것입니다. 별도 환경에서 복원해 보고 검증해야 합니다.

## 15. 백업 전에는 버전·계정·의존성을 확인합니다

**화면 구성**

- 체크리스트
  - pg_dump / pg_restore / psql 버전
  - 서버 버전
  - 백업 계정 권한
  - RLS 여부
  - 외부 스키마 의존성

**발표 스크립트**

백업 명령을 실행하기 전에 도구 버전과 서버 버전을 확인합니다. 오래된 `pg_dump`로 더 새로운 서버를 덤프하려고 하면 문제가 생길 수 있습니다.

또 백업 계정이 모든 데이터를 자동으로 읽을 수 있다고 가정하면 안 됩니다. 필요한 스키마와 테이블에 대한 권한이 있어야 하고, Row-Level Security가 있다면 정책도 영향을 줄 수 있습니다.

특정 스키마만 백업할 때는 외부 스키마 FK, 함수, 확장 기능 같은 의존성을 확인해야 합니다.

---

## 16. 백업 파일은 생성 후 바로 검증합니다

**화면 구성**

```text
명령 종료 코드 확인
파일 크기·생성 시각 기록
pg_restore --list 확인
SHA-256 해시 기록
보관 위치·접근 권한 확인
```

**발표 스크립트**

백업 명령을 실행한 뒤에는 파일이 생겼다는 사실만 보면 안 됩니다. 명령이 성공적으로 끝났는지, 파일 크기가 비정상적으로 작지는 않은지, 아카이브 목록을 읽을 수 있는지 확인합니다.

해시도 기록합니다. 해시는 파일이 나중에 바뀌었는지 확인하는 근거입니다. 하지만 해시가 맞다고 해서 복원 가능하다는 뜻은 아닙니다.

복원 가능성은 별도 데이터베이스에 실제로 복원해 봐야 확인됩니다.

---

## 17. 복원은 원본 DB가 아니라 별도 DB에 합니다

**화면 구성**

- 흐름: 백업 파일 → ai_database_book_restore → 구조·데이터 검증 → 권한 재적용 → 권한 동작 검증
- 강조: 원본 DB에 덮어쓰지 않음

**발표 스크립트**

복원 시험은 원본 데이터베이스에 바로 덮어쓰지 않습니다. 별도의 깨끗한 검증 DB를 만들고 그곳에 복원합니다.

작은 실습에서는 `pg_restore --single-transaction`으로 복원 전체를 하나의 트랜잭션처럼 처리합니다. 오류가 발생하면 일부 객체만 남는 위험을 줄일 수 있습니다.

대규모 운영 복원에서는 긴 트랜잭션, 잠금, 디스크 사용량을 별도로 검토해야 합니다. 하지만 입문 단계에서 기억할 핵심은 원본을 건드리지 않고 별도 DB에서 검증한다는 점입니다.

---

## 18. 복원 검증은 두 단계로 나눕니다

**화면 구성**

| 단계 | 확인 내용 |
|---|---|
| 1단계 | 구조, 데이터, 제약조건, 인덱스, IDENTITY, 소유권 |
| 2단계 | Role, GRANT, PUBLIC, 실제 허용·차단 동작 |

**발표 스크립트**

복원 검증은 먼저 구조와 데이터가 살아났는지 확인합니다. 테이블 행 수, JOIN 결과, 고아 FK, 활성 신청 중복, 제약조건, 부분 고유 인덱스, IDENTITY 시퀀스를 봅니다.

그다음 권한을 재적용하고 다시 확인합니다. `--no-owner --no-privileges`로 이동성을 높인 백업은 원본 권한을 그대로 복원하지 않으므로, 역할과 권한을 별도로 적용해야 합니다.

검증이 실패하면 백업 성공으로 기록하지 않습니다. 원인을 수정하고 다시 백업·복원·검증해야 합니다.

---

## 19. RPO·RTO는 복구 목표를 숫자로 정합니다

**화면 구성**

| 기준 | 질문 | 예시 |
|---|---|---|
| RPO | 얼마만큼의 데이터 손실을 허용하는가 | 최대 1시간 |
| RTO | 얼마 안에 서비스를 재개해야 하는가 | 2시간 |

**발표 스크립트**

복구 계획은 “백업을 해 둔다”로 충분하지 않습니다. 어느 시점까지의 데이터 손실을 허용할지, 장애 후 얼마 안에 서비스를 다시 열어야 하는지를 숫자로 정해야 합니다.

RPO가 1시간인데 하루 한 번만 백업하면 목표를 충족하지 못할 수 있습니다. RTO가 짧다면 백업 파일이 있어도 복원 시간이 너무 길면 문제가 됩니다.

그래서 복구 계획은 백업 주기, 보관 위치, 복원 시간, 검증 절차까지 함께 정해야 합니다.

---

## 20. AI 보안·백업 명령은 반드시 검토합니다

**화면 구성**

- 검토 항목: 권한 범위, PUBLIC 영향, 비밀 정보, 백업 범위, 원본 DB 보호, 복원 검증, 파괴적 명령
- 대표 오류: ALL PRIVILEGES, DROP CASCADE, 원본 DB 복원, 검증 없는 백업 성공 선언

**발표 스크립트**

AI는 보안 명령과 백업 명령의 초안을 만드는 데 도움을 줄 수 있습니다. 하지만 그대로 실행하면 위험할 수 있습니다.

특히 `ALL PRIVILEGES`, `DROP OWNED CASCADE`, 원본 DB에 직접 복원하는 명령, 비밀번호가 포함된 명령은 반드시 멈추고 검토해야 합니다.

AI에게 요청할 때도 현재 스키마, 허용할 작업, 차단할 작업, 백업 범위, 복원 대상 DB, 검증 기준을 함께 제공해야 합니다.

---

## 21. 핵심 정리: 허용·차단·복구를 모두 증거로 남깁니다

**화면 구성**

- 3개 카드
  - 필요한 작업만 허용
  - 실제 허용·차단 결과 확인
  - 별도 DB 복원 검증

**발표 스크립트**

이번 장의 핵심은 세 가지입니다. 첫째, 필요한 작업만 허용합니다. 둘째, 권한 설계가 실제로 허용할 작업은 허용하고 차단할 작업은 차단하는지 확인합니다.

셋째, 백업은 만들어 둔 파일이 아니라 복원에 성공한 절차입니다. 구조와 데이터, 권한까지 검증해야 복구 가능하다고 말할 수 있습니다.

보안은 한 번 설정하고 끝나는 작업이 아니라, 운영 중 계속 확인하고 기록해야 하는 과정입니다.
