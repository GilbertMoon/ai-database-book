# Chapter 11 이론 발표 강의안

## 데이터베이스를 안전하게 지키고 복구하는 방법

> 목적: 보안을 비밀번호 설정 하나가 아니라 보호 대상 식별, 최소 권한, 비밀 정보 보호, 백업, 복원 검증까지 이어지는 운영 설계로 설명한다.  
> 기준: 초보자가 “접속된다”가 아니라 “누가 무엇을 할 수 있고, 장애 후 어디까지 복구할 수 있는지 검증했다”라고 말할 수 있어야 한다.

---

## 1. Chapter 11은 빠른 DB보다 안전한 DB를 다룹니다

**화면 구성**

```text
보호 대상 파악
→ 최소 권한
→ 권한 검증
→ 비밀 정보 보호
→ 백업 생성
→ 별도 DB 복원 검증
```

**발표 스크립트**

앞 장에서는 인덱스와 실행 계획으로 빠른 조회를 검토했습니다. 하지만 데이터베이스가 아무리 빨라도 권한이 과도하거나, 접속 정보가 노출되거나, 백업을 복원할 수 없다면 안전한 시스템이라고 볼 수 없습니다.

이번 장의 핵심은 보안 명령어를 외우는 것이 아닙니다. 보호할 데이터가 무엇인지 정하고, 필요한 작업만 허용하며, 실제 허용·차단 결과와 복원 가능성을 확인하는 것입니다.

---

## 2. 보안과 복구는 함께 설계합니다

**화면 구성**

| 영역 | 핵심 질문 |
|---|---|
| 인증 | 누가 접속하는가? |
| 권한 | 무엇을 할 수 있는가? |
| 소유권 | 객체를 누가 관리하는가? |
| 비밀 보호 | 접속 정보가 노출되지 않는가? |
| 복구 | 장애 후 되돌릴 수 있는가? |

**발표 스크립트**

인증에 성공했다는 말은 단지 접속 주체를 확인했다는 뜻입니다. 그 사람이 어떤 테이블을 읽고 수정할 수 있는지는 권한 부여의 문제입니다.

또 객체 소유자는 일반 권한보다 더 큰 힘을 가질 수 있습니다. 앱 계정을 소유자로 사용하면 실수로 구조를 바꾸거나 권한을 재부여할 위험이 커집니다.

복구도 보안의 일부입니다. 실수로 삭제했거나 장애가 났을 때 필요한 시점으로 돌아갈 수 있어야 데이터베이스를 안전하게 운영한다고 말할 수 있습니다.

## 3. Chapter 11은 기존 실습 데이터를 보호합니다

**화면 구성**

```text
변경 금지:
course_project
transaction_lab
performance_lab
public

실습 대상:
security_lab
```

**발표 스크립트**

Chapter 11은 앞 장에서 만든 프로젝트, 트랜잭션, 성능 실험 데이터를 변경하지 않습니다.

보안과 백업 실습은 `security_lab`이라는 별도 스키마에서 진행합니다. 이렇게 해야 실습을 초기화하거나 권한을 확인할 때 앞 장의 기준 데이터가 깨지지 않습니다.

또 PostgreSQL Role은 클러스터 전역 객체일 수 있으므로 역할 생성과 삭제는 특히 조심해야 합니다. 그래서 역할·권한 SQL은 기본적으로 주석 상태로 제공하고, 관리자 권한이 있는 테스트 환경에서 필요한 문장만 선택 실행합니다.

## 4. 먼저 보호할 자산과 위험을 정합니다

**화면 구성**

| 자산 | 위험 |
|---|---|
| 개인정보 | 과도한 조회·유출 |
| 업무 데이터 | 무단 변경·삭제 |
| 접속 정보 | 계정 탈취 |
| 로그 | 비밀 정보 노출 |
| 백업 파일 | 전체 데이터 유출 |
| 복구 절차 | 장애 시 지연 |

**발표 스크립트**

보안은 막연히 “강하게” 하는 것이 아니라 무엇을 보호할지 정하는 것에서 시작합니다.

이 장에서는 이름과 이메일 같은 개인정보, 수강 상태와 금액 같은 업무 데이터, 접속 URL과 백업 파일을 보호 대상으로 봅니다.

위험은 외부 공격만 의미하지 않습니다. 개발 계정으로 운영 DB에 접속하거나, 백업 파일을 공개 저장소에 올리거나, AI가 만든 DROP 명령을 검토 없이 실행하는 것도 실제 위험입니다.

## 5. 인증·권한·소유권·감사를 구분합니다

**화면 구성**

```text
인증: 누가 접속했는가
권한: 무엇을 할 수 있는가
소유권: 객체를 변경·관리할 수 있는가
멤버십: 다른 역할의 권한을 쓸 수 있는가
감사: 누가 무엇을 했는가
```

**발표 스크립트**

초보자가 가장 많이 헷갈리는 부분은 접속 계정과 권한, 소유권을 같은 것으로 생각하는 것입니다.

PostgreSQL에서는 Role 하나가 로그인 계정이 될 수도 있고, 권한 묶음이 될 수도 있습니다. 하지만 운영 설계에서는 로그인 역할, 권한 역할, 소유 역할을 분리하는 것이 안전합니다.

소유권은 단순 SELECT 권한과 다릅니다. 객체를 바꾸거나 삭제할 수 있으므로 앱 계정에 소유권을 주지 않는 것이 기본 방향입니다.

---

## 6. 로그인 역할과 권한 역할을 분리합니다

**화면 구성**

| 역할 | LOGIN | 목적 |
|---|---|---|
| 소유 역할 | NOLOGIN | 객체 소유 |
| 읽기 권한 역할 | NOLOGIN | 보고용 SELECT |
| 앱 권한 역할 | NOLOGIN | 앱 실행 권한 |
| 백업 권한 역할 | NOLOGIN | 백업용 조회 |
| 읽기 로그인 | LOGIN | 실제 접속 |
| 앱 로그인 | LOGIN | 실제 접속 |

**발표 스크립트**

로그인 역할은 실제로 접속하는 계정이고, 권한 역할은 작업 권한을 묶어 두는 역할입니다.

예를 들어 보고용 사용자는 읽기 권한 역할의 멤버가 되고, 앱 사용자는 앱 권한 역할의 멤버가 됩니다. 이렇게 하면 여러 로그인 계정에 같은 권한 묶음을 일관되게 적용할 수 있습니다.

다만 멤버십이 있다는 것과 지금 그 권한을 실제로 사용할 수 있다는 것은 다를 수 있습니다. 그래서 `pg_has_role`에서 MEMBER와 USAGE를 구분해 확인합니다.

---

## 7. 권한은 객체 범위별로 나뉩니다

**화면 구성**

| 범위 | 대표 권한 | 의미 |
|---|---|---|
| 데이터베이스 | CONNECT | 접속 |
| 스키마 | USAGE | 객체 이름 사용 |
| 스키마 | CREATE | 객체 생성 |
| 테이블 | SELECT·INSERT·UPDATE·DELETE | 행 작업 |
| 컬럼 | UPDATE(status) | 특정 컬럼 작업 |
| 시퀀스 | USAGE | 자동 번호 사용 |

**발표 스크립트**

권한은 한 번에 모두 허용되는 것이 아닙니다. 데이터베이스 CONNECT가 있어도 테이블을 읽을 수 있는 것은 아닙니다.

스키마 USAGE가 있어야 스키마 안의 객체 이름을 사용할 수 있고, 테이블 SELECT가 있어야 행을 조회할 수 있습니다.

또 IDENTITY 자동값을 사용하려면 연결된 시퀀스 권한도 필요할 수 있습니다. 이 장의 앱 역할에는 자동 ID 생성을 위해 시퀀스 USAGE만 부여하고, 시퀀스 값을 직접 조회하는 SELECT는 기본 부여하지 않습니다.

---

## 8. 최소 권한은 작업 행렬로 설계합니다

**화면 구성**

| 작업 | 읽기 역할 | 앱 역할 |
|---|---|---|
| students SELECT | 허용 | 허용 |
| courses SELECT | 허용 | 허용 |
| enrollments SELECT | 허용 | 허용 |
| enrollments INSERT | 불허 | 허용 |
| status UPDATE | 불허 | 허용 |
| paid_amount UPDATE | 불허 | 불허 |
| DELETE | 불허 | 불허 |
| schema CREATE | 불허 | 불허 |

**발표 스크립트**

최소 권한은 “아무것도 못 하게 하는 것”이 아닙니다. 역할이 맡은 일을 하는 데 필요한 작업만 허용하는 것입니다.

읽기 역할은 조회만 할 수 있어야 합니다. 앱 역할은 수강신청을 만들고 상태를 바꿀 수 있지만, 결제 금액을 마음대로 바꾸거나 행을 삭제하면 안 됩니다.

따라서 `ALL PRIVILEGES`를 주고 시작하는 방식은 입문 실습에서도 피합니다. 먼저 작업 행렬을 만들고, 그 행렬에 맞게 GRANT합니다.

## 9. GRANT·REVOKE 후에는 유효 권한과 경로를 모두 확인합니다

**화면 구성**

```text
has_*_privilege
→ 최종적으로 가능한가?

ACL·PUBLIC·멤버십·소유권
→ 어떤 경로로 가능한가?
```

**발표 스크립트**

권한을 부여하거나 회수했다고 해서 기대 상태가 자동으로 보장되는 것은 아닙니다.

`REVOKE`는 특정 경로의 권한을 회수합니다. 하지만 다른 역할 멤버십, PUBLIC 권한, 객체 소유권 때문에 같은 작업이 여전히 가능할 수 있습니다.

그래서 유효 권한 함수로 “최종적으로 가능한가”를 확인하고, ACL과 PUBLIC 권한을 조회해 “어떤 경로로 가능한가”를 함께 봅니다.

---

## 10. 현재 객체 권한과 미래 객체 권한은 다릅니다

**화면 구성**

```text
GRANT ON TABLE
→ 지금 존재하는 테이블

ALTER DEFAULT PRIVILEGES
→ 앞으로 특정 역할이 만들 객체
```

**발표 스크립트**

현재 존재하는 테이블에 GRANT했다고 해서 앞으로 새로 생기는 테이블에도 자동으로 같은 권한이 들어가는 것은 아닙니다.

반대로 Default Privileges를 설정해도 이미 존재하는 객체 권한이 바뀌지는 않습니다.

특히 Default Privileges는 “어떤 역할이 미래 객체를 생성하는가”에 따라 달라집니다. 그래서 소유 역할과 객체 생성 역할이 누구인지 분명히 해야 합니다.

---

## 11. 권한은 실제 허용·차단 동작으로 검증합니다

**화면 구성**

```text
읽기 계정
SELECT 성공
INSERT·UPDATE·DELETE 실패

앱 계정
SELECT·INSERT·status UPDATE 성공
paid_amount UPDATE·DELETE·CREATE 실패
```

**발표 스크립트**

권한 함수 결과만 보고 끝내지 않습니다. 실제로 해당 계정으로 SQL을 실행해 허용되어야 할 작업이 성공하고, 차단되어야 할 작업이 실패하는지 확인해야 합니다.

특히 앱 계정은 테이블 전체 UPDATE 권한은 없어야 하지만, `status` 컬럼 UPDATE는 가능해야 합니다.

성공 테스트는 ROLLBACK으로 되돌려 기준 데이터를 보존하고, 실패 테스트는 한 문장씩 실행한 뒤 오류 상태를 복구합니다.

---

## 12. PUBLIC과 소유권은 조심해서 다룹니다

**화면 구성**

- PUBLIC 권한은 모든 역할에 영향을 줄 수 있음
- `REVOKE ALL FROM PUBLIC`은 의존성 확인 후
- 객체 소유자는 권한보다 강한 관리 권한을 가짐
- 역할 삭제 전 소유 객체·권한 경로 확인

**발표 스크립트**

PUBLIC은 특정 계정 하나가 아니라 모든 역할에 적용될 수 있는 경로입니다. 따라서 PUBLIC 권한을 무조건 지우거나 무조건 허용하면 다른 사용자와 애플리케이션에 영향을 줄 수 있습니다.

또 소유 역할을 삭제하려면 먼저 객체 소유권과 남은 권한을 정리해야 합니다. `DROP OWNED ... CASCADE`처럼 넓게 삭제하는 명령은 기본 정리 방법으로 사용하지 않습니다.

보안에서 중요한 습관은 “명령을 실행하기 전에 영향 범위를 확인하는 것”입니다.

## 13. 개발·테스트·운영 환경과 비밀 정보를 분리합니다

**화면 구성**

```text
.env.example → 변수 이름만
실제 .env → 저장소 밖
password file → OS 권한 제한
노출 발생 → 비밀번호·토큰 회전
```

**발표 스크립트**

실제 접속 정보는 저장소 예제에 넣지 않습니다. `.env.example`에는 변수 이름만 두고, 실제 값은 저장소 밖에서 관리합니다.

`PGPASSWORD`를 코드나 문서에 직접 남기는 방식도 피합니다. 실습에서는 libpq password file처럼 보호된 위치의 파일을 사용할 수 있습니다.

비밀 정보가 노출되면 Git에서 파일을 삭제하는 것만으로 끝나지 않습니다. 이미 복사되었을 수 있으므로 비밀번호와 토큰을 회전하고, 로그와 배포 환경까지 확인해야 합니다.

## 14. SQL Injection은 구조와 값을 분리해 막습니다

**화면 구성**

```text
위험:
SQL 문자열 + user_input

안전:
SQL 구조는 고정
값은 $1 같은 파라미터로 전달
```

**발표 스크립트**

SQL Injection은 사용자가 입력한 값이 SQL 구조를 바꾸는 문제입니다.

안전한 방향은 SQL 구조와 값을 분리하는 것입니다. 이메일 검색이라면 SQL은 `WHERE email = $1`처럼 고정하고, 실제 이메일 값은 파라미터로 전달합니다.

다만 테이블명, 컬럼명, 정렬 방향은 일반 값 파라미터로 처리하기 어렵습니다. 이런 경우에는 허용 목록에서 선택하도록 만들어야 합니다.

## 15. 로그와 백업 파일도 민감 데이터입니다

**화면 구성**

- 백업을 공개 저장소에 커밋하지 않음
- 백업 파일 암호화·접근 권한 확인
- 로그에 비밀번호·토큰·전체 접속 URL 기록 금지
- 임시 복원 DB와 임시 파일 삭제 정책 필요

**발표 스크립트**

백업 파일은 원본 데이터의 복사본입니다. 따라서 원본 데이터와 같은 수준으로 보호해야 합니다.

로그도 안전하다고 가정하면 안 됩니다. 오류 메시지나 접속 문자열에 비밀번호, 토큰, 전체 URL이 남으면 로그가 새로운 유출 경로가 됩니다.

복원 검증을 위해 만든 임시 DB와 임시 파일도 실습 후 어떻게 보관하거나 삭제할지 정해야 합니다.

## 16. 백업·복제·고가용성은 목적이 다릅니다

**화면 구성**

| 방식 | 목적 | 주의점 |
|---|---|---|
| 논리 백업 | 구조·데이터 복원 | 복원 시험 필요 |
| 물리 백업·PITR | 시점 복구 | WAL 정책 필요 |
| 복제 | 가용성·읽기 분산 | 삭제도 복제될 수 있음 |
| 스냅샷 | 시점 사본 | DB 일관성 확인 필요 |

**발표 스크립트**

복제 서버가 있다고 해서 백업이 필요 없는 것은 아닙니다. 실수로 데이터를 삭제하면 그 삭제도 복제될 수 있습니다.

스냅샷도 편리하지만 데이터베이스 관점의 일관성과 복원 가능성을 확인해야 합니다.

이 장에서는 입문 수준에서 논리 백업과 별도 데이터베이스 복원 검증에 집중합니다.

---

## 17. 백업 전에는 버전·계정·의존성을 확인합니다

**화면 구성**

```text
pg_dump --version
pg_restore --version
psql --version
SHOW server_version;

백업 계정 권한
스키마 외부 의존성
RLS 여부
```

**발표 스크립트**

백업 명령을 실행하기 전에 도구와 서버 버전을 확인합니다. 오래된 `pg_dump`로 새 서버를 백업하려 하면 문제가 생길 수 있습니다.

백업 계정도 최소 권한으로 설계합니다. `pg_dump`가 모든 테이블 읽기 권한을 자동으로 우회한다고 생각하면 안 됩니다.

특정 스키마만 백업할 때는 외부 스키마 FK, 함수, 확장, 트리거 같은 의존성이 빠지지 않는지 확인합니다.

---

## 18. 백업은 파일 생성이 아니라 파일 검증까지 포함합니다

**화면 구성**

```text
pg_dump 완료 코드 확인
파일 크기·생성 시각 기록
pg_restore --list 확인
SHA-256 해시 기록
보관 위치·접근 권한 확인
```

**발표 스크립트**

백업 명령을 실행해서 파일이 생겼다고 끝난 것이 아닙니다.

파일 크기가 비정상적으로 작지 않은지, 아카이브 목록을 열 수 있는지, 어느 DB를 언제 백업했는지 기록해야 합니다.

해시는 파일이 중간에 바뀌었는지 확인하는 근거입니다. 하지만 해시가 맞아도 복원이 된다는 뜻은 아니므로 별도 복원 시험이 필요합니다.

---

## 19. 복원 검증은 별도 DB에서 두 단계로 합니다

**화면 구성**

```text
ai_database_book_restore 생성
→ pg_restore --single-transaction
→ 06_restore_validation.sql
→ 역할·권한 재적용
→ 04·05 권한 재검증
```

**발표 스크립트**

복원 검증은 원본 DB에 덮어쓰지 않고 별도 데이터베이스에서 진행합니다.

1단계는 구조, 데이터, 제약조건, 인덱스, IDENTITY, 소유권이 복원되었는지 확인합니다. `06_restore_validation.sql`은 원본 DB에서 실행하면 안 되고 복원 DB에서만 실행해야 합니다.

2단계는 권한입니다. `--no-owner --no-privileges`로 이동성을 높였다면 역할과 권한은 복원 후 별도로 적용하고 다시 검증해야 합니다.

---

## 20. 핵심 정리: 보안은 허용·차단·복원 가능성의 검증입니다

**화면 구성**

```text
최소 권한
→ 실제 허용·차단 테스트
→ 비밀 정보 보호
→ 백업 파일 검증
→ 별도 DB 복원 검증
→ RPO·RTO와 Runbook 기록
```

**발표 스크립트**

Chapter 11의 핵심은 보안을 명령어 목록으로 보는 것이 아니라 검증 절차로 보는 것입니다.

읽기 계정은 읽기만 되고, 앱 계정은 필요한 입력과 상태 변경만 되며, 삭제와 금액 변경은 차단되어야 합니다.

백업도 파일 생성이 아니라 별도 DB 복원과 구조·데이터·권한 검증까지 끝나야 의미가 있습니다. 마지막으로 RPO, RTO, 복구 순서, 실패 원인과 수정 내용을 Runbook에 남겨야 실제 장애 상황에서 사용할 수 있습니다.
