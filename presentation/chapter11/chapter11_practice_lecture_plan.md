# Chapter 11 실습 발표 강의안

## 권한을 검증하고 백업을 복원해 확인하기

> 목적: `security_lab`에서 최소 권한을 설계·검증하고, 논리 백업 파일을 별도 DB에 복원해 구조·데이터·권한을 확인한다.  
> 기준: 초보자가 “무엇을 실행하고, 어떤 결과가 나와야 하며, 권한·복원 결과가 다르면 무엇을 확인해야 하는지” 직관적으로 이해할 수 있어야 한다.

---

## 1. 이번 실습은 허용·차단·복원을 확인합니다

**화면 구성**

- 큰 제목: 권한을 검증하고 백업을 복원해 확인하기
- 흐름: 스키마 생성 → 샘플 입력 → 권한 계획 → 권한 확인 → 동작 테스트 → 백업 → 복원 검증
- 강조 문장: 백업은 복원 검증까지 해야 완료

**발표 스크립트**

이번 실습은 데이터를 많이 조회하거나 빠르게 만드는 실습이 아닙니다. 데이터베이스를 안전하게 운영하기 위해 누가 어떤 작업을 할 수 있는지 직접 확인하고, 백업 파일이 실제로 복원되는지 검증합니다.

우리는 `security_lab` 스키마를 사용합니다. 기존 `course_project`, `transaction_lab`, `performance_lab`는 건드리지 않습니다.

오늘의 핵심은 세 가지입니다. 허용해야 할 작업은 성공해야 하고, 차단해야 할 작업은 실패해야 하며, 백업은 별도 DB에 복원되어야 합니다.

## 2. 실행 파일과 순서를 먼저 확인합니다

**화면 구성**

| 순서 | 파일 | 역할 |
|---:|---|---|
| 1 | 01_security_lab_schema.sql | 스키마·테이블 생성 |
| 2 | 02_security_lab_seed.sql | 샘플 데이터 입력 |
| 3 | 03_role_permission_plan.sql | 역할·권한 계획 선택 적용 |
| 4 | 04_permission_checks.sql | ACL·유효 권한 확인 |
| 5 | 05_permission_behavior_tests.sql | 허용·차단 동작 테스트 |
| 6 | 06_restore_validation.sql | 복원 DB 검증 |

**발표 스크립트**

파일 순서는 매우 중요합니다. 먼저 실습용 스키마와 테이블을 만들고, 샘플 데이터를 입력합니다. 그다음 역할과 권한 계획 파일에서 필요한 문장만 선택 실행합니다.

역할 생성과 삭제는 PostgreSQL 클러스터 전체에 영향을 줄 수 있으므로 자동으로 전체 실행하지 않습니다. 실습 환경에서 권한이 있는 경우에만 주석을 해제해 실행합니다.

백업과 복원은 SQL Editor가 아니라 터미널에서 `pg_dump`, `pg_restore`, `psql` 같은 도구로 진행합니다.

## 4. security_lab 스키마와 세 테이블을 생성합니다

**화면 구성**

```text
security_lab.students
security_lab.courses

```

- 체크: PK, UNIQUE, CHECK, FK, 부분 고유 인덱스

**발표 스크립트**

`01_security_lab_schema.sql`은 학생, 강의, 수강신청 테이블을 만듭니다. 구조 자체는 앞 장의 온라인 강의 도메인과 비슷하지만, 이번 장의 목적은 권한과 백업 검증입니다.

학생 이메일은 공백일 수 없고 정확히 같은 문자열은 중복될 수 없습니다. 수강신청 상태와 금액도 제약조건으로 검사합니다.

또 진행 중인 신청, 즉 `신청`과 `수강중` 상태는 같은 학생·강의 조합으로 중복되지 않도록 부분 고유 인덱스를 둡니다.

## 5. 샘플 데이터를 넣고 IDENTITY 다음 값을 확인합니다

**화면 구성**

| 테이블 | 샘플 ID | 다음 값 |
|---|---|---:|
| students | 101, 102, 103 | 104 |
| courses | 201, 202, 203 | 204 |
| enrollments | 1001, 1002, 1003 | 1004 |

**발표 스크립트**

`02_security_lab_seed.sql`은 관계를 쉽게 확인할 수 있도록 명시적 ID를 사용합니다. 학생은 101부터 103, 강의는 201부터 203, 신청은 1001부터 1003을 사용합니다.

명시적 ID를 넣으면 IDENTITY의 다음 값이 자동으로 이동한다고 생각하기 쉽지만 그렇지 않습니다. 그래서 파일 마지막에서 다음 자동값을 조정합니다.

권한 테스트에서 INSERT 후 ROLLBACK을 하더라도 시퀀스 번호는 회수되지 않을 수 있습니다. 번호가 빈다고 해서 데이터 오류는 아닙니다.

## 6. 최소 권한 작업 행렬을 작성합니다

**화면 구성**

| 작업 | 읽기 역할 | 앱 역할 |
|---|---|---|
| SELECT | 허용 | 허용 |
| INSERT enrollments | 불허 | 허용 |
| UPDATE status | 불허 | 허용 |
| UPDATE paid_amount | 불허 | 불허 |
| DELETE | 불허 | 불허 |
| CREATE schema | 불허 | 불허 |

**발표 스크립트**

권한을 주기 전에 역할별로 해야 할 일을 표로 정리합니다. 읽기 역할은 보고용이므로 조회만 허용합니다.

앱 역할은 수강신청을 추가하고 상태를 변경할 수 있어야 합니다. 하지만 결제 금액을 수정하거나 삭제할 수 있으면 위험합니다. 스키마를 만들 권한도 필요하지 않습니다.

이 표가 뒤에서 `GRANT`와 테스트의 기준이 됩니다. 설계 없이 권한을 주면 나중에 왜 허용했는지 설명하기 어렵습니다.

## 7. 역할·권한 계획 파일은 선택 실행합니다

**화면 구성**

```text
03_role_permission_plan.sql
- CREATE ROLE 예시는 주석 상태
- GRANT 예시는 필요 문장만 선택 실행
- SUPERUSER, ALL PRIVILEGES 사용 안 함
```

**발표 스크립트**

역할과 권한은 조심해서 다뤄야 합니다. 역할은 데이터베이스 안의 테이블처럼 단순히 한 스키마에만 영향을 주는 것이 아니라 PostgreSQL 클러스터 전체에 영향을 줄 수 있습니다.

따라서 `03_role_permission_plan.sql`은 기본적으로 주석 상태입니다. 실습 환경과 권한을 확인한 뒤 필요한 문장만 선택 실행합니다.

이번 실습에서는 `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `ALL PRIVILEGES` 같은 과도한 권한을 사용하지 않는 방향을 기본으로 합니다.

## 8. ACL과 유효 권한을 확인합니다

**화면 구성**

- 확인 항목
  - `has_database_privilege`
  - `has_schema_privilege`
  - `has_table_privilege`
  - `has_column_privilege`
  - `pg_indexes`, ACL, PUBLIC 권한

**발표 스크립트**

권한을 부여한 뒤에는 실제로 어떤 권한이 유효한지 확인합니다. 유효 권한 함수는 로그인 역할이 최종적으로 작업할 수 있는지 보여 줍니다.

하지만 유효 권한이 `true`라고 해서 반드시 방금 직접 `GRANT`한 권한 때문이라고 단정하면 안 됩니다. 다른 역할 멤버십, `PUBLIC`, 객체 소유권 같은 경로가 있을 수 있습니다.

그래서 ACL과 `PUBLIC` 권한도 함께 확인합니다. 특히 데이터베이스 `CONNECT`는 기본적으로 `PUBLIC`에 열려 있을 수 있습니다.

## 9. 읽기 계정의 허용·차단 동작을 테스트합니다

**화면 구성**

| 작업 | 기대 결과 |
|---|---|
| SELECT students | 성공 |
| INSERT enrollments | 실패 |
| UPDATE enrollments | 실패 |
| DELETE enrollments | 실패 |

**발표 스크립트**

읽기 계정은 조회만 해야 합니다. 따라서 `SELECT`는 성공해야 하지만, 삽입·수정·삭제는 실패해야 합니다.

이때 실패는 실습이 잘못된 것이 아닙니다. 오히려 차단해야 할 작업이 차단되었으므로 권한 설계가 맞다는 증거입니다.

실패 테스트는 한 문장씩 실행합니다. 오류가 발생한 뒤 트랜잭션 상태가 깨지면 `ROLLBACK` 또는 `ROLLBACK TO SAVEPOINT`로 복구합니다.

## 10. 앱 계정의 컬럼 단위 권한을 테스트합니다

**화면 구성**

| 작업 | 기대 결과 |
|---|---|
| SELECT | 성공 |
| ID 생략 INSERT | 성공 |
| status UPDATE | 성공 |
| paid_amount UPDATE | 실패 |
| DELETE | 실패 |
| schema CREATE | 실패 |

**발표 스크립트**

앱 계정은 읽기 계정보다 조금 더 많은 권한이 있습니다. 수강신청을 추가할 수 있고, 상태 컬럼은 수정할 수 있어야 합니다.

하지만 결제 금액인 `paid_amount`는 수정하면 안 됩니다. 그래서 테이블 전체 UPDATE 권한을 주지 않고, `status` 컬럼에 대한 UPDATE만 허용합니다.

테스트의 핵심은 “UPDATE가 된다”가 아니라 “status는 되고 paid_amount는 안 된다”입니다. 이 차이를 확인해야 컬럼 단위 권한을 이해할 수 있습니다.

## 11. 성공 테스트 후에는 ROLLBACK으로 기준 상태를 보존합니다

**화면 구성**

```text
BEGIN
→ 허용 SQL 실행
→ 결과 확인
→ ROLLBACK
→ 기준 행 수 재확인
```

**발표 스크립트**

권한 테스트 중에는 일부 SQL이 실제로 성공합니다. 예를 들어 앱 계정의 INSERT나 status UPDATE는 성공해야 합니다.

하지만 실습 기준 데이터를 계속 유지해야 하므로 성공 결과를 그대로 확정하지 않고 마지막에 `ROLLBACK`합니다.

이 방식은 “권한 동작은 확인하되, 실습 데이터는 원래 상태로 보존”하는 방법입니다. 테스트 뒤에는 행 수가 처음과 같은지 다시 확인합니다.

## 12. SQL Injection 방어 원칙을 코드 수준에서 확인합니다

**화면 구성**

```text
위험: 문자열 결합 SQL
안전: 파라미터 바인딩
추가: 컬럼명·정렬 방향은 허용 목록
```

**발표 스크립트**

SQL Injection은 권한과 함께 생각해야 합니다. 파라미터 바인딩은 사용자가 입력한 값을 SQL 구조가 아니라 값으로 처리하게 만듭니다.

하지만 컬럼명이나 정렬 방향처럼 SQL 구조에 들어가는 요소는 일반 값 파라미터로 처리하기 어렵습니다. 이때는 `name`, `joined_at`, `asc`, `desc`처럼 허용 목록을 만들어 그 안에서만 선택해야 합니다.

그리고 앱 계정에 최소 권한을 주면, 혹시 SQL Injection이 발생하더라도 피해 범위를 줄일 수 있습니다.

## 14. security_lab 백업 파일을 생성합니다

**화면 구성**

```bash
pg_dump \
  -U <backup_user> \
  -d ai_database_book \
  -Fc \
  --schema=security_lab \
  --no-owner \
  --no-privileges \
  -f <backup-dir>/security_lab.backup
```

**발표 스크립트**

이 명령은 `security_lab` 스키마를 사용자 정의 형식으로 백업합니다. `-Fc`는 `pg_restore`로 목록을 확인하고 선택 복원하기 좋은 형식입니다.

`--no-owner --no-privileges`는 다른 환경으로 옮겨 복원하기 쉽게 만듭니다. 대신 원본 소유권과 권한은 제외되므로 복원 후 역할과 권한을 별도로 적용해야 합니다.

백업 파일은 원본 데이터의 사본입니다. 저장 위치와 접근 권한을 신중하게 정해야 합니다.

## 15. 백업 파일 자체를 검증합니다

**화면 구성**

```bash
pg_restore --list <backup-dir>/security_lab.backup
```

```powershell
Get-FileHash <backup-dir>\security_lab.backup -Algorithm SHA256
```

- 체크: 종료 코드, 파일 크기, 생성 시각, 해시, 보관 위치

**발표 스크립트**

백업 파일이 생겼다고 바로 성공으로 표시하지 않습니다. 먼저 명령이 정상 종료되었는지 확인합니다. 파일 크기와 생성 시각도 기록합니다.

`pg_restore --list`로 백업 아카이브의 목록을 읽을 수 있는지 확인합니다. 그리고 SHA-256 해시를 기록해 나중에 파일이 바뀌었는지 확인할 수 있게 합니다.

하지만 해시는 복원 가능성의 증거가 아닙니다. 실제 복원 검증은 다음 단계에서 별도 DB에 수행합니다.

## 16. 원본이 아닌 별도 DB에 복원합니다

**화면 구성**

```bash
createdb \
  -U <admin_user> \
  -O <restore_user> \
  -T template0 \
  ai_database_book_restore
```

```bash
pg_restore \
  -U <restore_user> \
  -d ai_database_book_restore \
  --single-transaction \
  --no-owner \
  --no-privileges \
  <backup-dir>/security_lab.backup
```

**발표 스크립트**

복원 검증은 원본 DB에 하지 않습니다. `ai_database_book_restore`처럼 별도 검증 DB를 만들고 거기에 복원합니다.

작은 실습에서는 `--single-transaction`을 사용해 복원 중 오류가 나면 일부 객체만 남는 위험을 줄입니다.

복원 명령이 성공했더라도 아직 끝난 것이 아닙니다. 구조, 데이터, 제약조건, 소유권, 권한을 확인해야 합니다.

## 17. 복원 DB에서 구조와 데이터를 검증합니다

**화면 구성**

| 검증 항목 | 기대 결과 |
|---|---:|
| students | 3 |
| courses | 3 |
| enrollments | 3 |
| JOIN 결과 | 3 |
| 고아 FK | 0 |
| 활성 신청 중복 | 0 |
| 명시 제약조건 | 유지 |
| 부분 고유 인덱스 | 유지 |

**발표 스크립트**

복원 DB에서는 `06_restore_validation.sql`을 실행합니다. 이 파일은 원본 DB에서 잘못 실행하지 않도록 현재 데이터베이스 이름을 확인합니다.

복원 검증은 행 수만 보는 것이 아닙니다. JOIN 결과, 고아 FK, 활성 신청 중복, 명시 제약조건, 부분 고유 인덱스, IDENTITY 시퀀스를 함께 봅니다.

다음 자동값이 기존 최대 ID보다 큰지도 확인합니다. 복원 후 새 INSERT가 기존 ID와 충돌하지 않아야 하기 때문입니다.

## 18. 복원 후 역할과 권한을 다시 적용하고 확인합니다

**화면 구성**

```text
03 역할·권한 계획 검토
→ 필요한 Role·GRANT 적용
→ 04 권한 확인
→ 05 허용·차단 DML 재검증
```

**발표 스크립트**

`--no-owner --no-privileges`로 백업했다면 복원된 객체의 권한은 원본과 다를 수 있습니다. 그래서 복원 뒤에는 역할과 권한 계획을 다시 적용해야 합니다.

그다음 원본에서 했던 것처럼 읽기 계정과 앱 계정의 허용·차단 동작을 확인합니다.

복원은 데이터만 돌아오는 것이 아니라 운영에 필요한 권한 모델도 함께 재현되어야 합니다.

## 19. RPO·RTO와 복구 기록을 남깁니다

**화면 구성**

| 기록 항목 | 예 |
|---|---|
| 백업 시각·파일 경로 | 기록 |
| 파일 크기·해시 | 기록 |
| 복원 시작·완료 시각 | 기록 |
| 검증 결과 | 성공/실패 |
| RPO·RTO 충족 여부 | 기록 |
| 다음 복원 시험일 | 기록 |

**발표 스크립트**

백업과 복원은 담당자의 기억에 의존하면 안 됩니다. `BACKUP_RESTORE_RUNBOOK.md`에 실제 실행 기록을 남깁니다.

언제 어떤 계정으로 백업했는지, 파일이 어디에 있고 해시는 무엇인지, 복원에 얼마나 걸렸는지, 검증 결과는 어땠는지를 기록합니다.

RPO와 RTO도 함께 적습니다. 복구 목표를 만족하지 못했다면 백업 주기나 복원 절차를 다시 설계해야 합니다.

## 20. AI 보안·백업 명령을 검토합니다

**화면 구성**

| 검토 항목 | 확인 질문 |
|---|---|
| 권한 | 과도한 권한은 없는가 |
| 범위 | 원본 DB를 덮어쓰지 않는가 |
| 비밀 | 비밀번호가 노출되지 않는가 |
| 백업 | 목록·해시·복원 검증이 있는가 |
| 파괴 명령 | DROP·CASCADE를 검토했는가 |

**발표 스크립트**

AI가 만든 명령은 초안으로는 유용하지만 바로 실행하면 위험할 수 있습니다. 특히 보안과 백업 명령은 파괴적이거나 권한을 과도하게 줄 수 있습니다.

`ALL PRIVILEGES`, `DROP OWNED CASCADE`, 원본 DB 복원, 비밀번호가 포함된 명령은 반드시 멈추고 검토해야 합니다.

AI 결과를 승인하려면 권한 범위, 실행 대상, 백업 파일 보호, 복원 검증, 실패 시 복구 방법까지 확인해야 합니다.

## 21. 최종 점검: 보안은 실제 결과로 확인합니다

**화면 구성**

- 체크리스트
  - 기존 스키마 보호
  - 최소 권한 행렬 작성
  - 허용·차단 테스트 통과
  - 백업 파일 목록·해시 확인
  - 별도 DB 복원 성공
  - 구조·데이터·권한 검증
  - Runbook 기록

**발표 스크립트**

마지막으로 오늘 실습의 완료 기준을 확인합니다. 기존 프로젝트 데이터는 보호되어야 하고, `security_lab`만 실습 대상으로 사용해야 합니다.

읽기 계정과 앱 계정의 허용·차단 결과가 기대와 맞아야 합니다. 백업 파일은 생성뿐 아니라 목록과 해시를 확인해야 하며, 별도 DB 복원까지 성공해야 합니다.

보안과 백업은 선언이 아니라 증거입니다. 실제 허용·차단 결과와 복원 검증 결과를 기록할 수 있어야 실습이 완료됩니다.
