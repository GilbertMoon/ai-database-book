# Chapter 13 이론 발표 강의안

## AI와 실행 증거로 데이터베이스 설계 검증하기

> 목적: AI가 만든 ERD·DDL·SQL을 그대로 믿지 않고, 요구사항·메타데이터·정상값·경계값·반례·diff를 기준으로 검토하는 사고방식을 설명한다.  
> 기준: 초보자가 각 장표를 보며 “AI 결과를 왜 검증해야 하는지, 무엇을 증거로 승인해야 하는지” 직관적으로 이해할 수 있어야 한다.

---

## 1. AI가 만든 SQL은 정답이 아니라 검토 대상입니다

**화면 구성**

- 큰 제목: AI와 실행 증거로 설계 검증하기
- 흐름: 요구사항 → AI 초안 → 격리 실행 → 증거 수집 → 사람 승인
- 강조 문장: 실행 성공 ≠ 설계 검증 완료

**발표 스크립트**

이번 장에서는 AI를 사용하지 말자는 이야기를 하는 것이 아닙니다. 오히려 AI를 더 안전하게 잘 쓰기 위한 방법을 다룹니다.

AI는 요구사항을 정리하고, ERD와 DDL 초안을 만들고, 테스트 SQL까지 빠르게 제안할 수 있습니다. 하지만 AI가 만든 SQL이 실행된다는 사실만으로 업무 규칙이 맞다는 뜻은 아닙니다.

그래서 오늘의 핵심은 “AI가 만든 결과를 어떤 증거로 검토할 것인가”입니다. 요구사항, 실제 메타데이터, 정상 데이터, 실패해야 하는 반례, 파일 diff가 모두 연결되어야 승인할 수 있습니다.

---

## 2. 이 장의 전체 검토 흐름

**화면 구성**

```text
요구사항·결정 정리
→ AI 문맥 제공
→ ERD·DDL·SQL 초안
→ 격리 스키마 실행
→ 메타데이터·정합성·반례 검증
→ diff 검토
→ 승인·보류·거절
```

**발표 스크립트**

검토는 SQL 문법을 보는 일에서 끝나지 않습니다. 먼저 어떤 요구사항이 확인되었고, 어떤 정책은 아직 미확정인지 나눕니다.

그다음 AI에게 충분한 문맥을 줍니다. AI가 초안을 만들면 바로 운영 데이터에 적용하지 않고 `ai_review_lab` 같은 격리된 공간에서 실행합니다.

마지막으로 실제 생성된 테이블, 제약조건, 인덱스, 정상·오류 데이터 결과, 파일 변경 diff를 확인합니다. 여기까지 확인한 뒤에야 사람이 승인 여부를 결정합니다.

---

## 3. ChatGPT·Codex·사람의 역할을 나눕니다

**화면 구성**

| 참여자 | 잘하는 일 | 맡기면 안 되는 일 |
| --- | --- | --- |
| ChatGPT | 요구사항 정리, 대안 비교, 프롬프트 초안 | 미확정 정책 확정 |
| Codex | 파일 탐색, SQL·테스트 작성, diff 지원 | 변경 자동 승인 |
| 사람 | 요구사항 확인, 실행 결과·diff 검토 | 최종 책임 이전 |

**발표 스크립트**

ChatGPT와 Codex는 역할이 조금 다릅니다. ChatGPT는 요구사항을 구조화하거나 “어떤 점을 검토해야 하는가”를 정리하는 데 유용합니다.

Codex는 저장소 파일을 보고 실제 SQL 파일이나 테스트 파일을 고치는 데 도움이 됩니다. 하지만 둘 다 최종 승인자는 아닙니다.

정책을 사람이 확인하고, AI가 초안을 만들고, 격리 환경에서 실행하고, 증거를 수집한 뒤 사람이 승인하는 흐름을 유지해야 합니다.

---

## 4. AI에게 줄 문맥은 계약처럼 작성합니다

**화면 구성**

- 업무 목표
- 확인된 요구사항
- 결정·미확정 정책
- 현재 DB 구조와 행 수
- 수정 범위와 금지 범위
- 검증 기준과 완료 보고 형식

**발표 스크립트**

AI에게 “온라인 강의 DB 만들어 줘”라고만 말하면, AI는 부족한 부분을 스스로 추정해서 채울 수 있습니다. 이때 문제가 생깁니다.

예를 들어 삭제 정책이 미확정인데 `ON DELETE CASCADE`를 넣거나, 이메일 대소문자 정책이 결정되지 않았는데 대소문자 무시 규칙을 넣을 수 있습니다.

따라서 프롬프트에는 확인된 요구사항, 미확정 정책, 수정 가능한 파일, 절대 건드리면 안 되는 스키마와 데이터를 분명히 적어야 합니다. 실제 개인정보나 비밀번호는 넣지 않습니다.

## 5. 요구사항·결정·테스트·검증 ID를 분리합니다

**화면 구성**

```text
P13-Rxx: 확인된 요구사항
P13-Dxx: 결정·단순화·미확정 정책
P13-Txx: 테스트
P13-Vxx: 실행·검증 단계
```

**발표 스크립트**

ID를 붙이는 이유는 멋있어 보이기 위해서가 아닙니다. 나중에 “이 제약조건은 어떤 요구사항 때문에 생겼는가”를 추적하기 위해서입니다.

`P13-R01`처럼 확인된 요구사항과 `P13-D07`처럼 아직 별도 결정이 필요한 정책을 섞으면 안 됩니다.

AI가 만든 설계를 검토할 때는 각 테이블, 제약조건, 테스트가 어떤 ID와 연결되는지 확인합니다. 연결되지 않는 구현은 의심해야 합니다.

## 6. 활성 신청 중복 정책은 부분 고유 인덱스로 표현합니다

**화면 구성**

```sql
CREATE UNIQUE INDEX uq_ai_review_enrollments_active
ON ai_review_lab.enrollments (student_id, course_id)
WHERE status IN ('신청', '수강중');
```

- 전체 UNIQUE: 모든 이력 중복 차단
- 부분 UNIQUE: 진행 중 중복만 차단

**발표 스크립트**

학생과 강의 조합을 전체 `UNIQUE`로 묶으면 같은 학생이 같은 강의를 다시 신청하는 이력까지 막을 수 있습니다.

하지만 이 프로젝트의 정책은 다릅니다. `신청`이나 `수강중` 상태는 동시에 두 건 있으면 안 되지만, `완료`나 `취소` 이력 뒤 재신청은 허용합니다.

그래서 전체 고유 제약조건이 아니라 상태 조건이 붙은 부분 고유 인덱스를 사용합니다. 이 차이를 AI가 놓치기 쉽기 때문에 반드시 검토해야 합니다.

## 7. 나쁜 설계는 역할이 한 테이블에 섞여 있습니다

**화면 구성**

- 나쁜 예: `bad_enrollments`
- 문제: 학생·강의·강사·신청·결제 정보 혼합
- 위험: 반복, 자유 문자열, FK 없음, 민감정보 평문

**발표 스크립트**

나쁜 설계 예시는 일부러 여러 역할을 한 행에 섞어 둡니다. 학생 이름, 강의 제목, 강사 정보, 신청 상태, 결제 정보가 한 테이블에 들어갑니다.

처음 보기에는 편해 보일 수 있습니다. 하지만 이름이 반복되고, 상태값을 아무 문자열로나 넣을 수 있고, 존재하지 않는 강의나 학생도 막을 수 없습니다.

또 실제 카드번호 형태의 민감정보를 테스트에 넣으면 안 됩니다. 실습에서는 `TEST-SENSITIVE-PLAINTEXT-01` 같은 명확한 가상값만 사용합니다.

## 8. 좋은 설계는 역할별 테이블로 분리합니다

**화면 구성**

| 테이블 | 역할 |
| --- | --- |
| students | 학생 기본 정보 |
| instructors | 강사 기본 정보 |
| courses | 강의 현재 정보 |
| enrollments | 학생·강의 신청 사건 |
| payments | 현재 결제 상태 |

**발표 스크립트**

좋은 설계에서는 각 테이블의 한 행이 무엇을 뜻하는지가 분명해야 합니다.

학생 정보는 `students`, 강사 정보는 `instructors`, 강의의 현재 정보는 `courses`에 둡니다. 학생이 강의를 신청한 사건은 `enrollments`에 둡니다.

결제는 현재 모델에서 신청 한 건에 최대 한 건만 둡니다. 결제 시도나 부분 환불 이력을 모두 저장하려면 나중에 1:N 결제 원장 모델로 확장해야 합니다.

## 9. 타입과 제약조건은 업무 의미를 담아야 합니다

**화면 구성**

| 규칙 | 구현 | 검증 |
| --- | --- | --- |
| 이메일 중복·공백 금지 | UNIQUE + CHECK | 중복·공백 실패 |
| 허용 상태 | CHECK | 잘못된 상태 실패 |
| 금액 0 이상 | CHECK | 음수 실패·0 성공 |
| 부모 참조 | FK | 없는 ID 실패 |
| 카드번호 미저장 | 전용 컬럼 없음 | 컬럼·Seed 검토 |

**발표 스크립트**

제약조건은 단순히 오류를 내기 위한 장치가 아닙니다. 업무상 허용되는 값과 허용되지 않는 값을 데이터베이스 수준에서 표현하는 방법입니다.

예를 들어 이메일은 비어 있으면 안 되고, 정확히 같은 문자열은 중복되면 안 됩니다. 금액은 0은 가능하지만 음수는 안 됩니다.

다만 상태 `CHECK`는 상태 단어만 제한합니다. `신청 → 수강중 → 완료` 같은 전이 순서는 별도 서비스 로직이나 추가 설계가 필요합니다.

## 10. 현재 가격·합의 금액·결제 금액은 다릅니다

**화면 구성**

```text
courses.price
= 현재 기본 강의 가격

enrollments.agreed_amount
= 신청 시점에 확정된 금액

payments.amount
= 현재 결제 상태에 기록된 금액
```

**발표 스크립트**

가격 컬럼이 여러 개 나오면 초보자는 중복이라고 생각하기 쉽습니다. 하지만 시점과 의미가 다릅니다.

`courses.price`는 지금 강의의 기본 가격입니다. `enrollments.agreed_amount`는 신청 당시 학생과 서비스가 합의한 금액입니다. 할인이나 가격 변경이 있으면 두 값이 달라질 수 있습니다.

`payments.amount`는 현재 결제 상태에 기록된 금액입니다. 이번 단순 모델에서는 합의 금액과 결제 금액이 같아야 하지만, 부분 결제나 부분 환불을 지원하면 모델이 더 복잡해집니다.

## 11. paid_at과 refunded_at을 분리합니다

**화면 구성**

| 결제 상태 | paid_at | refunded_at |
| --- | --- | --- |
| 결제대기 | NULL | NULL |
| 결제실패 | NULL | NULL |
| 결제완료 | NOT NULL | NULL |
| 환불 | NOT NULL | NOT NULL, paid_at 이후 |

**발표 스크립트**

결제 시각과 환불 시각을 하나의 컬럼으로 표현하면 의미가 모호해집니다. 이 시간이 결제 완료 시간인지, 환불 완료 시간인지 알기 어렵습니다.

그래서 결제가 완료된 시각은 `paid_at`, 환불된 시각은 `refunded_at`으로 분리합니다.

이번 모델에서 환불 상태의 금액은 최초 전액 결제 금액입니다. 부분 환불 금액이나 여러 번의 환불 이력은 별도 결제·환불 원장이 필요합니다.

## 12. 실제 메타데이터로 설계를 확인합니다

**화면 구성**

- 정확한 테이블 이름 6개
- 좋은 설계 제약조건 29개
- 정확한 FK 4개
- IDENTITY id 컬럼 6개
- 활성 신청 부분 고유 인덱스

**발표 스크립트**

DDL 파일을 눈으로 보는 것만으로는 충분하지 않습니다. 실제 PostgreSQL에 어떤 테이블과 제약조건이 만들어졌는지 확인해야 합니다.

단순히 “제약조건이 29개 있다”처럼 개수만 보면 안 됩니다. 엉뚱한 제약조건이 하나 추가되고 필요한 제약조건이 하나 빠져도 개수는 같을 수 있습니다.

그래서 FK 이름, 출발 컬럼, 대상 컬럼, 삭제 정책, 부분 고유 인덱스 정의까지 구체적으로 확인합니다.

## 13. 정상 경계값과 실패 반례를 함께 봅니다

**화면 구성**

- 실패 반례: 중복 이메일, 없는 FK, 잘못된 상태, 음수 금액, 활성 중복, 결제 시각 오류
- 정상 경계값: 가격 0, 한 글자 이름, description NULL, 결제 없는 신청, 완료·취소 후 재신청

**발표 스크립트**

오류 테스트만 하면 제약조건이 잘못 강해져서 정상 데이터까지 막는 문제를 놓칠 수 있습니다.

예를 들어 가격 0은 무료 강의라면 정상이어야 합니다. 설명이 없는 강의라면 `description NULL`도 정상일 수 있습니다.

반대로 음수 금액, 없는 학생 참조, 잘못된 상태값은 실패해야 합니다. 좋은 테스트는 “성공해야 하는 것”과 “실패해야 하는 것”을 모두 확인합니다.

## 14. SQLSTATE와 제약조건 이름을 함께 기록합니다

**화면 구성**

```text
expected_sqlstate
actual_sqlstate
expected_constraint
actual_constraint
actual_table
actual_column
```

**발표 스크립트**

오류가 났다는 사실만으로는 충분하지 않습니다. 의도한 규칙 때문에 실패했는지 확인해야 합니다.

예를 들어 어떤 입력이 실패했는데, 우리가 기대한 `CHECK` 때문이 아니라 다른 `NOT NULL` 때문에 실패했을 수도 있습니다.

그래서 SQLSTATE와 실제 제약조건 이름을 함께 기록합니다. Chapter 13의 테스트는 `GET STACKED DIAGNOSTICS`로 실제 오류 정보를 모읍니다.

## 15. LEFT JOIN의 NULL을 조심합니다

**화면 구성**

위험한 조건:

```sql
p.payment_status <> '결제완료'
```

안전한 방향:

```sql
p.payment_status IS DISTINCT FROM '결제완료'
```

**발표 스크립트**

LEFT JOIN으로 결제 정보를 붙이면 결제가 없는 신청은 오른쪽 결제 컬럼이 NULL이 됩니다.

이때 `p.payment_status <> '결제완료'`라고 쓰면 NULL 비교 결과는 TRUE가 아니라 UNKNOWN입니다. 그래서 결제 누락을 발견하지 못할 수 있습니다.

필수 결제 누락까지 잡으려면 `IS DISTINCT FROM`을 사용하거나 NULL 조건을 명시적으로 포함해야 합니다.

---

## 16. diff 검토 없이는 AI 변경을 승인하지 않습니다

**화면 구성**

검토 항목:

- 요청한 파일만 바뀌었는가?
- 금지 스키마를 건드리지 않았는가?
- DROP·DELETE·ALTER가 안전한가?
- 테스트와 README가 같이 갱신되었는가?
- 실제 개인정보·비밀이 포함되지 않았는가?

**발표 스크립트**

AI가 파일을 수정했다면 결과 SQL만 보는 것이 아니라 diff를 봐야 합니다. 관련 없는 파일이 바뀌었을 수도 있고, 금지한 스키마를 건드렸을 수도 있습니다.

특히 DROP, DELETE, ALTER, GRANT, REVOKE는 위험도가 큽니다. 대상 환경, 백업, 롤백, 검증 SQL이 없으면 바로 적용하면 안 됩니다.

검토가 끝나면 다시 격리 스키마를 생성하고 01번부터 08번까지 재실행합니다.

---

## 17. 승인 상태는 명시적으로 기록합니다

**화면 구성**

| 상태 | 의미 |
| --- | --- |
| 승인 | 필수 요구사항과 증거 충족 |
| 조건부 승인 | 제한된 조건에서만 사용 가능 |
| 보류 | 정책 또는 증거 부족 |
| 거절 | 요구사항 위반·보안 위험·파괴적 변경 |

**발표 스크립트**

검토 결과를 “괜찮아 보임”처럼 적으면 나중에 근거를 찾기 어렵습니다. 승인 상태를 명확히 기록해야 합니다.

모든 필수 요구사항과 실행 증거가 있으면 승인입니다. 일부 환경에서만 쓸 수 있거나 후속 조치가 있으면 조건부 승인입니다.

정책 결정이나 테스트 증거가 부족하면 보류이고, 요구사항 위반이나 보안 위험이 크면 거절입니다. 검증하지 않은 항목은 통과로 표시하지 않습니다.

## 18. 핵심 정리

**화면 구성**

```text
AI 결과는 변경 후보입니다.
요구사항 ID와 실행 증거를 연결합니다.
정상·경계값·반례를 모두 확인합니다.
LEFT JOIN NULL과 제약조건 이름을 확인합니다.
diff와 재실행 결과를 사람이 승인합니다.
```

**발표 스크립트**

Chapter 13의 핵심은 AI를 불신하자는 것이 아니라, AI 결과를 검증 가능한 변경 후보로 다루자는 것입니다.

AI 설명이 자연스럽다고 해서 설계가 맞는 것은 아닙니다. SQL이 실행된다고 해서 업무 규칙을 만족하는 것도 아닙니다.

좋은 검토는 요구사항, 실제 메타데이터, 정상값, 경계값, 반례, 업무 정합성, diff를 연결합니다. 최종 책임은 사람이 가집니다.
