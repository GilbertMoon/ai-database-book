# Chapter 13 이론 발표 강의안

## AI와 실행 증거로 데이터베이스 설계 검증하기

> 목적: AI가 만든 ERD·DDL·SQL을 그대로 믿지 않고, 요구사항 ID, 실제 메타데이터, 정상값, 경계값, 반례, 업무 정합성, diff를 기준으로 검토하는 사고방식을 설명한다.  
> 기준: 초보자가 “AI가 실행 가능한 SQL을 만들었다”가 아니라 “요구사항과 실행 증거가 연결되어 승인할 수 있다”라고 말할 수 있어야 한다.

---

## 1. Chapter 13은 AI 결과를 검증하는 장입니다

**화면 구성**

```text
AI 초안
→ 격리 실행
→ 메타데이터 확인
→ 정상·경계·반례 테스트
→ diff 검토
→ 사람 승인
```

**발표 스크립트**

이번 장은 에이아이를 쓰지 말자는 이야기가 아닙니다. 에이아이를 더 안전하게 쓰기 위한 장입니다.

에이아이는 요구사항 정리, 이알디 초안, 디디엘, 샘플 데이터, 검증 에스큐엘을 빠르게 만들 수 있습니다. 하지만 에스큐엘이 실행된다는 사실만으로 업무 규칙이 맞다는 뜻은 아닙니다.

그래서 핵심 질문은 “에이아이가 무엇을 만들었는가”가 아니라 “그 결과를 어떤 증거로 승인할 수 있는가”입니다.

---

## 2. 실행 성공과 설계 검증은 다릅니다

**화면 구성**

```text
실행 성공
= 문법적으로 가능
= 참조 가능한 객체가 있음

설계 검증
= 요구사항 반영
= 잘못된 데이터 차단
= 정상 경계값 허용
= 업무 정합성 유지
```

**발표 스크립트**

초보자가 가장 조심해야 할 오해는 “에러 없이 실행되면 맞다”입니다.

잘못된 유니크가 있어도 에스큐엘은 실행될 수 있고, 미확정 삭제 정책을 캐스케이드로 고정해도 문법적으로는 성공할 수 있습니다.

따라서 실행 성공은 출발점일 뿐입니다. 요구사항, 제약조건, 실제 메타데이터, 테스트 결과가 모두 연결되어야 설계 검증이라고 말할 수 있습니다.

## 3. ChatGPT·Codex·사람의 역할을 구분합니다

**화면 구성**

| 참여자 | 잘하는 일 | 최종 책임이 아닌 일 |
|---|---|---|
| ChatGPT Chat | 요구사항 정리, 대안 비교, 검토 질문 | 미확정 정책 확정 |
| ChatGPT Work | 긴 다단계 검토, 자료 분석, 완성 산출물 작성 지원 | 실행 증거 없이 변경 승인 |
| Codex | 파일 탐색, SQL·테스트 작성, diff 지원 | 변경 자동 승인 |
| 사람 | 정책 확인, 실행 결과·diff 검토 | 책임을 AI에 이전 |

**발표 스크립트**

챗지피티는 요구사항을 구조화하고 검토 질문을 만드는 데 좋습니다. 코덱스는 저장소 파일을 찾고 에스큐엘과 테스트 파일을 수정하는 데 도움을 줄 수 있습니다.

하지만 업무 정책을 확정하고, 위험한 변경을 승인하고, 운영 반영을 결정하는 주체는 사람입니다. 2026년 8월 출판 검수 시점의 OpenAI 공식 안내는 Chat을 빠른 대화형 지원, Work를 더 길고 여러 단계인 작업과 완성된 산출물, Codex를 소프트웨어 개발·기술 작업에 맞춘 환경으로 설명합니다. 제공 범위는 플랜·워크스페이스·사용 화면에 따라 달라질 수 있으므로 실제 사용 시 최신 공식 안내를 다시 확인합니다.

에이아이는 초안을 만들고 실행을 도울 수 있지만, 최종 판단과 책임은 사람이 가져야 합니다.

## 4. AI에는 질문 한 줄이 아니라 문맥 묶음을 줍니다

**화면 구성**

```text
업무 목표
확인 요구사항
결정·미확정 정책
현재 DB 구조
수정 대상
수정 금지 범위
검증 기준
완료 보고 형식
```

**발표 스크립트**

에이아이에게 “DB 설계해 줘”라고만 요청하면 에이아이가 비어 있는 정책을 임의로 채울 수 있습니다.

좋은 프롬프트는 계약서처럼 작성합니다. 무엇을 저장하는지, 이미 확인된 요구사항은 무엇인지, 아직 결정하지 않은 정책은 무엇인지, 어디까지 수정해도 되는지 명확히 적습니다.

특히 실제 개인정보, 비밀번호, 접속 유알엘, 운영 데이터 샘플은 프롬프트에 넣지 않습니다.

## 5. 요구사항·결정·테스트·검증을 ID로 분리합니다

**화면 구성**

```text
P13-Rxx → 확인된 요구사항
P13-Dxx → 결정·단순화·미확정 정책
P13-Txx → 테스트
P13-Vxx → 실행·검증 단계
```

**발표 스크립트**

검토를 잘하려면 말로만 “요구사항 반영”이라고 하면 안 됩니다. 아이디를 붙여 추적해야 합니다.

P13-R은 확인된 요구사항입니다. P13-D는 이번 장에서 단순화했거나 아직 조직 정책이 필요한 항목입니다.

이렇게 나누면 에이아이가 미확정 정책을 임의로 DB 규칙으로 고정했는지 확인할 수 있습니다.

## 6. 활성 신청 중복은 전체 UNIQUE가 아닙니다

**화면 구성**

```sql
CREATE UNIQUE INDEX uq_ai_review_enrollments_active
ON ai_review_lab.enrollments (student_id, course_id)
WHERE status IN ('신청', '수강중');
```

비교:

```text
전체 UNIQUE → 완료·취소 이력 뒤 재신청까지 막을 수 있음
부분 고유 인덱스 → 활성 상태만 중복 차단
```

**발표 스크립트**

학생과 강의 조합을 무조건 유니크로 만들면 완료나 취소 이력이 있는 학생이 같은 강의를 다시 신청하지 못할 수 있습니다.

챕터 13은 챕터 07의 정책을 유지합니다. 신청 또는 수강중 상태는 중복을 막지만, 완료·취소 이력 뒤 재신청은 허용합니다.

이 차이는 초보자에게 매우 중요합니다. “중복을 막는다”가 아니라 “어떤 상태의 중복을 막는가”를 정확히 말해야 합니다.

## 7. ERD는 예쁘게 그렸는지가 아니라 요구사항 반영으로 봅니다

**화면 구성**

확인 질문:

```text
핵심 엔터티가 빠지지 않았는가?
N:M 관계가 enrollments로 해소되었는가?
강사와 강의 방향이 맞는가?
결제 관계가 현재 가정과 맞는가?
미확정 정책을 UNIQUE나 CASCADE로 고정하지 않았는가?
```

**발표 스크립트**

이알디 검토는 그림이 보기 좋은지 보는 작업이 아닙니다.

학생과 강의의 N:M 관계가 중간 테이블로 풀렸는지, 강의가 강사 한 명을 참조하는지, 결제가 신청과 어떤 관계인지 요구사항 기준으로 확인해야 합니다.

특히 결제는 현재 상태 한 건만 저장하는 단순 모델입니다. 결제 시도·실패·부분 환불 이력을 모두 저장하려면 별도 원장 모델이 필요합니다.

## 8. 나쁜 설계는 한 행에 너무 많은 역할을 섞습니다

**화면 구성**

```text
bad_enrollments
- 학생·강의·강사·신청·결제 정보 혼합
- 모든 값 TEXT
- FK 없음
- 상태값 자유 입력
- 날짜 문자열
- 민감정보 평문 예시
```

**발표 스크립트**

나쁜 설계 예시는 일부러 한 행에 너무 많은 의미를 넣습니다. 학생 정보, 강의 정보, 강사 정보, 신청 정보, 결제 정보가 섞여 있습니다.

이렇게 되면 같은 이메일과 이름이 반복되고, 부모 데이터가 실제로 존재하는지 에프케이로 확인할 수 없습니다.

에이아이가 이런 구조를 제안했다면 “테이블이 만들어졌으니 성공”이 아니라 역할 분리가 필요한 설계 문제로 봐야 합니다.

## 9. 타입과 제약조건은 업무 의미로 검토합니다

**화면 구성**

| 업무 규칙 | 설계 | 검증 |
|---|---|---|
| 존재하는 부모 참조 | FK | 없는 ID 차단 |
| 이메일 중복·공백 금지 | UNIQUE + CHECK | 중복·공백 차단 |
| 활성 신청 중복 금지 | 부분 고유 인덱스 | 활성 중복 차단 |
| 금액 0 이상 | CHECK | 음수 실패·0 성공 |
| 결제·환불 시각 | 복합 CHECK | 잘못된 조합 차단 |

**발표 스크립트**

제약조건은 단순히 문법을 붙이는 것이 아닙니다. 업무 규칙을 데이터베이스가 어디까지 막아 줄지 정하는 장치입니다.

다만 체크가 모든 업무 흐름을 보장하지는 않습니다. 예를 들어 상태값 체크는 허용 단어를 제한하지만, 상태 전이 순서 전체를 보장하지는 않습니다.

그래서 제약조건과 별도의 업무 정합성 검증이 함께 필요합니다.

## 10. 이메일 UNIQUE의 범위를 명확히 합니다

**화면 구성**

```text
현재 보장:
- NULL 불가
- 공백 문자열 불가
- 정확히 같은 문자열 중복 불가

아직 별도 정책:
- 대소문자 정규화
- 대소문자 비구분 비교
```

**발표 스크립트**

현재 설계의 이메일 유니크는 정확히 같은 문자열 중복을 막습니다.

따라서 `Kim@example.com`과 `kim@example.com`을 같은 이메일로 볼지 다른 문자열로 볼지는 별도 정책입니다.

에이아이가 이것을 마음대로 소문자 정규화하거나 대소문자 비구분 인덱스로 바꾸면 안 됩니다. 미확정 정책은 미확정으로 남겨야 합니다.

## 11. 현재 가격·신청 시점 기록 금액·결제 상태 기록 금액은 다릅니다

**화면 구성**

```text
courses.price
→ 현재 기본 강의 가격

enrollments.recorded_amount
→ 신청 시점 확정 금액

payments.amount
→ 현재 결제 상태에 기록된 금액
```

**발표 스크립트**

가격 관련 컬럼은 이름이 비슷하지만 의미가 다릅니다.

강의 현재 가격은 나중에 바뀔 수 있습니다. 하지만 신청 시점에 합의한 금액은 과거 기록입니다.

현재 가격과 신청 시점 기록 금액이 다르다고 자동 오류는 아닙니다. 할인이나 가격 변경일 수 있습니다. 반대로 이번 단순 모델에서는 신청 시점 기록 금액과 결제 금액이 맞는지 확인합니다.

## 12. 결제 시각과 환불 시각을 분리합니다

**화면 구성**

| 상태 | paid_at | refunded_at |
|---|---|---|
| 결제대기·결제실패 | NULL | NULL |
| 결제완료 | NOT NULL | NULL |
| 환불 | NOT NULL | NOT NULL, paid_at 이후 |

**발표 스크립트**

`paid_at` 하나로 결제와 환불 시점을 모두 표현하면 의미가 모호해집니다.

결제 완료 시각과 환불 완료 시각은 서로 다른 사건입니다. 그래서 `paid_at`과 `refunded_at`을 분리합니다.

다만 이 장의 환불은 전액 환불 샘플입니다. 부분 환불과 여러 번의 환불 이벤트를 다루려면 결제·환불 원장을 별도로 설계해야 합니다.

## 14. 실제 메타데이터를 정확히 확인합니다

**화면 구성**

```text
정확한 테이블 이름 6개
제약조건 29개
FK 4개
IDENTITY id 6개
활성 신청 부분 고유 인덱스
ON DELETE RESTRICT 또는 NO ACTION
```

**발표 스크립트**

테이블 개수만 맞다고 검증이 끝난 것은 아닙니다. 잘못된 테이블이 하나 있고 필요한 테이블이 하나 빠져도 개수는 같을 수 있습니다.

그래서 실제 포스트그레스큐엘 메타데이터를 봅니다. 테이블 이름, 제약조건 이름, 에프케이 출발 컬럼과 대상 컬럼, 인덱스 조건까지 확인합니다.

설계 문서가 아니라 실제 생성된 구조를 확인하는 것이 중요합니다.

## 15. 정상 경계값과 실패 반례를 함께 봅니다

**화면 구성**

```text
예상 실패 24개
+ 정상 경계값 6개
= 전체 30개
```

예:

```text
음수 금액은 실패
0원 가격은 성공
중복 활성 신청은 실패
완료·취소 이력 뒤 재신청은 성공
```

**발표 스크립트**

오류 테스트만 하면 제약조건이 너무 강해서 정상 데이터까지 막는 문제를 놓칠 수 있습니다.

그래서 실패해야 하는 반례와 성공해야 하는 경계값을 함께 테스트합니다.

특히 에스큐엘 스테이트만 보지 않고 실제 constraint name까지 기록합니다. 같은 오류 코드라도 다른 제약조건 때문에 실패했을 수 있기 때문입니다.

---

## 16. LEFT JOIN의 NULL을 놓치지 않습니다

**화면 구성**

주의:

```sql
p.payment_status <> '결제완료'
```

권장:

```sql
p.payment_status IS DISTINCT FROM '결제완료'
```

**발표 스크립트**

레프트 조인 결과에서 결제가 없으면 payment 쪽 컬럼은 널입니다.

그런데 `널 <> '결제완료'`는 TRUE가 아니라 UNKNOWN입니다. 그래서 누락 결제를 잡지 못할 수 있습니다.

필수 결제 누락까지 찾으려면 `IS 디스팅트 FROM`처럼 널까지 안전하게 비교하는 표현을 사용해야 합니다.

---

## 17. 제약조건 이후에도 업무 정합성 조회가 필요합니다

**화면 구성**

0행이어야 하는 항목:

```text
이메일 중복
필수 문자열 공백
신청 시점 기록 금액·결제 상태 기록 금액 불일치
고아 관계
활성 신청 중복
상태·결제 조합 위반
```

정보용:

```text
현재 가격·신청 시점 기록 금액 차이 = 1행
```

**발표 스크립트**

제약조건이 있어도 업무 정합성 조회가 필요합니다. 여러 테이블을 함께 봐야 발견되는 문제가 있기 때문입니다.

예를 들어 신청 상태와 결제 상태의 조합은 한 테이블의 체크만으로 충분하지 않을 수 있습니다.

또 현재 가격과 신청 시점 기록 금액 차이는 정보용입니다. 이것을 무조건 오류로 처리하면 할인이나 가격 변경을 잘못 판단할 수 있습니다.

## 18. 민감정보 미저장은 여러 증거로 확인합니다

**화면 구성**

```text
카드번호·CVV 전용 컬럼 없음
payment_reference는 실습용 가상 외부 참조값
실제 보호 수준은 조직 정책으로 판단
Seed는 PAY-REVIEW-TEST-* 가상값
프롬프트·로그에 실제 민감값 없음
애플리케이션 흐름에서 카드정보 미전달
```

**발표 스크립트**

컬럼 이름에 `card`가 없다고 해서 실제 카드번호를 저장하지 않는다고 완전히 증명할 수는 없습니다.

민감값은 `memo`, `value`, `reference` 같은 일반 컬럼에 들어갈 수도 있습니다.

따라서 컬럼명, Seed 데이터, 로그, 프롬프트, 애플리케이션 흐름을 함께 봐야 합니다. 보안 요구사항은 하나의 증거로 끝내지 않습니다.

## 19. AI가 만든 diff와 파괴적 SQL을 별도로 검토합니다

**화면 구성**

위험 신호:

```text
DROP / TRUNCATE
조건 없는 UPDATE·DELETE
ALTER COLUMN TYPE
SET NOT NULL
UNIQUE 추가
ON DELETE CASCADE
권한 GRANT·REVOKE
```

**발표 스크립트**

에이아이가 파일을 수정했다면 최종 결과만 보지 말고 디프를 봐야 합니다.

요청한 파일만 바뀌었는지, `ai_review_lab` 외 스키마가 변경되지 않았는지, 실제 개인정보나 비밀이 들어가지 않았는지 확인합니다.

특히 파괴적 에스큐엘은 별도 검토가 필요합니다. 기존 데이터 통과 여부, 잠금, 백업, 롤백, 변경 전후 검증이 있어야 합니다.

## 20. 핵심 정리: AI 결과는 증거로 승인합니다

**화면 구성**

```text
AI 결과는 변경 후보입니다.
요구사항 ID와 연결합니다.
격리 스키마에서 실행합니다.
메타데이터와 테스트 결과를 확인합니다.
정상·경계·반례를 함께 봅니다.
diff와 파괴적 변경을 검토합니다.
사람이 승인 상태를 기록합니다.
```

**발표 스크립트**

챕터 13의 핵심은 에이아이를 믿느냐 믿지 않느냐가 아닙니다.

에이아이 결과를 요구사항과 실행 증거로 검증할 수 있느냐가 핵심입니다.

검증하지 않은 항목은 통과로 표시하지 않습니다. 승인, 조건부 승인, 보류, 거절을 명확히 기록해야 안전한 에이아이 기반 데이터베이스 설계 검토가 됩니다.
