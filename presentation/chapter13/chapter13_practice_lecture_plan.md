# Chapter 13 실습 발표 강의안

## AI 설계를 격리 스키마에서 실행 증거로 검증하기

> 목적: `ai_review_lab`에서 나쁜 설계와 좋은 설계를 비교하고, 메타데이터·업무 정합성·반례·최종 자동 검증 결과를 기록한다.  
> 기준: 초보자가 “무엇을 실행하고, 어떤 결과가 나와야 하며, AI 결과를 승인하려면 어떤 증거가 필요한지” 직관적으로 이해할 수 있어야 한다.

---

## 1. 이번 실습은 AI 설계를 바로 믿지 않는 연습입니다

**화면 구성**

- 큰 제목: AI 설계를 실행 증거로 검증합니다
- 흐름: 격리 스키마 → 나쁜 설계 → 좋은 설계 → 메타데이터 → 반례 → 최종 판정
- 강조 문장: 실행 성공보다 검증 증거가 중요합니다

**발표 스크립트**

이번 실습은 AI가 만든 데이터베이스 설계를 어떻게 검토할지 연습합니다. 목표는 SQL을 많이 실행하는 것이 아니라, 실행 결과를 근거로 설계를 승인할 수 있는지 판단하는 것입니다.

실습은 `ai_review_lab`이라는 별도 스키마에서 진행합니다. 앞 장의 `course_project`, `transaction_lab`, `performance_lab`, `security_lab`, `nosql_lab`은 변경하지 않습니다.

우리는 나쁜 설계와 좋은 설계를 비교하고, 실제 PostgreSQL 메타데이터와 테스트 결과를 워크북에 기록합니다.

## 7. 전체 UNIQUE와 부분 고유 인덱스를 비교합니다

**화면 구성**

```sql
CREATE UNIQUE INDEX uq_ai_review_enrollments_active
ON ai_review_lab.enrollments (student_id, course_id)
WHERE status IN ('신청', '수강중');
```

| 비교 | 전체 UNIQUE | 부분 고유 인덱스 |
| --- | --- | --- |
| 활성 중복 | 차단 | 차단 |
| 완료·취소 이력 | 차단 가능 | 허용 |
| 재신청 | 어려움 | 가능 |

**발표 스크립트**

이 장에서 반드시 확인해야 할 핵심 정책입니다. 전체 `UNIQUE(student_id, course_id)`를 만들면 모든 이력에서 같은 학생·강의 조합을 한 번만 허용합니다.

하지만 우리 정책은 신청·수강중 중복만 막고, 완료나 취소 이력 뒤의 재신청은 허용합니다.

따라서 부분 고유 인덱스가 맞습니다. AI가 전체 UNIQUE를 제안했다면 요구사항 위반으로 기록해야 합니다.

## 8. 기준 데이터와 IDENTITY 값을 확인합니다

**화면 구성**

| 항목 | 기대 행 수 | 다음 자동값 |
| --- | ---: | ---: |
| bad_enrollments | 3 | 4 이상 |
| students | 3 | 104 이상 |
| instructors | 2 | 203 이상 |
| courses | 3 | 304 이상 |
| enrollments | 4 | 1005 이상 |
| payments | 4 | 9005 이상 |

**발표 스크립트**

04번 Seed 파일은 관계를 재현하기 쉽게 명시적 ID를 사용합니다. 명시적 ID를 넣으면 결과를 설명하기 쉽지만 주의할 점이 있습니다.

PostgreSQL의 IDENTITY 내부 다음 값은 명시적 ID 입력만으로 자동 조정되지 않습니다. 그래서 Seed 파일은 `RESTART WITH`로 다음 자동값을 맞춥니다.

자동 번호에 빈틈이 생기는 것은 정합성 오류가 아닙니다. 중요한 것은 FK 관계와 기대 행 수가 맞는지입니다.

## 9. 실제 메타데이터 검증을 실행합니다

**화면 구성**

- 실행 파일: `05_metadata_validation.sql`
- 기대: 정확한 테이블 6개, 제약조건 29개, FK 4개, IDENTITY 6개, 부분 고유 인덱스

**발표 스크립트**

05번 파일은 우리가 의도한 구조가 실제로 만들어졌는지 확인합니다. 단순히 SQL 파일을 봤다고 끝내지 않습니다.

PostgreSQL 시스템 카탈로그와 information schema를 통해 실제 테이블, 제약조건, FK, IDENTITY, 인덱스를 확인합니다.

검증 SQL이 예외를 발생시키면 다음 단계로 넘어가지 않습니다. 구조가 틀린 상태에서 업무 검증이나 반례 테스트를 해도 의미가 약해집니다.

## 10. 업무 정합성 검증을 실행합니다

**화면 구성**

- 실행 파일: `06_business_validation.sql`
- 확인: JOIN 결과, 금액 일치, 결제 상태, LEFT JOIN NULL, 민감정보 부재

**발표 스크립트**

업무 정합성 검증은 테이블이 잘 만들어졌는지보다 한 단계 더 나아갑니다. 여러 테이블을 JOIN했을 때 업무적으로 모순이 없는지 확인합니다.

예를 들어 완료된 신청에는 결제완료가 있어야 하고, 합의 금액과 결제 금액이 일치해야 합니다.

또 결제 누락을 찾을 때 LEFT JOIN의 NULL을 놓치면 안 됩니다. `IS DISTINCT FROM` 같은 NULL 안전 비교가 필요한 이유를 여기서 확인합니다.

## 11. 정상 경계값과 실패 반례를 실행합니다

**화면 구성**

- 실행 파일: `07_negative_tests.sql`
- 실패 반례 22개
- 정상 경계값 5개
- 기대: 전체 27, 통과 27, unexpected 0

**발표 스크립트**

07번 파일은 이름은 negative tests이지만 실패 반례만 보는 것이 아닙니다. 정상 경계값도 함께 확인합니다.

실패해야 하는 예에는 중복 이메일, 없는 FK, 잘못된 상태, 음수 금액, 결제 시각 조합 오류 등이 있습니다.

성공해야 하는 예에는 가격 0, 한 글자 이름, `description NULL`, 결제 없는 신청, 완료·취소 이력 뒤 재신청이 있습니다. 둘 다 통과해야 제약조건이 적절하다고 볼 수 있습니다.

같은 SQLSTATE라도 다른 제약조건에서 발생했을 수 있습니다. 예를 들어 중복 오류는 맞지만 엉뚱한 UNIQUE가 막았을 수도 있습니다.

워크북에는 실제 SQLSTATE와 실제 제약조건 이름을 함께 기록합니다.

하지만 통과 메시지만 보고 끝내지 않습니다. 워크북과 보고서에 어떤 요구사항이 어떤 증거로 확인되었는지 기록해야 합니다.

## 14. diff와 금지 범위를 검토합니다

**화면 구성**

검토 질문:

```text
요청한 파일만 변경되었는가?
ai_review_lab 외 스키마를 건드리지 않았는가?
DROP·DELETE·ALTER가 안전한가?
비밀·개인정보가 들어가지 않았는가?
테스트와 문서가 코드와 일치하는가?
```

**발표 스크립트**

AI나 Codex가 저장소 파일을 수정했다면 SQL 실행 결과만 보지 말고 diff를 확인해야 합니다.

관련 없는 파일이 바뀌었거나, 금지한 스키마를 수정했거나, DROP·DELETE 같은 위험한 변경이 들어갈 수 있습니다.

diff 검토 후에는 관련 없는 변경을 제거하고, 다시 01번부터 08번까지 재실행해 같은 결과가 나오는지 확인합니다.

## 15. 검토 보고서에 승인 상태를 남깁니다

**화면 구성**

| 상태 | 사용 조건 |
| --- | --- |
| 승인 | 필수 요구사항·검증 증거 충족 |
| 조건부 승인 | 제한 조건과 후속 조치 있음 |
| 보류 | 정책 또는 실행 증거 부족 |
| 거절 | 요구사항 위반·보안 위험 |

**발표 스크립트**

실습의 마지막은 SQL 실행이 아니라 보고서 작성입니다. AI 결과를 승인할지, 조건부 승인할지, 보류할지, 거절할지 명시해야 합니다.

검증하지 않은 항목은 절대 통과로 표시하지 않습니다. 실행하지 못한 테스트가 있다면 미실행 항목으로 남깁니다.

보고서에는 변경 파일, 변경 이유, 실행 결과, 남은 가정, 후속 조치를 적습니다.

## 16. 최종 점검

**화면 구성**

체크리스트:

- 보호 범위 확인

- 반례·경계값 통과
- diff 검토
- 승인 상태 기록

**발표 스크립트**

이번 실습을 마치면 여러분은 AI가 만든 데이터베이스 설계를 무조건 믿지 않고, 증거로 검토하는 흐름을 설명할 수 있어야 합니다.

중요한 것은 AI를 쓰느냐 마느냐가 아닙니다. AI 결과를 요구사항과 실행 증거에 연결할 수 있느냐입니다.

최종적으로 “이 설계는 어떤 요구사항을 만족했고, 어떤 증거로 확인했으며, 어떤 가정이 남아 있는가”를 말할 수 있으면 Chapter 13의 목표를 달성한 것입니다.
