# Chapter 14 이론 발표 강의안

## SQL 데이터 분석과 Python 확장

> 목적: SQL과 Python을 경쟁 도구가 아니라 같은 분석 질문을 검증하는 협업 도구로 이해시키고, 분석 결과를 질문·기간·행 단위·검산으로 확인하는 사고방식을 설명한다.  
> 기준: 초보자가 각 장표를 보며 “무엇을 분석하는지, 어떤 기간과 단위로 세는지, 왜 SQL과 Python 결과를 대조해야 하는지” 직관적으로 이해할 수 있어야 한다.

---

## 1. 분석은 코드가 아니라 질문에서 시작합니다

**화면 구성**

- 큰 제목: SQL 데이터 분석과 Python 확장
- 흐름: 질문 정의 → SQL 집계 → VIEW → Python 확장 → 교차 검증 → 해석
- 강조 문장: 그래프보다 먼저 질문과 기준을 정합니다

**발표 스크립트**

이번 장은 데이터베이스에 저장된 데이터를 분석하는 방법을 다룹니다. 하지만 시작점은 SQL 문법이나 Python 코드가 아닙니다. 먼저 어떤 질문에 답하려는지 정해야 합니다.

예를 들어 “월별 신청이 늘었는가?”라고 묻는다면, 신청일 기준인지 결제일 기준인지, 신청 한 건을 셀 것인지 학생 수를 셀 것인지, 취소를 포함할 것인지 먼저 정해야 합니다.

이 기준이 정해지지 않으면 SQL도 실행되고 그래프도 그려지지만, 결과가 무엇을 의미하는지 설명할 수 없습니다.

## 2. 이 장의 분석 흐름을 한눈에 봅니다

**화면 구성**

```text
분석 질문 정의
→ 기간·행 단위·지표 의미 확정
→ SQL 필터·JOIN·집계
→ 데이터 품질 확인
→ 분석 VIEW 생성
→ Python 가공·시각화
→ SQL·pandas 교차 검증
→ 관찰·해석·한계 기록
```

**발표 스크립트**

분석은 한 번에 끝나는 작업이 아닙니다. 먼저 질문을 정의하고, SQL로 필요한 데이터 범위와 관계를 확정합니다.

그다음 데이터 품질을 확인하고, 분석용 VIEW를 만듭니다. 이 VIEW는 Python이 사용할 기준 데이터셋입니다.

마지막에는 pandas 결과를 SQL 기준 결과와 비교합니다. Python 코드가 실행되었다고 맞는 것이 아니라, 같은 데이터에서 같은 결과가 나오는지 확인해야 합니다.

## 3. SQL과 Python의 역할은 다릅니다

**화면 구성**

- 좌측: SQL 역할
  - 필터
  - JOIN
  - 집계
  - 기준값 계산
- 우측: Python 역할
  - 피벗
  - 시각화
  - 추가 분석
  - 결과 비교

**발표 스크립트**

SQL과 Python은 어느 하나만 쓰는 관계가 아닙니다. SQL은 데이터가 저장된 곳에서 필요한 행과 열을 줄이고, 기본키와 외래키 관계를 따라 JOIN하고, 큰 집계를 처리하는 데 강합니다.

Python은 SQL이 만든 분석 데이터셋을 받아 피벗하거나 그래프로 표현하고, 추가 검증을 자동화하는 데 좋습니다.

중요한 것은 원본 테이블 전체를 Python으로 가져와서 관계와 필터를 다시 구현하지 않는 것입니다. 데이터베이스가 잘하는 일은 SQL에서 처리하고, Python은 그 결과를 확장하는 방식이 안전합니다.

## 4. 분석 질문에는 기준이 필요합니다

**화면 구성**

| 항목 | 예시 |
| --- | --- |
| 분석 대상 | 학생, 강의, 신청 |
| 분석 기간 | 2026년 1월~6월 |

이 장에서는 2026년 1월 1일부터 7월 1일 전까지의 신청을 분석합니다. 날짜 기준은 신청일인 `enrolled_at`이고, 한 행은 수강신청 1건입니다.

이 기준을 먼저 정해 두어야 상태별 집계, 월별 집계, 강의별 집계가 모두 같은 의미를 가질 수 있습니다.

## 5. 반개방 날짜 구간을 사용합니다

**화면 구성**

```sql
WHERE enrolled_at >= DATE '2026-01-01'
  AND enrolled_at <  DATE '2026-07-01'
```

- 시작일 포함
- 종료일 제외
- 날짜·시간 경계가 명확함

**발표 스크립트**

분석 기간은 `[2026-01-01, 2026-07-01)`로 표현합니다. 시작일은 포함하고 종료일은 제외하는 방식입니다.

이 방식은 날짜 컬럼이 나중에 시간까지 포함하는 자료형으로 바뀌어도 안전합니다. `6월 30일 23시 59분 59초` 같은 경계값을 억지로 만들 필요가 없습니다.

Seed 데이터가 1월부터 6월까지만 있다고 해서 기간 조건을 생략하면 안 됩니다. 나중에 7월 데이터가 추가되면 같은 SQL의 의미가 달라지기 때문입니다.

## 9. 분석 전 데이터 품질을 확인합니다

**화면 구성**

- PK 중복 0
- 고아 FK 0
- 완료 상태와 완료일 일치
- 완료일 ≥ 신청일
- 신청일 ≥ 가입일·개설일
- 음수 금액 0

**발표 스크립트**

예를 들어 완료일이 신청일보다 빠르면 완료 기간 평균은 의미가 없습니다. 신청일이 학생 가입일보다 빠른 것도 업무적으로 이상합니다.

NULL도 무조건 오류는 아닙니다. 신청이나 수강중 상태에서는 완료일이 NULL인 것이 정상입니다. 상태와 함께 해석해야 합니다.

결과의 한 행이 무엇인지 정한 뒤 `GROUP BY`와 집계 함수를 선택합니다. 마지막에는 합계가 기준값과 맞는지 확인합니다.

이 순서를 따르면 “SQL은 돌아가는데 뭘 센 건지 모르는” 상황을 줄일 수 있습니다.

## 11. COUNT 함수는 세는 대상이 다릅니다

**화면 구성**

```text
COUNT(*)
→ 결과 행 자체를 셈

COUNT(e.id)
→ 실제 신청 행을 셈

COUNT(DISTINCT s.id)
→ 고유 학생 수를 셈
```

**발표 스크립트**

`COUNT`는 모두 같은 함수처럼 보이지만 의미가 다릅니다. `COUNT(*)`는 결과 행 자체를 셉니다.

`LEFT JOIN`에서는 신청이 없는 강의도 강의 행이 남기 때문에 `COUNT(*)`를 쓰면 1건처럼 보일 수 있습니다. 실제 신청 수를 세려면 `COUNT(e.id)`처럼 자식 테이블의 PK를 세는 것이 안전합니다.

학생 수처럼 중복을 제거해야 하는 경우에는 `COUNT(DISTINCT s.id)`를 사용합니다.

## 12. 월별 분석에는 date spine이 필요합니다

**화면 구성**

```text
월 기준표 생성
→ 실제 월별 집계와 LEFT JOIN
→ 데이터 없는 월도 0건으로 유지
```

**발표 스크립트**

월별 분석에서 실제 데이터만 `GROUP BY`하면 데이터가 없는 월은 결과에서 사라집니다.

예를 들어 4월 데이터가 없으면 5월의 이전 행이 3월처럼 보일 수 있습니다. 그러면 전월 대비 분석이 잘못됩니다.

그래서 먼저 1월부터 6월까지의 월 기준표, 즉 date spine을 만들고 실제 집계를 붙입니다. 이렇게 하면 데이터가 없는 월도 0건으로 유지됩니다.


**발표 스크립트**

Python에서 PostgreSQL에 연결할 때 전체 접속 URL과 비밀번호를 코드에 적지 않습니다. libpq 환경 변수와 password file을 사용합니다.

연결 후에는 올바른 데이터베이스인지, 분석 VIEW가 존재하는지, 트랜잭션이 읽기 전용인지 확인합니다.

분석 코드는 조회용이어야 합니다. 실수로 원본 데이터를 변경하지 않도록 연결 단계에서부터 방어합니다.

---

## 18. Python 검증은 오류를 숨기면 안 됩니다

**화면 구성**

```python
pd.to_numeric(
    df["completion_days"],
    errors="raise",
)
```

- 정확한 17개 컬럼
- 행 수 24
- 중복 enrollment_id 0
- 날짜·숫자·boolean strict 변환

**발표 스크립트**

Python에서 흔히 하는 실수는 변환 오류를 조용히 NULL로 바꾸는 것입니다. `errors="coerce"`를 쓰면 잘못된 문자열이 NaN으로 바뀌어 원인을 숨길 수 있습니다.

이 장에서는 `errors="raise"`를 사용해 잘못된 값이 있으면 바로 중단합니다.

또한 정확한 컬럼 17개, 행 수 24, 중복 없는 `enrollment_id`, 상태와 완료 여부의 일치까지 공통 검증 함수로 확인합니다.

## 19. 시각화는 검증 뒤에 수행합니다

**화면 구성**

- 제목과 축 단위
- 월 정렬
- 데이터 점 6개
- Y축 0 시작
- SQL·pandas 합계 일치

**발표 스크립트**

그래프는 분석을 보기 쉽게 해 주지만, 분석의 증거를 대신하지 않습니다.

먼저 SQL과 pandas 결과가 맞는지 검증하고, 그다음 시각화합니다. 월 순서가 맞는지, 데이터 점이 6개인지, Y축이 0부터 시작하는지 확인합니다.

특히 작은 차이를 과장하는 그래프는 해석을 왜곡할 수 있습니다.

## 20. SQL 결과와 pandas 결과를 직접 대조합니다

**화면 구성**

```text
실제 SQL 상태별 집계
↔ pandas 상태별 집계

실제 SQL 월별 집계
↔ pandas 월별 집계

실제 SQL 완료 기간
↔ pandas 완료 기간
```

**발표 스크립트**

Python 코드에 기대값을 하드코딩해서 비교하는 것은 회귀 검증에는 도움이 되지만, 실제 SQL과 pandas의 교차 검증이라고 보기는 어렵습니다.

PostgreSQL 경로에서는 같은 읽기 전용 스냅샷에서 분석 데이터셋과 SQL 집계를 함께 읽습니다. 그리고 pandas가 같은 데이터셋으로 만든 결과와 비교합니다.

결과가 다르면 기대값을 실제값으로 바꿔서 통과시키면 안 됩니다. 기간, JOIN, NULL, date spine, 자료형을 차례로 확인해야 합니다.

## 21. 관찰·해석·한계를 분리합니다

**화면 구성**

```text
관찰: 3월 신청 건수 5건
해석: 기준 데이터에서 3월 활동이 가장 많음
한계: 실제 서비스 성장 추세로 일반화 불가
```

**발표 스크립트**

분석 결과를 쓸 때는 관찰, 해석, 한계를 분리해야 합니다.

관찰은 데이터에서 직접 확인한 사실입니다. 해석은 그 사실을 바탕으로 조심스럽게 말할 수 있는 설명입니다. 한계는 말할 수 없는 범위입니다.

이 장의 데이터는 학습용 기준 데이터입니다. 실제 서비스 성장 추세로 일반화하거나, 기록 금액을 실제 매출이라고 해석해서는 안 됩니다.

## 22. AI가 만든 분석 코드도 검토해야 합니다

**화면 구성**

- 기간 조건이 있는가?
- JOIN 경로가 맞는가?
- `COUNT` 대상이 맞는가?
- 없는 월을 유지하는가?
- `recorded_amount`를 매출로 부르지 않는가?
- Python이 오류를 숨기지 않는가?
- 실제 SQL과 pandas를 비교하는가?

**발표 스크립트**

AI가 분석 SQL이나 Python 코드를 만들어 주면 편리합니다. 하지만 분석 기준을 잘못 이해하면 실행되는 코드라도 틀린 결론을 만들 수 있습니다.

특히 기간 조건 누락, `COUNT(*)` 오용, 학생 수와 신청 수 혼동, 데이터 없는 월 누락, 기록 금액을 매출로 표현하는 오류를 주의해야 합니다.

AI 코드는 초안입니다. 질문, 기간, 행 단위, 지표 의미, 교차 검증 결과를 사람이 확인해야 승인할 수 있습니다.
