## 1. Chapter 14는 분석 결과를 믿을 수 있게 만드는 장입니다

**화면 구성**

```text
분석 질문
→ 기간·행 단위·지표 의미
→ SQL 필터·JOIN·집계
→ 분석 VIEW
→ Python 확장
→ SQL·pandas 교차 검증
→ 관찰·해석·한계
```

**발표 스크립트**

분석 결과가 신뢰되려면 먼저 질문이 명확해야 합니다. 어떤 기간을 볼 것인지, 한 행을 무엇으로 볼 것인지, 금액이 실제 매출인지 기록 금액인지 정해야 합니다.

그다음 에스큐엘로 분석 경계를 만들고 파이썬으로 확장합니다. 마지막에는 에스큐엘 결과와 판다스 결과가 같은지 확인해야 합니다.

## 2. SQL과 Python은 역할이 다릅니다

**화면 구성**

| SQL | Python |
|---|---|
| 필요한 행·열 필터 | 피벗·재구조화 |
| PK·FK JOIN | 시각화 |
| 대규모 집계 | 추가 분석 |
| 기준 VIEW 생성 | SQL 결과와 비교 |

**발표 스크립트**

에스큐엘과 파이썬은 어느 하나만 선택하는 관계가 아닙니다.

에스큐엘은 데이터가 저장된 곳에서 필요한 범위를 줄이고, 관계를 따라 조인하고, 기준 집계를 만드는 데 강합니다.

파이썬은 에스큐엘이 만든 분석 데이터셋을 받아 피벗, 시각화, 추가 검증을 수행하는 데 적합합니다. 원본 테이블 전체를 파이썬으로 가져와 관계와 필터를 다시 구현하면 오류 가능성이 커집니다.

## 3. 분석 질문에는 기준이 필요합니다

**화면 구성**

질문 예시:

```text
상태별 신청 건수는?
월별 신청 수와 기록 금액은?
강의별 신청 건수는?
지역별 학생 수와 신청 수는?
완료된 신청의 완료 기간은?
```

필수 기준:

```text
분석 대상 / 기간 / 날짜 기준 / 행 단위 / 비교 기준 / 지표 의미
```

**발표 스크립트**

“월별 신청이 늘었는가?”라는 질문은 쉬워 보이지만 기준이 필요합니다.

신청일 기준인지 결제일 기준인지, 신청 건수를 볼 것인지 학생 수를 볼 것인지, 취소를 포함할 것인지 정해야 합니다.

이 기준이 없으면 에스큐엘도 실행되고 그래프도 나오지만, 결과가 무엇을 의미하는지 설명할 수 없습니다.

## 4. 분석 기간은 반개방 구간으로 고정합니다

**화면 구성**

```sql
WHERE enrolled_at >= DATE '2026-01-01'
  AND enrolled_at <  DATE '2026-07-01'
```

```text
[2026-01-01, 2026-07-01)
시작 포함, 끝 제외
```

**발표 스크립트**

챕터 14의 분석 기간은 2026년 1월 1일부터 7월 1일 전까지입니다.

이렇게 시작은 포함하고 끝은 제외하는 방식을 반개방 구간이라고 합니다. 날짜뿐 아니라 시간이 포함된 데이터로 확장해도 경계가 명확합니다.

Seed 데이터가 현재 1월부터 6월까지만 있어도 기간 조건은 생략하지 않습니다. 나중에 7월 데이터가 추가되면 결과가 달라질 수 있기 때문입니다.

## 5. `recorded_amount`는 실제 매출이 아니라 기록 금액입니다

**화면 구성**

```text
recorded_amount
→ 신청 시점 기록 금액
→ 결제 성공 여부 아님
→ 환불 완료 여부 아님
→ 회계 매출 아님
```

분석 별칭:

```sql
SUM(recorded_amount) AS recorded_amount_sum
```

**발표 스크립트**

이 장의 `recorded_amount`라는 컬럼 이름은 초보자에게 오해를 줄 수 있습니다.

여기서는 실제 결제 완료 매출이 아니라 신청 당시 기록된 금액으로 해석합니다. 신청이나 수강중 상태에도 양수 금액이 있을 수 있고, 취소는 기준 데이터에서 0으로 기록됩니다.

그래서 에스큐엘과 파이썬에서는 `recorded_amount`라는 이름을 사용합니다. 실제 매출 분석은 별도의 결제·환불 모델이 필요합니다.

## 9. JOIN과 집계는 한 행의 단위에서 시작합니다

**화면 구성**

먼저 한 행의 단위를 정하고 그 단위에 맞게 조인과 그룹 바이를 구성해야 합니다.

## 10. `COUNT(*)`, `COUNT(e.id)`, `COUNT(DISTINCT s.id)`는 다릅니다

**화면 구성**

| 함수 | 세는 대상 | 주의점 |
|---|---|---|
| `COUNT(*)` | JOIN 결과 행 | LEFT JOIN에서 부모만 있어도 1 |
| `COUNT(e.id)` | 실제 신청 행 | 자식 행 수 계산 |
| `COUNT(DISTINCT s.id)` | 고유 학생 | 반복 학생 중복 제거 |

**발표 스크립트**

초보자가 가장 많이 헷갈리는 부분이 `카운트`입니다.

`카운트 별표`는 결과 행을 셉니다. 강의는 있는데 신청이 없는 경우에도 레프트 조인 결과에는 강의 행이 남을 수 있습니다.

신청 수를 세려면 신청 테이블의 피케이인 `e.id`를 세고, 학생 수를 세려면 `카운트(디스팅트 s.id)`처럼 중복을 제거해야 합니다.

## 11. date spine은 데이터가 없는 월도 유지합니다

**화면 구성**

```text
월 기준표 생성
→ 실제 월별 집계와 LEFT JOIN
→ 없는 월은 0건으로 유지
```

```sql
COALESCE(a.enrollment_count, 0)
```

**발표 스크립트**

월별 분석에서 데이터가 없는 월을 결과에서 없애면 문제가 생깁니다.

예를 들어 4월 데이터가 없을 때 단순 그룹 바이는 4월 행을 만들지 않습니다. 그러면 5월의 이전 행이 3월처럼 보일 수 있습니다.

그래서 먼저 1월부터 6월까지 월 기준표를 만들고 실제 집계를 붙입니다. 이렇게 해야 0건인 월도 분석에 남습니다.

## 12. 현재 완료 상태 비중과 완료율은 다릅니다

**화면 구성**

| 지표 | 의미 |
|---|---|
| 현재 완료 상태 비중 | 전체 신청 중 현재 `완료` 상태의 비율 |
| 완료율 | 충분한 시간이 지난 코호트 기준 완료 비율 |

**발표 스크립트**

현재 완료 상태 비중은 전체 24건 중 완료 상태가 몇 건인지 보는 단순 비중입니다.

하지만 이것을 완료율이라고 부르면 위험합니다. 최근 신청이나 아직 수강중인 행은 완료할 시간이 충분하지 않았을 수 있습니다.

완료율을 말하려면 어떤 코호트를 볼지, 취소를 분모에 포함할지, 관찰 기간을 어떻게 정할지 별도로 정의해야 합니다.

## 13. 완료 기간은 완료된 신청에만 적용됩니다

**화면 구성**

```text
완료 12건
평균 25일
최소 18일
최대 36일
```

주의:

```text
완료된 신청만의 완료 기간
전체 수강생 평균으로 일반화 금지
```

**발표 스크립트**

완료 기간 분석은 `status = '완료'`인 행만 대상으로 합니다.

평균 25일이라는 결과는 완료된 신청 12건의 평균입니다. 아직 신청 상태이거나 수강중인 사람은 제외되어 있습니다.

따라서 “전체 수강생은 평균 25일 만에 완료한다”라고 일반화하면 안 됩니다.

## 15. CSV는 manifest와 함께 관리해야 합니다

그래서 씨에스브이를 사용할 때는 manifest에 출처, 기간, 행 수, 생성 시각, SHA-256 해시를 함께 기록해야 합니다.

## 17. Python 공통 검증은 오류를 숨기지 않아야 합니다

**화면 구성**

검증 항목:

```text
정확한 17개 컬럼
행 수 24
enrollment_id 중복 0
날짜 strict 변환
recorded_amount 숫자형
completion_days 숫자 또는 NULL
is_completed boolean
분석 기간 안의 행
```

금지 방향:

```python
errors="coerce"
```

**발표 스크립트**

파이썬에서 데이터를 읽은 뒤에는 컬럼, 행 수, 자료형, 업무 규칙을 공통 검증해야 합니다.

특히 `errors='coerce'`는 잘못된 문자열을 NaN으로 바꿔 오류를 숨길 수 있습니다. 데이터 오류를 정상 널처럼 보이게 만들 수 있습니다.

분석 코드는 보기 좋게 넘어가는 것보다 잘못된 데이터를 발견하면 중단하는 것이 더 안전합니다.

**발표 스크립트**

Y축을 0부터 시작하지 않거나 월 순서가 틀리면 작은 차이가 과장될 수 있습니다. 그래프도 검토 대상입니다.

## 20. 핵심 정리: 분석은 질문과 검증으로 완성됩니다

**화면 구성**

```text
질문·기간·행 단위를 먼저 정한다.
recorded_amount를 매출로 해석하지 않는다.
COUNT는 세는 단위에 맞게 선택한다.
date spine으로 없는 월을 유지한다.
Python은 SQL 기준 데이터셋을 확장한다.
SQL·pandas 결과를 같은 스냅샷에서 검증한다.
관찰·해석·한계를 분리한다.
```

**발표 스크립트**

챕터 14의 핵심은 에스큐엘이나 파이썬 중 하나를 잘 쓰는 것이 아닙니다.

에스큐엘로 분석의 경계를 확정하고, 파이썬으로 확장한 결과를 같은 증거로 다시 검증하는 것입니다.

좋은 분석은 실행되는 코드와 예쁜 그래프가 아니라, 질문·기간·행 단위·지표 의미·검산·해석 한계가 함께 정리된 결과입니다.
