오늘 목표는 복잡한 설계를 완성하는 것이 아닙니다. 데이터베이스 구조를 정확한 말로 읽고 설명할 수 있게 되는 것입니다.

## 2. 먼저 세 단어를 구분합니다: 데이터, 데이터베이스, DBMS

**화면 구성**

| 구분 | 쉬운 설명 | 예시 |
| --- | --- | --- |
| 데이터 | 기록된 값이나 사실 | 김민지, 20260001, 신청 |
| 데이터베이스 | 관련 데이터를 담는 논리적 공간 | `ai_database_book` |
| DBMS | 데이터베이스를 관리하는 소프트웨어 | PostgreSQL |

**스크립트**

먼저 데이터, 데이터베이스, DBMS를 구분하겠습니다.

데이터는 기록된 값이나 사실입니다. 예를 들어 학생 이름, 학번, 신청일, 신청 상태 같은 값입니다.

데이터베이스는 이런 관련 데이터를 일정한 구조로 모아 두는 논리적 공간입니다. 이 책에서는 뒤에서 `ai_database_book`이라는 데이터베이스를 만들게 됩니다.

DBMS는 그 데이터베이스를 만들고 관리하고 SQL을 실행하는 소프트웨어입니다. 이 책의 기본 DBMS는 PostgreSQL입니다.

일상에서는 모두 DB라고 부르기도 하지만, 설치 문제나 접속 오류를 해결하려면 세 용어를 구분해야 합니다.

## 3. DBeaver는 데이터베이스가 아닙니다

**화면 구성**

```text
사용자
→ DBeaver: SQL을 쓰고 결과를 보는 클라이언트
→ PostgreSQL: 데이터를 저장하고 SQL을 실행하는 DBMS
```

**스크립트**

초보자가 가장 많이 헷갈리는 부분이 DBeaver와 PostgreSQL의 관계입니다.

DBeaver는 데이터를 저장하는 시스템이 아닙니다. DBeaver는 PostgreSQL에 접속해서 SQL을 보내고 결과를 보여 주는 클라이언트 도구입니다.

실제로 SQL을 실행하고 데이터를 저장하는 쪽은 PostgreSQL입니다.

그래서 DBeaver를 닫아도 PostgreSQL 서버와 데이터 저장소가 정상이라면 데이터는 사라지지 않습니다. 반대로 DBeaver가 열려 있어도 PostgreSQL 서버가 꺼져 있거나 접속 정보가 틀리면 연결할 수 없습니다.

이 차이를 이해하면 Chapter 03에서 설치와 접속 오류를 볼 때 훨씬 덜 혼란스럽습니다.

---

## 4. PostgreSQL 구조는 위에서 아래로 읽습니다

**화면 구성**

```text
PostgreSQL 서버
└── 데이터베이스
    └── 스키마
        └── 테이블
            ├── 행
            └── 열
```

**스크립트**

PostgreSQL 안의 구조는 계층으로 이해하면 쉽습니다.

가장 위에는 PostgreSQL 서버가 있습니다. 그 안에 여러 데이터베이스가 있을 수 있습니다.

하나의 데이터베이스 안에는 스키마가 있고, 스키마 안에는 테이블과 뷰 같은 객체가 있습니다.

테이블 안에는 행과 열이 있습니다. 행은 하나의 기록이고, 열은 그 기록을 구성하는 항목입니다.

앞으로 DBeaver의 탐색 화면을 볼 때도 이 순서대로 보면 됩니다. 서버를 열고, 데이터베이스를 선택하고, 스키마를 열고, 테이블을 찾는 흐름입니다.

## 6. 스키마는 데이터베이스 안의 이름 공간입니다

**화면 구성**

```text
students
public.students
course_project.students
```

- 강조 문구: 같은 `students`라도 스키마가 다르면 다른 테이블일 수 있음

**스크립트**

스키마는 데이터베이스 안에서 테이블과 뷰 같은 객체 이름을 구분하는 이름 공간입니다.

예를 들어 `public.students`와 `course_project.students`는 둘 다 `students`라는 이름을 갖지만 서로 다른 테이블일 수 있습니다.

스키마 이름을 생략하고 `students`라고만 쓰면 PostgreSQL은 `search_path`에 따라 어느 스키마의 테이블을 찾을지 결정합니다.

초보자에게는 이 부분이 매우 중요합니다. 같은 SQL을 실행했는데 결과가 다르다면, 실제로 어느 스키마의 테이블을 보고 있는지 확인해야 합니다.

그래서 실습에서는 현재 데이터베이스, 현재 스키마, 검색 경로를 자주 확인합니다.

```sql
SELECT current_database();
SELECT current_schema();
SHOW search_path;
```

## 7. 테이블은 표처럼 보이지만 화면 위치로 찾지 않습니다

**화면 구성**

| id | name | email | major |
| ---: | --- | --- | --- |
| 1 | 김민지 | minji@example.com | 컴퓨터공학 |
| 2 | 이준호 | junho@example.com | 데이터사이언스 |
| 3 | 박서연 | seoyeon@example.com | 경영학 |

- 오른쪽 강조:

```text
테이블 = 같은 성격의 기록 모음
행 = 하나의 기록
열 = 기록의 항목
셀 = 행과 열이 만나는 값
```

**스크립트**

테이블은 스프레드시트처럼 행과 열로 보이지만, SQL에서는 화면 위치로 값을 찾지 않습니다.

`students` 테이블의 한 행은 학생 한 명을 나타냅니다. `name`, `email`, `major` 같은 열은 학생 기록을 구성하는 항목입니다.

셀은 설명을 위한 표현입니다. 예를 들어 `id = 1`인 행의 `major` 값은 `컴퓨터공학`입니다.

하지만 SQL에서는 첫 번째 행의 네 번째 칸 같은 방식으로 접근하지 않습니다. 조건으로 행을 찾고, 열 이름으로 값을 조회합니다.

## 8. 행의 순서는 보장되지 않습니다

**화면 구성**

- 큰 문장:

```text
ORDER BY가 없으면 조회 결과의 순서는 보장되지 않습니다.
```

- 예시:

```sql
SELECT * FROM students;
SELECT * FROM students ORDER BY id;
```

**스크립트**

테이블을 표처럼 보면 자연스럽게 첫 번째 행, 두 번째 행이라는 표현을 쓰게 됩니다.

하지만 관계형 데이터베이스에서 행의 표시 순서는 기본적으로 보장되지 않습니다. 화면에서 지금 첫 번째로 보였다고 해서 다음에도 항상 첫 번째로 나온다고 생각하면 안 됩니다.

정렬 기준이 필요하면 `ORDER BY`를 명시해야 합니다.

지금은 `ORDER BY` 문법을 깊게 배우지는 않지만, 앞으로 결과 비교를 할 때 순서가 필요하면 반드시 정렬 기준을 지정해야 한다는 점을 기억하면 됩니다.

## 9. id와 학번은 둘 다 식별에 쓰이지만 역할이 다릅니다

**화면 구성**

```text
id = 데이터베이스 내부에서 행을 안정적으로 구분하는 값
student_number = 학교 업무에서 사용하는 학번
```

**스크립트**

`id`와 학번은 모두 학생을 식별하는 데 쓰일 수 있지만 역할이 다릅니다.

`id`는 데이터베이스 내부에서 학생 행을 안정적으로 구분하기 위한 값입니다. 보통 사람이 외우거나 직접 의미를 해석하기 위한 값은 아닙니다.

반면 학번은 학교 업무에서 부여한 업무 식별자입니다. 학번은 형식이 바뀔 수도 있고, 앞자리 0이 필요할 수도 있으며, 학교 정책에 따라 재발급 규칙이 달라질 수도 있습니다.

그래서 이 책에서는 데이터베이스 내부 식별자인 `id`와 업무 식별자인 `student_number`를 구분합니다.

## 10. 한 행이 무엇을 의미하는지 먼저 정합니다

**화면 구성**

```text
students 한 행 = 학생 한 명
courses 한 행 = 강의 한 개
enrollments 한 행 = 학생 한 명의 강의 신청 한 건
```

**스크립트**

좋은 데이터 구조의 출발점은 한 행이 무엇을 의미하는지 정하는 것입니다.

`students`의 한 행은 학생 한 명입니다. `courses`의 한 행은 강의 한 개입니다. `enrollments`의 한 행은 학생 한 명이 강의 한 개를 신청한 한 건입니다.

이 기준이 흔들리면 나중에 집계 결과도 흔들립니다. 예를 들어 `enrollments`의 한 행이 학생인지, 강의인지, 신청인지 애매하면 수강신청 수를 세는 SQL도 정확해질 수 없습니다.

따라서 테이블을 볼 때 첫 질문은 항상 “이 테이블의 한 행은 무엇을 나타내는가?”입니다.

## 11. 관계형의 ‘관계’와 업무 관계는 구분해서 설명합니다

**화면 구성**

| 용어 | 의미 |
| --- | --- |
| 릴레이션 | 관계 모델에서 테이블에 가까운 구조 |
| 업무 관계 | 학생이 강의를 신청한다 같은 대상 간 연결 |
| 카디널리티 | 1:1, 1:N, N:M 같은 연결 개수 |

**스크립트**

관계형 데이터베이스라는 말의 관계와, 학생이 강의를 신청한다는 업무 관계는 같은 말처럼 들리지만 구분하는 것이 좋습니다.

관계형 데이터베이스는 관계 모델을 바탕으로 데이터를 행과 열의 구조로 다룹니다. 이때 릴레이션이라는 용어가 나옵니다.

실무에서 우리가 자주 말하는 관계는 학생과 강의, 주문과 상품처럼 업무 대상이 서로 연결되는 규칙입니다.

이 책에서는 너무 이론적으로 깊게 들어가지는 않지만, 관계형이라는 말이 단순히 테이블끼리 선으로 연결할 수 있다는 뜻만은 아니라는 점을 짚고 넘어갑니다.

## 12. N:M 관계는 연결 테이블로 풀어냅니다

**화면 구성**

```text
students 1 ── N enrollments N ── 1 courses
```

- 하단 예시:

```text
한 학생은 여러 강의를 신청할 수 있다.
한 강의에는 여러 학생이 신청할 수 있다.
```

**스크립트**

온라인 강의에서는 한 학생이 여러 강의를 신청할 수 있고, 한 강의에도 여러 학생이 신청할 수 있습니다. 이것을 N:M 관계라고 부릅니다.

관계형 데이터베이스에서는 보통 이 관계를 직접 하나의 선으로만 처리하지 않고, `enrollments` 같은 연결 테이블을 둡니다.

그러면 학생과 수강신청은 1:N, 강의와 수강신청도 1:N이 됩니다.

지금은 연결 테이블을 설계하는 방법을 자세히 배우지는 않습니다. 오늘은 `enrollments`가 학생과 강의 사이의 신청 기록을 표현한다는 정도를 이해하면 충분합니다.

## 13. 기본키는 자기 테이블 안에서 행을 구분합니다

**화면 구성**

| id | name | email |
| ---: | --- | --- |
| 1 | 김민지 | minji@example.com |
| 2 | 김민지 | minji2@example.com |

- 강조:

```text
이름은 같을 수 있지만 id는 서로 다른 행을 구분합니다.
```

**스크립트**

기본키는 한 테이블 안에서 각 행을 고유하게 구분하는 열 또는 열의 조합입니다.

예시에서 두 학생의 이름은 모두 김민지일 수 있습니다. 이름만으로는 두 행을 안정적으로 구분하기 어렵습니다.

하지만 `id`가 1과 2로 다르면 데이터베이스는 두 행을 서로 다른 학생 기록으로 구분할 수 있습니다.

기본키 값은 중복되지 않고, 기본키를 구성하는 값은 NULL일 수 없습니다. 초반 실습에서는 이해하기 쉬운 단일 `id` 열을 기본키로 사용합니다.

## 14. 외래키는 다른 행을 참조합니다

**화면 구성**

| enrollment_id | student_id | course_id | status |
| ---: | ---: | ---: | --- |
| 1 | 1 | 10 | 신청 |
| 2 | 1 | 20 | 수강중 |
| 3 | 2 | 10 | 완료 |

```text
student_id → students.id
course_id  → courses.id
```

**스크립트**

외래키는 다른 행을 참조하는 열입니다.

수강신청 테이블의 `student_id`는 학생 테이블의 `id`를 참조합니다. `course_id`는 강의 테이블의 `id`를 참조합니다.

이렇게 하면 수강신청 한 건이 어느 학생과 어느 강의에 연결되는지 알 수 있습니다.

중요한 점은 외래키 값은 반복될 수 있다는 것입니다. 한 학생이 여러 강의를 신청하면 `student_id = 1`이 여러 행에 나타나는 것은 정상입니다.

외래키는 기본적으로 UNIQUE가 아닙니다. 또한 별도의 `NOT NULL` 규칙이 없으면 NULL을 허용할 수도 있습니다.

---

## 15. DBMS는 저장뿐 아니라 규칙도 적용합니다

**화면 구성**

```text
제약조건
동시 처리
권한
백업과 복구
```

**스크립트**

DBMS는 데이터를 저장하는 기능만 제공하지 않습니다.

잘못된 값이나 잘못된 참조를 줄이기 위해 제약조건을 적용할 수 있습니다. 예를 들어 학생 이름은 비어 있을 수 없고, 이메일은 중복될 수 없고, 존재하지 않는 학생의 수강신청은 저장할 수 없게 할 수 있습니다.

여러 사용자가 동시에 작업할 때는 트랜잭션과 동시성 제어가 필요합니다.

또 사용자와 역할별로 권한을 나누고, 장애나 실수를 대비해 백업과 복구 절차를 구성할 수도 있습니다.

다만 DBMS가 기능을 제공한다고 해서 자동으로 안전해지는 것은 아닙니다. 사람이 요구사항에 맞게 규칙과 절차를 설계하고 검증해야 합니다.

---

## 16. SQL은 DBMS에 요청을 전달하는 언어입니다

**화면 구성**

| CRUD | 의미 | SQL 예 |
| --- | --- | --- |
| Create | 새 데이터 추가 | INSERT |
| Read | 데이터 조회 | SELECT |
| Update | 데이터 수정 | UPDATE |
| Delete | 데이터 삭제 또는 삭제 처리 | DELETE 또는 상태 변경 |

**스크립트**

SQL은 DBMS에 요청을 전달하는 언어입니다.

CRUD는 데이터를 다루는 네 가지 기본 작업을 말합니다. Create는 새 데이터를 추가하는 작업이고, SQL에서는 보통 `INSERT`를 사용합니다.

Read는 조회이고 `SELECT`를 사용합니다. Update는 수정이고 `UPDATE`를 사용합니다.

Delete는 삭제라는 뜻이지만 업무 기능의 삭제가 항상 SQL `DELETE`를 의미하지는 않습니다. 이력을 보존해야 하면 행을 실제로 지우지 않고 상태를 `deleted`로 바꾸거나 삭제 시각을 기록할 수 있습니다.

따라서 화면에서 삭제 버튼이 있다고 해서 데이터베이스에서 항상 행이 물리적으로 삭제된다고 단정하면 안 됩니다.

---

## 17. 데이터 모양과 저장 방식은 같은 말이 아닙니다

**화면 구성**

| 구분 | 예시 |
| --- | --- |
| 정형 데이터 | 테이블 형태의 학생·신청 데이터 |
| 반정형 데이터 | JSON, XML |
| 비정형 데이터 | 이미지, 음성, 자유 텍스트 |

- 강조 문구:

```text
정형/반정형/비정형은 데이터 모양의 구분입니다.
RDBMS/NoSQL/파일은 저장·관리 방식의 구분입니다.
```

**스크립트**

정형, 반정형, 비정형 데이터라는 말은 데이터의 모양을 구분하는 표현입니다.

정형 데이터는 행과 열이 정해진 테이블 형태로 표현하기 쉽습니다. 학생, 강의, 수강신청 같은 데이터가 여기에 해당합니다.

반정형 데이터는 JSON처럼 구조는 있지만 행과 열이 고정된 표와는 다른 형태입니다. 비정형 데이터는 이미지, 음성, 자유 텍스트처럼 고정된 표 구조로 바로 표현하기 어려운 데이터입니다.

중요한 점은 데이터 모양과 저장 기술을 같은 말로 보면 안 된다는 것입니다. JSON도 PostgreSQL에 저장할 수 있고, 파일 시스템에도 저장할 수 있습니다.

## 18. 기준 데이터, 파생 데이터, AI 생성 결과를 다시 구분합니다

**화면 구성**

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 기준 데이터 | 업무 판단의 기준 | 학생 가입, 신청, 결제 원장 |
| 결정적 파생 데이터 | 계산식으로 다시 만들 수 있는 결과 | 월별 집계, 대시보드 지표 |
| AI 생성 결과 | 모델과 입력 조건으로 생성된 결과 | 요약, 추천, 생성 답변 |

**스크립트**

Chapter 01에서 본 기준 데이터, 파생 데이터, AI 생성 결과를 데이터 구조 관점에서 다시 보겠습니다.

기준 데이터는 업무에서 직접 발생하고 판단의 기준이 되는 데이터입니다. 학생 가입, 수강신청, 결제 원장 같은 데이터입니다.

결정적 파생 데이터는 정해진 원본, 계산식, 기준 시점이 있으면 다시 만들 수 있는 결과입니다. 월별 집계나 대시보드 지표가 여기에 해당합니다.

AI 생성 결과는 조금 다릅니다. 모델, 입력 데이터 기준 시점, 프롬프트 버전, 생성 조건에 따라 결과가 달라질 수 있습니다.

따라서 AI 결과가 실제 업무 기록이 되었다면 실행 맥락과 승인 상태를 따로 관리해야 합니다.

---

## 19. 일반 VIEW는 결과를 저장하지 않습니다

**화면 구성**

```text
일반 VIEW
→ 조회 정의를 저장
→ 호출할 때 원본 데이터 조회

Materialized View / 집계 테이블 / 캐시
→ 결과를 별도로 저장할 수 있음
```

**스크립트**

파생 데이터를 다룰 때 VIEW라는 말이 나옵니다.

일반 VIEW는 조회 결과 자체를 저장하는 것이 아니라 조회 정의를 저장합니다. 그래서 VIEW를 호출하면 그 정의를 바탕으로 원본 데이터를 다시 조회합니다.

반면 Materialized View, 집계 테이블, 캐시는 결과를 별도로 저장할 수 있습니다.

지금은 자세한 문법보다 오해를 피하는 것이 중요합니다. 일반 VIEW를 “결과가 저장된 표”로 생각하면 나중에 데이터 최신성과 성능을 잘못 판단할 수 있습니다.

VIEW와 집계는 뒤 장에서 다시 다룹니다.

## 20. 하나의 사례로 구조를 읽어 봅니다

**화면 구성**

```text
students.id ← enrollments.student_id
enrollments.course_id → courses.id
```

| 개념 | 사례에서의 의미 |
| --- | --- |
| DBMS | PostgreSQL |
| 데이터베이스 | `ai_database_book` |
| 테이블 | `students`, `courses`, `enrollments` |
| 기본키 | 각 테이블의 `id` |
| 외래키 | `enrollments.student_id`, `enrollments.course_id` |

**스크립트**

이제 앞에서 배운 용어를 하나의 작은 사례에 연결해 보겠습니다.

DBMS는 PostgreSQL입니다. 데이터베이스는 `ai_database_book`입니다. 개념 예제에서는 스키마를 생략했지만 실제 프로젝트에서는 `course_project` 같은 스키마를 사용합니다.

테이블은 `students`, `courses`, `enrollments`입니다. 각 테이블의 `id`는 기본키입니다.

`enrollments.student_id`는 `students.id`를 참조하고, `enrollments.course_id`는 `courses.id`를 참조합니다.

지금 단계에서 중요한 것은 이 구조를 직접 설계하는 것이 아니라, 주어진 구조를 정확한 용어로 읽는 것입니다.

## 21. AI가 만든 테이블은 기본 용어로 검토합니다

**화면 구성**

```sql
CREATE TABLE student_courses (
    student_name VARCHAR(50),
    student_email VARCHAR(100),
    course_title VARCHAR(100),
    instructor_name VARCHAR(50)
);
```

- 배지: 개념 설명용 SQL · 지금은 실행하지 않습니다
- 체크 질문:

```text
한 행은 무엇을 나타내는가?
기본키가 있는가?
학생·강의·강사 정보가 섞였는가?
참조해야 할 값을 문자열로 반복하지 않았는가?
```

**스크립트**

AI가 이처럼 하나의 테이블을 제안했다고 가정하겠습니다. 문법적으로 실행될 수 있지만, 기본 용어로만 읽어도 확인할 질문이 많습니다.

먼저 한 행이 무엇을 나타내는지 분명하지 않습니다. 학생 한 명인지, 강의 한 개인지, 수강신청 한 건인지 애매합니다.

각 행을 안정적으로 구분할 기본키도 없습니다.

학생, 강의, 강사라는 서로 다른 성격의 데이터가 한 테이블에 섞여 있습니다.

또 강의 제목이나 강사 이름처럼 다른 테이블을 참조해야 할 값이 문자열로 반복될 가능성이 큽니다.

이 장에서는 기본 용어로 문제를 발견하는 데 집중합니다. 테이블 분리, ERD, 정규화는 뒤 장에서 차근차근 다룹니다.

## 22. 자주 하는 오해를 정리합니다

**화면 구성**

```text
DBeaver = 데이터베이스가 아니다.
DBMS와 데이터베이스는 다르다.
스키마와 데이터베이스는 다르다.
ORDER BY 없는 행 순서는 보장되지 않는다.
외래키는 반복될 수 있고 NULL일 수도 있다.
CRUD Delete는 항상 SQL DELETE가 아니다.
일반 VIEW는 결과를 저장하지 않는다.
```

**스크립트**

마지막으로 오늘 배운 개념에서 자주 하는 오해를 정리하겠습니다.

DBeaver는 데이터베이스가 아니라 클라이언트입니다. PostgreSQL은 DBMS이고, 그 안에 만든 `ai_database_book`은 데이터베이스입니다.

PostgreSQL에서 스키마는 데이터베이스 안에 있는 이름 공간입니다.

테이블의 행은 `ORDER BY`가 없으면 항상 같은 순서로 보인다고 가정하면 안 됩니다.

외래키는 1:N 관계에서 반복될 수 있고, 별도의 규칙이 없으면 NULL도 허용될 수 있습니다.

또 업무 기능의 Delete가 항상 SQL `DELETE`는 아니며, 일반 VIEW는 조회 결과 자체를 저장하지 않습니다.

이 오해들을 피하면 이후 SQL 실습에서 오류를 훨씬 정확하게 이해할 수 있습니다.

## 24. 핵심 정리와 다음 장 연결

**화면 구성**

```text
데이터 = 기록된 값이나 사실
데이터베이스 = 관련 데이터를 담는 논리적 공간
DBMS = 데이터베이스를 관리하는 소프트웨어
클라이언트 = DBMS에 SQL을 보내고 결과를 보여 주는 도구
테이블 = 행과 열로 구성된 데이터 구조
키 = 행을 구분하고 관계를 연결하는 기준
```

**스크립트**

Chapter 02의 핵심을 정리하겠습니다.

데이터는 기록된 값이나 사실입니다. 데이터베이스는 관련 데이터를 담는 논리적 공간이고, DBMS는 그 데이터베이스를 관리하는 소프트웨어입니다.

DBeaver 같은 클라이언트는 DBMS에 SQL을 보내고 결과를 보여 주는 도구입니다.

PostgreSQL에서는 서버, 데이터베이스, 스키마, 테이블, 행과 열의 계층을 이해해야 합니다.

기본키는 자기 테이블에서 행을 구분하고, 외래키는 다른 행을 참조해 업무 관계를 표현합니다.

다음 Chapter 03에서는 이 개념을 실제 환경에서 확인합니다. PostgreSQL과 DBeaver를 준비하고, 직접 접속해 현재 데이터베이스와 스키마를 확인해 보겠습니다.
