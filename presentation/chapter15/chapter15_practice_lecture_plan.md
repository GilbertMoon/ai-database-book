# Chapter 15 실습 발표 강의안

## AI 튜터링 DB 종합 프로젝트를 실행 증거로 완성하기

> 목적: `tutor_project`에서 스키마 생성, Seed, 메타데이터 검증, 업무 검증, 트랜잭션, 반례, 성능·운영 점검, 분석 VIEW, Python 교차 검증, 백업·복원을 하나의 흐름으로 실행한다.  
> 기준: 초보자가 “파일을 실행했다”가 아니라 “각 단계의 기대 결과와 완료 증거를 확인했다”라고 말할 수 있어야 한다.

## 1. 이번 실습은 책 전체를 하나의 프로젝트로 실행하는 과정입니다

**화면 구성**

```text
SQL 01~10
→ Python 01~03
→ 백업·복원
→ 복원 DB 11
→ 보고서·AI diff·최종 판단
```

**발표 스크립트**

이번 실습은 마지막 종합 프로젝트입니다. 지금까지 배운 내용을 따로따로 실행하는 것이 아니라 하나의 서비스 데이터베이스로 연결합니다.

대상은 AI 튜터링 질문 관리 서비스입니다. 학생, 튜터, 질문, 답변, 학습 자료, 질문-자료 연결을 관리합니다.

핵심은 끝까지 실행했다는 사실이 아닙니다. 각 단계에서 어떤 결과가 나와야 하고, 어떤 증거를 보고 완료라고 판단할지 기록하는 것입니다.

## 4. 요구사항과 후속 정책을 먼저 적습니다

**화면 구성**

```text
P15-R01~R13: 확정 요구사항
P15-D02~D08: 미확정·후속 정책
```

**발표 스크립트**

SQL을 실행하기 전에 요구사항 표를 확인합니다.

학생은 질문을 등록하고, 튜터는 답변을 작성하며, 질문과 학습 자료는 N:M으로 연결됩니다. 질문 없는 학생도 0건으로 조회해야 하고, 연결되지 않은 자료도 찾을 수 있어야 합니다.

반면 closed 질문에 추가 답변을 허용할지, 비활성 사용자가 작업할 수 있는지, `access_scope`를 실제 권한으로 어떻게 연결할지는 후속 정책입니다. 이번 실습에서 임의로 확정하지 않습니다.

## 5. `01_schema.sql`은 구조를 만들고 기준을 세웁니다

**화면 구성**

```text
테이블 6
제약조건 36
FK 5
IDENTITY PK 5
업무 인덱스 3
CASCADE 0
```

**발표 스크립트**

`01_schema.sql`을 실행하면 `tutor_project` 스키마와 6개 테이블이 만들어집니다.

이 단계에서 중요한 것은 “오류 없이 생성됨”이 아닙니다. 어떤 구조가 생성되어야 하는지를 알고 있어야 합니다.

테이블은 6개, 제약조건은 36개, FK는 5개, IDENTITY 기본키는 5개, 업무 인덱스는 3개입니다. CASCADE FK는 없어야 합니다. 이 기준은 뒤의 03번 파일에서 실제 PostgreSQL 카탈로그로 검증합니다.

**발표 스크립트**

## 9. `05_transaction_checks.sql`은 함께 바뀌어야 하는 작업을 확인합니다

**화면 구성**

```text
실행 전: answers 5, question 303 open
트랜잭션 내부: answers 6, question 303 answered
ROLLBACK 후: answers 5, question 303 open
```

**발표 스크립트**

이 파일은 답변 등록과 질문 상태 변경을 하나의 트랜잭션으로 묶어 확인합니다.

정상 경로에서는 답변이 추가되고 질문 상태가 answered로 바뀝니다. 하지만 실습 기준 데이터를 보존하기 위해 마지막에 ROLLBACK합니다.

실패 경로도 중요합니다. 잘못된 튜터 ID로 답변 INSERT가 실패하면 질문 상태 변경도 남지 않아야 합니다.

## 10. `06_negative_tests.sql`은 실패와 정상 경계값을 함께 확인합니다


**발표 스크립트**

이 파일은 SQLSTATE와 constraint name을 기록합니다. 예상한 제약조건이 실제로 작동했는지 확인하기 위해서입니다.

## 13. `09_analysis_dataset.sql`은 분석 VIEW를 만듭니다

**화면 구성**


## 16. 결과가 다르면 먼저 기준을 확인합니다

**화면 구성**

```text
같은 DB인가?
같은 분석 기간인가?
같은 VIEW인가?
같은 읽기 전용 스냅샷인가?
질문 없는 학생을 포함했는가?
답변 0건 튜터를 포함했는가?
자식 테이블 JOIN으로 과대 집계하지 않았는가?
```

**발표 스크립트**

SQL과 pandas 결과가 다르면 코드를 바로 고치지 않습니다. 먼저 기준을 확인합니다.

같은 DB를 읽었는지, 같은 분석 기간을 사용했는지, 같은 VIEW를 사용했는지 확인합니다.

또 학생별 분석에서 질문 없는 학생을 빠뜨리지 않았는지 봐야 합니다. 직접 자식 테이블 둘을 한 번에 JOIN하면 답변 수와 자료 수가 곱해져 과대 집계될 수 있으므로 먼저 질문별로 집계한 뒤 연결해야 합니다.

## 17. 백업과 별도 DB 복원으로 복구 가능성을 확인합니다

**화면 구성**

```text
pg_dump --schema=tutor_project
createdb tutor_project_restore
pg_restore --single-transaction
11_restore_validation.sql
```

**발표 스크립트**

백업 실습은 파일을 만드는 데서 끝나지 않습니다. 별도 DB에 복원하고 검증해야 합니다.

먼저 `pg_dump`로 `tutor_project` 스키마를 백업합니다. 그다음 `tutor_project_restore`라는 깨끗한 DB를 만들고 `pg_restore`로 복원합니다.

복원 DB에서는 `11_restore_validation.sql`을 실행합니다. 원본 DB에서 실행하면 중단됩니다. 통과해야 복구 증거로 인정할 수 있습니다.

## 18. 완료 판단은 단계별 증거로 나눕니다

**화면 구성**

| 단계 | 증거 | 판정 |
|---|---|---|
| DB 완료 | 10 통과 |  |
| Python 완료 | SQL·pandas 일치 |  |
| 복구 완료 | 11 통과 |  |
| 권한 완료 | 허용·차단 시험 |  |
| 문서 완료 | 보고서·diff 승인 |  |

**발표 스크립트**

워크북의 완료 판단 표를 채웁니다. DB 완료, Python 완료, 복구 완료, 권한 완료, 문서 완료를 나누어 기록합니다.

어떤 단계는 완료되었고 어떤 단계는 아직 실행하지 않았을 수 있습니다. 이 경우 전체 판단은 조건부 완료나 보류가 될 수 있습니다.

가장 중요한 원칙은 미실행 항목을 통과로 표시하지 않는 것입니다. 실행하지 않은 것은 미실행이라고 적어야 프로젝트 신뢰도가 유지됩니다.

## 19. AI diff와 보고서는 사람이 승인합니다

**화면 구성**

```text
변경 파일 목록
요구사항 유지 여부
금지 범위 변경 여부
접속 정보·개인정보 노출 여부
dropna·errors=coerce 여부
미실행 항목을 완료로 표시했는지
```

**발표 스크립트**

AI나 Codex가 프로젝트 파일을 수정했다면 결과만 보지 말고 diff를 확인합니다.

요청하지 않은 파일이 바뀌었는지, 근거 없는 UNIQUE나 CASCADE가 들어갔는지, 접속 정보가 노출되었는지 확인합니다.

보고서도 검토 대상입니다. 실행하지 않은 항목을 완료로 썼거나, 선택 확장을 한 것처럼 표현하면 안 됩니다. 최종 승인은 사람이 합니다.

## 20. 최종 정리는 “재현 가능한 증거”로 마무리합니다

**화면 구성**

```text
요구사항·정책
ERD·DDL
Seed·검증 SQL
트랜잭션·반례
인덱스·운영 점검
분석 VIEW·Python 비교
백업·복원
AI diff·보고서
최종 상태
```

**발표 스크립트**

마지막 정리는 기능 목록이 아니라 증거 목록으로 마무리합니다.

이 프로젝트가 어떤 문제를 다루었고, 어떤 범위를 제외했으며, 어떤 요구사항을 DB 구조로 구현했고, 어떤 검증을 통과했는지 설명합니다.

데이터베이스 프로젝트의 완성은 SQL을 실행한 순간이 아닙니다. 다른 사람이 같은 절차로 실행하고 같은 근거를 확인할 수 있을 때 시작됩니다.
