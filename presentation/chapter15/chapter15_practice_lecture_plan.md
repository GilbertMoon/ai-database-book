## 1. 이번 실습은 책 전체를 하나의 프로젝트로 묶는 과정입니다

**화면 구성**

대상은 AI 튜터링 질문 관리 서비스입니다. 학생, 튜터, 질문, 답변, 학습 자료, 질문-자료 연결을 관리합니다.

실습의 핵심은 파일을 끝까지 실행하는 것이 아니라, 각 단계에서 어떤 증거가 나와야 하는지 기록하는 것입니다. 실행하지 않은 항목은 통과로 표시하지 않습니다.

## 9. `05_transaction_checks.sql`은 함께 바뀌어야 하는 작업을 검증합니다

**화면 구성**

```text
실행 전: answers 5, question 303 open
트랜잭션 내부: answers 6, question 303 answered
ROLLBACK 후: answers 5, question 303 open
```

**발표 스크립트**

이 파일은 답변 등록과 질문 상태 변경을 하나의 트랜잭션으로 묶어 확인합니다.

정상 경로에서는 답변이 추가되고 질문 상태가 answered로 바뀝니다. 하지만 실습 기준 데이터를 보존하기 위해 마지막에 ROLLBACK합니다. 그래서 실행 후 최종 상태는 다시 답변 5건, 질문 303은 open이어야 합니다.

실패 경로도 중요합니다. 잘못된 튜터 ID로 답변 INSERT가 실패하면 질문 상태 변경도 남지 않아야 합니다.

## 16. 결과가 다르면 먼저 기준을 확인합니다

**화면 구성**

- 같은 DB인가?
- 같은 분석 기간인가?
- 같은 VIEW인가?
- 읽기 전용 같은 스냅샷인가?
- 질문 없는 학생·답변 0건 튜터가 포함되었는가?

**발표 스크립트**

SQL과 pandas 결과가 다르면 코드를 바로 고치지 않습니다. 먼저 기준을 확인합니다.

같은 DB를 읽었는지, 같은 분석 기간을 사용했는지, 같은 VIEW를 사용했는지 확인합니다. 학생별 분석에서 질문 없는 학생을 빠뜨리지 않았는지도 봐야 합니다.

또한 직접 자식 테이블 둘을 한 번에 JOIN하면 답변 수와 자료 수가 곱해져 과대 집계될 수 있습니다. 이 경우에는 먼저 질문별로 집계한 뒤 연결해야 합니다.

## 17. 백업과 별도 DB 복원으로 복구 가능성을 확인합니다

**화면 구성**

```text
pg_dump --schema=tutor_project
createdb tutor_project_restore
pg_restore --single-transaction
11_restore_validation.sql
```

**발표 스크립트**

백업 실습은 파일을 만드는 데서 끝나지 않습니다. 별도 DB에 복원하고 검증해야 합니다.

먼저 `pg_dump`로 `tutor_project` 스키마를 백업합니다. 그다음 `tutor_project_restore`라는 깨끗한 DB를 만들고 `pg_restore`로 복원합니다.

복원 DB에서는 `11_restore_validation.sql`을 실행합니다. 원본 DB에서 실행하면 중단됩니다. 통과해야 복구 증거로 인정할 수 있습니다.

## 18. 완료 판단은 단계별 증거로 나눕니다

**화면 구성**

| 단계 | 증거 | 판정 |
| --- | --- | --- |
| DB 완료 | 10 통과 |  |
| Python 완료 | SQL·pandas 일치 |  |
| 복구 완료 | 11 통과 |  |
| 권한 완료 | 허용·차단 시험 |  |
| 문서 완료 | 보고서·diff 승인 |  |

**발표 스크립트**

워크북의 완료 판단 표를 채웁니다. DB 완료, Python 완료, 복구 완료, 권한 완료, 문서 완료를 나누어 기록합니다.

어떤 단계는 완료되었고 어떤 단계는 아직 실행하지 않았을 수 있습니다. 이 경우 전체 판단은 조건부 완료나 보류가 될 수 있습니다.

가장 중요한 원칙은 미실행 항목을 통과로 표시하지 않는 것입니다. 실행하지 않은 것은 “미실행”이라고 적어야 프로젝트 신뢰도가 유지됩니다.

## 19. AI diff와 보고서는 사람이 승인합니다

**화면 구성**

- 변경 파일 목록
- 요구사항 유지 여부
- 파괴적 SQL 여부
- 개인정보·비밀 정보 포함 여부
- 검증 결과와 미실행 항목

**발표 스크립트**

AI가 SQL이나 Python 파일을 수정했다면 반드시 diff를 확인합니다. 요청하지 않은 파일을 바꾸지 않았는지, 앞 장 스키마를 건드리지 않았는지, DROP이나 CASCADE 같은 위험 변경이 없는지 봅니다.

Python 코드에서는 오류를 숨기는 `dropna`, `drop_duplicates`, `errors='coerce'`가 없는지 확인합니다.

보고서에는 실행한 것과 실행하지 않은 것을 구분해서 적습니다. AI의 설명이 그럴듯해도 실행 증거가 없으면 승인할 수 없습니다.

## 20. 최종 발표는 기술보다 근거 흐름을 설명합니다

**화면 구성**

```text
문제와 범위
→ 요구사항 ID
→ ERD와 DDL
→ Seed와 경계 사례
→ 검증 SQL
→ Python 교차 검증
→ 백업·복원
→ 한계와 다음 버전
```

**발표 스크립트**

최종 발표에서는 “무엇을 만들었는가”보다 “왜 그렇게 설계했고 어떻게 검증했는가”를 설명해야 합니다.

먼저 문제와 범위를 말합니다. 그다음 요구사항 ID와 ERD, 실제 DDL, 기준 데이터, 경계 사례, 검증 SQL, Python 교차 검증, 백업·복원 결과를 순서대로 보여 줍니다.

마지막에는 한계를 말합니다. 실제 로그인, 웹 API, ORM 마이그레이션, 실제 권한 정책, NoSQL 연동, 클라우드 배포는 다음 버전으로 남길 수 있습니다. 좋은 프로젝트는 한계까지 투명하게 설명합니다.
