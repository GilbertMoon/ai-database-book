# Chapter 15 이론 발표 강의안

## 데이터베이스 종합 프로젝트

> 목적: 지금까지 배운 요구사항 분석, ERD, 정규화, 무결성, 트랜잭션, 인덱스, 보안, 복구, 분석, AI 검토를 하나의 재현 가능한 프로젝트로 연결한다.  
> 기준: 초보자가 각 장표를 보며 “프로젝트가 끝났다는 것을 무엇으로 증명해야 하는지” 직관적으로 이해할 수 있어야 한다.

## 1. 마지막 장은 기술 목록이 아니라 완성 증거를 다룹니다

**화면 구성**

- 큰 제목: 데이터베이스 종합 프로젝트
- 흐름: 요구사항 → 설계 → 구현 → 검증 → 분석 → 복구 → 보고
- 강조 문장: 프로젝트 완성도는 재현 가능한 증거로 판단합니다

**발표 스크립트**

이번 장은 책 전체의 마지막 장입니다. 새로운 SQL 문법 하나를 더 배우는 장이라기보다, 지금까지 배운 내용을 하나의 프로젝트로 묶어 보는 장입니다.

기준 예제는 AI 튜터링 질문 관리 서비스입니다. 학생이 질문을 등록하고, 튜터가 답변을 작성하고, 질문에 학습 자료를 연결합니다. 운영자는 상태와 시간 관계가 맞는지 확인하고, 분석 담당자는 질문과 답변 현황을 SQL과 Python으로 분석합니다.

중요한 기준은 “기술을 많이 썼는가”가 아닙니다. 요구사항, 실제 DB 구조, 검증 SQL, 분석 결과, 복구 절차가 서로 연결되어 있고, 다른 사람이 같은 절차로 다시 실행할 수 있어야 프로젝트가 완성됩니다.

## 2. 필수 경로와 선택 확장을 먼저 나눕니다

**화면 구성**

- 좌측: 필수 경로
- 우측: 선택 확장
- 하단: Python 분석은 필수, 웹·NoSQL·배포는 선택

**발표 스크립트**

프로젝트를 시작할 때 가장 먼저 할 일은 범위를 줄이는 것입니다. 모든 것을 한 번에 만들려고 하면 완성 기준이 흐려집니다.

이 장의 필수 경로는 요구사항, ERD, 전용 스키마, 기준 데이터, 메타데이터 검증, 업무 검증, 트랜잭션, 반례 테스트, 인덱스 후보, 권한·보안 점검, 백업·복원 계획, 분석 VIEW, Python 교차 검증, AI diff 검토입니다.

반대로 웹 CRUD, 실제 API, 별도 NoSQL 서버, 클라우드 배포는 선택 확장입니다. 선택 확장을 하지 않아도 데이터베이스 프로젝트는 충분히 완성될 수 있습니다. 단, 필수 경로의 증거는 빠지면 안 됩니다.

## 3. 파일 구조가 실행 순서와 증거를 설명해야 합니다

**화면 구성**

```text
01_schema.sql
02_seed.sql
03_metadata_validation.sql
04_requirement_queries.sql
...
10_completion_gate.sql
python/01~03
11_restore_validation.sql
```

**발표 스크립트**

좋은 프로젝트는 파일 이름만 보아도 실행 순서가 보입니다. `01_schema.sql`은 구조를 만들고, `02_seed.sql`은 기준 데이터를 넣고, `03_metadata_validation.sql`은 실제 생성 구조를 확인합니다.

그 뒤에는 요구사항 조회, 트랜잭션 확인, 실패 반례, 성능 후보, 운영 점검, 분석 데이터셋, 완료 게이트가 이어집니다. Python 파일은 DB 분석 결과를 pandas로 다시 계산하고 SQL 결과와 비교합니다.

마지막으로 백업을 만든 뒤 별도 복원 DB에서 `11_restore_validation.sql`을 실행합니다. 이 순서는 단순한 정리가 아니라 프로젝트의 증거 흐름입니다.

## 4. 문제·사용자·제외 범위를 명확히 합니다

**화면 구성**

- 사용자 4명: 학생, 튜터, 운영자, 분석 담당자
- 제외 범위: 실제 로그인, LLM API, 웹/API, 배포, 자동 백업

**발표 스크립트**

AI 튜터링 질문 관리 서비스에는 네 종류의 사용자가 있습니다. 학생은 질문을 등록하고 자신의 질문을 조회합니다. 튜터는 질문을 읽고 답변을 작성합니다. 운영자는 상태, 답변, 자료 연결, 시간 정합성을 확인합니다. 분석 담당자는 질문·답변·자료 현황을 분석합니다.

여기서 실제 로그인, 실제 개인정보 수집, 알림, 결제, 실제 LLM API 호출, 웹 화면, 클라우드 배포는 제외합니다.

제외 범위를 명시하는 이유는 중요합니다. 제외한 기능을 구현하지 않았다고 실패가 아닙니다. 반대로 제외한 기능을 구현한 것처럼 보고서에 쓰면 검증되지 않은 내용을 완료로 표시하는 문제가 됩니다.

## 5. P15 추적 ID로 요구사항과 정책을 분리합니다

**화면 구성**

- P15-R: 확정 요구사항
- P15-D: 미확정 또는 후속 정책
- 예: 질문 등록, 복수 답변, N:M 자료 연결, 0건 학생 조회

**발표 스크립트**

프로젝트가 커질수록 요구사항을 문장으로만 관리하면 놓치는 부분이 생깁니다. 그래서 이 장에서는 P15-R01처럼 ID를 붙입니다.

예를 들어 학생은 질문을 등록한다, 이메일은 공백이 아니고 정확히 같은 문자열은 중복되지 않는다, 질문에는 여러 답변이 가능하다, 질문과 학습 자료는 N:M 관계라는 요구사항을 각각 추적합니다.

반면 같은 튜터가 한 질문에 여러 답변을 작성할 수 있는지, closed 질문에 추가 답변을 허용할지, 비활성 사용자가 신규 작업을 할 수 있는지는 후속 정책으로 남깁니다. 미확정 정책을 AI나 DB 제약조건이 임의로 확정하면 안 됩니다.

## 6. ERD는 테이블 그림이 아니라 업무 문장의 구조입니다

**화면 구성**

```text
students 1 → N questions
questions 1 → N answers
tutors 1 → N answers
questions N ↔ M learning_materials
```

**발표 스크립트**

이 프로젝트의 핵심 관계는 단순합니다. 학생 한 명은 질문을 여러 개 등록할 수 있고, 질문 하나에는 답변이 여러 개 달릴 수 있습니다. 튜터 한 명은 여러 답변을 작성할 수 있습니다.

질문과 학습 자료는 N:M 관계입니다. 한 질문에 여러 자료가 연결될 수 있고, 하나의 자료가 여러 질문에 연결될 수 있습니다. 그래서 `question_materials` 연결 테이블이 필요합니다.

ERD는 예쁜 도형이 아니라 이런 업무 문장을 테이블과 키로 바꾸는 작업입니다.

## 7. 실제 메타데이터로 설계를 확인합니다

**화면 구성**

- 검증 대상: 테이블 6개, 제약조건 36개, FK 5개, IDENTITY PK 5개, 업무 인덱스 3개, CASCADE 0
- 강조: 개수만 맞는 것으로 충분하지 않음

**발표 스크립트**

설계 문서에 테이블이 6개라고 적혀 있어도 실제 PostgreSQL에 그렇게 만들어졌는지 확인해야 합니다.

`03_metadata_validation.sql`은 단순히 개수만 세지 않습니다. 정확한 테이블 이름, 제약조건 이름, 외래키의 출발 컬럼과 대상 컬럼, 복합 PK의 컬럼 순서, 인덱스 정의까지 확인합니다.

개수만 맞으면 안 됩니다. 잘못된 FK 하나가 빠지고 관련 없는 제약조건 하나가 추가되어도 개수는 같을 수 있습니다. 그래서 실제 메타데이터 검증이 필요합니다.

## 8. 기준 데이터는 테스트용 이야기여야 합니다

**화면 구성**

- students 4, tutors 3, questions 5, answers 5, materials 6, links 7
- 경계 사례: 질문 없는 학생, 미연결 자료, 답변 없는 open 질문, 답변 2개 질문

**발표 스크립트**

Seed 데이터는 단순히 행 수를 채우는 것이 아닙니다. 검증할 수 있는 이야기를 담아야 합니다.

이 장의 기준 데이터에는 질문 없는 학생이 1명 있습니다. 연결되지 않은 자료도 1건 있습니다. 답변 없는 open 질문도 있고, 답변이 2개인 질문도 있습니다.

이런 경계 사례가 있어야 LEFT JOIN, 0건 포함 집계, 복수 답변, 미연결 자료 조회가 실제로 검증됩니다.

## 9. 시간 정합성은 테이블 내부와 테이블 간 검증으로 나눕니다

**화면 구성**

- 테이블 내부: updated_at >= created_at
- 테이블 간: 질문 작성일 >= 학생 가입일, 답변 작성일 >= 질문 작성일, 자료 연결일 >= 질문 작성일

**발표 스크립트**

시간 검증에는 두 종류가 있습니다. 같은 테이블 안에서 확인할 수 있는 규칙은 CHECK 제약조건으로 어느 정도 막을 수 있습니다. 예를 들어 질문의 수정 시각은 생성 시각보다 빠르면 안 됩니다.

하지만 여러 테이블을 함께 봐야 하는 규칙도 있습니다. 질문 작성일은 학생 가입일보다 빨라서는 안 됩니다. 답변 작성 시각은 질문 작성 시각이나 튜터 생성 시각보다 빠르면 안 됩니다.

이런 규칙은 검증 SQL로 확인합니다. 모든 업무 규칙을 CHECK 하나로 해결하려고 하면 오히려 설계가 복잡해질 수 있습니다.

## 10. 트랜잭션은 정상과 실패를 모두 증명해야 합니다

**화면 구성**

```text
실행 전: answers 5, question 303 open
트랜잭션 내부: answers 6, question 303 answered
ROLLBACK 후: answers 5, question 303 open
```

**발표 스크립트**

답변 등록은 단순 INSERT 하나로 끝나지 않을 수 있습니다. 답변을 추가하고 질문 상태를 open에서 answered로 바꾸는 작업이 함께 처리되어야 합니다.

이 장의 트랜잭션 실습은 먼저 정상 경로를 확인합니다. 트랜잭션 안에서는 답변이 6건으로 보이고 질문 상태도 answered가 됩니다. 그러나 마지막에 ROLLBACK하면 기준 데이터는 다시 답변 5건, 질문 303은 open으로 돌아갑니다.

또한 잘못된 tutor 때문에 답변 INSERT가 실패하는 경우 상태 변경도 남지 않아야 합니다. 트랜잭션은 성공뿐 아니라 실패 후 남는 것이 없는지도 확인해야 합니다.

## 11. 반례 테스트는 SQLSTATE와 제약조건 이름까지 기록합니다

**화면 구성**

- 실패 반례 18개
- 정상 경계값 5개
- expected_sqlstate / actual_sqlstate / expected_constraint / actual_constraint

**발표 스크립트**

오류가 발생했다는 사실만으로 충분하지 않습니다. 의도한 규칙 때문에 실패했는지 확인해야 합니다.

예를 들어 중복 이메일, 없는 부모 FK, 잘못된 상태, 빈 제목, 잘못된 시간 순서, 중복 자료 연결 같은 반례를 넣습니다. 이때 SQLSTATE뿐 아니라 실제로 작동한 제약조건 이름도 기록합니다.

또한 실패 테스트만 하면 안 됩니다. 한 글자 이름, NULL note, 질문별 복수 답변처럼 정상이어야 하는 경계값도 통과해야 합니다. 좋은 제약조건은 나쁜 값은 막고 정상 경계값은 허용합니다.

## 12. 인덱스는 작은 Seed 결과만으로 단정하지 않습니다

**화면 구성**

- 후보 인덱스 3개
- 학생별 상태별 질문, 질문별 답변 시간순, 자료별 질문 조회
- 강조: 작은 Seed의 Seq Scan은 자동 오류가 아님

**발표 스크립트**

이 프로젝트에는 업무 조회를 위한 인덱스 후보가 있습니다. 학생별 질문을 상태와 생성일 순서로 찾거나, 질문별 답변을 시간순으로 찾거나, 특정 자료가 연결된 질문을 찾는 패턴입니다.

하지만 Seed 데이터가 작으면 PostgreSQL이 인덱스보다 전체 테이블 읽기를 선택할 수 있습니다. 이것만 보고 인덱스가 틀렸다고 판단하면 안 됩니다.

실제 인덱스 효과를 판단하려면 운영과 비슷한 데이터 크기, 인덱스 전후 동일 SQL, 실행 계획, 버퍼, 쓰기 비용, 배포 잠금까지 함께 봐야 합니다.

## 13. 보안 점검은 값 분류와 실제 권한을 구분합니다

**화면 구성**

- PUBLIC, ACL, owner, has_*_privilege
- access_scope는 분류 값, 실제 접근 통제는 Role·VIEW·RLS

**발표 스크립트**

`learning_materials.access_scope`에 public, internal, restricted 같은 값이 있다고 해서 실제 접근이 차단되는 것은 아닙니다. 이것은 업무 분류 값일 뿐입니다.

실제 접근 통제는 Role, VIEW, RLS 같은 장치로 구현해야 합니다. 그래서 운영 점검에서는 객체 owner, ACL, PUBLIC 권한, 현재 사용자의 최종 유효 권한을 확인합니다.

또한 Python 접속 정보는 `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSFILE`로 관리하고 실제 password file은 저장소 밖에 둡니다.

## 14. 백업은 파일 생성이 아니라 복원 검증까지입니다

**화면 구성**

```text
pg_dump → 별도 DB createdb → pg_restore → 11_restore_validation.sql
```

**발표 스크립트**

백업 파일을 만들었다고 복구가 준비된 것은 아닙니다. 그 파일이 실제로 복원되는지 확인해야 합니다.

이 프로젝트는 `tutor_project` 스키마를 사용자 정의 형식으로 백업하고, 원본 DB가 아니라 `tutor_project_restore`라는 별도 DB에 복원합니다.

복원 DB에서만 `11_restore_validation.sql`을 실행합니다. 원본 DB에서 이 파일을 실행하면 중단되도록 설계합니다. 복원 검증에는 테이블, 시퀀스, VIEW, 행 수, 제약조건, 인덱스, 시간 정합성, owner 확인이 포함됩니다.

## 15. 분석 VIEW는 행 단위와 0건 포함 여부를 분리합니다

**화면 구성**

- question_analysis_dataset: 질문 1건
- student_question_summary: 학생 1명, 질문 0건 포함
- tutor_answer_summary: 튜터 1명, 답변 0건 포함

**발표 스크립트**

분석에서는 한 행이 무엇을 의미하는지 먼저 정해야 합니다. `question_analysis_dataset`의 한 행은 질문 1건입니다.

하지만 질문 VIEW만으로 학생별 분석을 하면 질문이 없는 학생은 사라집니다. 그래서 학생 단위 분석에는 `student_question_summary`가 따로 필요합니다. 튜터별 답변 분석도 마찬가지입니다.

0건을 포함해야 하는 질문인지, 실제 존재하는 질문만 보면 되는 질문인지에 따라 VIEW가 달라집니다.

## 16. SQL과 pandas 결과는 같은 스냅샷에서 비교합니다

**화면 구성**

- READ ONLY, REPEATABLE READ
- SQL 상태·월·학생·튜터·첫 답변 요약
- pandas `assert_frame_equal()`

**발표 스크립트**

Python 분석은 SQL을 대체하는 것이 아니라 검증을 확장하는 역할입니다.

하나의 읽기 전용 연결에서 같은 스냅샷을 사용해 원본 테이블, 분석 VIEW, SQL 요약 결과를 읽습니다. pandas가 같은 데이터로 만든 결과와 실제 SQL 결과를 직접 비교합니다.

Python 코드 안에 기대 상수를 복사해 놓고 비교하는 것은 회귀 테스트에는 도움이 되지만, 실제 SQL과 pandas 교차 검증이라고 보기에는 부족합니다. 같은 데이터에서 나온 두 결과가 일치해야 합니다.

## 17. DB 완료 게이트와 전체 프로젝트 완료는 다릅니다

**화면 구성**

| 단계 | 증거 |

**발표 스크립트**

Python 교차 검증, 백업·복원 검증, 실제 권한 허용·차단 시험, 문서와 AI diff 검토는 별도 증거가 필요합니다.

미실행 항목은 통과로 표시하지 않습니다. 프로젝트 완료 판단은 완료, 조건부 완료, 보류, 미완료처럼 명시적으로 기록해야 합니다.

## 18. AI 변경은 diff와 실행 증거로 승인합니다

**화면 구성**

- AI 제안 → 파일별 diff → 격리 실행 → 검증 → 재수정 → 사람 승인
- 위험 항목: 임의 UNIQUE, CASCADE, dropna, 접속 정보 노출

**발표 스크립트**

AI는 SQL, Python, 문서 초안을 빠르게 만들 수 있습니다. 하지만 AI가 만든 결과는 승인된 변경이 아니라 검토 대상입니다.

먼저 파일별 diff를 확인합니다. 요청하지 않은 파일을 바꾸지 않았는지, 근거 없는 UNIQUE나 CASCADE가 들어가지 않았는지, 접속 정보가 노출되지 않았는지 확인합니다.

분석 코드에서는 임의 `dropna`, `drop_duplicates`, `errors='coerce'`처럼 오류를 숨기는 코드가 없는지 봐야 합니다. 최종 승인은 설명이 자연스러운지가 아니라 실행 증거가 충분한지로 판단합니다.
