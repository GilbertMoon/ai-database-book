## 4. 문제·사용자·제외 범위를 명확히 합니다

**화면 구성**

| 사용자 | 작업 |
|---|---|
| 학생 | 질문 등록·자신의 질문 조회 |
| 튜터 | 질문 조회·답변 작성 |
| 운영자 | 상태·자료 연결·정합성 확인 |

**발표 스크립트**

AI 튜터링 질문 관리 서비스에는 학생, 튜터, 운영자, 분석 담당자가 있습니다.

학생은 질문을 등록하고, 튜터는 답변을 작성합니다. 운영자는 질문 상태와 답변, 자료 연결, 시간 정합성을 확인합니다. 분석 담당자는 질문과 답변 현황을 SQL과 Python으로 분석합니다.

동시에 제외 범위도 명확히 해야 합니다. 실제 로그인, 실제 개인정보 수집, 알림, 결제, LLM API 호출, 웹 API, 배포는 이번 필수 범위가 아닙니다. 제외한 것을 구현하지 않았다고 실패가 아니며, 구현하지 않은 것을 완료로 표시하면 안 됩니다.

## 5. P15 추적 ID로 요구사항과 후속 정책을 분리합니다

**화면 구성**

```text
P15-R: 확정 요구사항
P15-D: 미확정·후속 정책
```

예:

```text
질문 등록 / 복수 답변 / N:M 자료 연결 / 0건 학생 조회
closed 질문 답변 허용 여부 / 비활성 사용자 작업 여부
```

**발표 스크립트**

프로젝트가 커질수록 요구사항을 그냥 문장으로만 관리하면 빠뜨리기 쉽습니다. 그래서 P15-R01처럼 ID를 붙입니다.

확정 요구사항은 DB 구조와 검증 SQL에 연결되어야 합니다. 예를 들어 질문은 학생을 참조하고, 질문에는 여러 답변이 가능하며, 질문과 학습 자료는 N:M 관계입니다.

반면 closed 질문에 답변을 허용할지, 비활성 학생이나 튜터가 신규 작업을 할 수 있는지는 후속 정책입니다. 이런 미확정 정책을 AI나 DB 제약조건이 임의로 확정하면 안 됩니다.

## 6. ERD는 업무 문장을 테이블과 관계로 바꾸는 작업입니다

**화면 구성**

```text
students 1 → N questions
questions 1 → N answers
tutors 1 → N answers
questions N ↔ M learning_materials
```

**발표 스크립트**

ERD는 예쁜 그림을 그리는 작업이 아니라 업무 문장을 구조로 바꾸는 작업입니다.

학생 한 명은 여러 질문을 등록할 수 있습니다. 질문 하나에는 여러 답변이 달릴 수 있고, 튜터 한 명은 여러 답변을 작성할 수 있습니다.

질문과 학습 자료는 N:M 관계입니다. 한 질문에 여러 자료가 연결될 수 있고, 하나의 자료가 여러 질문에 연결될 수 있습니다. 그래서 `question_materials` 연결 테이블이 필요합니다.

## 7. 실제 메타데이터로 설계를 확인합니다

**화면 구성**

```text
base tables 6
constraints 36
FK 5
IDENTITY PK 5
업무 인덱스 3
CASCADE 0
```

**발표 스크립트**

설계 문서에 테이블이 6개라고 적혀 있어도 실제 PostgreSQL에 그렇게 만들어졌는지 확인해야 합니다.

`03_metadata_validation.sql`은 단순히 개수만 보지 않습니다. 정확한 테이블 이름, 제약조건 이름, 외래키의 출발 컬럼과 대상 컬럼, 복합 PK의 컬럼 순서, 인덱스 정의까지 확인합니다.

개수만 맞는 것은 충분하지 않습니다. 잘못된 FK 하나가 빠지고 관련 없는 제약조건 하나가 추가되어도 총 개수는 같을 수 있습니다.

## 8. Seed 데이터는 테스트할 이야기를 담아야 합니다

**화면 구성**

```text
students 4 / tutors 3 / questions 5
answers 5 / materials 6 / question_materials 7
```

경계 사례:

```text
질문 없는 학생 1명
연결되지 않은 자료 1건
답변 없는 open 질문 1건
답변 2개 질문 1건
```

**발표 스크립트**

Seed 데이터는 단순히 행 수를 채우는 데이터가 아닙니다. 검증할 수 있는 이야기가 있어야 합니다.

질문 없는 학생이 있어야 학생별 요약에서 0건 학생을 포함하는지 확인할 수 있습니다. 연결되지 않은 자료가 있어야 미사용 자료를 찾을 수 있습니다.

답변 없는 open 질문과 답변이 2개인 질문도 필요합니다. 그래야 LEFT JOIN, 0건 포함 집계, 복수 답변 정책을 실제로 확인할 수 있습니다.

## 9. 시간 정합성은 제약조건과 검증 SQL로 나눕니다

**화면 구성**

```text
테이블 내부: updated_at >= created_at
테이블 간: 질문일 >= 학생 가입일
테이블 간: 답변일 >= 질문일·튜터 생성일
테이블 간: 자료 연결일 >= 질문일
```

**발표 스크립트**

시간 규칙은 두 종류로 나누어 봐야 합니다.

같은 테이블 안에서 확인할 수 있는 규칙은 CHECK 제약조건으로 막을 수 있습니다. 예를 들어 질문의 수정 시각은 생성 시각보다 빠르면 안 됩니다.

하지만 여러 테이블을 함께 봐야 하는 규칙도 있습니다. 질문 작성일은 학생 가입일보다 빨라서는 안 되고, 답변 작성 시각은 질문 작성 시각이나 튜터 생성 시각보다 빨라서는 안 됩니다. 이런 규칙은 검증 SQL로 확인합니다.

## 10. 트랜잭션은 성공과 실패 후 복구를 모두 증명합니다

**화면 구성**

```text
실행 전: answers 5, question 303 open
트랜잭션 내부: answers 6, question 303 answered
ROLLBACK 후: answers 5, question 303 open
```

**발표 스크립트**

답변 등록은 단순 INSERT 하나로 끝나지 않을 수 있습니다. 답변을 추가하고 질문 상태를 open에서 answered로 바꾸는 작업이 함께 처리되어야 합니다.

정상 경로에서는 트랜잭션 안에서 답변이 6건으로 보이고 질문 상태도 answered가 됩니다. 그러나 마지막에 ROLLBACK하면 기준 데이터는 다시 답변 5건, 질문 303은 open으로 돌아갑니다.

실패 경로도 중요합니다. 잘못된 tutor 때문에 답변 INSERT가 실패하는 경우 상태 변경도 남지 않아야 합니다.

## 11. 반례 테스트는 실패와 정상 경계값을 함께 봅니다

**화면 구성**

```text
실패 반례 18개
정상 경계값 5개
전체 23 / 통과 23 / unexpected 0
```

**발표 스크립트**

오류가 발생했다는 사실만으로는 충분하지 않습니다. 의도한 규칙 때문에 실패했는지 확인해야 합니다.

그래서 SQLSTATE와 실제 제약조건 이름을 함께 기록합니다. 중복 이메일, 없는 부모 FK, 잘못된 상태, 빈 제목, 잘못된 시간 순서, 중복 자료 연결 같은 반례를 확인합니다.

동시에 정상 경계값도 확인합니다. 한 글자 이름, NULL note, 질문별 복수 답변처럼 정상이어야 하는 값이 통과해야 제약조건이 과도하지 않다는 것을 알 수 있습니다.

## 12. 인덱스는 후보와 실제 효과 검증을 구분합니다

**화면 구성**

| 인덱스 | 조회 패턴 |
|---|---|
| questions(student_id, status, created_at DESC) | 학생별 상태별 질문 |
| answers(question_id, created_at) | 질문별 답변 시간순 |
| question_materials(material_id) | 자료별 질문 |

**발표 스크립트**

이 프로젝트의 인덱스 후보는 학생별 상태별 질문 조회, 질문별 답변 시간순 조회, 자료별 질문 조회에 대응합니다.

다만 작은 Seed에서는 PostgreSQL이 Seq Scan을 선택할 수 있습니다. 이것은 자동 오류가 아닙니다. 실제 효과 검증에는 운영과 비슷한 데이터 크기, 인덱스 전후 동일 SQL, 실행 계획, 버퍼, 쓰기 비용, 배포 잠금 검토가 필요합니다.

## 13. 보안 점검은 분류 값과 실제 권한을 구분합니다

**화면 구성**

```text
access_scope = 업무 분류 값
실제 접근 통제 = Role / VIEW / RLS / GRANT
```

점검:

```text
owner / ACL / PUBLIC / has_*_privilege / 가상 데이터
```

**발표 스크립트**

`learning_materials.access_scope`에 public, internal, restricted가 있다고 해서 실제 접근이 차단되는 것은 아닙니다. 이것은 업무 분류 값입니다.

실제 접근 통제는 Role, VIEW, RLS, GRANT 같은 장치로 구현해야 합니다.

운영 점검에서는 객체 owner, ACL, PUBLIC 권한, 현재 사용자의 최종 유효 권한을 확인합니다. 또한 실제 개인정보, 비밀번호, 운영 URL이 Seed나 코드에 들어가지 않았는지도 확인합니다.

## 14. 백업은 파일 생성이 아니라 별도 DB 복원으로 증명합니다

**화면 구성**

```text
pg_dump --schema=tutor_project
→ createdb tutor_project_restore
→ pg_restore --single-transaction
→ 11_restore_validation.sql
```

**발표 스크립트**

백업 파일을 만들었다고 복구가 준비된 것은 아닙니다. 그 파일이 실제로 복원되는지 확인해야 합니다.

이 프로젝트는 `tutor_project` 스키마를 백업하고, 원본 DB가 아니라 `tutor_project_restore`라는 별도 DB에 복원합니다.

복원 DB에서만 `11_restore_validation.sql`을 실행합니다. 검증에는 테이블, 시퀀스, VIEW, 행 수, 제약조건, 인덱스, 시간 정합성, owner 확인이 포함됩니다.

## 15. 분석 VIEW는 질문 단위와 0건 포함 요약을 분리합니다

**화면 구성**

```text
question_analysis_dataset       한 행 = 질문 1건
student_question_summary        한 행 = 학생 1명, 질문 0건 포함
tutor_answer_summary            한 행 = 튜터 1명, 답변 0건 포함
```

**발표 스크립트**

분석에서는 한 행이 무엇을 의미하는지 먼저 정해야 합니다.

`question_analysis_dataset`의 한 행은 질문 1건입니다. 하지만 이 VIEW만으로 학생별 질문 수를 분석하면 질문이 없는 학생은 사라집니다.

그래서 학생 단위 요약 VIEW가 따로 필요합니다. 튜터별 답변 수 역시 답변이 0건인 튜터까지 포함해야 한다면 별도 요약 VIEW나 원본 LEFT JOIN이 필요합니다.

## 16. SQL과 pandas 결과는 같은 스냅샷에서 비교합니다

**화면 구성**

```text
READ ONLY + REPEATABLE READ
→ 실제 SQL 요약
→ pandas 요약
→ assert_frame_equal()
```

**발표 스크립트**

Python 분석은 SQL을 대체하는 것이 아니라 검증을 확장하는 역할입니다.

하나의 읽기 전용 연결에서 같은 스냅샷을 사용해 원본 테이블, 분석 VIEW, SQL 요약 결과를 읽습니다.

그다음 pandas가 같은 데이터로 만든 결과와 실제 SQL 결과를 직접 비교합니다. Python 코드 안에 기대 상수를 복사해 놓고 비교하는 것은 회귀 테스트에는 도움이 되지만, 실제 SQL·pandas 교차 검증이라고 보기에는 부족합니다.

## 17. DB 완료 게이트와 전체 프로젝트 완료는 다릅니다

**화면 구성**

| 단계 | 증거 |
|---|---|
| DB 완료 | `10_completion_gate.sql` 통과 |
| Python 완료 | SQL·pandas 요약 5종 일치 |
| 복구 완료 | 백업·복원·`11` 통과 |
| 권한 완료 | 실제 Role 허용·차단 시험 |
| 문서 완료 | 요구사항·ERD·보고서·AI diff 승인 |

**발표 스크립트**

`10_completion_gate.sql`이 통과하면 DB 구조와 기준 데이터, 핵심 SQL 검증은 통과한 것입니다.

하지만 이것을 전체 프로젝트 완료로 확대하면 안 됩니다. Python 교차 검증, 백업·복원 검증, 실제 권한 허용·차단 시험, 문서와 AI diff 검토는 별도 증거가 필요합니다.

미실행 항목은 통과로 표시하지 않습니다. 실행하지 않았다면 “미실행”이라고 적어야 합니다.

## 18. AI 변경은 diff와 실행 증거로 승인합니다

**화면 구성**

```text
AI 제안
→ 파일별 diff
→ 격리 실행
→ DB·Python·복원 검증
→ 사람 승인
```

위험 신호:

```text
근거 없는 UNIQUE·CASCADE·트리거·RLS
접속 정보 노출
dropna·drop_duplicates·errors=coerce
분석 기간·행 단위 변경
```

**발표 스크립트**

AI는 SQL, Python, 문서 초안을 빠르게 만들 수 있습니다. 하지만 AI가 만든 결과는 승인된 변경이 아니라 검토 대상입니다.

먼저 파일별 diff를 확인합니다. 요청하지 않은 파일을 바꾸지 않았는지, 근거 없는 UNIQUE나 CASCADE가 들어가지 않았는지, 접속 정보가 노출되지 않았는지 확인합니다.

분석 코드에서는 임의 `dropna`, `drop_duplicates`, `errors='coerce'`처럼 오류를 숨기는 코드가 없는지 봐야 합니다. 최종 승인은 설명이 자연스러운지가 아니라 실행 증거가 충분한지로 판단합니다.

## 19. 프로젝트 완성도는 일곱 축으로 설명합니다

**화면 구성**

```text
1. 문제와 범위
2. 요구사항·정책과 설계 일관성
3. 재현 가능한 SQL·Python
4. 정상·경계·오류·시간·트랜잭션 증거
5. 성능·권한·보안·백업·복구 계획
6. AI diff·실행 결과·사람 승인
7. 한계와 다음 버전
```

**발표 스크립트**

프로젝트 발표는 기능 목록을 나열하는 시간이 아닙니다.

무엇을 해결하려고 했고, 무엇을 제외했으며, 어떤 근거로 설계했고, 어떤 검증을 통과했는지 설명해야 합니다.

특히 정상 데이터뿐 아니라 경계값, 실패 반례, 시간 정합성, 트랜잭션, 분석 결과, 복구 절차를 제시하면 프로젝트 신뢰도가 높아집니다.

## 20. 핵심 정리: 프로젝트 완성은 재현 가능한 증거입니다

**화면 구성**

```text
기술 목록보다 증거 흐름이 중요합니다.
요구사항 ID가 DB 구조와 연결되어야 합니다.
검증 SQL은 실제 메타데이터와 데이터를 확인해야 합니다.
Python 분석은 SQL 결과와 직접 비교해야 합니다.
백업은 별도 DB 복원으로 증명해야 합니다.
AI 결과는 diff와 실행 증거로 승인해야 합니다.
```

**발표 스크립트**

Chapter 15의 핵심은 “무엇을 만들었는가”보다 “그것이 맞다는 것을 어떻게 증명했는가”입니다.

데이터베이스 프로젝트의 완성은 SQL이나 그래프를 만드는 순간이 아닙니다.

다른 사람이 같은 절차로 실행하고 같은 근거를 확인할 수 있을 때, 비로소 프로젝트가 완성되었다고 말할 수 있습니다.
