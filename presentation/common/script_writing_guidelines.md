# 발표 스크립트 작성 공통 규칙

이 문서는 데이터베이스 교재 발표자료의 장표별 강의 스크립트를 작성·검수·반영할 때 공통으로 적용하는 기준을 정리한다.

## 1. 기본 원칙

### 1.1 장표 문장을 그대로 읽지 않는다

장표 제목, 본문, 카드 문구를 단순히 이어 붙이지 않는다. 스크립트는 장표의 핵심 개념을 강사가 자연스럽게 설명하는 형태로 다시 구성한다.

다음과 같은 상투적 표현은 반복하지 않는다.

- `이번에는 ‘○○’이라는 주제를 살펴보겠습니다.`
- `각 항목의 뜻을 단순히 외우기보다 이해하는 것이 중요합니다.`
- `에이아이가 만든 결과도 같은 기준으로 확인해야 합니다.`

필요한 경우에만 자연스럽게 사용하고, 장표마다 동일한 문장을 자동 반복하지 않는다.

### 1.2 한 장표에는 하나의 핵심 메시지를 둔다

스크립트 전체가 한 문장으로 요약될 수 있어야 한다.

예시:

- 실행되는 에스큐엘과 올바른 에스큐엘은 다르다.
- 계산 대상이 학생이라면 학생 테이블을 기준으로 해야 한다.
- 이너 조인은 누락과 중복을 만들 수 있다.
- 한 테이블에 여러 업무 대상을 섞으면 변경 문제가 커진다.
- 에이아이가 만든 결과도 사람이 검증해야 한다.

### 1.3 설명은 원인과 결과가 연결되도록 구성한다

다음 흐름을 기본으로 사용한다.

1. 장표에서 다루는 문제를 제시한다.
2. 코드, 구조 또는 요구사항이 무엇을 의미하는지 설명한다.
3. 어떤 문제가 발생하는지 설명한다.
4. 왜 요구사항과 맞지 않는지 판단한다.
5. 사람이 확인해야 할 기준을 정리한다.

예시:

> 이너 조인은 연결되는 행만 남긴다.  
> → 질문이 없는 학생은 빠진다.  
> → 질문이 여러 개인 학생은 반복된다.  
> → 학생 수가 아니라 연결된 질문 행 수를 셀 수 있다.

## 2. 강의체와 문장 스타일

### 2.1 그대로 읽을 수 있는 자연스러운 강의체로 작성한다

- 한 문장에는 하나의 의미만 담는다.
- 지나치게 긴 수식어를 줄인다.
- 문어체보다 자연스러운 설명체를 사용한다.
- 같은 표현을 반복하지 않는다.
- 추상적인 설명 뒤에는 구체적인 사례를 붙인다.
- 전문 용어를 사용한 직후 의미를 설명한다.

### 2.2 카드나 목록을 단순 나열하지 않는다

항목 이름과 설명을 그대로 반복하지 말고, 각 항목이 어떻게 연결되는지 설명한다.

예시:

> 식별자가 없으면 학생과 강의를 안정적으로 구분하기 어렵습니다. 그 결과 같은 이름과 강의 제목이 여러 행에 반복되고, 이름이 변경될 때 관련 행을 모두 수정해야 합니다. 여기에 제약조건까지 부족하면 중복 신청이나 잘못된 상태값도 막기 어렵습니다.

### 2.3 화면 위치에 의존하지 않는다

다음과 같은 표현은 사용하지 않는다.

- 화면 왼쪽을 보겠습니다.
- 오른쪽 카드에는 다음 내용이 있습니다.
- 위에서 아래로 살펴보겠습니다.
- 하단의 코드를 보겠습니다.

장표 배치가 변경되어도 사용할 수 있도록 개념과 내용 자체를 기준으로 설명한다.

## 3. 에스큐엘 설명 공통 기준

### 3.1 실행 여부와 결과의 정확성을 구분한다

모든 관련 장표에서 다음 관점을 유지한다.

> 문법적으로 실행된다 ≠ 요구사항에 맞는다  
> 숫자가 출력된다 ≠ 검증된 결과다

에스큐엘이 정상적으로 실행되더라도 다음을 확인한다.

- 무엇을 계산하려는가
- 어떤 테이블이 기준인가
- 결과의 한 행은 무엇을 의미하는가
- 포함되어야 할 대상이 빠지지 않았는가
- 같은 대상이 중복되지 않았는가
- 집계 함수가 실제 계산 대상을 세고 있는가
- 예상 결과와 실제 결과가 일치하는가

### 3.2 요구사항을 먼저 해석한 뒤 에스큐엘을 설명한다

문법부터 설명하지 않고 먼저 다음을 확인한다.

- 계산 또는 조회 대상은 무엇인가
- 반드시 포함해야 하는 대상은 무엇인가
- 제외 조건은 무엇인가
- 기준 테이블은 무엇인가
- 필요한 관계와 조인 조건은 무엇인가

예시 요구사항:

> 전체 학생 수를 계산하되 질문이 없는 학생도 포함한다.

해석:

- 계산 대상은 질문이 아니라 학생이다.
- 질문 작성 여부와 관계없이 모든 학생을 포함해야 한다.
- 기준 테이블은 학생 테이블이다.
- 질문 테이블을 불필요하게 조인하면 누락이나 중복이 생길 수 있다.

### 3.3 집계에서는 한 행의 의미를 반드시 설명한다

`COUNT(*)`는 현재 조회 결과에 존재하는 행의 수를 센다. 따라서 다음 질문을 강조한다.

> 현재 결과의 한 행은 학생 한 명인가, 질문 한 개가 연결된 행인가?

조인 이후에는 한 학생이 여러 행으로 나타날 수 있으므로, 숫자가 같더라도 의미가 다를 수 있음을 설명한다.

### 3.4 조인 설명에서는 누락, 중복, 의미 오류를 함께 다룬다

- **누락:** 연결되는 행이 없는 대상은 결과에서 빠질 수 있다.
- **중복:** 하나의 대상과 여러 행이 연결되면 같은 대상이 반복될 수 있다.
- **의미 오류:** 계산 결과가 원래 대상 수가 아니라 조인된 결과 행 수가 될 수 있다.

조인의 정의만 설명하지 말고, 조인 이후 데이터의 의미가 어떻게 달라지는지 설명한다.

### 3.5 코드를 한 글자씩 읽지 않는다

코드 전체를 낭독하기보다 다음을 중심으로 설명한다.

- 어떤 테이블을 기준으로 조회하는가
- 어떤 조건으로 연결하는가
- 어떤 행이 남거나 제외되는가
- 집계 결과가 무엇을 의미하는가
- 요구사항과 어떤 차이가 있는가

## 4. 데이터 모델링 설명 공통 기준

### 4.1 서로 다른 업무 대상을 구분한다

에이아이가 만든 테이블 구조를 검토할 때 다음을 확인한다.

- 학생, 강의, 강사, 수강신청처럼 서로 다른 대상을 한 테이블에 섞지 않았는가
- 각 대상을 식별하는 기본키가 있는가
- 테이블 간 관계를 표현하는 외래키가 있는가
- 이름이나 제목을 관계 연결 기준으로 사용하지 않았는가
- 같은 정보가 여러 행에 반복되지 않는가
- 하나의 값을 변경할 때 여러 행을 수정해야 하지 않는가

### 4.2 식별자는 이름이나 제목과 구분한다

사람 이름이나 강의 제목은 중복되거나 변경될 수 있다. 따라서 안정적인 관계를 관리하려면 별도의 식별자가 필요하다는 점을 설명한다.

### 4.3 구조적 문제를 실제 운영 문제로 연결한다

단순히 정규화가 필요하다고 말하지 않고 다음 문제로 연결한다.

- **반복 저장:** 같은 강의명과 강사명이 여러 행에 반복된다.
- **수정 이상:** 강사명이 바뀌면 관련된 모든 행을 수정해야 한다.
- **불일치:** 일부 행만 수정되면 같은 대상을 서로 다르게 기록할 수 있다.
- **삽입 문제:** 연결 데이터가 없으면 기준 정보를 저장하기 어려울 수 있다.
- **삭제 문제:** 마지막 연결 행을 삭제하면서 기준 정보까지 사라질 수 있다.
- **규칙 적용 문제:** 중복 신청, 필수값, 허용 상태 등을 제한하기 어렵다.

## 5. 에이아이와 사람의 역할 구분

### 5.1 에이아이가 잘하는 일

- 테이블 구조 초안 생성
- 에스큐엘 초안 작성
- 문법 오류 설명
- 코드 수정안 제안
- 여러 해결 방법 제시

### 5.2 사람이 담당해야 하는 일

- 업무 규칙 정의
- 포함 대상과 제외 대상 결정
- 기준 테이블 선택
- 데이터 관계 판단
- 예상 결과 설정
- 실행 결과 검증
- 보안과 운영 책임 판단

스크립트는 `에이아이가 만들었기 때문에 맞다`는 인상을 주지 않는다.

## 6. 기술 용어 발음 규칙

화면에는 영문 용어를 표시하더라도 스크립트에는 실제 발표할 때의 한글 발음을 사용한다.

| 화면 표시 | 스크립트 표기 |
|---|---|
| AI | 에이아이 |
| SQL | 에스큐엘 |
| JOIN | 조인 |
| INNER JOIN | 이너 조인 |
| NULL | 널 |
| DBMS | 디비엠에스 |
| RDBMS | 알디비엠에스 |
| NoSQL | 노에스큐엘 |
| PostgreSQL | 포스트그레스큐엘 |
| DBeaver | 디비버 |
| ERD | 이알디 |
| COUNT(*) | 카운트 별표 |
| ID | 아이디 |

새로운 약어가 추가되면 같은 방식으로 발음 가능한 한글 표기를 우선 사용한다.

## 7. 장표 간 연결 규칙

### 7.1 이전 장표의 결론을 자연스럽게 이어받는다

각 장표는 독립적으로 이해할 수 있어야 하지만, 전체 수업 흐름도 이어져야 한다.

예시 흐름:

1. 실행되는 에스큐엘과 올바른 에스큐엘은 다르다.
2. 요구사항을 먼저 정확히 읽는다.
3. 에이아이가 제안한 에스큐엘을 검토한다.
4. 이너 조인의 누락과 중복 문제를 확인한다.
5. 숫자가 우연히 같을 수 있음을 확인한다.
6. 학생 수는 학생 테이블에서 계산한다.
7. 결과 숫자를 검증하는 기준을 정리한다.
8. 에이아이가 만든 테이블 구조도 검증한다.
9. 한 테이블에 모든 정보를 넣을 때의 문제를 살펴본다.

### 7.2 다음 장표의 내용을 미리 모두 설명하지 않는다

현재 장표의 핵심을 마무리한 뒤, 필요한 경우 다음 학습 내용으로 이어지는 한 문장만 사용한다.

## 8. 권장 스크립트 구조

```text
이번 장표에서는 [핵심 주제]를 설명합니다.

먼저 [코드·구조·요구사항]이 무엇을 의미하는지 설명합니다.

이 방식에서는 [누락·중복·변경·불일치] 문제가 발생할 수 있습니다.
구체적인 사례를 통해 문제가 발생하는 과정을 설명합니다.

따라서 [업무 요구사항 또는 데이터 의미]를 기준으로
[확인해야 할 판단 기준]을 검토해야 합니다.

정리하면 [이 장표의 핵심 결론]입니다.
```

이 구조를 기계적으로 반복하지 말고, 장표의 성격에 따라 자연스럽게 조정한다.

## 9. 분량 기준

- 일반 개념 장표: 약 30초에서 60초
- 사례 또는 코드 분석 장표: 약 45초에서 90초
- 전환 또는 정리 장표: 약 20초에서 40초
- 장표 정보량에 따라 조정하되, 불필요한 반복으로 분량을 늘리지 않는다.

## 10. 레포지토리 반영 규칙

### 10.1 장표 번호와 배열 인덱스를 구분한다

장표 번호가 `N`이면 배열 인덱스는 일반적으로 `N - 1`이다.

예시:

- 18번 장표 → `window.CH1_SLIDES[17]`
- 19번 장표 → `window.CH1_SLIDES[18]`

### 10.2 스크립트는 `s` 속성에 명시적으로 작성한다

자동 생성되는 공통 문구에 의존하지 않고, 중요한 장표에는 명시적인 스크립트를 제공한다.

```javascript
if (window.CH1_SLIDES[17]) {
  window.CH1_SLIDES[17].s = `장표별 강의 스크립트`;
}
```

### 10.3 최신 파일과 SHA를 확인한 뒤 수정한다

- 수정 전에 대상 파일의 현재 내용을 가져온다.
- 현재 SHA를 사용해 업데이트한다.
- 같은 파일에 대한 연속 수정은 최신 content SHA를 사용한다.
- 기존 파일을 덮어쓰기 전에 다른 변경사항이 없는지 확인한다.

### 10.4 HTML 로드 여부를 확인한다

별도의 패치 파일을 만들었으면 발표자료 HTML에서 실제로 로드되는지 확인한다.

```html
<script src="chapter01_script_patch.js"></script>
```

### 10.5 개별 패치 파일을 과도하게 늘리지 않는다

유지보수를 위해 장표마다 새 파일을 만드는 방식보다 하나의 스크립트 패치 파일에 장표별 명시적 스크립트를 통합하는 방식을 우선한다.

### 10.6 화면 표시와 발표 스크립트를 구분한다

- 장표 화면: `AI`, `SQL`, `JOIN`, `PostgreSQL` 등 영문 표기
- 발표 스크립트: `에이아이`, `에스큐엘`, `조인`, `포스트그레스큐엘` 등 실제 발음 표기

## 11. 최종 검수 체크리스트

- [ ] 장표 제목과 본문을 그대로 이어 붙이지 않았는가
- [ ] 한 장표의 핵심 메시지가 분명한가
- [ ] 원인과 결과가 자연스럽게 연결되는가
