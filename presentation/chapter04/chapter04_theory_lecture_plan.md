# Chapter 04 이론 발표 강의안

## 관계형 데이터베이스와 SQL 시작하기

> 목적: 초보자가 첫 테이블을 만들고 `INSERT`, `SELECT`, `WHERE`, `NULL`, `ORDER BY`, `UPDATE`, `DELETE`의 의미를 단순 문법이 아니라 데이터 변화와 검증 흐름으로 이해하도록 설명한다.  
> 기준: 학습자가 “SQL을 실행했다”가 아니라 “어떤 행이 추가·조회·수정·삭제될지 예상하고, 실제 결과를 확인했다”라고 말할 수 있어야 한다.

## 1. Chapter 04는 첫 번째 데이터 변경 수업입니다

**화면 구성**

- 큰 제목: 관계형 데이터베이스와 SQL 시작하기
- 흐름 그림:

핵심은 SQL을 많이 외우는 것이 아닙니다. SQL을 실행하기 전에 무엇이 바뀔지 예상하고, 실행 후 실제 행 수와 결과가 예상과 맞는지 확인하는 습관을 만드는 것입니다.

SELECT current_database();

위치 확인은 귀찮은 절차가 아니라 다른 데이터베이스나 스키마에 객체를 만드는 사고를 막는 안전장치입니다.

## 3. CRUD와 SQL 명령을 구분합니다

**화면 구성**

| CRUD | SQL | 의미 |
| --- | --- | --- |
| Create | `INSERT` | 새 행 추가 |
| Read | `SELECT` | 행 조회 |
| Update | `UPDATE` | 기존 행 수정 |
| Delete | `DELETE` | 기존 행 삭제 |

보조 문구:

```text
CREATE TABLE은 CRUD의 Create가 아니라 테이블 구조 생성입니다.
```

**발표 스크립트**

초보자가 자주 헷갈리는 부분은 CRUD의 Create와 SQL의 `CREATE TABLE`입니다.

CRUD에서 Create는 새 데이터를 추가한다는 뜻이며 SQL에서는 `INSERT`가 여기에 해당합니다. 반면 `CREATE TABLE`은 데이터를 추가하는 것이 아니라 데이터를 담을 구조를 만드는 명령입니다.

이번 장에서는 구조를 먼저 만든 뒤 실제 데이터 행을 다루는 네 가지 CRUD를 차례대로 확인합니다.

## 4. `students` 테이블의 한 행 의미를 먼저 정합니다

**화면 구성**

```text
Table: public.students
한 Row: 학생 한 명
PK: id
Columns: id, name, email, major, grade, created_at
```

**발표 스크립트**

테이블을 만들기 전에 반드시 정해야 하는 것이 한 행이 무엇을 의미하는가입니다.

`students` 테이블에서 한 행은 학생 한 명입니다. 이 기준이 있어야 `COUNT(*)`가 무엇을 세는지, `UPDATE`가 몇 명을 바꾸는지, `DELETE`가 어떤 학생을 삭제하는지 판단할 수 있습니다.

SQL 문법보다 먼저 한 행의 의미를 정하는 것이 좋은 데이터베이스 학습의 출발점입니다.

## 5. `CREATE TABLE`은 구조와 규칙을 함께 정의합니다

**화면 구성**

```sql
CREATE TABLE public.students (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    major VARCHAR(100),
    grade INTEGER,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

강조:

```text
id → 내부 식별자
NOT NULL → 값 필수
UNIQUE → 같은 값 중복 금지
DEFAULT → 생략 시 기본값
```

**발표 스크립트**

이 SQL은 단순히 빈 표를 만드는 명령이 아닙니다. 어떤 열이 있고 각 열에 어떤 종류의 값이 들어가며 어떤 규칙을 지켜야 하는지 함께 정의합니다.

`id`는 내부 식별자입니다. `name`과 `email`은 반드시 있어야 하며, 이메일에는 `UNIQUE`가 있어 같은 문자열의 중복을 막습니다. `major`와 `grade`는 값을 모르면 생략할 수 있고 이 경우 `NULL`이 저장됩니다.

---

## 6. IDENTITY 값은 학생 수가 아닙니다

**화면 구성**

```text
id = 행을 구분하는 내부 식별자
COUNT(*) = 현재 행 수
```

```text
자동 생성 id는 빈틈없는 업무 번호를 보장하지 않습니다.
```

**발표 스크립트**

자동 생성되는 `id`는 학생 수가 아닙니다.

입력 실패, 삭제 또는 트랜잭션 취소 같은 상황에서 번호 사이에 빈 구간이 생길 수 있습니다. 따라서 가장 큰 `id`를 학생 수로 해석하면 안 됩니다.

학생 수는 `COUNT(*)`로 확인하고, 업무상 학번이 필요하면 별도 열로 설계해야 합니다.

## 7. `INSERT`는 새 행을 추가하고 결과를 확인합니다

**화면 구성**

```sql
INSERT INTO public.students (name, email, major, grade)
VALUES ('김민지', 'minji@example.com', '컴퓨터공학', 2)
RETURNING id, name, created_at;
```

확인 포인트:

```text
추가 행 수
자동 생성 id
기본값 created_at
```

**발표 스크립트**

`INSERT`는 새 행을 추가합니다. 여기서는 `name`, `email`, `major`, `grade`를 직접 입력하고 `id`, `created_at`은 PostgreSQL이 결정합니다.

`RETURNING`을 사용하면 방금 추가된 행의 자동 생성 값을 바로 확인할 수 있습니다. 다만 실제 `id`가 반드시 1일 것이라고 미리 단정하지는 않습니다.

Chapter 04의 단계별 입력 파일은 여러 INSERT를 하나의 트랜잭션으로 묶어 중간 실패로 부분 입력 상태가 남는 위험도 줄입니다.

---

## 8. `NULL`은 0이나 빈 문자열이 아닙니다

**화면 구성**

```text
NULL = 값이 없거나 아직 알려지지 않은 상태
0 = 실제 숫자 값
'' = 실제 빈 문자열 값
```

```sql
WHERE major IS NULL
```

**발표 스크립트**

전공이나 학년을 모르는 학생은 값을 생략할 수 있고 이때 `NULL`이 저장됩니다.

`NULL`은 0도 아니고 빈 문자열도 아닙니다. 그래서 `major = NULL`처럼 일반 값과 비교하듯 쓰면 원하는 행을 찾지 못합니다.

`NULL` 여부는 `IS NULL` 또는 `IS NOT NULL`로 확인합니다. `NULL`을 포함한 비교가 왜 특별한지는 심화 학습에서 3값 논리로 연결합니다.

---

## 9. `SELECT`는 어떤 열과 어떤 행을 볼지 정합니다

**화면 구성**

```sql
SELECT id, name, email, major
FROM public.students
ORDER BY id ASC;
```

검증 질문:

```text
반환 Column은 무엇인가?
반환 Row 수는 몇 개인가?
ORDER BY가 있는가?
```

**발표 스크립트**

`SELECT`는 저장된 데이터를 조회합니다. 처음 확인할 때 `SELECT *`가 편리할 수 있지만 필요한 열을 명시하면 결과의 의미가 더 분명해집니다.

또 `ORDER BY`가 없으면 조회 결과의 순서는 보장되지 않습니다. 순서가 필요하면 정렬 기준을 명시하고, 동률이 가능하면 `id` 같은 보조 기준을 사용합니다.

---

## 10. `WHERE`는 행을 고르는 기준입니다

**화면 구성**

```sql
SELECT id, name, grade
FROM public.students
WHERE grade >= 3
ORDER BY grade DESC, id ASC;
```

```text
조건: grade가 3 이상
정렬: 높은 학년 먼저, 같으면 id 오름차순
```

**발표 스크립트**

`WHERE`는 조건에 맞는 행만 남깁니다.

SQL을 실행하기 전에 조건을 말로 풀어 설명하고 예상 행을 생각해 봅니다. 그다음 실제 반환 행과 비교합니다. 이 습관이 있어야 문법이 맞지만 요구사항과 다른 SQL을 발견할 수 있습니다.

---

## 11. `AND`, `OR`, `IN`은 조건 범위를 바꿉니다

**화면 구성**

```sql
WHERE major = '컴퓨터공학'
  AND (grade = 2 OR grade = 3)
```

```text
AND와 OR를 함께 쓰면 괄호로 의도를 표시합니다.
```

**발표 스크립트**

`AND`는 모든 조건을 만족해야 하고 `OR`는 하나 이상을 만족하면 됩니다. 같은 열을 여러 값과 비교할 때는 `IN`이 읽기 쉬울 수 있습니다.

`AND`와 `OR`를 함께 사용하면 연산 우선순위를 암기하는 것보다 괄호로 의도를 명확히 표시하는 습관이 좋습니다.

---

## 12. 문자열 검색은 `LIKE`, 대소문자 무시는 `ILIKE`입니다

**화면 구성**

```sql
WHERE name LIKE '김%'
WHERE email ILIKE '%EXAMPLE.COM'
```

```text
% = 0개 이상의 문자
_ = 정확히 한 문자
```

**발표 스크립트**

`LIKE`는 문자열 패턴 검색에 사용합니다. `%`는 0개 이상의 문자, `_`는 정확히 한 문자를 의미합니다.

`ILIKE`는 PostgreSQL에서 대소문자를 구분하지 않는 검색에 사용할 수 있습니다. 다른 DBMS에서는 지원 방식이 다를 수 있으므로 PostgreSQL 선택 기능으로 구분합니다.

---

## 13. `ORDER BY`와 `LIMIT`는 함께 생각합니다

**화면 구성**

```sql
SELECT *
FROM public.students
ORDER BY created_at DESC, id DESC
LIMIT 3;
```

```text
ORDER BY = 어떤 순서인가
LIMIT = 그중 몇 행인가
```

**발표 스크립트**

`LIMIT`은 몇 행을 가져올지 정하지만, 그 전에 어떤 순서에서 자를지 결정해야 합니다.

여러 행의 `created_at`이 같을 수 있으므로 `id DESC`를 보조 정렬 기준으로 둡니다. 최신 3명처럼 순서가 중요한 질문에서는 정렬 기준과 동률 처리 기준을 함께 확인합니다.

---

## 14. `UPDATE`는 대상 확인 후 실행합니다

**화면 구성**

```text
수정 전 SELECT
→ UPDATE ... RETURNING
→ 영향받은 Row 수 확인
→ 수정 후 SELECT
```

```sql
UPDATE public.students
SET grade = 4
WHERE email = 'junho@example.com'
RETURNING id, name, grade;
```

**발표 스크립트**

`UPDATE`는 기존 행의 값을 바꾸므로 조회보다 더 조심해야 합니다.

먼저 같은 `WHERE`로 대상이 이준호 한 명인지 확인합니다. 그다음 `UPDATE ... RETURNING`으로 실제 수정된 행을 확인하고 마지막으로 다시 조회합니다.

단계별 SQL 파일은 현재 데이터베이스와 초기 데이터 상태를 먼저 검사하므로 잘못된 상태에서 변경을 진행하는 위험도 줄입니다.

---

## 15. `DELETE`도 대상 확인 후 실행합니다

**화면 구성**

```text
삭제 전 SELECT
→ DELETE ... RETURNING
→ 영향받은 Row 수 확인
→ 삭제 후 SELECT 0행 확인
```

```sql
-- 실행하지 않는 전체 삭제 예
-- DELETE FROM public.students;
```

**발표 스크립트**

`DELETE`는 행을 삭제합니다. 삭제 전에는 같은 조건으로 대상 행을 확인하고, `DELETE ... RETURNING`으로 실제 삭제된 행이 맞는지 확인합니다. 마지막으로 같은 조건을 다시 조회해 0행인지 확인합니다.

`WHERE` 없는 `DELETE`는 모든 행을 삭제할 수 있으므로 실행 금지 예제로만 다룹니다.

## 16. 데이터 상태를 자연어로 구분합니다

**화면 구성**

| 상태 | 학생 수 | 이준호 학년 | 박서연 |
| --- | ---: | ---: | --- |
| 초기 데이터 상태 | 6 | 3 | 존재 |
| 수정 실습 후 상태 | 6 | 4 | 존재 |
| 삭제 실습 후 상태 | 5 | 4 | 삭제 |

**발표 스크립트**

실습 중 데이터 상태가 계속 바뀌기 때문에 어느 상태를 기준으로 SQL을 해석하는지가 중요합니다.

기존의 체크포인트 A·B·C 같은 기호 대신 실제 의미가 바로 보이는 `초기 데이터 상태`, `수정 실습 후 상태`, `삭제 실습 후 상태`를 사용합니다.

문제나 예제를 실행하기 전에 현재 상태가 무엇인지 먼저 확인하면 예상 결과가 달라지는 이유를 쉽게 찾을 수 있습니다.

## 17. AI가 만든 SQL도 같은 기준으로 검토합니다

**화면 구성**

```text
현재 데이터 상태
사용 Table과 Column
WHERE 조건
NULL 포함 여부
예상 Row 수
ORDER BY 안정성
변경 SQL 위험
```

**발표 스크립트**

AI가 만든 SQL도 사람이 작성한 SQL과 같은 기준으로 검토합니다.

현재 데이터 상태가 무엇인지 확인하고, 어떤 테이블과 열을 사용하는지, 조건이 요구사항과 맞는지, `NULL` 때문에 빠지는 행은 없는지, 예상 행 수는 몇 개인지 확인합니다.

특히 `UPDATE`와 `DELETE`는 바로 실행하지 않고 같은 조건의 `SELECT`를 먼저 실행합니다.

## 18. Chapter 04의 핵심은 문법보다 검증 습관입니다

**화면 구성**

```text
SQL 읽기
→ 예상 결과 작성
→ 실행 위치·범위 확인
→ 실행
→ 반환·영향 Row 확인
→ 재조회
→ 예상과 실제 비교
```

**발표 스크립트**

Chapter 04에서 배운 명령은 앞으로 계속 반복됩니다. 하지만 더 중요한 것은 실행 습관입니다.

SQL을 읽고 예상 결과를 적고, 현재 위치와 실행 범위를 확인하고, 실행 후 반환 행과 영향받은 행 수를 확인하고, 실제 데이터를 다시 조회합니다.

이 습관이 있어야 이후 JOIN, 트랜잭션, 인덱스, 그리고 AI SQL 검토까지 안전하게 이어갈 수 있습니다.
