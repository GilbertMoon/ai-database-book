- 주의: 같은 이름의 테이블이 다른 스키마에 있을 수 있음

**스크립트**

그래서 `CREATE TABLE`보다 먼저 현재 데이터베이스, 현재 스키마, 검색 경로를 확인합니다. 이 확인은 귀찮은 절차가 아니라 실습 사고를 막는 안전장치입니다.

## 3. CRUD와 SQL 명령을 구분합니다

**화면 구성**

| CRUD | SQL | 의미 |
| --- | --- | --- |
| Create | `INSERT` | 새 행 추가 |
| Read | `SELECT` | 행 조회 |
| Update | `UPDATE` | 기존 행 수정 |
| Delete | `DELETE` | 기존 행 삭제 |

보조 문구:

```text
CREATE TABLE은 CRUD의 Create가 아니라 테이블 구조 생성입니다.
```

**스크립트**

초보자가 가장 자주 헷갈리는 부분은 CRUD의 Create와 SQL의 `CREATE TABLE`입니다.

CRUD에서 Create는 새 데이터를 추가한다는 뜻입니다. SQL에서는 보통 `INSERT`가 여기에 해당합니다. 반면 `CREATE TABLE`은 데이터를 추가하는 것이 아니라 데이터를 담을 구조를 만드는 명령입니다.

오늘은 구조를 만드는 `CREATE TABLE`을 먼저 사용한 뒤, 실제 데이터 행을 다루는 `INSERT`, `SELECT`, `UPDATE`, `DELETE`를 차례대로 확인합니다.

## 4. `students` 테이블의 한 행 의미를 먼저 정합니다

**화면 구성**

```text
테이블: public.students
한 행: 학생 한 명
기본키: id
열: id, name, email, major, grade, created_at
```

**스크립트**

테이블을 만들기 전에 반드시 정해야 하는 것이 있습니다. 바로 한 행이 무엇을 의미하는가입니다.

이번 장의 `students` 테이블에서 한 행은 학생 한 명입니다. 이 기준이 있어야 `COUNT(*)`가 무엇을 세는지, `UPDATE`가 몇 명의 학생을 바꾸는지, `DELETE`가 어떤 학생을 삭제하는지 판단할 수 있습니다.

SQL 문법보다 먼저 한 행의 의미를 정하는 것이 좋은 데이터베이스 학습의 출발점입니다.

## 5. `CREATE TABLE`은 구조와 규칙을 함께 정의합니다

**화면 구성**

```sql
CREATE TABLE public.students (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    major VARCHAR(100),
    grade INTEGER,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

강조 표시:

- `id`: 내부 식별자
- `NOT NULL`: 반드시 입력
- `UNIQUE`: 중복 금지
- `DEFAULT`: 생략 시 기본값

**스크립트**

이 SQL은 단순히 빈 표를 만드는 명령이 아닙니다. 어떤 열이 있고, 각 열에 어떤 종류의 값이 들어가며, 어떤 값은 반드시 있어야 하고 어떤 값은 중복되면 안 되는지를 함께 정의합니다.

`id`는 학생을 구분하는 내부 식별자입니다. `name`과 `email`은 반드시 있어야 하므로 `NOT NULL`이 붙어 있습니다. `email`에는 `UNIQUE`가 있어 같은 이메일 문자열이 중복되지 않습니다.

`major`와 `grade`에는 `NOT NULL`이 없으므로 값을 모르면 생략할 수 있습니다. 이 경우에는 `NULL`이 저장됩니다.

## 6. IDENTITY 값은 학생 수가 아닙니다

**화면 구성**

```text
id = 행을 구분하는 내부 식별자
COUNT(*) = 현재 행 수
```

주의 문구:

```text
자동 생성 id는 빈틈없는 번호를 보장하지 않습니다.
```

**스크립트**

자동 생성되는 `id`는 학생 번호처럼 보이지만 학생 수를 의미하지 않습니다.

입력에 실패하거나, 데이터를 삭제하거나, 트랜잭션을 취소하는 과정에서 자동 번호에는 빈 구간이 생길 수 있습니다. 그래서 `id`의 최댓값을 학생 수로 해석하면 안 됩니다.

학생 수는 `COUNT(*)`로 확인하고, 업무상 학번이 필요하다면 `student_number` 같은 별도 열로 설계해야 합니다.

## 7. `INSERT`는 새 행을 추가하고 `RETURNING`으로 확인합니다

**화면 구성**

```sql
INSERT INTO public.students (name, email, major, grade)
VALUES ('김민지', 'minji@example.com', '컴퓨터공학', 2)
RETURNING id, name, created_at;
```

확인 포인트:

```text
추가 행 수
자동 생성 id
기본값 created_at
```

**스크립트**

`INSERT`는 테이블에 새 행을 추가하는 명령입니다.

여기서는 `name`, `email`, `major`, `grade`만 직접 입력합니다. `id`와 `created_at`은 입력하지 않았지만 PostgreSQL이 자동으로 만들어 줍니다.

`RETURNING`은 PostgreSQL에서 매우 유용한 기능입니다. 입력 후 다시 조회하지 않아도 방금 추가된 행의 자동 생성값을 확인할 수 있습니다.

## 8. `NULL`은 0이나 빈 문자열이 아닙니다

**화면 구성**

```text
NULL = 값이 없거나, 아직 알려지지 않았거나, 해당되지 않는 상태
0 = 실제 숫자 값
'' = 실제 빈 문자열 값
```

예시:

```sql
WHERE major IS NULL
```

**스크립트**

전공이나 학년을 아직 모르는 학생은 해당 열을 생략해 입력할 수 있습니다. 이때 저장되는 값이 `NULL`입니다.

`NULL`은 숫자 0도 아니고 빈 문자열도 아닙니다. 값이 아직 없거나 알려지지 않았거나 해당되지 않는 상태를 표현합니다.

그래서 `major = NULL`처럼 일반 값과 비교하듯 쓰면 원하는 결과가 나오지 않습니다. `NULL` 여부는 `IS NULL` 또는 `IS NOT NULL`로 확인해야 합니다.

## 9. `SELECT`는 어떤 열과 어떤 행을 볼지 정하는 명령입니다

**화면 구성**

```sql
SELECT id, name, email, major
FROM public.students
ORDER BY id ASC;
```

검증 질문:

```text
반환 열은 무엇인가?
반환 행 수는 몇 개인가?
ORDER BY가 있는가?
```

**스크립트**

`SELECT`는 데이터를 조회하는 명령입니다. `SELECT *`는 모든 열을 가져오기 때문에 초급 실습에서는 편리하지만, 실제 분석이나 애플리케이션에서는 필요한 열을 명시하는 것이 좋습니다.

또 하나 중요한 점은 행 순서입니다. `ORDER BY`가 없으면 조회 결과의 순서는 보장되지 않습니다. 화면에서 입력 순서대로 보이는 것 같아도 그 순서에 의존하면 안 됩니다.

순서가 필요하면 `ORDER BY`를 명시하고, 같은 값이 있을 수 있으면 `id` 같은 보조 기준을 함께 둡니다.

---

## 10. `WHERE`는 행을 고르는 기준입니다

**화면 구성**

```sql
SELECT *
FROM public.students
WHERE grade >= 3
ORDER BY grade DESC, id ASC;
```

예상:

```text
조건: grade가 3 이상
정렬: 높은 학년 먼저, 같으면 id 오름차순
```

**스크립트**

`WHERE`는 조건에 맞는 행만 남기는 역할을 합니다.

이 SQL은 모든 학생을 보는 것이 아니라 `grade`가 3 이상인 학생만 조회합니다. 그리고 학년이 큰 학생부터 정렬하고, 같은 학년이면 `id`가 작은 학생을 먼저 보여 줍니다.

실행 전에 조건과 정렬 기준을 말로 풀어 설명할 수 있어야 합니다. 그래야 실행 결과가 맞는지 판단할 수 있습니다.

---

## 11. `AND`, `OR`, `IN`은 조건의 범위를 바꿉니다

**화면 구성**

```sql
WHERE major = '컴퓨터공학'
  AND (grade = 2 OR grade = 3)
```

보조 문구:

```text
AND와 OR를 함께 쓰면 괄호로 의도를 표시합니다.
```

**스크립트**

조건이 하나일 때는 비교적 쉽습니다. 하지만 `AND`와 `OR`가 함께 나오면 조건 범위가 헷갈리기 쉽습니다.

`AND`는 두 조건을 모두 만족해야 하고, `OR`는 둘 중 하나 이상을 만족하면 됩니다. 문제는 두 연산자가 함께 있을 때입니다.

SQL은 보통 `AND`를 `OR`보다 먼저 평가합니다. 그래서 문법 오류가 없더라도 사람이 의도한 범위와 다르게 읽힐 수 있습니다. 초보 단계에서는 괄호를 사용해 의도를 명확하게 표현하는 습관이 중요합니다.

## 12. 문자열 검색은 `LIKE`, 대소문자 무시는 PostgreSQL의 `ILIKE`입니다

**화면 구성**

```sql
WHERE name LIKE '김%'
WHERE email ILIKE '%EXAMPLE.COM'
```

패턴:

```text
% = 0개 이상의 문자
_ = 정확히 한 문자
```

**스크립트**

`LIKE`는 문자열의 일부가 일치하는 행을 찾을 때 사용합니다.

`김%`는 김으로 시작하는 이름을 찾습니다. `%민%`은 중간에 민이 들어가는 값을 찾습니다. `_`는 아무 문자 하나를 뜻합니다.

`ILIKE`는 PostgreSQL에서 제공하는 대소문자 구분 없는 패턴 검색입니다. 다른 DBMS에서는 같은 문법이 없을 수 있으므로, 이 기능은 PostgreSQL 문법이라는 점을 함께 기억합니다.

## 13. `ORDER BY`와 `LIMIT`는 함께 생각해야 합니다

**화면 구성**

```sql
SELECT *
FROM public.students
ORDER BY created_at DESC, id DESC
LIMIT 3;
```

핵심:

```text
ORDER BY = 어떤 순서인가
LIMIT = 그중 몇 행인가
```

**스크립트**

`LIMIT`는 몇 행만 가져오는 명령입니다. 하지만 어떤 순서에서 몇 행을 가져올지 정하지 않으면 결과가 안정적이지 않을 수 있습니다.

그래서 `LIMIT 3`만 보는 것이 아니라 반드시 `ORDER BY`를 함께 봐야 합니다. 여기서는 등록 시각이 최신인 학생부터 가져오되, 등록 시각이 같을 수 있으므로 `id DESC`를 보조 정렬 기준으로 사용합니다.

최신 3명처럼 순서가 중요한 질문에서는 정렬 기준과 동률 처리 기준을 함께 명시해야 합니다.

## 14. `UPDATE`는 세 단계로 실행합니다

**화면 구성**

```text
수정 전 SELECT
→ UPDATE ... RETURNING
→ 수정 후 SELECT
```

예시:

```sql
UPDATE public.students
SET grade = 4
WHERE email = 'junho@example.com'
RETURNING id, name, grade;
```

**스크립트**

`UPDATE`는 기존 행을 수정하는 명령입니다. 그래서 조회보다 더 조심해야 합니다.

먼저 같은 `WHERE` 조건으로 수정 대상이 누구인지 확인합니다. 그다음 `UPDATE`를 실행하고 `RETURNING`으로 실제 바뀐 행을 확인합니다. 마지막으로 다시 `SELECT`해서 데이터가 의도대로 바뀌었는지 확인합니다.

특히 자동 커밋 상태에서는 실행 직후 변경이 확정될 수 있습니다. 일반 문서 편집처럼 실행 취소하면 된다고 생각하면 안 됩니다.

---

## 15. `DELETE`도 세 단계로 실행합니다

**화면 구성**

```text
삭제 전 SELECT
→ DELETE ... RETURNING
→ 삭제 후 SELECT
```

위험 예시:

```sql
DELETE FROM public.students;
```

**스크립트**

`DELETE`는 행을 삭제합니다. 테이블 구조는 남지만 데이터 행이 사라집니다.

삭제 전에는 반드시 대상 행을 `SELECT`로 확인해야 합니다. 그다음 `DELETE ... RETURNING`으로 실제 삭제된 행을 확인하고, 마지막으로 같은 조건으로 다시 조회해 0행이 되었는지 확인합니다.

`WHERE` 없는 `DELETE`는 모든 행을 삭제합니다. 문법적으로 맞는 SQL과 실행해도 되는 SQL은 다르다는 점을 여기서 반드시 기억해야 합니다.

## 16. 체크포인트로 기준 데이터 상태를 고정합니다

**화면 구성**

| 체크포인트 | 기준 상태 |
| --- | --- |
| A | 6명 입력 완료 |
| B | 이준호 grade 4 수정 |
| C | 박서연 삭제 후 5명 |

**스크립트**

이번 장은 실습 중간에 데이터 상태가 바뀝니다. 그래서 어느 시점을 기준으로 문제를 푸는지가 중요합니다.

체크포인트 A는 샘플 학생 6명을 입력한 직후입니다. 체크포인트 B는 이준호의 학년을 4로 수정한 뒤입니다. 체크포인트 C는 박서연 학생을 삭제한 뒤입니다.

문제나 예제가 어느 체크포인트를 기준으로 하는지 확인하지 않으면 예상 결과가 달라집니다. 데이터베이스 실습에서는 기준 데이터 상태를 명확히 기록해야 합니다.

## 17. AI가 만든 SQL도 같은 기준으로 검토합니다

**화면 구성**

```text
사용 테이블과 열
WHERE 조건
NULL 포함 여부
예상 행 수
ORDER BY 안정성
변경 SQL의 위험
```

**스크립트**

AI가 만든 SQL도 사람이 작성한 SQL과 같은 기준으로 검토합니다.

어떤 테이블과 열을 사용하는지, 조건이 요구사항과 맞는지, `NULL`이 있을 때 빠지는 행은 없는지, 예상 행 수는 몇 개인지 확인합니다.

특히 `UPDATE`나 `DELETE`처럼 데이터를 바꾸는 SQL은 바로 실행하지 않습니다. 먼저 같은 조건의 `SELECT`로 대상 행을 확인하고, 영향받는 행 수와 자동 커밋 상태를 함께 봐야 합니다.

## 18. Chapter 04의 핵심은 문법보다 검증 습관입니다

**화면 구성**

```text
SQL 읽기
→ 예상 결과 작성
→ 실행 범위 확인
→ 실행
→ 행 수·RETURNING 확인
→ 재조회
```

**스크립트**

Chapter 04에서 배운 명령은 앞으로 계속 반복됩니다. `CREATE TABLE`, `INSERT`, `SELECT`, `WHERE`, `ORDER BY`, `UPDATE`, `DELETE`는 데이터베이스의 기본입니다.

하지만 더 중요한 것은 실행 습관입니다. SQL을 읽고, 예상 결과를 적고, 실행 범위를 확인하고, 실행 후 행 수와 실제 데이터를 비교해야 합니다.

이 습관이 있어야 이후 JOIN, 트랜잭션, 인덱스, AI SQL 검토까지 안전하게 이어갈 수 있습니다.
