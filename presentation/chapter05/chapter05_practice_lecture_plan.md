# Chapter 05 실습 발표 강의안

## 요구사항을 ERD와 PostgreSQL 구조로 검증하기

> 목적: 도서 대여 요구사항을 바탕으로 `members`, `books`, `loans` 구조를 만들고, 샘플 데이터와 검증 SQL로 관계가 실제로 표현되는지 확인한다.  
> 기준: 초보자가 “ERD를 작성했다”가 아니라 “요구사항이 어떤 테이블·열·관계로 구현되었고, 작은 데이터로 검증했다”라고 말할 수 있어야 한다.

---

## 1. 이번 실습은 SQL 작성보다 설계 검증이 핵심입니다

**화면 구성**

```text
요구사항 분석
→ ERD 초안
→ PostgreSQL DDL
→ 샘플 데이터 입력
→ 검증 SQL 실행
→ 요구사항 추적표 확인
```

**스크립트**

이번 실습은 단순히 SQL 파일을 실행하는 시간이 아닙니다. 요구사항을 읽고, 그 요구사항이 어떤 테이블과 열, 관계로 바뀌었는지 확인하는 실습입니다.

우리는 `members`, `books`, `loans` 세 테이블을 사용합니다. 그리고 샘플 데이터를 넣어 회원 한 명이 여러 대여 기록을 가질 수 있는지, 도서 한 권이 시간에 따라 여러 대여 기록을 가질 수 있는지 확인합니다.

실습의 목표는 오류 없이 실행하는 것만이 아닙니다. 실행 결과가 요구사항과 맞는지 설명할 수 있어야 합니다.

---

## 2. 실행 파일의 역할을 먼저 구분합니다

**화면 구성**

| 파일 | 역할 | 실행 시점 |
| --- | --- | --- |
| `library_schema.sql` | 테이블 생성 | 구조가 없을 때 |
| `library_seed.sql` | 샘플 데이터 입력 | 구조 생성 후 |
| `library_validation.sql` | 구조와 관계 검증 | 입력 후 반복 실행 |
| `reset_library.sql` | 초기화 | 정말 다시 시작할 때만 |

**스크립트**

실습 파일은 역할이 다릅니다. `library_schema.sql`은 테이블 구조를 만듭니다. `library_seed.sql`은 샘플 데이터를 넣습니다. `library_validation.sql`은 구조와 관계가 요구사항대로 표현되는지 확인합니다.

`reset_library.sql`은 주의해서 다루어야 합니다. 이 파일은 기존 테이블과 데이터를 삭제할 수 있으므로, 단순 오류 해결용으로 바로 실행하면 안 됩니다. 현재 데이터베이스와 스키마를 확인하고 정말 초기화가 필요한 경우에만 사용합니다.

---

## 3. 실행 위치를 먼저 확인합니다

**화면 구성**

```sql
SELECT current_database();
SELECT current_schema();
SHOW search_path;
```

**기대 기준**

```text
current_database = ai_database_book
스키마 = public 사용 가능
search_path 의미 확인
```

**스크립트**

테이블을 만들기 전에 반드시 현재 위치를 확인합니다. 같은 SQL이라도 다른 데이터베이스나 다른 스키마에서 실행하면 전혀 다른 위치에 테이블이 만들어질 수 있습니다.

이 책의 기본 실습은 `ai_database_book` 데이터베이스와 `public` 스키마를 기준으로 합니다. 따라서 현재 데이터베이스가 무엇인지, 현재 스키마와 검색 경로가 무엇인지 먼저 확인해야 합니다.

이 과정은 귀찮은 절차가 아니라 데이터를 잘못된 위치에 만드는 일을 막는 안전장치입니다.

## 4. 요구사항을 다시 읽고 확정·미확정 규칙을 표시합니다

**화면 구성**

```text
확정:
- 회원과 도서를 관리한다.
- 대여 기록은 회원과 도서를 연결한다.
- 대여일, 반납예정일, 실제반납일을 저장한다.
- 실제반납일은 비어 있을 수 있다.

미확정:
- 이메일 고유성
- ISBN 고유성
- 복본 관리
- 최대 대여 권수
- 삭제 정책
```

**스크립트**

실습에 들어가기 전에 요구사항을 다시 읽습니다. 확정된 규칙은 테이블과 관계에 반영합니다. 미확정 규칙은 질문 목록으로 남깁니다.

특히 이메일과 ISBN의 고유성은 아직 확정하지 않습니다. 그래서 Chapter 05의 DDL에는 `UNIQUE`가 없습니다. 이것은 중복을 허용한다는 뜻이 아니라, 아직 정책이 정해지지 않았다는 뜻입니다.

이 구분을 하지 않으면 AI나 사람이 임의로 제약조건을 추가해 실제 업무와 다른 설계를 만들 수 있습니다.

---

## 5. 텍스트 ERD를 먼저 확인합니다

**화면 구성**

```text
members
- id PK
- name
- email
- joined_at

books
- id PK
- title
- author
- published_year
- isbn

loans
- id PK
- member_id FK -> members.id
- book_id FK -> books.id
- borrowed_at
- due_at
- returned_at
```

**스크립트**

그림 ERD를 보기 전에 텍스트 ERD를 먼저 읽습니다. 텍스트로 구조를 설명할 수 있어야 그림도 제대로 이해할 수 있습니다.

`members`는 회원 한 명을 나타냅니다. `books`는 이 장의 범위에서 하나의 대여 대상 도서를 나타냅니다. `loans`는 회원과 도서 사이에서 발생한 대여 한 건을 나타냅니다.

`loans`의 `member_id`와 `book_id`는 각각 `members.id`, `books.id`를 참조합니다. 이 두 외래키가 관계를 실제 테이블 구조로 연결합니다.

---

## 6. 테이블 생성 순서를 설명한 뒤 실행합니다

**화면 구성**

```text
1. public.members
2. public.books
3. public.loans
```

**스크립트**

테이블 생성 순서는 중요합니다. `loans`는 `members`와 `books`를 참조합니다. 따라서 참조 대상인 부모 테이블이 먼저 만들어져야 합니다.

먼저 `members`를 만들고, 다음으로 `books`를 만듭니다. 마지막으로 두 테이블을 참조하는 `loans`를 만듭니다.

실행할 때는 파일 전체를 무심코 실행하기보다 현재 구간을 확인합니다. 이미 테이블이 있다면 같은 `CREATE TABLE`을 다시 실행하면 오류가 날 수 있습니다.

---

## 7. DDL에서 아직 구현하지 않은 정책을 확인합니다

**화면 구성**

```text
현재 구현:
- id PRIMARY KEY
- 필수값 NOT NULL
- loans.member_id, loans.book_id 참조

아직 보류:
- members.email UNIQUE
- books.isbn UNIQUE
- 날짜 선후 관계 CHECK
- 동시 활성 대여 차단
```

**스크립트**

Chapter 05의 DDL은 최종 운영용 완성본이 아닙니다. 요구사항에서 확정된 최소 구조를 PostgreSQL로 바꾼 초안입니다.

기본키와 필수값, 외래키 관계는 표현합니다. 하지만 이메일과 ISBN 고유성, 날짜 선후 관계, 같은 도서의 동시 활성 대여 차단 같은 규칙은 아직 확정 또는 구현하지 않았습니다.

이 규칙들은 Chapter 06에서 제약조건과 무결성 관점으로 다시 다룹니다. 지금은 “무엇을 구현했고, 무엇을 보류했는지”를 구분하는 것이 중요합니다.

## 8. 샘플 데이터는 관계 검증용으로 입력합니다

**화면 구성**

```text
members: 회원 2명
books: 도서 2권
loans: 대여 3건
```

**스크립트**

샘플 데이터는 단순히 표를 채우기 위한 것이 아닙니다. 관계가 실제로 표현되는지 확인하기 위한 작은 증거입니다.

회원 2명과 도서 2권을 넣고, 대여 기록 3건을 입력합니다. 이때 한 회원이 여러 대여 기록을 가질 수 있고, 한 도서가 시간에 따라 여러 대여 기록에 나타날 수 있어야 합니다.

샘플 데이터가 너무 많으면 구조 검증이 어려워집니다. 처음에는 작고 의도가 분명한 데이터가 좋습니다.

---

## 9. 입력 후 기준 행 수를 확인합니다

**화면 구성**

```text
members: 2행
books: 2행
loans: 3행
```

**스크립트**

샘플 입력 후에는 먼저 행 수를 확인합니다. `members`가 2행, `books`가 2행, `loans`가 3행이어야 합니다.

행 수 확인은 단순한 숫자 확인이 아닙니다. 뒤의 관계 검증과 요구사항 검토가 이 기준 데이터 위에서 진행되기 때문입니다.

만약 기대 행 수와 다르다면 이후 검증 결과도 달라질 수 있습니다. 이 경우 다음 단계로 넘어가기 전에 중복 실행, 입력 실패, 잘못된 연결 대상을 확인해야 합니다.

## 10. JOIN은 관계가 연결되는지 확인하는 용도로만 사용합니다

**화면 구성**

```sql
SELECT
    loans.id,
    members.name AS member_name,
    books.title AS book_title,
    loans.returned_at
FROM public.loans AS loans
JOIN public.members AS members
    ON loans.member_id = members.id
JOIN public.books AS books
    ON loans.book_id = books.id
ORDER BY loans.id;
```

**스크립트**

이 장에서 JOIN을 깊게 배우지는 않습니다. JOIN은 Chapter 08의 주요 주제입니다.

하지만 Chapter 05에서는 ERD의 관계가 실제 조회로 연결되는지 확인하기 위해 최소한의 JOIN을 사용합니다. `loans.member_id`를 통해 회원 이름을 가져오고, `loans.book_id`를 통해 도서 제목을 가져옵니다.

결과를 보면 대여 기록 한 건이 어떤 회원과 어떤 도서를 연결하는지 확인할 수 있습니다. 이것이 ERD가 실제 데이터 조회로 이어지는 첫 번째 증거입니다.

## 11. 1:N 관계를 작은 질문으로 검증합니다

**화면 구성**

```text
검증 질문
1. 한 회원이 여러 대여 기록을 가질 수 있는가?
2. 한 도서가 시간에 따라 여러 대여 기록을 가질 수 있는가?
3. 미반납 대여는 returned_at NULL로 표현되는가?
```

**스크립트**

모델이 맞는지 확인하려면 작은 질문을 던져야 합니다. 예를 들어 한 회원이 여러 대여 기록을 가질 수 있는지 확인합니다.

또 한 도서가 시간에 따라 여러 대여 기록에 나타날 수 있는지도 확인합니다. 이 구조가 가능해야 회원과 도서의 N:M 관계를 `loans` 사건 테이블로 푼 의미가 있습니다.

미반납 상태는 `returned_at`이 `NULL`인 행으로 표현합니다. 이 값은 대여 사건의 상태를 나타내는 중요한 속성입니다.

---

## 12. 요구사항 추적표와 실행 결과를 연결합니다

**화면 구성**

| 요구사항 | 구조 | 실행 증거 |
| --- | --- | --- |
| 회원 관리 | members | 회원 2행 조회 |
| 도서 관리 | books | 도서 2행 조회 |
| 여러 대여 | loans.member_id | 한 회원의 여러 대여 |
| 미반납 표현 | loans.returned_at | NULL 행 존재 |

**스크립트**

요구사항 추적표는 문서로만 끝나면 안 됩니다. 실제 실행 결과와 연결해야 합니다.

예를 들어 “회원을 관리한다”는 요구사항은 `members` 테이블과 회원 행 조회 결과로 확인합니다. “미반납 대여를 표현한다”는 요구사항은 `returned_at`이 `NULL`인 대여 행으로 확인합니다.

이렇게 요구사항, 설계 구조, 실행 증거가 연결되면 나중에 AI가 만든 설계나 SQL을 검토할 때도 훨씬 안전해집니다.

## 13. AI가 만든 설계는 실행 전 질문으로 검토합니다

**화면 구성**

```text
AI 초안 검토 질문
- 한 행의 의미가 분명한가?
- 관계를 양방향 문장으로 설명했는가?
- N:M을 사건 테이블로 풀었는가?
- 요구사항 없는 UNIQUE/CHECK/삭제 정책을 넣지 않았는가?
- 미확정 규칙을 질문 목록으로 분리했는가?
```

**스크립트**

AI가 만든 ERD나 DDL은 바로 실행하지 않습니다. 먼저 질문으로 검토합니다.

한 행의 의미가 분명한지, 어떤 테이블이 어떤 요구사항에서 나왔는지 확인합니다. 회원과 도서의 N:M 관계를 `loans` 같은 사건 테이블로 풀었는지도 봅니다.

또 요구사항에 없는 `UNIQUE`, `CHECK`, 삭제 정책을 임의로 넣지 않았는지 확인합니다. AI가 만든 초안도 요구사항 추적표와 작은 샘플 데이터로 검증해야 합니다.

## 14. 초기화 파일은 마지막 수단으로 사용합니다

**화면 구성**

```text
오류 발생
→ 현재 DB·스키마 확인
→ 중복 실행 여부 확인
→ 필요한 구간만 재실행
→ 정말 초기화가 필요할 때 reset_library.sql
```

**스크립트**

실습 중 오류가 나면 바로 초기화 파일을 실행하지 않습니다. 먼저 현재 데이터베이스와 스키마를 확인하고, 같은 구간을 중복 실행했는지 살펴봅니다.

`library_schema.sql`은 기존 테이블을 자동으로 삭제하지 않습니다. 그래서 같은 테이블이 이미 있으면 생성 오류가 날 수 있습니다. 이때 무조건 삭제하기보다 기존 데이터가 필요한지 먼저 판단해야 합니다.

정말 처음부터 다시 시작해야 할 때만 `reset_library.sql`을 사용합니다. 초기화는 데이터를 지우는 작업이므로 항상 현재 위치를 확인한 뒤 실행해야 합니다.

## 15. 실습 완료 기준을 숫자와 문장으로 확인합니다

**화면 구성**

```text
완료 기준
- members, books, loans 테이블 생성
- members 2행, books 2행, loans 3행 확인
- loans.member_id와 loans.book_id 관계 조회 가능
- 미반납 대여를 returned_at NULL로 표현
- 이메일·ISBN 고유성은 미확정으로 보류했음을 설명
- 요구사항 추적표와 실행 결과 연결
```

**스크립트**

실습 완료 기준은 “SQL 파일을 실행했다”가 아닙니다. 세 테이블이 생성되었고, 기대 행 수가 맞고, 관계 조회가 가능해야 합니다.

또 `returned_at`이 `NULL`인 행으로 미반납 상태를 표현할 수 있어야 합니다. 이메일과 ISBN 고유성은 아직 적용하지 않았다는 점도 설명할 수 있어야 합니다.

마지막으로 각 구조가 어느 요구사항에서 나왔고 어떤 실행 결과로 확인했는지 연결하면 Chapter 05 실습이 완료됩니다.
