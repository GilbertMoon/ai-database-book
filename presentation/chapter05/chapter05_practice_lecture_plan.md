# Chapter 05 실습 발표 강의안

## 요구사항을 ERD와 PostgreSQL 구조로 검증하기

> 목적: 도서 대여 요구사항을 바탕으로 `members`, `books`, `loans` 구조를 만들고, 번호형 SQL 파일과 작은 샘플 데이터로 관계가 실제로 표현되는지 확인한다.  
> 기준: 초보자가 “ERD를 작성했다”가 아니라 “요구사항이 어떤 테이블·열·관계로 구현되었고, 작은 데이터로 검증했다”라고 말할 수 있어야 한다.

---

## 1. 이번 실습은 SQL 작성보다 설계 검증이 핵심입니다

**화면 구성**

```text
요구사항 분석
→ ERD 초안
→ PostgreSQL DDL
→ 샘플 데이터 입력
→ 검증 SQL 실행
→ 요구사항 추적표 확인
```

**스크립트**

이번 실습은 단순히 SQL 파일을 실행하는 시간이 아닙니다. 요구사항을 읽고, 그 요구사항이 어떤 테이블과 열, 관계로 바뀌었는지 확인하는 실습입니다.

우리는 `members`, `books`, `loans` 세 테이블을 사용합니다. 샘플 데이터를 넣어 회원 한 명이 여러 대여 기록을 가질 수 있는지, 도서 한 건이 시간에 따라 여러 대여 기록을 가질 수 있는지 확인합니다.

실습의 목표는 오류 없이 실행하는 것만이 아닙니다. 실행 결과가 요구사항과 맞는지 설명할 수 있어야 합니다.

## 2. 번호형 실행 파일의 역할을 먼저 구분합니다

**화면 구성**

| 파일 | 역할 | 실행 시점 |
| --- | --- | --- |
| `01_library_schema.sql` | 테이블 생성 | 구조가 없을 때 |
| `02_library_seed.sql` | 샘플 데이터 입력 | 구조 생성 후 |
| `03_library_validation.sql` | 구조와 관계 검증 | 입력 후 반복 실행 |
| `reset_library.sql` | 초기화 | 정말 다시 시작할 때만 |

보조 문구:

```text
library_schema.sql / library_seed.sql / library_validation.sql
→ 기존 링크 호환용
→ 번호 파일과 중복 실행하지 않음
```

**스크립트**

처음 학습하는 독자는 번호형 파일을 순서대로 사용합니다. `01_library_schema.sql`은 구조를 만들고, `02_library_seed.sql`은 샘플 데이터를 입력하며, `03_library_validation.sql`은 구조와 관계를 반복 검증합니다.

기존 `library_*.sql` 파일은 예전 링크와 강의 자료 호환을 위해 유지하지만 번호형 파일과 같은 역할입니다. 같은 역할의 두 파일을 모두 실행하면 안 됩니다.

`reset_library.sql`은 기존 테이블과 데이터를 삭제하므로 단순 오류 해결용으로 바로 실행하지 않습니다.

## 5. 한 행의 의미와 텍스트 ERD를 먼저 확인합니다

**화면 구성**

```text
members 한 행 = 회원 한 명
books 한 행 = 대여 대상으로 관리하는 도서 한 건
loans 한 행 = 특정 회원이 특정 도서를 대여한 사건 한 건

members
- id PK
- name
- email
- joined_at

books
- id PK
- title
- author
- published_year
- isbn

loans
- id PK
- member_id FK -> members.id
- book_id FK -> books.id
- borrowed_at
- due_at
- returned_at
```

**스크립트**

그림 ERD보다 먼저 각 테이블의 한 행 의미를 설명합니다. `members`는 회원 한 명, `books`는 이 장에서 대여 대상으로 관리하는 도서 한 건, `loans`는 대여 사건 한 건입니다.

`loans.member_id`와 `loans.book_id`는 각각 `members.id`, `books.id`를 참조합니다. 외래키는 Chapter 05에서 관계를 실제 테이블 구조로 연결하면서 처음 본격적으로 사용합니다.

## 6. 관계를 양방향 문장으로 읽고 생성 순서를 정합니다

**화면 구성**

```text
한 회원은 0개 이상의 대여 기록을 가질 수 있다.
한 대여 기록은 정확히 한 회원을 참조한다.

한 도서는 0개 이상의 대여 기록을 가질 수 있다.
한 대여 기록은 정확히 한 도서를 참조한다.
```

```text
생성 순서
public.members
→ public.books
→ public.loans
```

**스크립트**

관계는 양방향으로 읽습니다. 회원과 도서에는 아직 대여 기록이 없을 수 있으므로 부모에서 대여 기록으로는 `0..N`입니다. 반대로 대여 기록 한 건은 반드시 한 회원과 한 도서를 참조합니다.

`loans`가 두 부모 테이블을 외래키로 참조하므로 생성 순서는 `members`, `books`, `loans`입니다.

## 7. 현재 DDL과 보류한 정책을 구분합니다

**화면 구성**

```sql
CREATE TABLE public.books (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    author VARCHAR(100) NOT NULL,
    published_year INTEGER,
    isbn VARCHAR(20) NOT NULL
);
```

```text
현재 구현
- id PRIMARY KEY
- 필수값 NOT NULL
- loans.member_id, loans.book_id FOREIGN KEY

아직 보류
- members.email UNIQUE
- books.isbn UNIQUE
- 날짜 선후 관계 CHECK
- 동시 활성 대여 차단
```

**스크립트**

현재 DDL은 요구사항에서 확정된 최소 구조를 PostgreSQL로 바꾼 초안입니다. `books`의 제목과 저자, ISBN은 저장해야 하는 값으로 `NOT NULL`이며 출판연도는 현재 초안에서 선택값으로 둡니다.

이메일과 ISBN의 고유성, 날짜 선후 관계, 같은 도서의 동시 활성 대여 차단은 아직 이 장에서 제약조건으로 확정하지 않습니다. Chapter 06에서 무결성 관점으로 보완합니다.

## 11. 최소 JOIN과 1:N 관계를 작은 질문으로 검증합니다

**화면 구성**

```sql
SELECT
    l.id AS loan_id,
    m.name AS member_name,
    b.title AS book_title,
    l.returned_at
FROM public.loans AS l
JOIN public.members AS m
    ON l.member_id = m.id
JOIN public.books AS b
    ON l.book_id = b.id
ORDER BY l.id;
```

검증 질문:

```text
회원 101이 여러 대여 기록을 가지는가? → 2건
도서 201이 시간에 따라 여러 대여 기록을 가지는가? → 2건
미반납은 returned_at NULL로 표현되는가? → 3건
```

**스크립트**

이 장에서 JOIN 자체를 깊게 배우지는 않습니다. 관계가 실제 조회로 연결되는지 확인하기 위한 최소 JOIN만 사용합니다.

회원 101의 대여 두 건, 도서 201의 시간별 대여 두 건, 미반납 세 건을 확인하면 이 장에서 설계한 1:N 관계와 선택 속성이 샘플 데이터로 표현되는지 검증할 수 있습니다.

## 13. AI가 만든 설계는 실행 전에 질문으로 검토합니다

**화면 구성**

```text
AI 초안 검토 질문
1. 각 테이블과 열의 요구사항 근거가 있는가?
2. 각 테이블의 한 행 의미가 명확한가?
3. 미확정 정책을 임의로 확정하지 않았는가?
4. 관계를 양방향으로 읽었을 때 카디널리티가 맞는가?
5. N:M 관계와 반복 사건을 적절히 분리했는가?
6. 작은 샘플 시나리오를 구조가 표현할 수 있는가?
```

**스크립트**

AI가 만든 ERD나 DDL은 바로 실행하지 않습니다. 요구사항 근거와 한 행 의미, 양방향 관계 문장부터 검토합니다.

특히 요구사항에 없는 `UNIQUE`, `CHECK`, 삭제 정책을 자연스럽게 추가하지 않았는지 확인합니다. AI 초안도 같은 추적표와 샘플 시나리오를 통과해야 합니다.

## 14. 초기화 파일은 마지막 수단으로 사용합니다

**화면 구성**

```text
오류 발생
→ 현재 DB 확인
→ 중복 실행 여부 확인
→ 현재 테이블·데이터 상태 확인
→ 필요한 파일만 재실행
→ 정말 처음부터 다시 시작할 때 reset_library.sql
```

**스크립트**

정말 처음부터 다시 시작해야 할 때만 `reset_library.sql`을 사용합니다. 이 파일은 `public.loans → public.books → public.members` 순서로 테이블과 데이터를 삭제합니다.
