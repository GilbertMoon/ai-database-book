# Chapter 06 실습 발표 강의안

## 정규화와 무결성 규칙을 실행으로 검증하기

> 목적: 정규화 전후 구조를 비교하고, 확정된 업무 규칙 C-01~C-08을 PostgreSQL 제약조건과 부분 고유 인덱스로 구현한 뒤 정상·경계·오류 데이터로 검증한다.  
> 기준: 초보자가 “SQL을 실행했다”가 아니라 “어떤 규칙이 어떤 객체로 구현되었고 어떤 데이터가 허용·거부되는지 실행 증거로 설명할 수 있다”라고 말할 수 있어야 한다.

## 1. 정규화와 무결성 규칙을 실행으로 검증합니다

**화면 구성**

```text
구조 생성
→ 정상 샘플
→ 정규화 비교
→ 규칙 추가
→ 정상·경계·오류 검증
```

- 키워드: PostgreSQL / C-01~C-08 / 실행 증거

**발표 스크립트**

이번 실습은 에스큐엘 파일을 끝까지 오류 없이 실행하는 것이 목표가 아닙니다. 먼저 정규화 전후 구조와 기준 데이터를 확인하고, 그다음 확정된 규칙을 별도 단계에서 제약조건으로 추가합니다.

정상값과 허용 경계값은 성공해야 하고, 규칙을 위반하는 오류값은 예상한 제약조건이나 인덱스가 거부해야 합니다.

마지막에는 실패 테스트 이후에도 기준 데이터가 그대로 유지되는지 확인합니다.

## 2. 이번 실습을 마치면 할 수 있는 일

**화면 구성**

- 정규화 전 위험한 중복과 이상 현상 설명
- `members_nf`, `books_nf`, `loans_nf`의 한 행 의미 설명
- C-01~C-08과 제약조건 연결
- 정상·경계·오류 데이터 구분
- 오류 후 기준 상태 재검증

**발표 스크립트**

첫째, 정규화 전 구조에서 같은 현재 사실이 반복될 때 왜 문제가 생기는지 설명할 수 있어야 합니다.

둘째, `members_nf`, `books_nf`, `loans_nf`의 한 행 의미와 관계를 확인합니다.

셋째, C-01부터 C-08까지 확정된 규칙을 `낫 널`, `유니크`, `체크`, 외래키와 부분 고유 인덱스에 연결합니다.

넷째, 성공해야 하는 값과 실패해야 하는 값을 구분해 실행합니다. 다섯째, 오류 테스트 뒤에도 기준 행 수와 관계가 그대로 유지되는지 확인합니다.

## 3. 예상하고 실행한 뒤 증거로 확인합니다

**화면 구성**

```text
① 위치·시작 상태 확인
→ ② 기본 구조·샘플 생성
→ ③ 정규화 전후 비교
→ ④ 무결성 규칙 추가
→ ⑤ 경계·오류 검증
```

강조 문장:

```text
예상 결과 → 한 단계 실행 → 실제 결과 → 규칙 확인
```

**발표 스크립트**

현재 데이터베이스와 시작 상태를 먼저 확인합니다. 그다음 제약조건 적용 전의 기본 구조를 만들고 정상 샘플을 입력합니다.

세 번째 단계에서는 정규화 전후의 반복과 관계가 예상과 같은지 비교합니다. 네 번째 단계에서 기존 데이터가 새 규칙을 만족하는지 검사한 뒤 C-01부터 C-08을 추가합니다.

마지막으로 경계값과 오류값을 한 테스트씩 실행해 실제 저장 경계를 확인합니다.

## 4. 파일 역할과 실행 순서를 먼저 확인합니다

**화면 구성**

| 순서 | 파일 | 완료 상태 |
| --- | --- | --- |
| 1 | `01_normalization_schema.sql` | 제약조건 전 빈 기본 구조 |
| 2 | `02_normalization_seed.sql` | 정상 샘플 3 / 2 / 2 / 3 |
| 3 | `03_normalization_compare.sql` | 정규화 전후·관계 자동 확인 |
| 4 | `04_add_integrity_rules.sql` | C-01~C-08 적용 |
| 5 | `05_integrity_tests.sql` | 경계·오류 테스트 |

초기화가 필요할 때만 `reset_normalization.sql`을 사용합니다.

**발표 스크립트**

처음 학습하는 경우에는 번호형 파일을 사용합니다. `01`은 제약조건이 아직 없는 기본 구조만 만듭니다. `02`는 정상 샘플을 입력하고 아이덴티티 다음 값을 조정합니다.

`03`은 데이터를 바꾸지 않고 정규화 전후 상태를 자동 비교합니다. `04`가 기존 데이터를 검사한 뒤 `낫 널`, `유니크`, `체크`, 외래키와 부분 고유 인덱스를 추가합니다.

`05`에는 성공·실패 테스트가 있으므로 주석을 한 번에 하나씩 해제해 실행합니다. 기존 `normalization_*.sql` 파일은 호환용이므로 번호 파일과 중복 실행하지 않습니다.

## 5. 현재 데이터베이스와 스키마를 확인합니다

**화면 구성**

```sql
SELECT current_database();
SELECT current_schema();
SHOW search_path;
```

```text
Database = ai_database_book
주요 객체 = public.table_name
Auto-commit 상태 확인
```

**발표 스크립트**

연결 이름만 보고 실행하지 않습니다. `current_database()`로 `ai_database_book`에 연결했는지 확인하고 `current_schema()`와 `search_path`도 확인합니다.

이번 장의 주요 객체는 `public.members_nf`처럼 스키마를 이름에 직접 명시합니다. 따라서 현재 스키마가 반드시 `public`이어야 하는 것은 아닙니다.

오류 테스트 전에는 자동 커밋인지 수동 커밋인지도 확인합니다. 수동 커밋이나 명시적 트랜잭션에서 한 문장이 실패하면 다음 문장도 실행되지 않는 실패 상태가 될 수 있습니다.

## 6. 한 행에 세 종류의 사실이 섞여 있습니다

**화면 구성**

| 대여 사건 | 회원 현재 정보 | 도서 현재 정보 |
| --- | --- | --- |
| `loan_id`, 날짜 | `member_name`, `member_email` | `book_title`, `author` |

- 삽입 이상
- 수정 이상
- 삭제 이상

**발표 스크립트**

`library_records_raw`의 한 행은 대여 사건 한 건을 중심으로 하지만 회원과 도서의 현재 정보까지 함께 저장합니다.

이 때문에 아직 대여되지 않은 도서를 독립적으로 등록하기 어렵고, 회원 이메일 변경 시 여러 행을 함께 수정해야 하며, 마지막 대여 행을 삭제할 때 도서 정보까지 잃을 수 있습니다.

이런 이상 현상은 에스큐엘 문법 오류가 아니라 서로 다른 사실의 주인을 한 행에 섞은 구조 문제입니다.

## 7. 현재 정보와 사건 정보를 각각의 주인에게 저장합니다

**화면 구성**

```text
members_nf 한 행 = 회원 한 명
books_nf 한 행   = 이 장에서 대여 대상으로 관리하는 도서 한 건
loans_nf 한 행   = 특정 회원의 특정 도서 대여 사건 한 건
```

```text
현재 사실 → 부모 테이블에 한 번 저장
대여 사건 → member_id·book_id로 연결
```

**발표 스크립트**

회원의 현재 정보는 `members_nf`, 도서의 현재 정보는 `books_nf`, 대여 사건은 `loans_nf`에서 관리합니다.

`loans_nf`에 회원 이메일이나 도서 제목을 다시 복사하지 않고 `member_id`와 `book_id`로 부모 행을 가리킵니다.

여기서 `books_nf` 한 행은 제목·판본·실제 복본을 모두 엄밀히 분리한 운영 모델이 아니라, 이 장에서 대여 대상으로 관리하는 도서 한 건이라는 단순화된 의미입니다.

## 8. C-01부터 C-08까지 구현 대상을 확인합니다

**화면 구성**

| ID | 규칙 | 구현 |
| --- | --- | --- |
| C-01 | 같은 이메일 문자열 중복 금지 | `UNIQUE` |
| C-02 | 같은 ISBN 문자열 중복 금지 | `UNIQUE` |
| C-03 | 공백 이름·제목 금지 | `CHECK` |
| C-04·05 | 날짜 순서 | `CHECK` |
| C-06·07 | 부모 존재·이력 보존 | FK·`RESTRICT` |
| C-08 | 도서당 미반납 최대 한 건 | 부분 고유 인덱스 |

**발표 스크립트**

제약조건은 좋은 아이디어를 임의로 추가하는 기능이 아닙니다. 챕터 05에서 미확정이었던 정책 가운데 이번 실습에서 명시적으로 확정한 C-01부터 C-08만 구현합니다.

이메일 대소문자 정규화, 동일 ISBN의 여러 복본, 여러 저자와 과거 대여 기간 전체 중첩은 이번 범위에 포함하지 않습니다.

따라서 각 디디엘을 볼 때 문법보다 먼저 어떤 규칙 아이디를 구현하는지 확인합니다.

## 9. DDL에서 규칙이 구현된 위치를 찾습니다

**화면 구성**

```text
01 기본 구조
→ PK와 타입 중심
→ 업무 규칙 미적용

04 규칙 추가
→ 기존 데이터 검사
→ SET NOT NULL
→ UNIQUE / CHECK / FOREIGN KEY
→ 부분 고유 인덱스
→ 적용 상태 검증
```

**발표 스크립트**

`01_normalization_schema.sql`은 정규화 전후를 비교하기 위한 기본 테이블만 만듭니다. 업무 제약조건은 아직 넣지 않습니다.

정상 샘플과 비교를 끝낸 뒤 `04_add_integrity_rules.sql`이 널, 중복, 공백, 날짜, 고아 참조와 활성 중복을 먼저 검사합니다.

현재 데이터가 규칙을 만족할 때만 `ALTER TABLE`과 부분 고유 인덱스로 C-01부터 C-08을 추가합니다. 적용 과정은 하나의 트랜잭션이므로 중간 오류 시 일부 규칙만 남기지 않습니다.

## 10. 테스트 전 기대 상태를 숫자로 고정합니다

**화면 구성**

```text
library_records_raw = 3
members_nf = 2
books_nf = 2
loans_nf = 3
미반납 = 2
회원 101 대여 = 2
도서 201 대여 = 2
고아 참조 = 0
날짜 오류 = 0
활성 중복 = 0
```

**발표 스크립트**

오류 테스트를 시작하기 전에 현재 상태를 숫자로 고정합니다. 원시 테이블은 3행, 회원 2행, 도서 2행, 대여 3행이며 미반납은 2행입니다.

회원 101과 도서 201은 각각 두 대여 이력을 갖습니다. 고아 회원 참조와 고아 도서 참조는 0이고, 날짜 순서 오류와 같은 도서의 미반납 중복도 0이어야 합니다.

`03_normalization_compare.sql`이 이 상태를 자동 판정하고 통과하면 `챕터 06 normalization comparison passed`를 표시합니다.

## 11. 정상 데이터는 저장되어야 합니다

**화면 구성**

```text
02_normalization_seed.sql
→ raw 3 / members 2 / books 2 / loans 3
```

- 회원 101의 여러 대여 허용
- 도서 201은 반납 후 재대여
- 현재 미반납은 도서당 한 건

**발표 스크립트**

정상 샘플이 규칙 때문에 거부되어서는 안 됩니다. 회원 한 명이 여러 대여 이력을 가질 수 있고 도서 한 건도 시간에 따라 여러 대여 이력을 가질 수 있습니다.

도서 201의 첫 대여는 반납된 뒤 다음 날 다시 시작되므로 반복 이력은 허용됩니다.

C-08은 과거 이력을 금지하는 규칙이 아니라 현재 `returned_at IS 널`인 대여가 도서당 하나만 존재하도록 제한합니다.

## 12. 허용하기로 한 경계값도 성공해야 합니다

**화면 구성**

| 경계값 | 기대 |
| --- | --- |
| `due_at = borrowed_at` | 성공 |
| `returned_at = borrowed_at` | 성공 |
| `returned_at = NULL` | 성공 |
| `published_year = NULL` | 성공 |
| 공백이 아닌 한 글자 이름 | 성공 |

**발표 스크립트**

`체크` 제약조건은 잘못된 값을 막아야 하지만 요구사항이 허용한 경계값까지 거부하면 안 됩니다.

반납예정일과 실제반납일은 대여일과 같은 날일 수 있습니다. 실제반납일은 아직 반납하지 않았다면 `널`일 수 있고 출판연도는 이번 모델에서 선택값입니다.

이름은 공백만 아니면 한 글자도 허용됩니다. `05` 파일의 경계 테스트는 임시 행을 넣고 바로 삭제해 기준 상태로 돌아옵니다.

## 13. 실패해야 하는 SQL은 한 문장씩 실행합니다

**화면 구성**

| 오류값 | 기대 객체 |
| --- | --- |
| NULL 이름 | NOT NULL |
| 중복 이메일 | `uq_members_nf_email` |
| 중복 ISBN | `uq_books_nf_isbn` |
| 공백 이름·제목 | `chk_...not_blank` |
| 없는 회원 | `fk_loans_nf_member` |
| 없는 도서 | `fk_loans_nf_book` |
| 잘못된 날짜 | `chk_loans_nf_...` |
| 참조 부모 삭제 | FK / `RESTRICT` |

**발표 스크립트**

`05_integrity_tests.sql`의 오류 예제는 기본적으로 주석 처리되어 있습니다. 한 테스트만 선택해 주석을 해제하고 실행합니다.

실패해야 하는 에스큐엘에서 오류가 발생하면 테스트가 성공한 것입니다. 오류 메시지에서 `uq_members_nf_email`, `fk_loans_nf_member`, `chk_loans_nf_due_date` 같은 객체 이름을 확인해 어떤 규칙이 동작했는지 기록합니다.

C-06은 없는 회원뿐 아니라 없는 도서를 참조하는 경우도 각각 확인합니다.

## 14. 현재 미반납 상태의 중복만 차단합니다

**화면 구성**

```sql
CREATE UNIQUE INDEX uq_loans_nf_active_book
ON public.loans_nf (book_id)
WHERE returned_at IS NULL;
```

```text
반납 완료 이력 여러 건 → 허용
같은 도서의 미반납 두 건 → 두 번째 차단
```

**발표 스크립트**

부분 고유 인덱스는 `returned_at`이 `널`인 행만 대상으로 `book_id`의 고유성을 검사합니다.

따라서 반납된 과거 이력은 여러 건 존재할 수 있지만 같은 도서에 현재 미반납 대여를 두 건 만들면 두 번째 입력이 실패합니다.

이 규칙은 과거 대여 기간 전체의 중첩을 검사하는 규칙이 아닙니다. 기간 중첩은 별도의 심화 주제입니다.

---

## 15. 트랜잭션 실패 상태에서는 롤백합니다

**화면 구성**

```sql
BEGIN;
-- 실패 테스트
-- ERROR
SELECT ...;
-- current transaction is aborted
ROLLBACK;
```

**발표 스크립트**

자동 커밋에서는 일반적으로 실패한 문장만 거부됩니다. 하지만 수동 커밋이나 `비긴` 안에서 오류가 발생하면 현재 트랜잭션이 실패 상태가 되어 이후 정상 쿼리도 실행되지 않을 수 있습니다.

이때 제약조건을 지우는 것이 아니라 `롤백;`으로 실패한 트랜잭션을 끝냅니다. 그 후 다음 테스트를 새 상태에서 실행합니다.

트랜잭션의 상세 원리는 챕터 09에서 다룹니다.

## 16. 구조·규칙·검증 증거를 함께 확인합니다

**화면 구성**

```text
구조
→ 각 테이블의 한 행 의미·사실의 주인

규칙
→ C-01~C-08
→ 제약조건 8개 + NOT NULL 열 10개 + 부분 고유 인덱스

검증 증거
→ 03: Chapter 06 normalization comparison passed
→ 05: Chapter 06 integrity test baseline preserved
```

**발표 스크립트**

최종 결과는 테이블을 여러 개 만들었다는 사실만으로 판단하지 않습니다. 각 테이블의 한 행 의미와 컬럼의 주인이 설명되어야 하고, C-01부터 C-08이 어떤 제약조건이나 인덱스로 구현되었는지 연결되어야 합니다.

정상값과 허용 경계값은 성공하고 오류값은 예상한 규칙으로 실패해야 합니다.

마지막으로 `05_integrity_tests.sql`의 자동 기준 상태 확인까지 통과하면 테스트 후에도 원래 데이터가 유지되었음을 확인할 수 있습니다.
