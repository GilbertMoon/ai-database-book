# Chapter 06 실습 발표 강의안

## 정규화 구조와 무결성 제약조건을 실제 데이터로 검증하기

> 목적: 정규화 전후 도서 대여 구조를 비교하고, 확정된 업무 규칙을 PostgreSQL 제약조건과 부분 고유 인덱스로 구현한 뒤 정상·경계·오류 데이터로 검증한다.  
> 기준: 초보자가 “DDL을 실행했다”가 아니라 “어떤 규칙이 어떤 제약조건으로 구현되었고, 어떤 데이터가 허용되거나 거부되는지 실행 결과로 설명할 수 있다”라고 말할 수 있어야 한다.

---

## 1. 이번 실습의 목표는 오류 없이 실행하는 것이 아닙니다

**화면 구성**

- 큰 제목: 허용할 데이터와 거부할 데이터의 경계를 확인합니다
- 흐름: 구조 생성 → 정상 데이터 → 구조 비교 → 경계값 → 오류값 → 최종 기록
- 키워드: 규칙 ID / 제약조건 / 실행 증거

**발표 스크립트**

이번 실습에서는 일부 SQL이 성공해야 하고 일부 SQL은 의도적으로 실패해야 합니다. 모든 문장이 오류 없이 실행되는 것이 목표가 아닙니다.

정상 데이터와 허용된 경계값은 저장되어야 하고, 확정된 업무 규칙을 위반하는 데이터는 DBMS가 거부해야 합니다. 실패한 오류 메시지도 제약조건이 동작했다는 중요한 실행 증거입니다.

각 테스트에서 어떤 규칙 ID를 확인하는지, 어떤 제약조건이 차단했는지, 기존 데이터가 그대로 유지되는지 기록합니다.

## 2. 파일은 역할별로 나누어 순서대로 실행합니다

**화면 구성**

```text
normalization_schema.sql
→ normalization_seed.sql
→ normalization_practice.sql
→ integrity_tests.sql
```

- 초기화: `reset_normalization.sql`
- 주의: 실패 테스트는 한 문장씩 선택 실행

**발표 스크립트**

`normalization_schema.sql`은 테이블과 제약조건을 만듭니다. `normalization_seed.sql`은 정상 샘플 데이터를 입력하고 IDENTITY의 다음 값을 조정합니다.

`normalization_practice.sql`은 정규화 전후 데이터와 관계를 조회해 기준 상태를 확인합니다. `integrity_tests.sql`은 실패해야 하는 SQL이 포함되어 있으므로 전체 파일을 실행하지 않고 테스트 하나씩 주석을 해제해 실행합니다.

처음부터 다시 시작할 때만 보호 구문이 있는 `reset_normalization.sql`을 사용합니다.

## 3. 실행 전에 데이터베이스·스키마·커밋 상태를 확인합니다

**화면 구성**

```sql
SELECT current_database();
SELECT current_schema();
SHOW search_path;
```

- 기대 DB: `ai_database_book`
- 기대 스키마: `public`
- Auto-commit / Manual commit 직접 확인

**발표 스크립트**

테이블 생성이나 초기화 전에 현재 연결 위치를 확인합니다. 같은 이름의 테이블이 다른 데이터베이스나 앞선 `search_path`에 있으면 전혀 다른 객체를 변경할 수 있습니다.

또 오류 테스트 전에 자동 커밋인지 수동 커밋인지 확인합니다. 수동 커밋이나 명시적 트랜잭션에서는 한 문장이 실패한 뒤 현재 트랜잭션 전체가 실패 상태가 될 수 있습니다.

화면에서 연결 이름만 믿지 말고 SQL 결과와 DBeaver의 커밋 모드를 함께 확인합니다.

```text
library_records_raw

```

- 정규화 구조 3개

**발표 스크립트**

## 5. 제약조건 이름과 규칙 ID를 연결해서 읽습니다

**화면 구성**

| 규칙 | 구현 예 |
|---|---|
| C-01 이메일 중복 금지 | `uq_members_nf_email` |
| C-03 공백 이름 금지 | `chk_members_nf_name_not_blank` |
| C-04 날짜 순서 | `chk_loans_nf_due_date` |
| C-06 부모 존재 | 외래키 |
| C-08 활성 대여 중복 | `uq_loans_nf_active_book` |

예를 들어 중복 이메일 오류에서 `uq_members_nf_email`이 표시되면 C-01 규칙이 동작한 것입니다. 반납예정일 오류에서 `chk_loans_nf_due_date`가 표시되면 C-04 날짜 규칙을 확인한 것입니다.

테스트 기록에는 SQL 문장만 복사하지 말고 규칙 ID, 제약조건 이름, 기대 결과와 실제 결과를 함께 적습니다.

## 6. 정상 샘플 데이터의 기준 상태를 먼저 만듭니다

**화면 구성**

```text
원시 대여 기록 3행
회원 2명: 101, 102
도서 2건: 201, 202
대여 3건: 1001~1003
미반납 대여 2건
```

**발표 스크립트**

`normalization_seed.sql`은 원시 테이블 3행과 정규화된 회원 2명, 도서 2건, 대여 3건을 입력합니다.

도서 201은 4월 1일 대여되어 4월 2일 반납된 뒤, 4월 3일 다시 대여됩니다. 따라서 과거 대여 이력은 여러 건이지만 현재 미반납 대여는 한 건입니다.

이 기준 상태가 다르면 뒤의 모든 테스트 결과가 달라지므로 오류 테스트 전에 행 수와 데이터 값을 확인합니다.

## 7. 명시적 ID 입력 후 IDENTITY 다음 값을 조정합니다

**화면 구성**

```text
members_nf 다음 ID: 103
books_nf 다음 ID: 203
loans_nf 다음 ID: 1004
raw 다음 loan_id: 1004
```

- 강조: 명시적 ID 입력은 자동 시퀀스를 소비하지 않음

**발표 스크립트**

샘플 관계를 쉽게 읽기 위해 101, 201, 1001처럼 명시적인 ID를 사용합니다. 하지만 명시적 ID를 넣어도 연결된 IDENTITY의 다음 값은 자동으로 바뀌지 않습니다.

따라서 샘플 입력 뒤 `ALTER TABLE ... RESTART WITH`로 다음 자동값을 조정합니다. 이 작업을 하지 않으면 나중에 자동 입력된 ID가 샘플 범위와 섞이거나 충돌할 수 있습니다.

자동 생성 ID는 데이터 개수나 빈틈없는 업무 순번이 아니라 행 식별자라는 점도 다시 확인합니다.

## 8. 원시 테이블에서 위험한 중복을 눈으로 확인합니다

**화면 구성**

- `library_records_raw` 3행 조회
- 김민지 정보 2행 반복
- 데이터베이스 입문 정보 2행 반복
- 질문: 어떤 값이 같은 사실의 복사본인가?

**발표 스크립트**

`normalization_practice.sql`의 첫 조회로 원시 데이터 3행을 확인합니다. 김민지의 이름과 이메일이 두 대여 행에 반복되고, 데이터베이스 입문 책 정보도 두 행에 반복됩니다.

이 반복은 각각 회원과 책의 현재 사실을 복사해 둔 것입니다. 일부 행만 변경하면 서로 다른 값이 되어 수정 이상이 생길 수 있습니다.

반면 정규화된 `loans_nf.member_id = 101`의 반복은 한 회원이 여러 대여 기록을 가진다는 정상적인 관계입니다.

## 9. 정규화 후 행 수와 테이블별 사실을 확인합니다

**화면 구성**

| 테이블 | 기대 행 수 | 한 행의 의미 |
|---|---:|---|
| `members_nf` | 2 | 회원 한 명 |
| `books_nf` | 2 | 도서 한 건 |
| `loans_nf` | 3 | 대여 사건 한 건 |

**발표 스크립트**

정규화 후에는 회원 정보가 회원 테이블 두 행, 책 정보가 도서 테이블 두 행, 대여 이력이 대여 테이블 세 행에 저장됩니다.

행 수가 줄거나 늘었다는 사실만으로 정규화 성공을 판단하지 않습니다. 각 테이블의 한 행이 하나의 분명한 사실을 나타내고, 필요한 관계가 외래키로 연결되는지 확인합니다.

회원 101과 도서 201이 각각 여러 대여 기록과 연결되는지도 조회해 1:N 관계를 확인합니다.

## 10. JOIN으로 원래 업무 화면을 다시 만들 수 있는지 확인합니다

**화면 구성**

```text
loans_nf
→ members_nf에서 회원 이름·이메일
→ books_nf에서 책 제목·저자
→ 결과 3행
```

- 주의: JOIN은 영구 중복 저장이 아님

**발표 스크립트**

정규화 후 테이블이 나뉘어 있어도 필요한 업무 화면은 외래키 관계를 따라 JOIN으로 만들 수 있습니다.

대여 ID를 기준으로 회원 이름과 이메일, 책 제목과 저자, 대여 날짜를 조회하면 원시 표와 같은 세 개의 업무 행을 얻습니다.

JOIN은 데이터를 다시 복사해 저장하는 것이 아니라 조회 시점에 필요한 결과를 구성합니다. 이번 장에서는 관계가 연결되는지만 확인하고 JOIN 문법은 Chapter 08에서 자세히 다룹니다.

## 11. `NOT NULL`과 공백 문자열은 다른 문제입니다

**화면 구성**

- 테스트 A: 이름에 `NULL` → 실패
- 테스트 B: 이름에 `'   '` → 실패
- 구현: `NOT NULL` + `CHECK (char_length(trim(name)) > 0)`

**발표 스크립트**

`NOT NULL`은 값이 아예 없는 상태를 막습니다. 하지만 공백 문자열은 실제 문자열 값이므로 `NOT NULL`만으로는 차단되지 않습니다.

이름과 제목은 공백만 저장할 수 없다는 C-03 규칙을 `CHECK`로 별도 구현합니다. 정상적인 한 글자 이름은 허용되어야 하므로 경계값도 함께 테스트합니다.

오류가 발생하면 입력값이 잘못된 것인지 제약조건이 지나치게 강한 것인지 요구사항과 비교합니다.

## 12. `UNIQUE`로 확정된 고유값의 중복을 테스트합니다

**화면 구성**

- 중복 이메일 `junho@example.com` 입력 → 실패
- 중복 ISBN `ISBN-002` 입력 → 실패
- 주의: 대소문자 정규화는 이번 범위 밖

**발표 스크립트**

C-01과 C-02에서는 정확히 같은 이메일 문자열과 ISBN 문자열의 중복을 허용하지 않는다고 확정했습니다.

따라서 기존 이메일이나 ISBN을 가진 새 행을 입력하면 `UNIQUE` 오류가 발생해야 합니다. 이것은 시스템이 고장 난 것이 아니라 확정 규칙을 지킨 결과입니다.

다만 이메일 대소문자나 별칭을 같은 값으로 볼지는 이번 실습에서 다루지 않습니다. `UNIQUE`를 적용했다고 모든 이메일 정규화 문제가 해결된 것은 아닙니다.

## 13. 외래키로 존재하지 않는 부모 참조를 차단합니다

**화면 구성**

- 오류 예: `member_id = 999`
- 기대: 외래키 위반
- 확인: 실패 후 `loans_nf` 행 수는 여전히 3

**발표 스크립트**

대여 기록은 반드시 존재하는 회원과 도서를 참조해야 합니다. 존재하지 않는 회원 999를 참조하는 대여를 입력하면 외래키 오류가 발생해야 합니다.

오류 메시지에서 어떤 외래키가 실패했는지 확인합니다. 실패 후 잘못된 행이 일부 저장되지 않았는지 행 수와 실제 데이터를 다시 조회합니다.

참조 무결성은 애플리케이션 화면의 입력 검증만으로 대신하지 않습니다. 여러 입력 경로가 있어도 DBMS가 마지막 경계에서 관계를 보호해야 합니다.

## 14. 날짜 `CHECK`는 오류값과 경계값을 함께 검증합니다

**화면 구성**

| 테스트 | 기대 결과 |
|---|---|
| `due_at < borrowed_at` | 실패 |
| `returned_at < borrowed_at` | 실패 |
| `due_at = borrowed_at` | 성공 |
| `returned_at = borrowed_at` | 성공 |
| `returned_at IS NULL` | 성공 |

**발표 스크립트**

C-04는 반납예정일이 대여일과 같거나 이후여야 한다는 규칙입니다. C-05는 실제반납일이 비어 있거나 대여일과 같거나 이후여야 한다는 규칙입니다.

오류값만 테스트하면 제약조건이 지나치게 강한지 알 수 없습니다. 같은 날 대여하고 반납하는 경계값과 아직 반납하지 않은 `NULL`이 허용되는지도 확인합니다.

정확한 경계는 요구사항에서 결정합니다. 만약 업무상 반드시 다음 날 이후여야 한다면 `>=`가 아니라 `>`가 필요하므로 정책부터 수정해야 합니다.

## 15. 부분 고유 인덱스로 두 번째 활성 대여를 차단합니다

**화면 구성**

```sql
CREATE UNIQUE INDEX uq_loans_nf_active_book
ON public.loans_nf (book_id)
WHERE returned_at IS NULL;
```

- 도서 201의 두 번째 미반납 대여 입력 → 실패

**발표 스크립트**

도서 201에는 이미 `returned_at IS NULL`인 활성 대여가 있습니다. 같은 도서에 두 번째 활성 대여를 입력하면 부분 고유 인덱스 오류가 발생해야 합니다.

일반 `UNIQUE(book_id)`가 아니라 조건을 만족하는 미반납 행만 검사한다는 점을 확인합니다.

오류 후 기존 활성 대여 한 건과 과거 반납 이력이 그대로 남아 있는지도 조회합니다.

---

## 16. 반납 처리 후에는 같은 도서를 다시 대여할 수 있습니다

**화면 구성**

```text
현재 활성 대여 반환 처리
→ returned_at에 날짜 저장
→ 새 미반납 대여 입력
→ 성공
```

- 주의: 실습 상태 변경 시 체크포인트 기록

**발표 스크립트**

부분 고유 인덱스의 목적은 평생 재대여를 막는 것이 아니라 동시에 진행 중인 대여만 한 건으로 제한하는 것입니다.

기존 활성 대여에 반납일을 저장하면 인덱스 조건에서 제외됩니다. 이후 같은 책의 새로운 미반납 대여는 성공해야 합니다.

이 실습을 실행하면 기준 데이터가 변경되므로 실행 전후 행 수, 활성 대여 수와 새 ID를 기록합니다. 뒤 테스트가 기준 상태 A를 요구한다면 초기화 후 다시 구성합니다.

---

## 17. 참조 중인 부모 삭제는 `RESTRICT`로 거부됩니다

**화면 구성**

- 회원 101 삭제 시도
- 기대: 참조 중이므로 실패
- 비교: 근거 없는 `CASCADE`였다면 대여 이력까지 삭제 가능

**발표 스크립트**

회원 101은 대여 이력을 가지고 있으므로 삭제를 시도하면 외래키의 `ON DELETE RESTRICT` 정책에 따라 실패해야 합니다.

이 실패는 대여 이력을 보존한다는 C-07 규칙의 실행 증거입니다. 오류를 없애기 위해 외래키를 제거하거나 `CASCADE`로 바꾸면 안 됩니다.

부모 삭제가 자식 이력 삭제를 의미한다는 요구사항이 명확할 때만 `CASCADE`를 사용합니다.

---

## 18. 오류 후 트랜잭션 상태를 확인합니다

**화면 구성**

```text
Auto-commit
→ 실패 문장만 거부되는 경우가 일반적

Manual commit / BEGIN 안
→ current transaction is aborted
→ ROLLBACK;
```

**발표 스크립트**

수동 커밋 상태나 명시적인 트랜잭션 안에서 오류가 발생하면 이후 정상 SQL도 실행되지 않고 `current transaction is aborted` 메시지가 나올 수 있습니다.

이때 제약조건을 수정할 문제가 아니라 실패한 트랜잭션을 `ROLLBACK;`으로 종료해야 합니다. 그 후 다음 테스트를 새 상태에서 실행합니다.

Chapter 09에서 트랜잭션 원리를 자세히 배우기 전에는 오류 테스트를 자동 커밋 상태에서 한 문장씩 실행하는 방식이 가장 단순합니다.

---

## 19. 초기화 파일은 대상 검증 후에만 실행합니다

**화면 구성**

- 파일: `reset_normalization.sql`
- 삭제 대상: Chapter 06 실습 전용 테이블
- 확인: DB·스키마·객체 이름·보존할 데이터

**발표 스크립트**

실습을 처음부터 다시 시작해야 할 때만 초기화 파일을 사용합니다. 초기화는 데이터를 되돌리는 편의 기능이 아니라 실제 테이블과 데이터를 삭제하는 작업입니다.

실행 전에 현재 데이터베이스가 `ai_database_book`인지, 대상이 Chapter 06의 `_nf` 테이블과 원시 테이블인지 확인합니다.

단순히 위치 조회문이 위에 있다는 이유만으로 안전하다고 가정하지 않습니다. 보호 구문이 잘못된 위치에서 삭제를 중단하는지도 확인합니다.

## 20. 최종 제출물은 구조·규칙·실행 결과를 연결한 증거입니다

**화면 구성**

- 최종 체크리스트
  - 테이블별 한 행 의미
  - 규칙 C-01~C-08
  - 제약조건·인덱스 이름
  - 정상·경계·오류 결과
  - 오류 후 데이터 상태
  - AI 제안과 수정 이유

**발표 스크립트**

최종 결과에는 테이블 생성 SQL만 제출하지 않습니다. 각 테이블의 한 행 의미, 컬럼의 주인, 확정 규칙과 구현 방법을 연결해 설명합니다.

정상 데이터와 허용 경계값의 성공 결과, 실패해야 하는 오류값의 오류 메시지, 실패 후 기존 데이터가 유지되는지도 기록합니다.

AI가 제안한 구조나 제약조건을 사용했다면 요구사항에 없는 `UNIQUE`, 근거 없는 `CASCADE`, 누락된 날짜 규칙, 과도한 테이블 분리를 검토하고 수정 이유를 남깁니다. 이것이 Chapter 06 실습의 최종 증거입니다.
