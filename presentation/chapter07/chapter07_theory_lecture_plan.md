# Chapter 07 이론 발표 강의안

## 실전 프로젝트 1: 온라인 강의 수강신청 DB 완성하기

> 목적: Chapter 01~06에서 배운 요구사항 분석, ERD, 정규화, 제약조건, 검증을 하나의 작은 서비스 프로젝트로 연결한다.  
> 기준: 초보자가 “테이블을 만들었다”가 아니라 “이 테이블·관계·제약조건·테스트가 어떤 요구사항과 결정에서 나왔는지 설명할 수 있다”라고 말할 수 있어야 한다.

---

## 1. Chapter 07은 앞 장의 개념을 하나의 프로젝트로 묶습니다

**화면 구성**

```text
요구사항·결정 ID
→ 설계 결정
→ ERD 구조
→ 제약조건과 인덱스
→ 샘플·변경 데이터
→ 검증 결과
```

**발표 스크립트**

이번 장은 새로운 에스큐엘 문법을 많이 배우는 장이 아닙니다. 챕터 01부터 06까지 배운 내용을 온라인 강의 수강신청 DB라는 하나의 작은 서비스로 연결합니다.

중요한 것은 “에스큐엘 파일을 실행했다”가 아닙니다. 왜 학생, 강사, 강의, 수강신청 테이블이 필요하고, 어떤 요구사항 때문에 외래키와 제약조건이 들어갔는지 설명할 수 있어야 합니다.

---

## 2. 프로젝트 완료 기준은 재현성과 설명 가능성입니다

**화면 구성**

- 다른 사람이 같은 파일 순서로 실행할 수 있음
- 같은 구조와 기준 데이터가 만들어짐
- 각 테이블·제약조건·인덱스의 근거를 설명함
- 검증 SQL의 기대값을 말할 수 있음

**발표 스크립트**

프로젝트가 끝났다는 뜻은 화면에 테이블이 보인다는 뜻이 아닙니다. 다른 사람이 저장소의 파일을 같은 순서로 실행했을 때 같은 데이터베이스가 만들어져야 합니다.

또한 학생 이메일 중복 금지, 강의 가격 음수 금지, 진행 중 중복 신청 차단 같은 규칙이 어떤 요구사항이나 결정 아이디에서 나왔는지 설명할 수 있어야 합니다.

## 3. 전용 스키마 `course_project`를 사용합니다

**화면 구성**

```text
course_project
├── students
├── instructors
├── courses
└── enrollments
```

**발표 스크립트**

앞 장에서는 `public` 스키마에 실습 테이블을 만들었습니다. 챕터 07에서는 프로젝트 객체를 `코스 프로젝트` 스키마에 모읍니다.

이렇게 하면 `public.스튜던츠`와 `코스 프로젝트.스튜던츠`를 구분할 수 있고, 프로젝트 초기화 범위도 명확해집니다. 모든 에스큐엘에서 `코스 프로젝트.스튜던츠`처럼 스키마를 명시하므로 `current_schema()`가 반드시 `코스 프로젝트`일 필요는 없습니다. 핵심은 현재 데이터베이스가 `ai_database_book`인지 확인하는 것입니다.

## 4. 범위 제외를 먼저 정해야 모델이 커지지 않습니다

**화면 구성**

| 제외 ID | 이번 버전에서 제외하는 기능 |
|---|---|
| `P07-O01` | 결제 시도·실패·환불 이력 |
| `P07-O02` | 정원과 대기 순번 |
| `P07-O03` | 상태 변경 이력 |
| `P07-O04` | 강의 콘텐츠·진도·수료 |

**발표 스크립트**

온라인 강의 서비스를 모두 모델링하려고 하면 결제, 환불, 정원, 대기, 진도율, 수료증, 리뷰까지 계속 늘어납니다.

그래서 이 장에서는 기본 수강신청 구조에 집중합니다. 범위 제외는 대충 빠뜨리는 것이 아니라, 이번 버전에서는 다루지 않는다고 명시적으로 기록하는 것입니다.

## 5. 확정 요구사항·프로젝트 결정·미확정 질문을 구분합니다

**화면 구성**

```text
확정 요구사항: 반드시 지켜야 하는 규칙
프로젝트 결정: 이번 버전에서 선택한 정책
미확정 질문: 운영 전 추가 확인이 필요한 정책
범위 제외: 이번 모델에서 만들지 않는 기능
```

**발표 스크립트**

학생은 이름과 이메일을 가진다, 강의는 강사를 참조한다, 상태는 네 값 중 하나라는 내용은 확정 요구사항입니다.

반면 활성 신청 중복을 막고 완료·취소 이력을 남기는 방식은 이번 프로젝트에서 선택한 정책입니다. 강사 변경 이력이나 회원 탈퇴 후 개인정보 처리처럼 더 확인해야 하는 내용은 미확정 질문으로 둡니다.

## 6. 한 행의 의미를 먼저 정합니다

**화면 구성**

| 테이블 | 한 행의 의미 |
|---|---|
| `students` | 학생 한 명 |
| `instructors` | 강사 한 명 |
| `courses` | 개설된 강의 한 개 |
| `enrollments` | 특정 학생의 특정 강의 신청 사건 한 건 |

**발표 스크립트**

좋은 설계는 한 행이 무엇을 의미하는지 분명합니다. `스튜던츠`의 한 행은 학생 한 명이고, `코시스`의 한 행은 강의 한 개입니다.

가장 중요한 테이블은 `인롤먼츠`입니다. 이 테이블은 단순히 학생과 강의를 연결하는 표가 아닙니다. 신청일, 상태, 신청 당시 기록 금액을 가지는 수강신청 사건을 저장합니다.

---

## 7. 현재 가격과 신청 당시 금액은 다른 사실입니다

**화면 구성**

```text
courses.price
→ 현재 강의의 기준 가격

enrollments.recorded_amount
→ 신청 시점에 신청 행에 기록한 금액
```

**발표 스크립트**

강의 가격과 신청 시 기록 금액은 값이 같아 보일 수 있지만 의미가 다릅니다. `코시스.price`는 현재 강의의 기준 가격입니다.

반면 `인롤먼츠.recorded_amount`는 특정 학생의 신청 행에 그 시점의 금액을 기록한 값입니다. 이번 프로젝트에는 할인 기능이 없기 때문에 신규 신청을 만들 때 현재 `코시스.price`를 조회해서 기록 금액으로 복사합니다. 강의 가격이 나중에 바뀌어도 과거 신청의 기록 금액은 그대로 남습니다. 이 값은 실제 결제 승인액이나 회계 매출을 뜻하지 않습니다.

---

## 8. 학생과 강의의 N:M 관계는 `enrollments`로 풉니다

**화면 구성**

```text
students 1 ── 0..N enrollments 0..N ── 1 courses
```

**발표 스크립트**

학생은 여러 강의를 신청할 수 있고, 강의 하나에도 여러 학생이 신청할 수 있습니다. 학생과 강의를 직접 보면 N:M 관계입니다.

관계형 데이터베이스에서는 여러 강의 아이디를 한 셀에 저장하지 않습니다. `인롤먼츠`라는 사건 테이블을 두고 두 개의 1:N 관계로 풀어야 외래키, 상태, 신청일, 금액을 안정적으로 관리할 수 있습니다.

---

## 9. 관계 문장은 외래키 위치를 결정합니다

**화면 구성**

```text
한 강의는 정확히 한 명의 강사를 참조한다.
→ courses.instructor_id

한 수강신청은 정확히 한 학생을 참조한다.
→ enrollments.student_id

한 수강신청은 정확히 한 강의를 참조한다.
→ enrollments.course_id
```

**발표 스크립트**

이알디를 그리기 전에 관계를 문장으로 읽어야 합니다. “한 강의는 정확히 한 명의 강사를 참조한다”라고 말하면 외래키가 `코시스`에 들어가야 함을 알 수 있습니다.

“한 학생은 여러 신청을 가질 수 있다”는 말은 `스튜던츠`에 신청 아이디 목록을 넣으라는 뜻이 아닙니다. 신청 쪽인 `인롤먼츠`에 `student_id`를 두라는 뜻입니다.

## 10. 무결성 규칙은 확정된 정책만 구현합니다

**화면 구성**

| 규칙 | 구현 |
|---|---|
| 이메일 중복 방지 | `UNIQUE` |
| 공백 문자열 방지 | `CHECK (trim(...) > 0)` |
| 난이도·상태 허용값 | `CHECK` |
| 음수 금액 방지 | `CHECK` |
| 존재하는 부모만 참조 | `FOREIGN KEY` |
| 부모 삭제 제한 | `ON DELETE RESTRICT` |

**발표 스크립트**

제약조건은 좋은 아이디어를 마음대로 추가하는 기능이 아닙니다. 요구사항이나 프로젝트 결정으로 확정된 규칙을 디비엠에스가 검사할 수 있게 선언하는 기능입니다.

예를 들어 이메일은 정확히 같은 문자열 중복을 막습니다. 하지만 대소문자를 같은 이메일로 볼지, 이메일 형식을 어디까지 검사할지는 별도 정책입니다.

## 11. 진행 중 중복 신청은 부분 고유 인덱스로 막습니다

**화면 구성**

```sql
CREATE UNIQUE INDEX uq_course_enrollments_active
ON course_project.enrollments (student_id, course_id)
WHERE status IN ('신청', '수강중');
```

**발표 스크립트**

같은 학생이 같은 강의를 동시에 두 번 신청 중이면 안 됩니다. 하지만 완료나 취소 이력까지 모두 막으면 재수강이나 과거 기록 보존이 어려워집니다.

그래서 이 장에서는 상태가 `신청` 또는 `수강중`인 활성 신청에만 고유성을 적용합니다. 완료나 취소 이력은 남길 수 있지만, 현재 진행 중인 중복 신청은 차단합니다. 이 객체는 일반 유니크 제약조건이 아니라 조건이 붙은 부분 고유 인덱스입니다.

## 12. 샘플 데이터는 테스트 목적을 가진 기준 데이터입니다

**화면 구성**

| 테이블 | 기본 입력 후 행 수 |
|---|---:|
| students | 3 |
| instructors | 2 |
| courses | 3 |
| enrollments | 4 |

**발표 스크립트**

샘플 데이터는 빈칸을 채우기 위한 값이 아닙니다. 학생 101이 여러 강의를 신청하고, 강의 301에 여러 학생이 신청하며, 강사 201이 여러 강의를 담당하는 관계를 보여 주기 위해 설계된 데이터입니다.

명시적 아이디를 사용하기 때문에 관계를 설명하기 쉽습니다. 대신 샘플 입력 후에는 아이덴티티의 다음 값을 조정해야 합니다.

## 13. 변경 시나리오는 예상 이전 상태를 조건에 넣습니다

**화면 구성**

```text
학생 102가 강의 302 신청
신청 1001: 수강중 → 완료
신청 1004: 신청 → 취소
```

**발표 스크립트**

변경 에스큐엘에서는 바꿀 행만 찾는 것이 아니라, 예상 이전 상태도 조건에 넣습니다. 예를 들어 신청 1001을 완료로 바꿀 때 `id = 1001`만 쓰지 않고 `status = '수강중'`도 함께 확인합니다.

`리터닝` 결과가 0행이면 에스큐엘이 실패한 것이 아니라 현재 데이터 상태가 예상과 다르다는 신호입니다. 그 상태를 확인하지 않고 다음 단계로 넘어가면 검증값이 모두 흔들립니다.

## 14. 검증은 행 수, 관계, 상태, 금액을 함께 확인합니다

**화면 구성**

```text
최종 행 수: 3 / 2 / 3 / 5
서비스 JOIN 결과: 5행
명명 제약조건: 15개
NOT NULL 열: 20개
전체 기록 금액: 590000
취소 제외 기록 금액: 440000
고아 관계: 0행
활성 중복 신청: 0행
```

**발표 스크립트**

검증은 테이블이 보이는지 확인하는 수준이 아닙니다. 최종 행 수가 학생 3명, 강사 2명, 강의 3개, 신청 5건인지 확인합니다.

또 조인 결과 5행, 핵심 관계의 반복 수, 명명 제약조건 15개, 낫 널 열 20개, 고아 관계와 활성 중복 0건을 확인합니다. 전체 기록 금액 590000과 취소 제외 기록 금액 440000도 검산값으로 사용합니다.

## 15. 정상값뿐 아니라 경계값과 오류값도 확인합니다

**화면 구성**

| 종류 | 예 |
|---|---|
| 성공해야 하는 경계 | 가격·기록 금액 0, 설명 NULL, 한 글자 이름, 완료 뒤 재신청 |
| 실패해야 하는 오류 | 공백 문자열, 중복 이메일, 음수 금액, 없는 부모, 잘못된 상태 |

**발표 스크립트**

정상 데이터만 성공하면 제약조건이 충분한지 알 수 없습니다. 무료 강의처럼 0원이 허용되어야 하는 값, 강의 설명처럼 널이 허용되어야 하는 값, 완료 이력 뒤 새 신청처럼 정책상 허용되는 상황도 실제로 성공해야 합니다.

반대로 공백 문자열, 중복 이메일, 음수 금액, 존재하지 않는 부모 참조, 잘못된 상태, 두 번째 활성 신청은 실패해야 합니다. 성공해야 할 값과 실패해야 할 값을 모두 테스트해야 설계가 적절한지 판단할 수 있습니다.

## 16. 초기화는 편의 기능이 아니라 삭제 작업입니다

**화면 구성**

```text
reset_course_project.sql
→ ai_database_book 확인
→ 알려진 객체만 삭제
→ 예상 밖 객체가 있으면 전체 ROLLBACK
→ DROP SCHEMA ... CASCADE 사용 안 함
```

**발표 스크립트**

실습을 처음부터 다시 시작할 때 초기화 파일을 사용할 수 있습니다. 하지만 초기화는 되돌리기 버튼이 아니라 실제 테이블과 데이터를 삭제하는 작업입니다.

파일은 현재 데이터베이스가 `ai_database_book`인지 확인하고 알려진 프로젝트 객체만 삭제합니다. 예상하지 않은 객체가 남아 있으면 스키마 삭제가 실패하고 전체 초기화 트랜잭션이 롤백되므로, 예상 밖 객체까지 함께 지우는 `DROP SCHEMA ... 캐스케이드`를 사용하지 않습니다.

## 17. AI 제안은 요구사항 추적표로 검토합니다

**화면 구성**

- 요구사항 없는 `CASCADE`
- 결제·환불 테이블 임의 추가
- 상태 변경 이력 누락 또는 임의 확정
- 활성 중복 신청 인덱스 누락
- `recorded_amount`를 실제 매출로 단정

**발표 스크립트**

에이아이는 이알디와 디디엘 초안을 빠르게 만들 수 있지만, 요구사항에 없는 정책을 확정하거나 중요한 검증을 빠뜨릴 수 있습니다.

그래서 에이아이 결과는 요구사항 아이디, 프로젝트 결정, 미확정 질문, 범위 제외 항목과 대조합니다. 특히 삭제 정책, 결제·환불, 상태 변경 이력, 활성 중복 신청, 금액 의미는 반드시 사람이 확인해야 합니다.

## 18. 핵심 정리: 프로젝트는 구조와 증거로 완성됩니다

**화면 구성**

```text
범위
→ 요구사항·결정·질문
→ 한 행의 의미
→ 관계와 ERD
→ 제약조건·인덱스
→ 샘플·변경·검증
→ AI 수정 근거
```

**발표 스크립트**

챕터 07의 핵심은 하나의 실행 가능한 프로젝트를 완성하는 것입니다. 하지만 단순히 테이블 네 개를 만드는 것이 목표는 아닙니다.

각 테이블의 한 행 의미, 관계 문장, 확정 규칙, 제약조건, 부분 고유 인덱스, 샘플 데이터와 검증값이 하나로 이어져야 합니다. 이 연결을 설명할 수 있을 때 다음 장의 조인과 집계 분석으로 넘어갈 준비가 된 것입니다.
