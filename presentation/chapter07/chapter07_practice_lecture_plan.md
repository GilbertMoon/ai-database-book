# Chapter 07 실습 발표 강의안

## 온라인 강의 수강신청 DB를 파일 순서대로 실행하고 검증하기

> 기준: 초보자가 “무엇을 실행하고, 무엇이 나와야 하며, 다르면 무엇을 확인해야 하는지”를 직관적으로 이해할 수 있어야 한다.

## 1. 온라인 강의 DB를 파일 순서대로 실행하고 검증합니다

**화면 구성**

- 큰 제목: 온라인 강의 DB를 파일 순서대로 실행하고 검증합니다
- 흐름: 스키마 생성 → 샘플 입력 → 변경 시나리오 → 검증 SQL → 경계·오류 테스트
- 키워드: 실행 순서 / RETURNING / 검증 결과

**발표 스크립트**

이번 실습은 Chapter 07 프로젝트를 실제 PostgreSQL에서 재현하는 과정입니다. 목표는 파일을 실행했다는 사실이 아니라, 각 단계가 어떤 상태를 만들어야 하는지 알고 확인하는 것입니다.

먼저 전용 스키마와 네 테이블을 만듭니다. 그다음 기준 샘플 데이터를 넣고, 변경 시나리오를 실행합니다.

마지막으로 행 수, 관계, 금액 검산값, 경계값과 오류값을 확인합니다. 초보자에게 가장 중요한 습관은 실행 전에 예상하고, 실행 후 결과를 확인하는 것입니다.

## 2. 이번 실습의 완료 기준

**화면 구성**

- 체크리스트
  - 프로젝트 파일을 올바른 순서로 실행
  - 기준 행 수와 IDENTITY 다음 값 확인
  - INSERT와 UPDATE 결과를 RETURNING으로 확인
  - 최종 검증 SQL의 기대값 설명
  - 오류 테스트 후 필요하면 ROLLBACK으로 복구

**발표 스크립트**

실습이 끝났을 때 여러분은 다섯 가지를 할 수 있어야 합니다. 첫째, 어떤 파일을 먼저 실행해야 하는지 설명할 수 있어야 합니다.

둘째, 샘플 데이터를 넣은 뒤 행 수와 IDENTITY 다음 값을 확인할 수 있어야 합니다. 셋째, 변경 SQL을 실행할 때 RETURNING 결과를 보고 실제 변경된 행을 확인해야 합니다.

넷째, 검증 SQL의 숫자가 왜 그 값이어야 하는지 설명할 수 있어야 합니다. 마지막으로 오류 테스트 후 트랜잭션이 실패 상태가 되면 ROLLBACK으로 복구할 수 있어야 합니다.

## 3. 실행 파일은 역할이 다릅니다

**화면 구성**

| 순서 | 파일 | 역할 |
|---:|---|---|
| 1 | 01_course_project_schema.sql | 스키마·테이블·제약조건·인덱스 생성 |
| 2 | 02_course_project_seed.sql | 기준 샘플 데이터 입력 |
| 3 | 03_course_project_changes.sql | 신규 신청과 상태 변경 |
| 4 | 04_course_project_validation.sql | 최종 행 수·관계·검산값 확인 |
| 5 | 05_course_project_integrity_tests.sql | 경계·오류 테스트를 하나씩 실행 |

**발표 스크립트**

파일 이름 앞의 숫자는 장식이 아닙니다. 실행 순서를 나타냅니다. 01 파일은 데이터가 들어갈 구조를 만듭니다. 02 파일은 기준 샘플 데이터를 넣습니다.

03 파일은 실제 서비스에서 일어날 수 있는 변경을 적용합니다. 04 파일은 최종 상태가 맞는지 조회만 합니다. 데이터를 변경하지 않으므로 여러 번 실행해도 안전한 편입니다.

05 파일은 경계값과 오류값을 테스트합니다. 특히 오류 SQL은 전체 실행이 아니라 한 구간씩 선택 실행해야 합니다.

## 4. 먼저 내가 어디에서 실행 중인지 확인합니다

**화면 구성**

```sql

```

- 확인 카드

  - Schema: course_project일 필요는 없음
  - 이름: 항상 course_project.students처럼 명시

**발표 스크립트**

실습 전에 가장 먼저 할 일은 내가 어디에서 실행하고 있는지 확인하는 것입니다. current_database는 ai_database_book이어야 합니다. 다른 데이터베이스에서 실행하면 프로젝트 객체가 엉뚱한 곳에 만들어질 수 있습니다.

## 6. DDL은 문법보다 규칙 중심으로 읽습니다

**화면 구성**

```sql
UNIQUE (email)
CHECK (char_length(trim(name)) > 0)
CHECK (status IN ('신청', '수강중', '완료', '취소'))
CHECK (paid_amount >= 0)
FOREIGN KEY (...) ON DELETE RESTRICT
```

**발표 스크립트**

DDL을 볼 때는 CREATE TABLE 전체를 한 줄씩 읽기보다 규칙 단위로 봅니다. 학생과 강사의 이메일은 정확히 같은 문자열이 중복될 수 없습니다. 그래서 UNIQUE가 있습니다.

이름과 이메일은 NOT NULL뿐 아니라 trim 후 길이가 0보다 커야 한다는 CHECK도 필요합니다. 수강신청의 status는 신청, 수강중, 완료, 취소 중 하나여야 합니다. paid_amount는 0 이상이어야 합니다.

외래키와 RESTRICT는 존재하는 부모만 참조하고, 이력이 있는 부모를 실수로 삭제하지 못하게 합니다.

## 8. 명시적 ID 뒤에는 다음 자동값을 조정합니다

**화면 구성**

| 테이블 | 샘플 최댓값 | 다음 자동값 |
|---|---:|---:|
| students | 103 | 104 |
| instructors | 202 | 203 |
| courses | 303 | 304 |
| enrollments | 1004 | 1005 |

**발표 스크립트**

이번 프로젝트는 관계를 쉽게 확인하기 위해 샘플 ID를 직접 넣습니다. 하지만 IDENTITY 컬럼에 값을 직접 넣었다고 해서 다음 자동 번호가 항상 그 다음 값으로 맞춰지는 것은 아닙니다.

그래서 02 파일의 마지막에서 각 테이블의 IDENTITY 다음 값을 조정합니다. students는 104, instructors는 203, courses는 304, enrollments는 1005부터 시작하도록 맞춥니다.

이 작업을 하지 않으면 나중에 ID를 생략한 INSERT에서 이미 사용한 ID와 충돌할 수 있습니다.

## 9. 03 파일은 세 가지 변화를 적용합니다

**화면 구성**

- 카드 1: 신규 신청 — 학생 102가 강의 302 신청, ID 1005
- 카드 2: 완료 처리 — 신청 1001, 수강중 → 완료
- 카드 3: 취소 처리 — 신청 1004, 신청 → 취소, 금액 유지

**발표 스크립트**

03 파일은 실제 서비스에서 일어날 수 있는 변화를 적용합니다. 먼저 학생 102가 강의 302를 새로 신청합니다. 이때 같은 학생과 강의 조합에 이미 신청 또는 수강중인 행이 없는지 먼저 확인합니다.

그다음 신청 1001은 수강중에서 완료로 바뀝니다. 신청 1004는 신청에서 취소로 바뀝니다.

중요한 점은 취소된 신청을 삭제하지 않는다는 것입니다. 그리고 paid_amount도 0으로 바꾸지 않습니다. 신청 당시 기록된 금액으로 남깁니다.

## 10. 신규 신청 전 확인 → INSERT → RETURNING

**화면 구성**

```sql
SELECT *
FROM course_project.enrollments
WHERE student_id = 102
  AND course_id = 302
  AND status IN ('신청', '수강중');

INSERT INTO course_project.enrollments (...)
VALUES (1005, 102, 302, '2026-04-07', '신청', 120000)
RETURNING *;
```

**발표 스크립트**

신규 신청을 넣기 전에 먼저 확인할 것이 있습니다. 학생 102가 실제로 존재하는지, 강의 302가 실제로 존재하는지, 그리고 같은 학생과 강의 조합의 진행 중 신청이 이미 있는지 확인합니다.

진행 중 신청 조회 결과가 0행이어야 새 신청을 넣을 수 있습니다. 그다음 INSERT를 실행하고 RETURNING 결과로 새로 들어간 행을 확인합니다.

RETURNING은 방금 바뀐 데이터를 바로 보여 주기 때문에 초보자가 INSERT 결과를 확인하기에 매우 좋은 습관입니다.

## 11. UPDATE에는 예상 이전 상태 조건을 넣습니다

**화면 구성**

```sql
UPDATE course_project.enrollments
SET status = '완료'
WHERE id = 1001
  AND status = '수강중'
RETURNING *;

UPDATE course_project.enrollments
SET status = '취소'
WHERE id = 1004
  AND status = '신청'
RETURNING *;
```

**발표 스크립트**

UPDATE에서 WHERE id만 쓰면 현재 상태가 무엇이든 덮어쓸 수 있습니다. 그래서 신청 1001을 완료로 바꿀 때는 현재 상태가 수강중인지 조건에 넣습니다.

신청 1004를 취소로 바꿀 때도 현재 상태가 신청인지 확인합니다. RETURNING 결과가 1행이면 예상한 행이 바뀐 것입니다. 0행이면 해당 ID가 없거나, 예상 이전 상태와 실제 상태가 다르다는 뜻입니다.

상태 CHECK는 허용값 목록만 검사합니다. 수강중에서 완료로 가야 한다는 전이 순서까지 자동으로 보장하지는 않습니다.

## 13. 최소 JOIN으로 서비스 화면을 확인합니다

**화면 구성**

```sql
SELECT e.id, s.name, c.title, i.name,
       e.status, e.paid_amount
FROM course_project.enrollments AS e
JOIN course_project.students AS s ON e.student_id = s.id
JOIN course_project.courses AS c ON e.course_id = c.id
JOIN course_project.instructors AS i ON c.instructor_id = i.id
ORDER BY e.id;
```

**발표 스크립트**

정규화된 테이블은 분리되어 있지만, 서비스에서 필요한 정보는 관계를 따라 다시 조회할 수 있어야 합니다.

수강신청 목록을 보여 주려면 enrollments에서 신청 상태와 금액을 가져오고, students에서 학생 이름을 가져옵니다. courses에서 강의 제목을 가져오고, instructors에서 강사 이름을 가져옵니다.

이 장에서는 JOIN을 깊게 설명하지 않습니다. 자세한 조인은 Chapter 08에서 다룹니다. 여기서는 분리된 테이블이 실제 서비스 화면에 필요한 정보로 다시 연결되는지만 확인합니다. 기대 결과는 수강신청 5건입니다.

## 14. 금액 합계는 취소 포함 여부를 구분합니다

**화면 구성**

- 전체 저장 기준: 신청 5건, 590000원
- 취소 제외 기준: 신청 4건, 440000원
- 강조: 전체 저장 금액은 취소 신청의 당시 금액도 포함한다.

**발표 스크립트**

금액 검산에서 중요한 것은 어떤 기준으로 합계를 내는지입니다. 전체 저장 결제금액은 enrollments에 저장된 paid_amount를 모두 더합니다.

취소된 신청 1004의 150000원도 신청 당시 사실이므로 포함됩니다. 그래서 전체 합계는 590000원입니다.

반면 취소를 제외한 신청만 보면 4건이고 금액 합계는 440000원입니다. 이 값은 실제 매출이나 환불 정산 기준이 아닙니다. Chapter 07의 기본 프로젝트에서는 환불 이력을 다루지 않기 때문입니다.

## 15. 경계값은 오류가 아니라 허용 범위입니다

**화면 구성**

| 테스트 | 기대 결과 | 의미 |
|---|---|---|
| 가격 0인 무료 강의 | 성공 | 0은 확정 금액 |
| paid_amount = 0 | 성공 | 무료 신청 |
| description = NULL | 성공 | 선택 설명 |
| 한 글자 학생 이름 | 성공 | 공백이 아님 |
| 완료 이력 뒤 재신청 | 성공 | 부분 인덱스 범위 밖 |

**발표 스크립트**

오류 테스트만 하면 제약조건이 너무 강하게 만들어졌는지 알기 어렵습니다. 무료 강의 가격 0은 오류가 아닙니다. NULL도 아닙니다. 확정된 금액이 0원이라는 뜻입니다.

paid_amount가 0인 무료 신청도 성공해야 합니다. description은 선택 속성이므로 NULL을 허용합니다. 학생 이름은 공백만 입력하는 것은 금지하지만 한 글자 이름은 정상입니다.

완료 이력 뒤 동일 학생과 강의의 재신청도 이번 정책에서는 허용됩니다. 부분 고유 인덱스는 신청 또는 수강중 상태만 제한하기 때문입니다.

---

## 16. 오류 테스트는 차단 규칙을 확인합니다

**화면 구성**

| 오류 입력 | 예상 차단 |
|---|---|
| NULL·공백 이름, 공백 이메일 | NOT NULL / CHECK |
| 중복 학생·강사 이메일 | UNIQUE |
| 허용되지 않은 난이도·상태 | CHECK |
| 음수 가격·음수 결제 금액 | CHECK |
| 없는 학생·강사·강의 참조 | FOREIGN KEY |
| 참조 중 부모 삭제 | RESTRICT |

**발표 스크립트**

05 파일의 오류 SQL은 한 번에 모두 실행하지 않습니다. 각 테스트를 실행하기 전에 어떤 규칙이 막아야 하는지 먼저 예상합니다.

실행 후에는 단순히 실패했다는 사실이 아니라 예상한 제약조건 또는 인덱스 때문에 실패했는지 확인합니다.

예를 들어 중복 이메일은 UNIQUE가 막아야 합니다. 없는 학생을 참조하는 수강신청은 FOREIGN KEY가 막아야 합니다. 오류 SQL을 여러 개 동시에 실행하면 어떤 테스트가 어떤 오류를 만든 것인지 구분하기 어렵습니다.

## 17. 두 번째 활성 신청은 실패해야 합니다

**화면 구성**

```sql
CREATE UNIQUE INDEX uq_course_enrollments_active
ON course_project.enrollments (student_id, course_id)
WHERE status IN ('신청', '수강중');
```

- 완료·취소 이력은 보존
- 신청·수강중 중복은 차단

**발표 스크립트**

부분 고유 인덱스 테스트는 이 프로젝트에서 매우 중요합니다. 이미 같은 학생과 강의 조합에 신청 또는 수강중 상태가 있다면, 두 번째 신청 또는 수강중 행은 실패해야 합니다.

하지만 완료나 취소 상태의 과거 이력이 있는 것은 괜찮습니다. 이력은 보존해야 하기 때문입니다.

따라서 이 테스트의 핵심은 “중복을 모두 막는다”가 아닙니다. 정확히 말하면 “현재 진행 중인 중복만 막고, 완료와 취소 이력은 허용한다”입니다.

## 18. current transaction is aborted가 나오면 ROLLBACK합니다

**화면 구성**

```sql
ERROR: current transaction is aborted

ROLLBACK;

SELECT COUNT(*) FROM course_project.students;
SELECT COUNT(*) FROM course_project.enrollments;
```

**발표 스크립트**

수동 커밋 상태이거나 명시적 트랜잭션 안에서 오류가 발생하면 PostgreSQL은 현재 트랜잭션을 실패 상태로 둡니다.

이 상태에서는 오류를 수정한 SQL뿐 아니라 단순한 SELECT도 계속 실패할 수 있습니다. 메시지에는 current transaction is aborted가 나타납니다.

이때 해결 방법은 제약조건을 지우는 것이 아닙니다. ROLLBACK을 실행해 실패한 트랜잭션을 취소한 뒤 다음 테스트를 진행합니다. ROLLBACK 후에는 기준 행 수를 다시 조회해 오류 테스트가 정상 데이터를 망가뜨리지 않았는지 확인합니다.

## 19. reset 파일은 처음부터 다시 시작할 때만 사용합니다

**화면 구성**

```text
enrollments
→ courses
→ instructors
→ students
→ course_project schema
```

- 강조: DROP SCHEMA ... CASCADE를 습관적으로 사용하지 않는다.

**발표 스크립트**

reset_course_project.sql은 실습을 처음부터 다시 시작해야 할 때만 사용합니다. 삭제 순서는 자식에서 부모 방향입니다. enrollments가 students와 courses를 참조하므로 enrollments를 먼저 삭제해야 합니다.

중요한 점은 DROP SCHEMA CASCADE를 습관적으로 사용하지 않는 것입니다. CASCADE는 예상하지 못한 객체까지 조용히 지울 수 있습니다.

이번 초기화 파일은 현재 데이터베이스를 확인하고, 알려진 프로젝트 객체만 순서대로 삭제하도록 설계합니다. 초기화도 실습의 일부이므로 안전하게 다뤄야 합니다.

## 20. Chapter 08로 넘길 최종 상태를 확인합니다

**화면 구성**

```text
students 3
instructors 2
courses 3
enrollments 5
1001 완료 / 1004 취소 / 1005 신청
전체 저장 결제금액 590000
취소 제외 결제금액 440000
활성 중복 신청 0건
```

**발표 스크립트**

실습의 마지막은 다음 장으로 넘어갈 수 있는 상태인지 확인하는 것입니다. 행 수는 students 3, instructors 2, courses 3, enrollments 5입니다.

신청 1001은 완료, 1004는 취소, 1005는 신청 상태입니다. 전체 저장 결제금액은 590000원이고, 취소를 제외한 결제금액은 440000원입니다.

진행 중 중복 신청은 0건이어야 합니다. 이 상태가 맞으면 Chapter 08에서 조인과 조회를 배울 때 모든 학생이 같은 데이터 상태에서 출발할 수 있습니다.
