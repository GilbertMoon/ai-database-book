# Chapter 07 실습 발표 강의안

## 온라인 강의 수강신청 DB를 파일 순서대로 실행하고 검증하기

> 목적: Chapter 07 프로젝트 파일을 순서대로 실행하고, 각 단계의 기대 상태를 행 수·관계·상태·금액·오류 테스트로 검증한다.  
> 기준: 초보자가 “무엇을 실행했고 무엇이 나와야 하는지”뿐 아니라 “다르면 어느 단계로 돌아가 확인해야 하는지”를 직관적으로 이해할 수 있어야 한다.

## 1. 이번 실습은 파일 실행이 아니라 상태 검증입니다

**화면 구성**

```text
01 schema
→ 02 seed
→ 03 changes
→ 04 validation
→ 05 core tests / 06 optional tests
```

**발표 스크립트**

이번 실습에서는 온라인 강의 수강신청 DB를 실제로 만듭니다. 하지만 목표는 파일을 모두 실행하는 것이 아니라, 각 파일이 어떤 상태를 만들어야 하는지 확인하는 것입니다.

핵심 경로는 스키마 생성, 기준 데이터 입력, 변경 시나리오, 최종 검증입니다. 그 뒤 05에서 핵심 경계·오류 규칙을, 06에서 선택 경계를 확인합니다. 중간 결과가 예상과 다르면 다음 파일로 넘어가지 않습니다.

## 2. 실행 전에 위치와 자동 커밋을 확인합니다

**화면 구성**

```sql
SELECT current_database();
SELECT current_schema();
SHOW search_path;
```

- 기대 데이터베이스: `ai_database_book`
- 테이블 이름은 항상 `course_project.students`처럼 명시
- Auto-commit / Manual commit 상태를 알고 실행

**발표 스크립트**

가장 먼저 현재 데이터베이스를 확인합니다. 이 프로젝트는 `코스 프로젝트` 스키마를 명시해서 사용하므로 현재 스키마가 꼭 `코스 프로젝트`일 필요는 없습니다.

01, 02, 03과 초기화 파일은 에스큐엘 안에서 `BEGIN`과 `COMMIT`으로 작업 단위를 직접 묶습니다. 따라서 클라이언트의 자동 커밋 여부와 별개로 이 파일 내부 작업은 하나의 트랜잭션으로 처리됩니다. 다만 05와 06의 주석 테스트를 수동으로 실행할 때는 현재 커밋 모드를 알고 있어야 오류 후 상태를 정확히 처리할 수 있습니다.

실행 후에는 네 테이블과 부분 고유 인덱스뿐 아니라 명명 제약조건 15개, 낫 널 열 20개, 네 테이블 0행 상태까지 자동 확인합니다. 중간 생성이 실패하면 전체 트랜잭션이 확정되지 않습니다.

## 4. 스키마 파일에서 제약조건의 역할을 읽습니다

**화면 구성**

| 확인 항목 | 예 |
|---|---|
| PK | 각 테이블 `id` |
| FK | `courses.instructor_id`, `enrollments.student_id` |
| CHECK | 상태, 난이도, 금액, 공백 문자열 |
| UNIQUE | 학생·강사 이메일 |
| 부분 고유 인덱스 | 활성 중복 신청 차단 |

**발표 스크립트**

스키마 파일은 단순히 테이블을 만드는 파일이 아닙니다. 이 안에는 업무 규칙을 디비엠에스가 검사할 수 있게 만든 제약조건이 들어 있습니다.

초보자는 이 단계에서 제약조건 이름을 외울 필요는 없습니다. 대신 어떤 오류를 막기 위한 규칙인지 읽어야 합니다. 예를 들어 음수 가격은 `체크`가 막고, 존재하지 않는 학생 신청은 외래키가 막습니다.

## 6. 명시적 ID와 IDENTITY 다음 값을 구분합니다

**화면 구성**

```text
샘플 ID
students: 101~103
instructors: 201~202
courses: 301~303
enrollments: 1001~1004

다음 자동값
enrollments: 1005
```

**발표 스크립트**

샘플 데이터는 관계를 이해하기 쉽도록 명시적 아이디를 사용합니다. 예를 들어 학생 101, 강의 301처럼 번호가 정해져 있습니다.

하지만 명시적 아이디를 입력한다고 해서 아이덴티티의 다음 값이 자동으로 맞춰지는 것은 아닙니다. 그래서 시드 파일 마지막에는 다음 자동값을 조정합니다. 이 조정을 하지 않으면 나중에 자동 생성 아이디가 기존 샘플 아이디와 충돌할 수 있습니다.

## 7. `03_course_project_changes.sql`은 변경 시나리오입니다

**화면 구성**

```text
학생 102 → 강의 302 신규 신청 1005
신청 1001: 수강중 → 완료
신청 1004: 신청 → 취소
```

**발표 스크립트**

세 번째 파일은 데이터가 실제 서비스처럼 변하는 상황을 보여 줍니다. 새 신청을 추가하고, 기존 신청의 상태를 완료와 취소로 변경합니다.

이 파일을 실행하면 최종 신청 수는 4건에서 5건이 됩니다. 신청 1004는 취소되지만 삭제되지 않고, 신청 시 기록 금액 150000도 그대로 남습니다. 세 변경은 하나의 트랜잭션으로 실행됩니다.

## 8. 신규 신청 전에는 기존 활성 신청을 먼저 확인합니다

**화면 구성**

```sql
SELECT *
FROM course_project.enrollments
WHERE student_id = 102
  AND course_id = 302
  AND status IN ('신청', '수강중');
```

- 기대: 0행

**발표 스크립트**

학생 102가 강의 302를 새로 신청하기 전에, 이미 진행 중인 같은 신청이 있는지 확인합니다.

기대 결과는 0행입니다. 0행이어야 새 활성 신청을 넣어도 부분 고유 인덱스와 충돌하지 않습니다. 만약 행이 나온다면 먼저 현재 데이터가 왜 다른지 확인해야 합니다.

## 9. 변경 SQL은 `RETURNING`으로 결과를 확인합니다

**화면 구성**

```sql
UPDATE course_project.enrollments
SET status = '완료'
WHERE id = 1001
  AND status = '수강중'
RETURNING *;
```

**발표 스크립트**

변경 에스큐엘에서는 `리터닝`을 사용해 실제로 바뀐 행을 바로 확인합니다. 특히 `웨어 id = 1001`만 쓰지 않고 `status = '수강중'`도 함께 넣습니다.

이 조건은 “내가 생각한 이전 상태가 맞을 때만 변경한다”는 안전장치입니다. `리터닝`이 0행이면 현재 상태가 예상과 다르므로 원인을 확인해야 합니다.

## 10. 변경 파일 실행 후 핵심 상태를 확인합니다

**화면 구성**

| 신청 ID | 기대 상태 | 기대 기록 금액 |
|---:|---|---:|
| 1001 | 완료 | 100000 |
| 1004 | 취소 | 150000 |
| 1005 | 신청 | 120000 |

**발표 스크립트**

변경 후에는 신청 1001, 1004, 1005를 확인합니다. 1001은 완료, 1004는 취소, 1005는 신청 상태여야 합니다.

여기서 중요한 점은 취소된 1004의 기록 금액이 0으로 바뀌지 않는다는 것입니다. 이 값은 환불 후 매출이 아니라 신청 시점에 신청 행에 기록한 금액입니다.

## 12. 관계 검증은 “연결이 실제로 되는가”를 확인합니다

**화면 구성**

```text
학생 101의 신청 = 2행
강의 301의 신청 = 2행
강사 201의 강의 = 2행
고아 관계 = 0행
```

**발표 스크립트**

관계 검증은 외래키가 선언되어 있다는 사실만 확인하는 것이 아닙니다. 실제 샘플 데이터에서 1:N 관계가 표현되는지 봅니다.

학생 101은 여러 강의를 신청해야 하고, 강의 301에는 여러 학생이 신청해야 하며, 강사 201은 여러 강의를 담당해야 합니다. 반대로 부모가 없는 고아 관계는 0행이어야 합니다.

## 15. 실패해야 하는 오류값은 한 테스트씩 실행합니다

**화면 구성**

- 중복 이메일·공백 문자열
- 잘못된 난이도·상태
- 음수 가격·기록 금액
- 없는 강사·학생·강의 참조
- 두 번째 활성 신청
- 참조 중인 부모 삭제

**발표 스크립트**

05는 핵심 요구사항의 실패 사례를, 06은 공백 문자열의 세부 경계를 확인합니다. 주석 처리된 테스트는 한꺼번에 실행하지 않고 하나씩 해제해 어떤 제약조건이나 인덱스가 차단했는지 확인합니다.

오류 메시지가 나온 것은 실패가 아니라 기대한 검증 결과일 수 있습니다. 중요한 것은 오류 후 기존 정상 데이터가 유지되는지 다시 04 또는 테스트 파일의 기준 상태 검사로 확인하는 것입니다.

## 16. 두 번째 활성 신청 오류는 부분 고유 인덱스의 증거입니다

**화면 구성**

```text
같은 student_id + course_id
상태가 신청 또는 수강중
→ 두 번째 행 실패

완료·취소 이력 뒤 재신청
→ 허용 가능
```

**발표 스크립트**

부분 고유 인덱스는 완료·취소 이력을 지우지 않으면서 현재 진행 중인 중복만 막습니다.

따라서 같은 학생과 강의의 두 번째 활성 신청은 실패해야 합니다. 하지만 완료나 취소 이력이 있는 뒤 새 신청을 허용하는 테스트는 성공해야 합니다. 이 두 결과를 함께 봐야 규칙이 정확한지 알 수 있습니다.

## 17. 오류 후 `current transaction is aborted`가 나오면 `ROLLBACK`합니다

**화면 구성**

```text
Manual commit / BEGIN 안에서 오류
→ current transaction is aborted
→ ROLLBACK;
→ 다음 테스트 실행
```

**발표 스크립트**

05와 06의 주석 테스트를 수동 커밋 상태나 명시적 트랜잭션 안에서 실행하다 오류가 발생하면, 이후 정상 에스큐엘도 실행되지 않을 수 있습니다.

이때 제약조건을 고칠 문제가 아니라 실패한 트랜잭션 상태를 종료해야 합니다. `롤백;`을 실행한 뒤 다음 테스트를 새 상태에서 진행합니다. 트랜잭션의 자세한 원리는 챕터 09에서 다룹니다.

## 18. 초기화 파일은 마지막 수단으로 사용합니다

**화면 구성**

```text
reset_course_project.sql
→ 현재 DB 확인
→ 알려진 객체만 삭제
→ 예상 밖 객체가 있으면 전체 ROLLBACK
```

**발표 스크립트**

실습이 꼬였을 때 초기화 파일을 사용할 수 있습니다. 하지만 초기화는 안전한 되돌리기가 아니라 삭제 작업입니다.

현재 데이터베이스를 확인한 뒤 알려진 프로젝트 객체만 자식에서 부모 순서로 삭제합니다. 예상 밖 객체가 남아 있으면 스키마 삭제가 실패하고 트랜잭션 전체가 롤백되므로, 의도하지 않은 객체까지 함께 삭제하지 않습니다.

## 19. AI 사용 기록은 수정 근거까지 남깁니다

**화면 구성**

```markdown
## AI 제안
## 사람이 수정한 내용
## 수정 이유
## 검증 결과
```

**발표 스크립트**

에이아이가 만든 이알디나 에스큐엘을 사용했다면 그대로 붙여 넣고 끝내지 않습니다. 어떤 제안을 받아들였고, 어떤 제안을 수정했는지 기록합니다.

예를 들어 에이아이가 결제 테이블을 임의로 추가했거나, 삭제 정책을 `캐스케이드`로 제안했거나, 활성 중복 신청 인덱스를 빠뜨렸다면 수정 이유를 남겨야 합니다.

## 20. 최종 완료 기준은 구조·데이터·오류 테스트가 모두 맞는 것입니다

**화면 구성**

- 네 테이블과 규칙 생성
- 기본 데이터와 변경 시나리오 완료
- 최종 행 수와 검산값 일치
- 고아 관계·활성 중복 신청 0행
- 허용 경계값 성공
- 금지 오류값 실패
- Chapter 08 인계 기준 유지

**발표 스크립트**

챕터 07 실습의 완료 기준은 네 테이블이 만들어졌다는 것만이 아닙니다.

구조, 기준 데이터, 변경 시나리오, 최종 검증값, 관계 검증, 경계값과 오류값이 모두 맞아야 합니다. 이 상태에서 다음 장이 같은 스키마와 `recorded_amount`를 그대로 읽을 수 있어야 프로젝트 인계까지 완성됩니다.
