# [AI 시대의 데이터베이스 입문 13] AI가 만든 DB 설계와 SQL, 어떻게 검증해야 할까?

안녕하세요. 아토믹데브입니다.

지난 Chapter 12에서는 RDBMS, JSONB, NoSQL을 조회 패턴과 데이터의 역할에 따라 선택하는 방법을 살펴봤습니다.

이번 시간에는 ChatGPT와 Codex 같은 AI를 데이터베이스 설계와 SQL 작성에 활용할 때, **AI 결과를 어떻게 안전하게 검증할 것인지**를 실습합니다.

AI는 매우 빠르게 ERD, DDL, 테스트 SQL과 수정안을 만들어 줍니다. 하지만 SQL이 실행된다는 사실만으로 설계가 올바른 것은 아닙니다.

이번 Chapter의 핵심은 다음 한 문장입니다.

```text
AI 결과는 정답이 아니라 검토해야 할 변경 후보이다.
```

## STEP 1. AI는 빠르지만 최종 책임자는 아닙니다

ChatGPT와 Codex에 다음처럼 요청하면 매우 빠르게 데이터베이스 구조를 받을 수 있습니다.

```text
온라인 강의 서비스의
학생, 강사, 강의, 수강신청, 결제 테이블을
PostgreSQL로 설계해 주세요.
```

AI는 몇 초 만에 다음을 만들어 줄 수 있습니다.

```text
테이블 후보
PK / FK
CREATE TABLE
CHECK 제약조건
UNIQUE
샘플 데이터
JOIN SQL
테스트 SQL
```

하지만 다음과 같은 문제가 숨어 있을 수 있습니다.

```text
요구사항에 없는 UNIQUE를 추가한다.
삭제 정책이 미확정인데 ON DELETE CASCADE를 넣는다.
현재 강의 가격과 신청 당시 금액을 같은 값으로 취급한다.
결제가 없는 신청을 오류로 가정한다.
운영 데이터를 DROP하는 초기화 SQL을 만든다.
실제 개인정보나 비밀번호를 테스트 데이터에 포함한다.
```

따라서 AI 결과는 바로 적용하는 것이 아니라 검증해야 합니다.

## STEP 2. 먼저 요구사항을 세 종류로 나눕니다

AI에게 요청하기 전에 다음을 분리합니다.

```text
확인된 요구사항
현재 프로젝트에서 선택한 결정
아직 미확정인 정책
```

예를 들어 다음과 같습니다.

### 확인된 요구사항

```text
학생 이메일은 공백일 수 없다.
강의는 반드시 한 명의 강사를 참조한다.
수강 상태는 정해진 값만 허용한다.
가격과 금액은 음수일 수 없다.
신청 중/수강중 상태는 학생-강의 조합당 최대 한 건이다.
```

### 현재 프로젝트 결정

```text
완료·취소 이후 재신청은 허용한다.
부모 행 삭제는 RESTRICT로 처리한다.
결제 없는 신청도 허용한다.
```

### 아직 미확정인 정책

```text
학생 이메일은 대소문자를 같은 값으로 볼 것인가?
개인정보는 몇 년 동안 보관하는가?
부분 환불을 지원할 것인가?
상태 전이 규칙을 DB에서 강제할 것인가?
```

AI가 미확정 정책을 임의로 확정하지 않도록 해야 합니다.

## STEP 3. 요구사항에 ID를 붙이면 검증이 쉬워집니다

이번 실습에서는 다음처럼 ID를 사용합니다.

```text
P13-R01 → 확인된 요구사항
P13-D01 → 현재 결정
P13-T01 → 테스트
P13-V01 → 검증 단계
```

예를 들어 다음과 같습니다.

| ID | 요구사항 |
| --- | --- |
| P13-R01 | 학생 이메일은 공백이 아니며 같은 문자열 중복을 허용하지 않는다 |
| P13-R02 | 강사 이메일도 공백과 같은 문자열 중복을 허용하지 않는다 |
| P13-R03 | 강의는 정확히 한 명의 강사를 참조한다 |
| P13-R04 | 학생과 강의는 N:M 관계이며 enrollments로 연결한다 |
| P13-R05 | 상태는 허용값만 사용한다 |
| P13-R06 | 가격과 금액은 음수가 될 수 없다 |
| P13-R07 | 결제는 수강신청을 참조한다 |
| P13-R08 | 실제 카드번호와 CVV를 저장하지 않는다 |
| P13-R09 | 신청·수강중은 학생·강의 조합당 최대 한 건이다 |

이렇게 하면 나중에 다음 질문을 할 수 있습니다.

```text
P13-R05는 어떤 CHECK 제약조건으로 구현됐는가?
P13-R07은 어떤 FK로 구현됐는가?
P13-R09는 어떤 UNIQUE 인덱스로 구현됐는가?
```

## STEP 4. AI에게는 질문 한 줄보다 문맥 묶음을 줍니다

좋은 데이터베이스 결과를 얻으려면 단순 요청보다 다음 내용을 함께 제공하는 것이 좋습니다.

```text
업무 목표
확인된 요구사항
프로젝트 결정
미확정 정책
PostgreSQL 버전
현재 테이블 구조
대표 샘플 데이터
수정할 파일 범위
수정하면 안 되는 범위
검증 기준
완료 보고 형식
```

예시 프롬프트입니다.

```text
PostgreSQL 데이터베이스 설계를 검토해 주세요.

확인된 요구사항:
- 학생 이메일은 공백 불가
- 동일 문자열 중복 불가
- 강의는 한 명의 강사를 참조
- 상태는 신청/수강중/완료/취소만 허용
- 가격은 음수 불가

미확정 정책:
- 이메일 대소문자 처리
- 개인정보 보관 기간
- 부분 환불

중요:
미확정 정책을 임의로 UNIQUE, CHECK, CASCADE 등으로 확정하지 마세요.

출력:
1. 테이블별 한 행 의미
2. PK/FK/제약조건 제안
3. 요구사항 ID별 구현 위치
4. 위험한 가정
5. 테스트 SQL
```

## STEP 5. 실제 개인정보와 비밀번호는 프롬프트에 넣지 않습니다

AI를 사용할 때도 보안 원칙은 그대로 적용됩니다.

다음 정보는 그대로 붙여 넣지 않는 것이 좋습니다.

```text
실제 고객 이름
실제 이메일
비밀번호
API Key
DB 접속 URL
운영 데이터 덤프
카드번호
CVV
```

테스트 데이터는 가상 값으로 바꿉니다.

```text
student@example.com
course_test_01
payment_ref_test_001
```

오류 메시지 역시 재현에 필요한 기술 정보는 남기되 개인정보와 비밀 정보는 마스킹합니다.

## STEP 6. AI 결과는 운영 DB가 아니라 격리 환경에서 실행합니다

이번 Chapter에서는 별도의 검토 스키마를 사용합니다.

```text
ai_review_lab
```

예를 들어 다음 구조를 만들 수 있습니다.

```text
ai_review_lab.students
ai_review_lab.instructors
ai_review_lab.courses
ai_review_lab.enrollments
ai_review_lab.payments
```

기존 프로젝트인 `course_project`는 변경하지 않습니다.

이렇게 격리하는 이유는 간단합니다.

```text
AI SQL이 잘못돼도 기존 데이터를 보호할 수 있다.
DROP이나 DELETE 위험을 제한할 수 있다.
테스트 후 스키마 전체를 쉽게 초기화할 수 있다.
AI가 어떤 객체를 만들었는지 구분하기 쉽다.
```

## STEP 7. 각 테이블의 한 행 의미부터 검토합니다

AI가 테이블을 많이 만들었다고 좋은 설계는 아닙니다.

먼저 각 테이블의 한 행 의미를 확인합니다.

```text
students 한 행
→ 학생 한 명

instructors 한 행
→ 강사 한 명

courses 한 행
→ 개설된 강의 한 개

enrollments 한 행
→ 특정 학생의 특정 강의 신청 사건 한 건

payments 한 행
→ 특정 수강신청과 연결된 결제 상태 한 건
```

한 행 의미가 불분명하면 이후 PK, FK, UNIQUE와 JOIN도 흔들릴 가능성이 큽니다.

## STEP 8. AI가 만든 PRIMARY KEY와 FOREIGN KEY를 확인합니다

예를 들어 다음 관계가 필요합니다.

```text
courses.instructor_id
→ instructors.id

enrollments.student_id
→ students.id

enrollments.course_id
→ courses.id

payments.enrollment_id
→ enrollments.id
```

AI가 단순히 이름이나 이메일로 JOIN하게 만들었다면 다시 검토해야 합니다.

좋은 관계는 안정적인 식별자와 명시적인 FK로 연결하는 것이 기본입니다.

---

## STEP 9. UNIQUE가 요구사항보다 강하지 않은지 확인합니다

AI가 자주 만드는 실수 중 하나입니다.

예를 들어 다음 제약조건은 지나치게 강할 수 있습니다.

```sql
UNIQUE (student_id, course_id)
```

이렇게 하면 완료나 취소 후 다시 신청하는 것도 막힐 수 있습니다.

이번 프로젝트의 실제 규칙은 다음입니다.

```text
신청 또는 수강중 상태에서는
학생-강의 조합당 최대 한 건
```

PostgreSQL에서는 부분 고유 인덱스로 표현할 수 있습니다.

```sql
CREATE UNIQUE INDEX uq_ai_review_enrollments_active
ON ai_review_lab.enrollments (student_id, course_id)
WHERE status IN ('신청', '수강중');
```

이 구조라면 완료·취소 이력을 남기면서 재신청도 허용할 수 있습니다.

## STEP 10. 삭제 정책을 반드시 확인합니다

AI가 다음과 같이 제안할 수 있습니다.

```sql
ON DELETE CASCADE
```

CASCADE는 편리해 보이지만 매우 강한 정책입니다.

예를 들어 학생 한 명을 삭제했을 때 연결된 수강신청과 결제까지 자동 삭제된다면 정말 업무 정책과 맞을까요?

확정되지 않았다면 다음처럼 보수적으로 접근할 수 있습니다.

```sql
ON DELETE RESTRICT
```

중요한 것은 CASCADE가 나쁘다는 것이 아니라 **업무 정책 근거 없이 자동 적용하지 않는 것**입니다.

## STEP 11. 정상 데이터부터 테스트합니다

AI가 만든 구조에 먼저 정상 데이터를 입력합니다.

예를 들어 다음 내용을 확인합니다.

```text
정상 학생 입력 성공
정상 강사 입력 성공
정상 강의 입력 성공
정상 수강신청 입력 성공
정상 결제 입력 성공
```

정상 데이터조차 저장되지 않는다면 구조 또는 제약조건에 문제가 있는 것입니다.

---

## STEP 12. 경계값 테스트도 필요합니다

금액이 0일 수 있다고 결정했다면 다음 값은 정상이어야 합니다.

```text
price = 0
recorded_amount = 0
```

반대로 다음 값은 실패해야 합니다.

```text
price = -1
recorded_amount = -1000
```

즉 제약조건 테스트에서는 다음 세 종류를 함께 사용합니다.

```text
정상값
경계값
오류값
```

---

## STEP 13. 의도적으로 실패해야 하는 테스트를 만듭니다

좋은 테스트는 성공만 확인하지 않습니다.

예를 들어 다음 테스트는 실패해야 합니다.

```text
공백 이메일 입력
중복 이메일 입력
존재하지 않는 강사 ID 입력
존재하지 않는 학생 ID 입력
허용하지 않은 상태 입력
음수 금액 입력
활성 상태 중복 신청 입력
```

이 테스트가 성공해 버린다면 요구사항이 DB에 제대로 구현되지 않은 것입니다.

---

## STEP 14. 오류 메시지만 보지 말고 SQLSTATE와 constraint도 확인합니다

PostgreSQL 오류를 자동 검증할 때는 오류 문자열 전체보다 다음 정보를 활용할 수 있습니다.

```text
SQLSTATE
constraint name
```

예를 들어 중복 데이터는 일반적으로 unique violation 계열 오류가 발생합니다.

중요한 것은 단순히 “오류가 났다”가 아닙니다.

```text
내가 의도한 제약조건 때문에 실패했는가?
```

를 확인해야 합니다.

---

## STEP 15. PostgreSQL 메타데이터로 실제 구조를 확인합니다

DDL 파일만 읽지 말고 PostgreSQL이 실제로 어떤 구조를 생성했는지 확인합니다.

예를 들어 다음 정보를 조회할 수 있습니다.

```text
테이블 목록
컬럼 타입
NOT NULL 여부
PRIMARY KEY
FOREIGN KEY
UNIQUE
CHECK
인덱스
```

대표적으로 `information_schema`와 PostgreSQL 시스템 카탈로그를 사용할 수 있습니다.

예를 들어 외래키 수와 대상을 확인하면 AI가 필요한 FK를 빠뜨리지 않았는지 검증할 수 있습니다.

## STEP 16. 업무 정합성 SQL을 작성합니다

제약조건을 통과했다고 업무적으로 완벽한 것은 아닙니다.

여러 테이블에 걸친 규칙은 별도 SQL로 검증해야 합니다.

예를 들어 다음과 같은 질문을 확인합니다.

```text
존재하지 않는 학생을 참조하는 신청이 있는가?
존재하지 않는 강의를 참조하는 신청이 있는가?
활성 중복 신청이 있는가?
결제가 연결되지 않은 수강중 신청이 있는가?
신청 금액과 결제 금액이 다른 행이 있는가?
```

이상 데이터를 찾는 SQL의 기대 결과를 다음처럼 정할 수 있습니다.

```text
0행
```

즉 “문제가 없다”는 것도 실행 결과로 증명합니다.

---

## STEP 17. 현재 값과 과거 기록 값을 구분합니다

온라인 강의 프로젝트에서는 다음 두 값이 비슷해 보입니다.

```text
courses.price
→ 현재 강의 기준 가격

enrollments.recorded_amount
→ 신청이 만들어진 시점에 기록한 금액
```

AI가 둘 중 하나를 없애거나 항상 JOIN해서 현재 가격을 사용하도록 바꾼다면 과거 신청 금액이 바뀔 수 있습니다.

따라서 다음 질문을 합니다.

```text
이 값은 현재 사실인가?
과거 사건 당시의 기록인가?
```

이 구분은 주문 가격, 계약 금액, 결제 금액에서도 매우 중요합니다.

---

## STEP 18. 결제 정보에는 저장하면 안 되는 값도 있습니다

결제 테이블을 설계할 때 AI가 실제 카드번호나 CVV 컬럼을 만들지 않는지 확인해야 합니다.

이번 실습에서는 다음처럼 가상 외부 참조값만 사용합니다.

```text
payment_reference
```

예:

```text
PAY-TEST-10001
```

실제 결제 데이터의 보안과 규제 범위는 별도 정책과 결제 서비스 설계가 필요합니다.

---

## STEP 19. AI가 수정한 파일은 diff로 검토합니다

Codex처럼 실제 저장소 파일을 수정할 수 있는 도구를 사용할 때는 변경 후 반드시 diff를 확인합니다.

검토 항목은 다음과 같습니다.

```text
요청한 파일만 수정했는가?
기존 프로젝트 파일을 삭제하지 않았는가?
DROP DATABASE가 추가되지 않았는가?
DROP SCHEMA CASCADE가 예상 범위 밖에 없는가?
대량 DELETE가 추가되지 않았는가?
실제 비밀번호나 URL이 들어가지 않았는가?
테스트 데이터에 개인정보가 들어가지 않았는가?
```

AI가 “완료했습니다”라고 말한 것과 실제 diff는 별개입니다.

---

## STEP 20. 파괴적 SQL은 별도로 표시합니다

특히 다음 명령은 주의해서 검토합니다.

```sql
DROP DATABASE
DROP SCHEMA
DROP TABLE
TRUNCATE
DELETE
ALTER TABLE ... DROP
REVOKE
GRANT
```

이 명령이 필요할 수도 있습니다.

하지만 다음 질문이 필요합니다.

```text
정말 필요한가?
어떤 객체에 적용되는가?
운영 데이터에 영향을 주는가?
롤백 가능한가?
백업 또는 복구 절차가 있는가?
```

---

## STEP 21. 자동 검증 결과를 하나로 모읍니다

검증 항목이 많아지면 마지막에 전체 통과 여부를 자동으로 확인하는 SQL을 만드는 것이 좋습니다.

예를 들어 다음 항목을 확인할 수 있습니다.

```text
필요 테이블 수
필수 FK 수
필수 CHECK 수
필수 NOT NULL 수
부분 고유 인덱스 존재
정상 데이터 행 수
업무 이상 조회 0행
```

모두 통과하면 다음과 같은 메시지를 출력할 수 있습니다.

```text
Chapter 13 AI review validation passed
```

이 메시지는 AI의 설명이 맞다는 뜻이 아니라 **정해 놓은 검증 기준을 실제 DB가 통과했다는 증거**입니다.

---

## STEP 22. 요구사항 추적표를 완성합니다

예를 들어 다음처럼 기록합니다.

| 요구사항 | 구현 위치 | 검증 방법 | 결과 |
| --- | --- | --- | --- |
| P13-R01 | students.email UNIQUE + CHECK | 중복/공백 테스트 | 통과 |
| P13-R03 | courses.instructor_id FK | 메타데이터 확인 | 통과 |
| P13-R05 | status CHECK | 잘못된 상태 입력 | 통과 |
| P13-R06 | price/amount CHECK | 0 및 음수 테스트 | 통과 |
| P13-R09 | 부분 UNIQUE 인덱스 | 활성 중복 신청 | 통과 |

이 표를 만들면 “AI가 설계했다”가 아니라 다음과 같이 설명할 수 있습니다.

```text
어떤 요구사항이
어디에 구현됐고
어떤 실행 결과로 검증됐는가?
```

---

## STEP 23. AI 결과의 최종 상태를 결정합니다

검토가 끝나면 결과를 다음 중 하나로 분류할 수 있습니다.

```text
승인
조건부 승인
보류
거절
```

### 승인

```text
요구사항 반영 확인
정상/경계/실패 테스트 통과
메타데이터 검증 통과
업무 정합성 검증 통과
위험한 diff 없음
```

### 조건부 승인

```text
핵심 구조는 맞지만
운영 전에 추가 정책 확인 필요
```

### 보류

```text
업무 정책이 아직 결정되지 않음
```

### 거절

```text
요구사항 위반
데이터 손실 위험
보안 문제
테스트 실패
```

AI가 만든 결과라고 특별한 승인 기준을 사용하는 것이 아닙니다.

오히려 사람이 작성한 코드와 똑같이 검증해야 합니다.

## AI 활용 실습 1. DB 설계 리뷰 프롬프트 만들기

ChatGPT에 다음과 같이 요청해 보세요.

```text
나는 PostgreSQL 데이터베이스 설계를 검토하고 있습니다.

확정 요구사항과 미확정 정책을 구분해서 제공하겠습니다.

당신은 다음 작업만 해 주세요.
1. 요구사항별 구현 위치 제안
2. PK/FK/CHECK/UNIQUE 후보 제안
3. 지나치게 강한 제약조건 위험 표시
4. 정상/경계/오류 테스트 작성
5. 검증 SQL 작성

미확정 정책을 임의로 확정하지 마세요.
DROP, TRUNCATE, CASCADE 같은 파괴적 변경은 별도 위험 항목으로 표시하세요.
```

AI의 답을 받은 뒤 다음을 확인합니다.

```text
미확정 정책을 임의로 결정했는가?
요구사항보다 강한 UNIQUE가 있는가?
CASCADE를 근거 없이 사용했는가?
실패 테스트가 포함됐는가?
```

## AI 활용 실습 2. AI가 만든 SQL의 검증 계획을 만들어 보세요

다음 프롬프트를 사용해 보세요.

```text
아래 PostgreSQL DDL을 운영 DB에 적용하기 전에 검증하려고 합니다.

운영 데이터는 절대 변경하지 않고
별도 ai_review_lab 스키마에서 검증한다고 가정하세요.

다음 검증 계획을 작성해 주세요.
1. 구조 검증
2. 정상 데이터 테스트
3. 경계값 테스트
4. 의도된 실패 테스트
5. FK/UNIQUE/CHECK 메타데이터 확인
6. 업무 정합성 0행 검증
7. 파괴적 SQL 검토
8. 최종 승인 체크리스트
```

이 프롬프트의 목적은 AI에게 정답을 맡기는 것이 아니라 **검증해야 할 항목을 빠르게 넓히는 것**입니다.

## 오늘의 핵심 정리

이번 Chapter에서 꼭 기억할 내용입니다.

```text
AI 결과
→ 정답이 아니라 변경 후보

확인 요구사항
→ AI가 반드시 지켜야 할 기준

미확정 정책
→ AI가 임의로 결정하면 안 되는 영역

격리 환경
→ 기존 데이터를 보호하며 테스트하는 공간

정상 테스트
→ 해야 할 일이 성공하는지 확인

실패 테스트
→ 하면 안 되는 일이 차단되는지 확인

메타데이터 검증
→ 실제 DB 구조가 예상과 같은지 확인

업무 정합성 검증
→ 여러 테이블 사이 의미가 맞는지 확인

Diff 검토
→ 요청하지 않은 변경과 파괴적 SQL 확인
```

그리고 가장 중요한 흐름은 다음과 같습니다.

```text
요구사항 확인
→ AI 초안 생성
→ 격리 환경 실행
→ 정상/경계/실패 테스트
→ 메타데이터 검증
→ 업무 정합성 검증
→ diff 검토
→ 사람이 최종 승인
```

AI 시대의 데이터베이스 실무자는 SQL을 모두 직접 작성하는 사람이라기보다, **AI가 만든 설계와 SQL을 증거를 기반으로 검증할 수 있는 사람**에 가까워지고 있습니다.
