# STEP 1. AI가 SQL을 만들어 주는데도 DB를 배워야 할까?

요즘은 ChatGPT나 Codex에게 다음과 같이 요청하면 몇 초 만에 SQL을 만들 수 있습니다.

```text
학생 정보를 저장할 PostgreSQL 테이블을 만들어 주세요.
학생별 질문 수를 계산하는 SQL도 작성해 주세요.
```

AI는 테이블 생성문과 조회문을 빠르게 제안합니다. 문법 오류가 발생하면 원인을 설명하고 수정된 코드도 만들어 줍니다.

그렇다면 이제 데이터베이스를 배우지 않아도 될까요?

그렇지 않습니다.

AI는 코드를 만들어 줄 수 있지만 다음과 같은 **업무 규칙**을 자동으로 확정할 수는 없습니다.

```text
학생 이메일은 중복될 수 있는가?
탈퇴한 학생의 데이터는 삭제해야 하는가?
질문이 없는 학생도 통계에 포함해야 하는가?
완료된 질문에는 반드시 답변이 있어야 하는가?
어떤 데이터가 개인정보인가?
누가 어떤 데이터를 조회할 수 있는가?
```

이 질문들은 SQL 문법 문제가 아닙니다. 서비스와 업무를 이해해야 결정할 수 있는 문제입니다.

따라서 AI 시대의 데이터베이스 학습은 SQL 문장을 전부 외우는 과정이 아닙니다.

```text
무엇을 저장해야 하는지 판단한다.
데이터가 어떻게 연결되는지 이해한다.
AI가 만든 구조와 SQL의 문제를 발견한다.
실행 결과가 실제 요구사항과 일치하는지 검증한다.
```

이 네 가지 능력이 더 중요해지고 있습니다.

# STEP 2. 데이터베이스를 배워야 하는 5가지 이유

데이터베이스를 배우는 이유를 다섯 가지로 정리해 보겠습니다.

| 이유 | 확인해야 할 질문 |
| --- | --- |
| AI 결과 검증 | 이 SQL과 숫자가 실제 요구사항에 맞는가? |
| 업무 구조 표현 | 사용자, 주문, 강의, 신청은 어떻게 연결되는가? |
| 정확한 분석 | 중복, 누락, NULL, 집계 기준이 올바른가? |
| 서비스 운영 | 사용자와 업무 상태를 안정적으로 관리할 수 있는가? |
| 안전성과 복구 | 잘못된 변경을 막고 문제가 생기면 복구할 수 있는가? |

핵심을 한 줄로 정리하면 다음과 같습니다.

```text
AI 결과 검증
+ 업무 구조 이해
+ 정확한 분석
+ 안정적인 운영
+ 안전성과 복구
```

AI를 활용하는 서비스도 결국 사용자, 요청, 상태, 결과와 같은 데이터를 지속적으로 저장하고 관리해야 합니다. 데이터베이스는 이런 정보를 구조적으로 관리하기 위한 기본 기술입니다.

---

# STEP 3. 실행되는 SQL과 올바른 SQL은 다르다

다음 요구사항을 보겠습니다.

```text
전체 학생 수를 계산해 주세요.
질문을 한 번도 작성하지 않은 학생도 포함해야 합니다.
```

AI가 다음 SQL을 만들었다고 가정해 보겠습니다.

```sql
SELECT COUNT(*) AS student_count
FROM students AS s
INNER JOIN questions AS q
    ON q.student_id = s.id;
```

SQL 문법 자체는 실행될 수 있습니다.

하지만 이 SQL은 **학생 수**가 아니라 학생과 질문이 연결된 **행의 수**를 세고 있습니다.

예를 들어 데이터가 다음과 같다고 해보겠습니다.

| 학생 | 질문 수 |
| --- | ---: |
| 학생 A | 2 |
| 학생 B | 1 |
| 학생 C | 0 |

전체 학생은 3명입니다.

하지만 `INNER JOIN`을 하면 질문이 없는 학생 C는 빠지고, 학생 A는 질문이 2개이므로 두 번 나타납니다.

```text
학생 A → 질문 2행
학생 B → 질문 1행
학생 C → 0행
합계   → 3행
```

결과 숫자는 우연히 3으로 같지만 의미는 완전히 다릅니다.

전체 학생 수를 세는 것이 목적이라면 더 단순하게 다음 SQL을 사용할 수 있습니다.

```sql
SELECT COUNT(*) AS student_count
FROM students;
```

여기서 가장 중요한 문장은 이것입니다.

> **실행 성공 ≠ 올바른 결과**

그리고 하나 더 기억해 주세요.

> **그럴듯한 숫자 ≠ 검증된 숫자**

AI가 SQL을 만들어 주더라도 결과를 사람이 확인해야 하는 이유입니다.

# STEP 4. AI가 만든 테이블도 구조적으로 틀릴 수 있다

AI에게 온라인 강의 서비스의 수강신청 테이블을 만들어 달라고 하면 다음과 비슷한 구조를 제안할 수 있습니다.

```sql
CREATE TABLE enrollments (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_name VARCHAR(50),
    course_title VARCHAR(100),
    instructor_name VARCHAR(50),
    recorded_amount INTEGER
);
```

처음 보면 학생, 강의, 강사, 금액이 모두 있으므로 문제가 없어 보입니다.

하지만 실제 서비스에서 사용하기 시작하면 여러 문제가 생길 수 있습니다.

- 학생을 이름만으로 구분하기 어렵습니다.
- 같은 학생 이름이 존재할 수 있습니다.
- 강의 제목이 바뀌면 여러 행을 수정해야 할 수 있습니다.
- 강사 이름과 강의 정보가 반복 저장됩니다.
- 학생, 강사, 강의, 수강신청이라는 서로 다른 대상이 한 테이블에 섞여 있습니다.
- 필수 입력값이나 중복 제한 규칙이 없습니다.

즉, **SQL이 실행된다고 좋은 데이터 구조가 되는 것은 아닙니다.**

좋은 데이터베이스를 만들려면 먼저 현실의 업무를 구분해야 합니다.

```text
학생
강사
강의
수강신청
```

그리고 각 대상이 어떻게 연결되는지 생각해야 합니다.

이 부분은 이후 Chapter 05~07에서 ERD, 정규화, 실제 PostgreSQL 테이블 생성으로 연결합니다.

# STEP 5. 현실의 업무를 데이터로 바꾸는 사고방식

데이터베이스를 공부할 때 가장 먼저 익혀야 하는 습관은 현실의 대상을 데이터 구조로 바꾸어 생각하는 것입니다.

온라인 강의 서비스를 예로 들어보겠습니다.

현실에서는 다음과 같은 일이 발생합니다.

```text
학생이 가입한다.
강사가 강의를 만든다.
학생이 강의를 신청한다.
학생이 질문을 남긴다.
강사가 답변한다.
```

이를 데이터 관점으로 보면 다음처럼 나눌 수 있습니다.

```text
students
instructors
courses
enrollments
questions
answers
```

그리고 관계를 생각합니다.

```text
학생 1명 → 여러 수강신청
강의 1개 → 여러 수강신청
학생 1명 → 여러 질문
질문 1개 → 답변 0개 또는 1개 이상
```

이처럼 현실의 업무를 **대상, 속성, 관계**로 바꾸어 생각하는 능력이 데이터 모델링의 출발점입니다.

# STEP 6. 파일, 엑셀, DBMS는 언제 사용해야 할까?

모든 데이터를 무조건 데이터베이스에 저장할 필요는 없습니다.

상황에 따라 파일이나 스프레드시트가 더 편할 수도 있습니다.

| 상황 | 적합한 방법 |
| --- | --- |
| 개인이 잠깐 사용하는 단순 목록 | 텍스트/CSV 파일 |
| 사람이 직접 편집하는 소규모 표 | Excel, Google Sheets |
| 여러 사용자가 동시에 사용하는 서비스 데이터 | DBMS |
| 데이터 간 관계와 규칙을 관리해야 하는 경우 | DBMS |
| 변경 이력, 권한, 트랜잭션이 중요한 경우 | DBMS |

예를 들어 학생 10명의 전화번호를 개인적으로 정리한다면 Excel로도 충분할 수 있습니다.

하지만 수천 명의 학생이 동시에 강의를 신청하고, 신청 상태와 결제 정보가 연결되고, 여러 직원이 데이터를 조회·수정해야 한다면 DBMS가 필요합니다.

중요한 것은 도구 자체가 아니라 **데이터의 규모, 관계, 동시성, 규칙, 안전성**입니다.

# STEP 7. AI가 잘하는 일과 사람이 해야 하는 일

AI는 데이터베이스 작업에서 매우 유용한 도구입니다.

## AI가 잘하는 일

- 요구사항 초안 정리
- 테이블 후보 제안
- SQL 초안 작성
- 오류 메시지 설명
- 테스트 SQL 후보 생성
- 코드 리팩터링과 설명

## 사람이 반드시 확인해야 하는 일

- 업무 규칙의 의미
- 한 행이 무엇을 의미하는지
- 기본키와 관계가 올바른지
- NULL을 허용해야 하는지
- 중복을 허용해야 하는지
- 삭제 정책이 적절한지
- 개인정보와 권한이 안전한지
- SQL 결과가 실제 질문과 일치하는지

정리하면 다음과 같습니다.

```text
AI = 빠른 초안 작성자
사람 = 의미와 결과의 최종 검증자
```

이 책 전체에서 계속 사용하는 원칙입니다.

# 실습 1. AI에게 데이터베이스 설계를 요청해 보기

ChatGPT 또는 Codex에 다음 프롬프트를 입력해 보세요.

```text
온라인 강의 서비스를 만들려고 합니다.
학생, 강사, 강의, 수강신청 정보를 저장할 PostgreSQL 테이블 구조를 제안해 주세요.

각 테이블의 역할과 기본키, 외래키도 설명해 주세요.
초보자가 이해할 수 있도록 쉽게 설명해 주세요.
```

AI의 답을 받은 뒤 바로 믿지 말고 다음 질문을 추가합니다.

```text
방금 만든 데이터베이스 설계에서 문제가 될 수 있는 부분을 스스로 검토해 주세요.

특히 다음을 확인해 주세요.
1. 중복 데이터가 생길 가능성
2. 기본키와 외래키가 적절한지
3. 필수값이 빠진 부분
4. 삭제할 때 문제가 생길 관계
5. 실제 서비스 요구사항을 추가로 확인해야 하는 부분
```

AI에게 **만들어 달라 → 스스로 검토하게 한다**는 흐름을 경험해 보는 것이 이번 실습의 목적입니다.

# 실습 2. 결과가 맞는지 작은 데이터로 검증하기

다음 상황을 직접 생각해 보세요.

```text
학생 A : 질문 2개
학생 B : 질문 1개
학생 C : 질문 0개
```

질문은 다음과 같습니다.

```text
전체 학생 수는 몇 명인가?
학생별 질문 수는 각각 몇 개인가?
질문을 한 번도 하지 않은 학생은 누구인가?
```

AI에게 SQL을 만들어 달라고 요청한 뒤, SQL 결과가 위의 예상 결과와 맞는지 확인합니다.

이 습관이 중요합니다.

```text
예상 결과를 먼저 생각한다.
→ SQL을 만든다.
→ 실행한다.
→ 실제 결과와 비교한다.
```

```text

2. 실행되는 SQL과 올바른 결과를 만드는 SQL은 다를 수 있다.
3. 좋은 데이터베이스는 현실의 대상을 올바르게 구조화하는 것에서 시작한다.

```

AI 시대에는 SQL을 전부 암기하는 능력보다 **AI가 만든 SQL과 데이터 구조가 맞는지 판단할 수 있는 능력**이 더 중요해지고 있습니다.
