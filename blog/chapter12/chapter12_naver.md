## STEP 1. NoSQL은 RDBMS의 반대말이 아닙니다

NoSQL을 처음 접하면 흔히 다음처럼 생각하기 쉽습니다.

```text
RDBMS = SQL을 사용하는 데이터베이스
NoSQL = SQL을 사용하지 않는 데이터베이스
```

하지만 실제로는 그렇게 단순하지 않습니다.

NoSQL은 관계형 테이블 모델만으로 설명되지 않는 여러 저장 모델을 넓게 묶어 부르는 표현입니다.

다음과 같은 오해를 조심해야 합니다.

```text
NoSQL은 스키마가 없다.
→ 실제로는 어디선가 구조 규칙이 필요합니다.

NoSQL에는 트랜잭션이 없다.
→ 제품과 작업 범위에 따라 지원 여부가 다릅니다.

NoSQL은 항상 RDBMS보다 빠르다.
→ 조회 패턴과 데이터 모델이 맞아야 합니다.

NoSQL은 자동으로 무한 확장된다.
→ 파티션 키, 핫스팟, 복제와 운영 설계가 필요합니다.
```

따라서 첫 질문은 제품명이 아니라 이것이어야 합니다.

```text
어떤 데이터를
어떤 키와 조건으로
얼마나 자주 읽고 쓰는가?
```

## STEP 2. 먼저 데이터의 역할을 구분합니다

온라인 강의 서비스를 예로 들어 보겠습니다.

같은 서비스 안에서도 데이터의 성격은 서로 다릅니다.

| 데이터 | 역할 |
| --- | --- |
| 수강신청 | 최종 판단 기준이 되는 원본 |
| 신청 당시 금액 | 반드시 보존해야 하는 원본 사실 |
| 인기 강의 TOP 3 | 원본에서 계산 가능한 파생 데이터 |
| 로그인 세션 | 일정 시간이 지나면 사라져도 되는 상태 |
| 강의 태그·옵션 | 구조가 유연하게 변할 수 있는 메타데이터 |
| 학습 이벤트 | 시간순으로 쌓이는 대량 로그 |
| 추천 관계 | 관계 탐색용 파생 구조 |

이 중 모든 데이터를 같은 방식으로 저장할 필요는 없습니다.

가장 먼저 다음을 구분합니다.

```text
Source of Truth
→ 최종 판단 기준이 되는 원본

Derived Data
→ 원본에서 다시 계산하거나 만들 수 있는 데이터

Cache
→ 빠른 조회를 위해 임시 저장한 파생 데이터

Event Log
→ 시간순으로 쌓이는 사실 기록
```

이 구분이 먼저 되어야 장애가 발생했을 때 무엇을 신뢰할지 결정할 수 있습니다.

## STEP 3. RDBMS가 잘 맞는 경우

PostgreSQL 같은 관계형 데이터베이스는 다음과 같은 상황에서 강합니다.

```text
관계가 명확하다.
PK와 FK가 중요하다.
UNIQUE와 CHECK 같은 제약조건이 중요하다.
여러 테이블 변경을 하나의 트랜잭션으로 처리해야 한다.
JOIN과 집계가 자주 필요하다.
정확한 원본 데이터를 보존해야 한다.
```

예를 들어 수강신청은 다음 관계를 가집니다.

```text
학생
→ 수강신청
→ 강의
```

그리고 다음 규칙도 중요합니다.

```text
존재하지 않는 학생은 신청할 수 없다.
존재하지 않는 강의는 신청할 수 없다.
신청 당시 금액을 정확히 보존해야 한다.
```

이런 데이터는 관계형 데이터베이스가 자연스럽습니다.

---

## STEP 4. NoSQL을 검토할 수 있는 경우

반대로 다음과 같은 요구에서는 NoSQL 계열 저장소를 검토할 수 있습니다.

```text
정확한 키로 매우 빠르게 읽는다.
문서마다 구조가 조금씩 다르다.
특정 파티션의 시간 범위를 매우 많이 읽는다.
여러 단계 관계 탐색이 핵심이다.
대규모 분산 저장이 중요하다.
```

하지만 중요한 점은 이것입니다.

```text
NoSQL을 쓴다고 자동으로 좋은 설계가 되는 것은 아니다.
```

조회 패턴과 데이터 성격이 맞아야 합니다.

---

## STEP 5. 대표적인 NoSQL 유형을 알아봅시다

NoSQL은 하나의 형태가 아닙니다.

| 유형 | 중심 구조 | 대표 사용 예 |
| --- | --- | --- |
| Key-Value | 키 → 값 | 세션, 캐시 |
| Document | JSON 형태 문서 | 설정, 가변 메타데이터 |
| Column-Family | 파티션 + 정렬 키 | 대량 이벤트 |
| Graph | 노드 + 관계 | 추천, 관계 탐색 |

각 유형은 서로 다른 문제를 해결합니다.

즉 다음처럼 생각하면 안 됩니다.

```text
NoSQL 하나를 골라 모든 데이터를 저장한다.
```

대신 이렇게 생각합니다.

```text
이 데이터는 어떤 조회 패턴을 가지는가?
그 패턴에 어떤 모델이 가장 자연스러운가?
```

---

## STEP 6. Key-Value 모델을 이해해 봅시다

Key-Value 저장소는 매우 단순합니다.

```text
key → value
```

예를 들어 다음과 같은 키를 사용할 수 있습니다.

```text
student:101:session
course:popular:v1:top3
feature:recommendation:v1
```

Key-Value 저장소는 다음과 같은 경우 잘 맞습니다.

```text
정확한 키를 알고 있다.
값 전체를 빠르게 읽고 싶다.
일정 시간이 지나면 만료되어도 된다.
원본 데이터에서 다시 만들 수 있다.
```

대표 사례가 **캐시와 세션**입니다.

---

## STEP 7. 캐시는 원본 데이터가 아닙니다

인기 강의 TOP 3를 캐시에 저장한다고 가정하겠습니다.

```text
course:popular:v1:top3
→ [301, 302, 303]
```

이 값은 원본이 아닙니다.

원본 데이터베이스의 수강신청을 집계해 다시 만들 수 있습니다.

일반적인 캐시 흐름은 다음과 같습니다.

```text
1. 캐시 조회
2. 값이 있으면 사용
3. 값이 없으면 PostgreSQL 조회
4. 결과를 캐시에 저장
5. 사용자에게 반환
```

이를 Cache Aside 패턴이라고 부르기도 합니다.

캐시를 사용할 때는 다음 정책도 필요합니다.

```text
TTL은 얼마인가?
원본이 바뀌면 캐시를 삭제할 것인가?
캐시가 오래되어도 허용되는가?
캐시 장애 시 원본 부하가 급증하지 않는가?
```

---

## STEP 8. TTL과 eviction은 다릅니다

초보자가 자주 혼동하는 부분입니다.

TTL은 키의 만료 시간을 정하는 정책입니다.

```text
30분 후 만료
1시간 후 만료
```

반면 eviction은 저장 공간이 부족할 때 어떤 데이터를 제거할지 정하는 정책입니다.

따라서 다음처럼 구분합니다.

```text
TTL
→ 시간 기준 만료

eviction
→ 저장 공간 압박 시 제거
```

둘은 같은 개념이 아닙니다.

## STEP 9. Document 모델을 이해해 봅시다

Document DB에서는 하나의 문서를 JSON과 비슷한 구조로 저장하는 경우가 많습니다.

예를 들어 강의 메타데이터를 다음처럼 표현할 수 있습니다.

```json
{
  "course_id": 301,
  "tags": ["database", "postgresql"],
  "options": {
    "level": "beginner",
    "subtitle": true
  }
}
```

문서마다 선택 속성이 다를 수 있다면 이런 구조가 편리할 수 있습니다.

다만 핵심 업무 데이터까지 모두 문서 안에 넣는 것은 별개의 판단입니다.

예를 들어 다음 데이터는 관계형 구조가 더 자연스러울 수 있습니다.

```text
학생
강의
수강신청
결제
```

특히 PK/FK와 트랜잭션이 중요하다면 더 그렇습니다.

---

## STEP 10. PostgreSQL JSONB도 좋은 선택지가 될 수 있습니다

PostgreSQL은 `JSONB` 타입을 제공합니다.

즉 관계형 테이블 안에 유연한 JSON 데이터를 함께 저장할 수 있습니다.

예를 들어 다음과 같은 구조를 생각할 수 있습니다.

```sql
CREATE TABLE course_metadata (
    course_id BIGINT PRIMARY KEY,
    metadata JSONB NOT NULL
);
```

`metadata`에는 다음처럼 가변 속성을 저장할 수 있습니다.

```json
{
  "tags": ["sql", "postgresql"],
  "theme": "dark",
  "subtitle_languages": ["ko", "en"]
}
```

따라서 바로 Document DB를 추가하기 전에 다음 질문을 해볼 수 있습니다.

```text
PostgreSQL JSONB로 충분한가?
```

---

## STEP 11. 모든 컬럼을 JSONB로 넣으면 좋은 것은 아닙니다

JSONB가 유연하다고 해서 모든 데이터를 JSON에 넣으면 안 됩니다.

예를 들어 다음 값은 일반 컬럼으로 두는 편이 자연스럽습니다.

```text
id
student_id
course_id
status
recorded_amount
created_at
```

이 값들은 다음과 같은 이유로 구조가 안정적입니다.

```text
JOIN에 사용한다.
제약조건이 중요하다.
검색과 정렬이 자주 필요하다.
데이터 타입이 명확하다.
```

반대로 다음은 JSONB 후보가 될 수 있습니다.

```text
표시 옵션
추가 태그
변경이 잦은 부가 메타데이터
```

따라서 혼합 설계가 가능합니다.

```text
안정된 핵심 속성
→ 일반 컬럼

가변 부가 속성
→ JSONB
```

---

## STEP 12. JSONB 데이터도 조회할 수 있습니다

예를 들어 다음 JSONB가 있다고 가정하겠습니다.

```json
{
  "level": "beginner",
  "tags": ["database", "sql"]
}
```

다음처럼 JSONB 필드를 조회할 수 있습니다.

```sql
SELECT metadata ->> 'level'
FROM course_metadata;
```

특정 JSON 구조를 자주 검색한다면 인덱스를 검토할 수도 있습니다.

예를 들어 GIN 인덱스 후보가 있습니다.

```sql
CREATE INDEX idx_course_metadata_gin
ON course_metadata
USING GIN (metadata);
```

하지만 Chapter 10에서 배운 것처럼 인덱스는 무조건 만드는 것이 아닙니다.

```text
실제 조회 패턴 확인
→ EXPLAIN ANALYZE
→ 인덱스 생성
→ 다시 측정
```

이 흐름을 유지합니다.

---

## STEP 13. 비정규화는 중복을 의도적으로 만드는 설계입니다

NoSQL에서는 조회를 빠르게 하기 위해 관련 데이터를 한 문서에 함께 저장하는 경우가 있습니다.

예를 들어 수강신청 문서에 강의 제목과 학생 이름을 함께 저장할 수 있습니다.

```json
{
  "student_id": 101,
  "student_name": "김민지",
  "course_id": 301,
  "course_title": "데이터베이스 입문"
}
```

조회는 편할 수 있습니다.

하지만 강의 제목이 바뀌면 여러 문서를 수정해야 할 수 있습니다.

즉 비정규화에는 비용이 있습니다.

```text
조회 단순화
↔ 중복 저장
↔ 동기화 책임 증가
```

따라서 중복은 실수로 생기는 것이 아니라 **명확한 이유와 갱신 전략이 있을 때 의도적으로 선택**해야 합니다.

---

## STEP 14. 동기화 실패를 반드시 생각해야 합니다

PostgreSQL과 별도 NoSQL 저장소를 함께 사용한다고 가정해 보겠습니다.

```text
PostgreSQL
→ 원본 수강신청

Document DB
→ 학생별 수강신청 조회용 문서
```

PostgreSQL에는 저장됐는데 Document DB 업데이트가 실패하면 어떻게 될까요?

```text
원본에는 신청 존재
파생 저장소에는 신청 없음
```

이때 어느 데이터를 믿어야 하는지 명확해야 합니다.

원본을 PostgreSQL로 정했다면 다음 원칙을 사용할 수 있습니다.

```text
PostgreSQL = Source of Truth
파생 저장소 = 다시 생성 가능한 데이터
```

이 구분이 매우 중요합니다.

---

## STEP 15. Column-Family는 파티션 중심 조회에 강합니다

대량 학습 이벤트를 생각해 보겠습니다.

```text
학생 101
2026-08-01 10:00 재생
2026-08-01 10:05 일시정지
2026-08-01 10:20 재생
```

조회 패턴이 다음처럼 매우 고정적일 수 있습니다.

```text
특정 학생의
특정 날짜 범위 이벤트를
시간순으로 조회
```

이런 경우 파티션 키와 정렬 키를 중심으로 설계하는 Column-Family 계열을 검토할 수 있습니다.

예를 들어 개념적으로 다음처럼 생각할 수 있습니다.

```text
Partition Key = student_id
Clustering Key = event_time
```

핵심은 테이블을 먼저 만든 뒤 쿼리를 맞추는 것이 아니라 **조회 패턴에서 데이터 모델을 시작한다는 점**입니다.

---

## STEP 16. Graph 모델은 관계 탐색이 핵심일 때 검토합니다

추천 시스템을 생각해 보겠습니다.

```text
학생
→ 수강한 강의
→ 강의 주제
→ 같은 주제의 다른 강의
→ 해당 강의를 들은 다른 학생
```

이처럼 여러 단계 관계를 반복적으로 탐색해야 한다면 Graph DB를 검토할 수 있습니다.

Graph 모델은 보통 다음 개념을 사용합니다.

```text
Node
→ 학생, 강의, 주제

Edge
→ 수강함, 관심있음, 관련있음
```

하지만 단순한 1~2단계 JOIN만 필요하다면 RDBMS로 충분할 수 있습니다.

Graph DB를 추가하면 운영 복잡성도 함께 증가합니다.

---

## STEP 17. 저장소를 여러 개 쓰면 책임도 늘어납니다

여러 저장소를 목적별로 사용하는 방식을 Polyglot Persistence라고 부릅니다.

예를 들어 다음 구성이 가능합니다.

```text
PostgreSQL
→ 수강신청 원본

Redis
→ 인기 강의 캐시

Document DB
→ 가변 메타데이터

Graph DB
→ 추천 관계
```

하지만 저장소가 늘어날수록 다음도 늘어납니다.

```text
운영 대상
보안 설정
백업 범위
장애 대응
모니터링
비용
동기화 코드
복구 절차
```

따라서 기술을 추가하는 것 자체가 목적이 되어서는 안 됩니다.

---

## STEP 18. RDBMS와 NoSQL 선택 체크리스트

다음 질문을 순서대로 확인해 보세요.

```text
1. 이 데이터가 Source of Truth인가?
2. PK/FK 관계가 중요한가?
3. 여러 변경의 원자성이 중요한가?
4. JOIN과 다양한 조건 조회가 많은가?
5. 특정 키 조회가 거의 대부분인가?
6. 문서 구조가 자주 달라지는가?
7. 특정 파티션의 범위 조회가 핵심인가?
8. 여러 단계 관계 탐색이 핵심인가?
9. 중복 데이터를 동기화할 수 있는가?
10. 장애 시 어떤 저장소를 기준으로 복구할 것인가?
```

이 질문을 먼저 답한 뒤 저장소 후보를 비교합니다.

---

## STEP 19. PostgreSQL 하나로 충분한지 먼저 검토합니다

새 기술을 추가하기 전에 먼저 현재 PostgreSQL로 해결 가능한지 확인하는 것이 좋습니다.

PostgreSQL은 다음 기능을 제공합니다.

```text
관계형 테이블
JSONB
GIN 인덱스
전문 검색 기능
트랜잭션
다양한 인덱스
확장 기능
```

따라서 단순히 “JSON 데이터가 있다”는 이유만으로 바로 Document DB를 도입할 필요는 없습니다.

좋은 질문은 이것입니다.

```text
현재 PostgreSQL로 요구사항을 충분히 만족하는가?
별도 저장소를 추가했을 때 얻는 이점이 운영 복잡성보다 큰가?
```

## 오늘의 핵심 정리

이번 Chapter에서 꼭 기억할 내용입니다.

```text
RDBMS
→ 관계, 제약조건, JOIN, 트랜잭션이 중요한 원본 데이터에 강함

Key-Value
→ 정확한 키 조회, 세션, 캐시에 적합

Document
→ 구조가 가변적인 문서·메타데이터에 적합

Column-Family
→ 파티션 중심의 대량 범위 조회에 적합

Graph
→ 여러 단계 관계 탐색에 적합

JSONB
→ PostgreSQL 안에서 관계형 구조와 유연한 문서 구조를 함께 사용할 수 있음
```

그리고 가장 중요한 판단 순서는 이것입니다.

```text
데이터 역할 정의
→ Source of Truth 구분
→ 조회 패턴 정의
→ 트랜잭션 범위 확인
→ 저장 모델 후보 비교
→ 동기화·복구 비용 확인
→ 작은 PoC
→ 최종 결정
```

AI 시대에도 기술 선택의 책임은 사람에게 있습니다.

```text
AI는 저장소 후보를 빠르게 추천할 수 있다.
하지만 어떤 데이터가 원본인지,
어떤 불일치를 허용할지,
장애 시 무엇을 기준으로 복구할지는 사람이 결정해야 한다.
```
