# [AI 시대의 데이터베이스 입문 07] 실전 프로젝트: 온라인 강의 수강신청 DB 완성하기

안녕하세요. 아토믹데브입니다.

이번 Chapter에서는 지금까지 배운 내용을 하나의 작은 프로젝트로 연결합니다.

앞에서는 SQL, 데이터 모델링, ERD, 정규화와 무결성을 각각 따로 배웠다면 이번에는 **온라인 강의 수강신청 데이터베이스를 실제로 설계하고 구현하고 검증**해 봅니다.

중요한 점은 SQL 파일을 만드는 것이 아니라, 다른 사람이 같은 순서로 실행했을 때 같은 구조와 같은 결과를 재현할 수 있도록 만드는 것입니다.

## 오늘 완성할 프로젝트

이번 프로젝트의 핵심 구조는 다음과 같습니다.

```text
course_project
├── students
├── instructors
├── courses
└── enrollments
```

각 테이블의 한 행 의미는 다음과 같습니다.

```text
students    → 학생 한 명
instructors → 강사 한 명
courses     → 개설된 강의 한 개
enrollments → 특정 학생이 특정 강의를 신청한 사건 한 건
```

## STEP 1. 프로젝트 범위를 먼저 정합니다

처음부터 모든 기능을 넣으려고 하면 프로젝트가 복잡해집니다.

이번 프로젝트에서는 다음 기능만 다룹니다.

```text
학생
강사
강의
수강신청
신청 상태
강의 기준 가격
신청 당시 기록 금액
```

반대로 다음 기능은 이번 범위에서 제외합니다.

```text
결제 승인·실패·환불
쿠폰·할인
강의 정원과 대기열
진도율과 수료
강의 콘텐츠
수강평
```

범위를 정하는 이유는 설계를 단순하게 만들기 위해서입니다.

## STEP 2. 핵심 요구사항을 정리합니다

이번 프로젝트의 기본 요구사항을 단순화하면 다음과 같습니다.

```text
1. 학생은 이름과 이메일을 가진다.
2. 강사는 이름과 이메일을 가진다.
3. 강의는 제목, 난이도, 가격을 가진다.
4. 한 강의는 한 명의 강사를 참조한다.
5. 학생은 여러 강의를 신청할 수 있다.
6. 하나의 강의에는 여러 학생이 신청할 수 있다.
7. 수강신청에는 신청일, 상태, 신청 당시 금액을 저장한다.
8. 존재하지 않는 학생이나 강의는 참조할 수 없다.
9. 가격은 음수가 될 수 없다.
```

여기서 중요한 점은 요구사항과 설계자의 임의 판단을 구분하는 것입니다.

예를 들어 다음 질문은 아직 별도로 결정해야 할 수 있습니다.

```text
학생과 강사의 이메일은 전체 서비스에서 하나만 허용할까?
탈퇴한 사용자의 신청 이력은 어떻게 보존할까?
취소된 학생이 같은 강의를 다시 신청할 수 있을까?
```

확정되지 않은 정책을 AI나 개발자가 임의로 정하면 안 됩니다.

## STEP 3. 관계를 문장으로 먼저 표현합니다

ERD를 그리기 전에 관계를 문장으로 정리하면 훨씬 쉽습니다.

```text
한 강사는 여러 강의를 담당할 수 있다.
한 강의는 한 명의 강사를 참조한다.

한 학생은 여러 수강신청을 가질 수 있다.
한 수강신청은 한 명의 학생을 참조한다.

한 강의는 여러 수강신청을 가질 수 있다.
한 수강신청은 한 개의 강의를 참조한다.
```

관계를 구조로 보면 다음과 같습니다.

```text
instructors 1 ─── N courses
students    1 ─── N enrollments
courses     1 ─── N enrollments
```

학생과 강의는 직접 보면 N:M 관계입니다.

```text
학생 여러 명 ↔ 강의 여러 개
```

이 관계를 `enrollments`라는 연결 테이블로 풀어냅니다.

```text
students 1 ─── N enrollments N ─── 1 courses
```

```sql
CREATE TABLE course_project.students (
```


학생과 강사를 하나의 테이블로 합칠 수도 있지만 이번 프로젝트에서는 역할을 분리해 관리합니다.

## STEP 7. courses 테이블을 만듭니다

```sql
CREATE TABLE course_project.courses (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    instructor_id INTEGER NOT NULL,
    title VARCHAR(150) NOT NULL,
    description TEXT,
    level VARCHAR(20) NOT NULL,
    price NUMERIC(12, 0) NOT NULL,
    opened_at DATE NOT NULL,
    CONSTRAINT fk_courses_instructor
        FOREIGN KEY (instructor_id)
        REFERENCES course_project.instructors(id)
        ON DELETE RESTRICT,
    CONSTRAINT chk_courses_price
        CHECK (price >= 0)
);
```

여기서 외래키가 관계를 연결합니다.

```text
courses.instructor_id
→ instructors.id 참조
```

즉 강의는 존재하는 강사만 참조할 수 있습니다.

가격은 음수가 될 수 없도록 `CHECK` 제약조건을 사용합니다.

---

## STEP 8. enrollments 테이블을 만듭니다

수강신청은 단순한 연결만 하는 테이블이 아닙니다.

신청일, 상태, 당시 금액이라는 자체 속성을 가진 사건입니다.

```sql
CREATE TABLE course_project.enrollments (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_id INTEGER NOT NULL,
    course_id INTEGER NOT NULL,
    enrolled_at DATE NOT NULL DEFAULT CURRENT_DATE,
    status VARCHAR(20) NOT NULL,
    recorded_amount NUMERIC(12, 0) NOT NULL,
    CONSTRAINT fk_enrollments_student
        FOREIGN KEY (student_id)
        REFERENCES course_project.students(id)
        ON DELETE RESTRICT,
    CONSTRAINT fk_enrollments_course
        FOREIGN KEY (course_id)
        REFERENCES course_project.courses(id)
        ON DELETE RESTRICT,
    CONSTRAINT chk_enrollments_status
        CHECK (status IN ('신청', '수강중', '완료', '취소')),
    CONSTRAINT chk_enrollments_amount
        CHECK (recorded_amount >= 0)
);
```

상태는 다음 네 가지 값만 허용합니다.

```text
신청
수강중
완료
취소
```

---

## STEP 9. 진행 중 중복 신청을 막습니다

같은 학생이 같은 강의를 동시에 여러 번 신청하면 문제가 될 수 있습니다.

다만 취소 후 재신청은 허용하고 싶다면 단순 `UNIQUE(student_id, course_id)`보다 조건부 규칙이 필요합니다.

PostgreSQL에서는 부분 고유 인덱스를 사용할 수 있습니다.

```sql
CREATE UNIQUE INDEX uq_active_enrollment
ON course_project.enrollments (student_id, course_id)
WHERE status IN ('신청', '수강중');
```

이렇게 하면 진행 중인 신청은 중복할 수 없지만 취소된 기록은 남겨둘 수 있습니다.

## STEP 11. 신청 당시 금액을 저장합니다

`courses.price`는 현재 강의 가격입니다.

반면 `enrollments.recorded_amount`는 신청 당시 저장한 금액입니다.

둘은 같은 값일 수 있지만 의미는 다릅니다.

```text
courses.price
→ 현재 기준 가격

enrollments.recorded_amount
→ 신청 당시 기록한 가격
```

예를 들어 다음처럼 현재 강의 가격을 조회하면서 수강신청 데이터를 만들 수 있습니다.

```sql
INSERT INTO course_project.enrollments (
    id,
    student_id,
    course_id,
    enrolled_at,
    status,
    recorded_amount
)
SELECT
    1001,
    101,
    c.id,
    CURRENT_DATE,
    '신청',
    c.price
FROM course_project.courses AS c
WHERE c.id = 301;
```

나중에 강의 가격이 변경되어도 기존 신청의 `recorded_amount`는 그대로 유지됩니다.

## STEP 12. JOIN으로 신청 현황을 확인합니다

학생 이름과 강의 제목을 함께 보고 싶다면 여러 테이블을 연결합니다.

```sql
SELECT
    e.id AS enrollment_id,
    s.name AS student_name,
    c.title AS course_title,
    e.status,
    e.recorded_amount
FROM course_project.enrollments AS e
JOIN course_project.students AS s
    ON s.id = e.student_id
JOIN course_project.courses AS c
    ON c.id = e.course_id
ORDER BY e.id;
```

이 결과에서 한 행은 **수강신청 한 건**을 의미합니다.

## STEP 13. 데이터를 안전하게 변경합니다

바로 `UPDATE`를 실행하기보다 먼저 현재 상태를 확인합니다.

```sql
SELECT id, status
FROM course_project.enrollments
WHERE id = 1001;
```

예상 상태가 맞다면 변경합니다.

```sql
UPDATE course_project.enrollments
SET status = '완료'
WHERE id = 1001
  AND status = '수강중';
```

이 방식의 장점은 다른 사람이 이미 상태를 바꾼 경우 예상치 못한 변경을 줄일 수 있다는 것입니다.

핵심 원칙은 다음과 같습니다.

```text
변경 전 SELECT
→ 예상 상태 확인
→ 조건부 UPDATE
→ 영향받은 행 수 확인
→ 변경 후 SELECT
```

## STEP 14. 고아 관계가 없는지 검사합니다

외래키가 정상적으로 동작한다면 존재하지 않는 학생이나 강의를 참조하는 신청은 없어야 합니다.

학생 기준으로 확인해 봅니다.

```sql
SELECT e.*
FROM course_project.enrollments AS e
LEFT JOIN course_project.students AS s
    ON s.id = e.student_id
WHERE s.id IS NULL;
```

결과가 0행이면 학생 고아 관계가 없다는 뜻입니다.

강의도 같은 방식으로 검사할 수 있습니다.

```sql
SELECT e.*
FROM course_project.enrollments AS e
LEFT JOIN course_project.courses AS c
    ON c.id = e.course_id
WHERE c.id IS NULL;
```

## STEP 15. 중복 신청을 검사합니다

진행 중 상태를 기준으로 학생과 강의가 중복되는지 확인합니다.

```sql
SELECT
    student_id,
    course_id,
    COUNT(*) AS cnt
FROM course_project.enrollments
WHERE status IN ('신청', '수강중')
GROUP BY student_id, course_id
HAVING COUNT(*) > 1;
```

결과가 0행이면 활성 중복 신청이 없다는 뜻입니다.

## STEP 16. 최종 행 수를 확인합니다

프로젝트를 완료했다면 테이블별 행 수를 확인합니다.

```sql
SELECT 'students' AS table_name, COUNT(*) AS row_count
FROM course_project.students
UNION ALL
SELECT 'instructors', COUNT(*)
FROM course_project.instructors
UNION ALL
SELECT 'courses', COUNT(*)
FROM course_project.courses
UNION ALL
SELECT 'enrollments', COUNT(*)
FROM course_project.enrollments;
```

프로젝트에서는 단순히 SQL이 실행됐다는 사실보다 **예상한 결과와 실제 결과가 일치하는지** 확인해야 합니다.

## 오늘의 핵심 정리

이번 프로젝트의 핵심 흐름은 다음과 같습니다.

```text
요구사항
→ 프로젝트 범위
→ 한 행의 의미
→ 관계 문장
→ ERD
→ PK·FK·제약조건
→ PostgreSQL 구현
→ 샘플 데이터
→ 변경 시나리오
→ 검증 SQL
→ 설계 결정 기록
```

특히 다음 세 가지를 기억하면 좋습니다.

```text
1. enrollments는 단순 연결 테이블이 아니라 신청 사건이다.
2. 현재 가격과 신청 당시 가격은 의미가 다를 수 있다.
3. 프로젝트 완료는 SQL 실행이 아니라 결과 검증까지 포함한다.
```

AI 시대의 데이터베이스 프로젝트에서도 사람이 해야 할 가장 중요한 일은 **요구사항과 실행 결과를 연결해서 검증하는 것**입니다.
