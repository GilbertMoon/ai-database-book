## STEP 3. 요구사항과 미확정 정책을 분리합니다

확정된 요구사항의 예입니다.

```text
학생은 질문을 등록할 수 있다.
질문은 학생 한 명을 참조한다.
질문에는 여러 답변이 있을 수 있다.
답변은 튜터 한 명을 참조한다.
질문과 학습 자료는 N:M 관계다.
질문 상태는 정해진 값만 사용한다.
학생·튜터 이메일은 공백일 수 없다.
```

반면 다음은 아직 정책 결정이 필요할 수 있습니다.

```text
같은 튜터가 한 질문에 여러 답변을 작성할 수 있는가?
closed 상태에서 추가 답변을 허용하는가?
비활성 학생이 질문을 만들 수 있는가?
삭제 후 데이터를 보존할 것인가?
```

중요한 원칙은 이것입니다.

```text
미확정 정책을 AI가 임의로 확정하지 않게 한다.
```

## STEP 4. 각 테이블의 한 행 의미를 정합니다

이번 프로젝트의 핵심 테이블은 다음과 같습니다.

| 테이블 | 한 행의 의미 |
| --- | --- |
| `students` | 학생 한 명 |
| `tutors` | 튜터 한 명 |
| `questions` | 학생이 등록한 질문 한 건 |

이 단계에서 항상 질문합니다.

```text
이 테이블의 한 행은 무엇을 의미하는가?
```

이 문장이 명확해야 PK와 관계도 명확해집니다.

## STEP 5. 관계를 문장으로 먼저 적습니다

```text
학생 한 명은 여러 질문을 가질 수 있다.
질문 하나는 학생 한 명을 참조한다.

질문 하나는 여러 답변을 가질 수 있다.
답변 하나는 질문 하나를 참조한다.

튜터 한 명은 여러 답변을 작성할 수 있다.
답변 하나는 튜터 한 명을 참조한다.

질문 하나는 여러 학습 자료와 연결될 수 있다.
학습 자료 하나는 여러 질문과 연결될 수 있다.
```

관계 구조는 다음과 같습니다.

```text
students 1 ── N questions
questions 1 ── N answers
tutors 1 ── N answers
questions N ── M learning_materials
```

N:M 관계는 `question_materials` 연결 테이블로 풀어 줍니다.

## STEP 7. students 테이블을 만듭니다

예시는 다음과 같습니다.

```sql
CREATE TABLE tutor_project.students (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(200) UNIQUE NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_students_name_not_blank
        CHECK (btrim(name) <> ''),
    CONSTRAINT chk_students_email_not_blank
        CHECK (btrim(email) <> '')
);
```

핵심 제약조건은 다음과 같습니다.

```text
PRIMARY KEY
→ 행 식별

NOT NULL
→ 필수값

UNIQUE
→ 동일 이메일 중복 방지

CHECK
→ 공백 문자열 방지
```

## STEP 8. questions 테이블을 만듭니다

```sql
CREATE TABLE tutor_project.questions (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_id INTEGER NOT NULL,
    title VARCHAR(200) NOT NULL,
    body TEXT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'open',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_questions_student
        FOREIGN KEY (student_id)
        REFERENCES tutor_project.students(id)
        ON DELETE RESTRICT,

    CONSTRAINT chk_questions_status
        CHECK (status IN ('open', 'answered', 'closed')),

    CONSTRAINT chk_questions_time
        CHECK (updated_at >= created_at)
);
```

`ON DELETE RESTRICT`는 참조 중인 부모 행을 임의로 삭제하지 못하게 합니다.

삭제 정책은 업무 요구사항에 따라 달라질 수 있으므로 AI가 무조건 `CASCADE`를 넣지 않도록 주의합니다.

## STEP 9. answers 테이블을 연결합니다

```sql
CREATE TABLE tutor_project.answers (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    question_id INTEGER NOT NULL,
    tutor_id INTEGER NOT NULL,
    body TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_answers_question
        FOREIGN KEY (question_id)
        REFERENCES tutor_project.questions(id)
        ON DELETE RESTRICT,

    CONSTRAINT fk_answers_tutor
        FOREIGN KEY (tutor_id)
        REFERENCES tutor_project.tutors(id)
        ON DELETE RESTRICT
);
```

한 질문에 여러 답변을 허용하기 때문에 `question_id` 자체에는 `UNIQUE`를 걸지 않습니다.

이것도 요구사항에서 나온 설계 판단입니다.

## STEP 10. 질문과 학습 자료의 N:M 관계를 구현합니다

연결 테이블 예시는 다음과 같습니다.

```sql
CREATE TABLE tutor_project.question_materials (
    question_id INTEGER NOT NULL,
    material_id INTEGER NOT NULL,
    display_order INTEGER NOT NULL,
    linked_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (question_id, material_id),

    CONSTRAINT fk_question_materials_question
        FOREIGN KEY (question_id)
        REFERENCES tutor_project.questions(id)
        ON DELETE RESTRICT,

    CONSTRAINT fk_question_materials_material
        FOREIGN KEY (material_id)
        REFERENCES tutor_project.learning_materials(id)
        ON DELETE RESTRICT,

    CONSTRAINT uq_question_materials_display_order
        UNIQUE (question_id, display_order),

    CONSTRAINT chk_question_materials_display_order
        CHECK (display_order > 0)
);
```

여기서 복합 기본키는 같은 질문과 같은 자료가 중복 연결되는 것을 막습니다.

## STEP 11. 기준 데이터를 넣습니다

테스트하기 좋은 데이터는 단순히 정상값만 넣지 않습니다.

다음 경계 사례를 포함하는 것이 좋습니다.

```text
질문이 없는 학생
답변이 없는 open 질문
답변이 2개인 질문
연결되지 않은 학습 자료
여러 월에 걸친 질문
```

이렇게 Seed 데이터를 설계하면 JOIN, LEFT JOIN, 집계와 실패 검증을 모두 연습할 수 있습니다.

---

## STEP 12. IDENTITY 번호도 확인합니다

명시적으로 ID를 넣으면 다음 자동 번호가 자동 조정되지 않을 수 있습니다.

예를 들어 최대 ID가 104라면 다음 자동값을 105로 맞춥니다.

```sql
ALTER TABLE tutor_project.students
    ALTER COLUMN id RESTART WITH 105;
```

다른 테이블도 같은 방식으로 조정합니다.

자동 ID는 행 수가 아니라 식별자라는 점도 다시 기억합니다.

## STEP 13. 정상 관계를 JOIN으로 확인합니다

```sql
SELECT
    q.id AS question_id,
    s.name AS student_name,
    q.title,
    q.status
FROM tutor_project.questions AS q
JOIN tutor_project.students AS s
    ON s.id = q.student_id
ORDER BY q.id;
```

질문과 학생 관계가 정상적으로 연결되는지 확인합니다.

다음처럼 답변까지 확장할 수 있습니다.

```sql
SELECT
    q.id AS question_id,
    q.title,
    a.id AS answer_id,
    t.name AS tutor_name
FROM tutor_project.questions AS q
LEFT JOIN tutor_project.answers AS a
    ON a.question_id = q.id
LEFT JOIN tutor_project.tutors AS t
    ON t.id = a.tutor_id
ORDER BY q.id, a.id;
```

답변이 없는 질문도 남겨야 하므로 `LEFT JOIN`이 적합합니다.

## STEP 14. 이상 데이터를 찾는 검증 SQL을 만듭니다

좋은 프로젝트에는 정상 조회뿐 아니라 **이상이 없어야 하는 조회**도 있어야 합니다.

예를 들어 고아 답변을 검사합니다.

```sql
SELECT a.*
FROM tutor_project.answers AS a
LEFT JOIN tutor_project.questions AS q
    ON q.id = a.question_id
WHERE q.id IS NULL;
```

정상 결과는 다음입니다.

```text
0행
```

시간 관계도 확인할 수 있습니다.

```sql
SELECT a.*
FROM tutor_project.answers AS a
JOIN tutor_project.questions AS q
    ON q.id = a.question_id
WHERE a.created_at < q.created_at;
```

이 역시 정상이라면 0행이어야 합니다.

## STEP 15. 질문 없는 학생도 0건으로 조회합니다

운영 분석에서는 활동이 없는 대상도 중요합니다.

```sql
SELECT
    s.id,
    s.name,
    COUNT(q.id) AS question_count
FROM tutor_project.students AS s
LEFT JOIN tutor_project.questions AS q
    ON q.student_id = s.id
GROUP BY s.id, s.name
ORDER BY s.id;
```

질문이 없는 학생도 `question_count = 0`으로 나타납니다.

이것이 `LEFT JOIN`의 중요한 활용입니다.

## STEP 17. 트랜잭션으로 답변 등록을 검증합니다

답변 작성과 질문 상태 변경을 하나의 업무 단위로 처리한다고 가정합니다.

```sql
BEGIN;

INSERT INTO tutor_project.answers (
    question_id,
    tutor_id,
    body
)
VALUES (
    303,
    201,
    '예시 답변입니다.'
);

UPDATE tutor_project.questions
SET status = 'answered',
    updated_at = CURRENT_TIMESTAMP
WHERE id = 303
  AND status = 'open'
RETURNING id, status;

-- 결과 확인

ROLLBACK;
```

이번 실습에서는 `ROLLBACK`을 사용해 기준 데이터를 원래 상태로 되돌립니다.

확인할 내용은 다음입니다.

```text
트랜잭션 안에서는 답변이 증가했는가?
질문 상태가 answered가 되었는가?
ROLLBACK 후 모두 원래 상태로 돌아왔는가?
```

## STEP 18. 실패 테스트도 반드시 작성합니다

예를 들어 존재하지 않는 학생을 참조하는 질문은 실패해야 합니다.

```sql
INSERT INTO tutor_project.questions (
    student_id,
    title,
    body,
    status
)
VALUES (
    999999,
    '잘못된 질문',
    'FK 테스트',
    'open'
);
```

정상 시스템에서는 FK 오류가 발생해야 합니다.

다음도 실패해야 합니다.

```text
공백 이메일
중복 이메일
허용되지 않은 상태
display_order = 0
같은 질문에서 동일 display_order 중복
```

성공 테스트만 있는 프로젝트는 충분히 검증된 프로젝트가 아닙니다.

## STEP 19. 메타데이터도 실제 DB에서 확인합니다

DDL 파일을 읽는 것만으로 끝내지 않습니다.

PostgreSQL 카탈로그에서 실제 구조를 확인합니다.

예를 들어 제약조건을 확인할 수 있습니다.

```sql
SELECT
    conname,
    contype
FROM pg_constraint
WHERE connamespace = 'tutor_project'::regnamespace
ORDER BY conname;
```

다음도 점검합니다.

```text
테이블 개수
PK 개수
FK 개수
UNIQUE/CHECK 존재 여부
FK 대상 컬럼
복합 PK 컬럼 순서
인덱스 정의
CASCADE 존재 여부
```

AI가 작성한 DDL과 실제 생성 구조가 같은지 확인해야 합니다.

## STEP 20. 인덱스 후보를 조회 패턴에서 찾습니다

인덱스를 무조건 많이 만들지 않습니다.

예상 조회 패턴을 먼저 적습니다.

```text
학생별 최근 질문 조회
질문별 답변 조회
튜터별 답변 조회
상태별 질문 조회
```

예를 들어 학생별 최근 질문 조회가 자주 사용된다면 다음 후보를 검토할 수 있습니다.

```sql
CREATE INDEX idx_questions_student_created_at
ON tutor_project.questions (student_id, created_at DESC);
```

생성 후에는 `EXPLAIN ANALYZE`로 실제 효과를 확인합니다.

Chapter 10에서 배운 원칙을 그대로 적용합니다.

```text
인덱스 전 측정
→ 인덱스 생성
→ 같은 SQL로 재측정
→ 유지 여부 결정
```

## STEP 23. 분석 VIEW를 만듭니다

질문 한 건을 기준으로 분석 데이터셋을 만들 수 있습니다.

```sql
CREATE VIEW tutor_project.question_analysis_dataset AS
SELECT
    q.id AS question_id,
    q.student_id,
    q.status,
    q.created_at,
    COUNT(DISTINCT a.id) AS answer_count,
    COUNT(DISTINCT qm.material_id) AS material_count
FROM tutor_project.questions AS q
LEFT JOIN tutor_project.answers AS a
    ON a.question_id = q.id
LEFT JOIN tutor_project.question_materials AS qm
    ON qm.question_id = q.id
GROUP BY
    q.id,
    q.student_id,
    q.status,
    q.created_at;
```

여기서 중요한 것은 `COUNT(DISTINCT ...)`입니다.

답변과 자료를 동시에 JOIN하면 행이 곱해질 수 있기 때문입니다.

Chapter 08과 Chapter 14에서 배운 과대 집계 문제를 다시 적용합니다.

## STEP 28. 최종 완료 게이트를 만듭니다

프로젝트를 감으로 완료 처리하지 않습니다.

다음 조건을 자동 검증할 수 있습니다.

```text
필수 테이블이 모두 존재한다.
기준 행 수가 맞다.
고아 FK 관계가 0건이다.
시간 정합성 오류가 0건이다.
허용되지 않은 상태가 0건이다.
질문 없는 학생이 정상적으로 0건 조회된다.
연결되지 않은 자료가 예상대로 조회된다.
트랜잭션 ROLLBACK이 정상 동작한다.
실패 테스트가 의도한 제약조건에서 차단된다.
분석 VIEW 행 수가 예상과 같다.
```

검증 실패 시 예외를 발생시키는 방식도 좋습니다.

```sql
DO $$
BEGIN
    IF EXISTS (
        SELECT 1
        FROM tutor_project.questions
        WHERE status NOT IN ('open', 'answered', 'closed')
    ) THEN
        RAISE EXCEPTION 'invalid question status detected';
    END IF;
END
$$;
```

이런 자동 검증을 **completion gate**로 사용할 수 있습니다.

```text
1. SQL을 실행하기 전에 결과를 예상한다.
```

AI는 앞으로 SQL, Python, 설계 문서와 테스트를 더 빠르게 만들어 줄 것입니다.

```text
이 데이터가 무엇을 의미하는가?
이 관계가 실제 업무와 맞는가?
이 변경을 확정해도 되는가?
이 숫자를 믿어도 되는가?
장애가 나면 복구할 수 있는가?
```

이 질문에 답할 수 있다면 AI를 단순 코드 생성기가 아니라 **데이터베이스 설계와 검증을 가속하는 도구**로 활용할 수 있습니다.


이것이 AI 시대에도 변하지 않는 데이터베이스의 핵심입니다.
