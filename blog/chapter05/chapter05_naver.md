# [AI 시대의 데이터베이스 입문 05] 요구사항에서 데이터 모델과 ERD 만들기

안녕하세요. 아토믹데브입니다.

Chapter 04까지는 이미 정해진 테이블을 만들고 SQL을 실행했습니다. 하지만 실제 프로젝트에서는 테이블 구조가 먼저 주어지지 않습니다.

먼저 해야 할 일은 **업무 요구사항을 읽고 무엇을 저장해야 하는지, 각 데이터가 어떻게 연결되는지 설계하는 것**입니다.

이번 글에서는 단순한 도서 대여 시스템을 예로 들어 요구사항을 데이터 모델과 ERD로 바꾸는 과정을 처음부터 따라가 보겠습니다.

## STEP 1. 요구사항을 먼저 읽습니다

이번 예제는 간단한 도서 대여 시스템입니다.

```text
R-01. 도서관은 회원을 관리한다.
R-02. 회원은 이름, 이메일, 가입일을 가진다.
R-03. 도서는 제목, 저자, 출판연도, ISBN 정보를 저장한다.
R-04. 회원은 여러 권의 책을 대여할 수 있다.
R-05. 책은 시간에 따라 여러 번 대여될 수 있다.
R-06. 대여 기록에는 대여일, 반납예정일, 실제반납일을 저장한다.
R-07. 아직 반납되지 않은 대여 기록은 실제반납일이 비어 있을 수 있다.
```

이때 바로 테이블부터 만들면 안 됩니다.

먼저 요구사항 안에서 다음 세 가지를 구분합니다.

```text
관리 대상
속성
업무 규칙
```

---

## STEP 2. 관리 대상과 속성을 나눠 봅니다

요구사항에서 핵심 명사를 찾습니다.

```text
회원
도서
대여
```

이 세 가지는 독립적으로 관리하거나 반복해서 발생하므로 **엔터티 후보**가 됩니다.

반면 다음 항목들은 엔터티를 설명하는 속성입니다.

```text
회원 이름
이메일
가입일
도서 제목
저자
출판연도
ISBN
대여일
반납예정일
실제반납일
```

정리하면 다음과 같습니다.

| 후보 | 분류 |
| --- | --- |
| 회원 | 엔터티 |
| 도서 | 엔터티 |
| 대여 | 사건 엔터티 |
| 이메일 | 회원 속성 |
| ISBN | 도서 속성 |
| 반납예정일 | 대여 속성 |

---

## STEP 3. 테이블 한 행의 의미를 정합니다

이 단계가 매우 중요합니다.

각 테이블의 한 행이 무엇을 의미하는지 문장으로 적어 봅니다.

```text
members 한 행 = 회원 한 명
books 한 행 = 도서 한 건
loans 한 행 = 특정 회원이 특정 도서를 빌린 대여 사건 한 건
```

이 문장이 명확해야 나중에 PK와 FK를 정하기 쉬워집니다.

좋은 데이터 모델은 테이블 이름만 그럴듯한 것이 아니라 **한 행의 의미를 설명할 수 있어야 합니다.**

---

## STEP 4. 기본키를 정합니다

각 테이블의 행을 구분할 값이 필요합니다.

예를 들어 다음처럼 내부 식별자를 사용할 수 있습니다.

```text
members.id
books.id
loans.id
```

각각 자신의 테이블에서 한 행을 구분하는 **기본키(PK)** 후보입니다.

여기서 이메일이나 ISBN을 바로 PK로 사용하는 것은 신중해야 합니다.

왜냐하면 업무 정책이 바뀔 수 있기 때문입니다.

```text
회원 이메일이 정말 항상 고유한가?
이메일 변경이 가능한가?
ISBN이 없는 책도 등록할 수 있는가?
같은 ISBN의 여러 실물 도서를 구분해야 하는가?
```

따라서 내부 식별자와 업무상 고유값은 구분해서 생각하는 것이 좋습니다.

---

## STEP 5. 관계를 문장으로 먼저 작성합니다

ERD를 그리기 전에 관계를 문장으로 적으면 훨씬 쉽습니다.

회원과 대여의 관계는 다음과 같습니다.

```text
회원 한 명은 여러 대여 기록을 가질 수 있다.
각 대여 기록은 한 명의 회원과 연결된다.
```

도서와 대여의 관계도 비슷합니다.

```text
도서 한 건은 시간에 따라 여러 대여 기록을 가질 수 있다.
각 대여 기록은 하나의 도서와 연결된다.
```

이렇게 양방향 문장으로 적으면 카디널리티를 판단하기 쉽습니다.

---

## STEP 6. 1:N 관계를 이해합니다

회원 한 명은 여러 번 대여할 수 있습니다.

```text
members 1 : N loans
```

도서도 시간에 따라 여러 번 대여될 수 있습니다.

```text
books 1 : N loans
```

따라서 `loans` 테이블에는 다음 외래키가 필요합니다.

```text
member_id
book_id
```

구조는 다음처럼 생각할 수 있습니다.

```text
members
- id PK
- name
- email
- joined_at

books
- id PK
- title
- author
- published_year
- isbn

loans
- id PK
- member_id FK
- book_id FK
- borrowed_at
- due_at
- returned_at
```

---

## STEP 7. N:M 관계는 연결 테이블로 풀어냅니다

회원과 도서를 직접 연결해 보면 다음과 같습니다.

```text
한 회원은 여러 도서를 빌릴 수 있다.
한 도서는 시간에 따라 여러 회원에게 빌려질 수 있다.
```

개념적으로 보면 회원과 도서는 N:M 관계입니다.

하지만 관계형 데이터베이스에서는 N:M 관계를 그대로 두기보다 **연결 테이블**로 풀어냅니다.

이번 예제에서는 `loans`가 바로 그 역할을 합니다.

```text
members 1 : N loans N : 1 books
```

그리고 `loans`는 단순 연결만 하는 것이 아닙니다.

다음처럼 자체 속성을 가지고 있습니다.

```text
borrowed_at
due_at
returned_at
```

따라서 `loans`는 단순 연결 테이블이면서 동시에 **대여 사건 자체를 기록하는 엔터티**입니다.

---

## STEP 8. NULL이 필요한 속성을 판단합니다

요구사항에는 다음 문장이 있습니다.

```text
아직 반납되지 않은 대여 기록은 실제반납일이 비어 있을 수 있다.
```

따라서 `returned_at`은 `NULL`을 허용해야 합니다.

```text
returned_at = NULL
→ 아직 반납되지 않음
```

이처럼 NULL 허용 여부도 요구사항에서 나옵니다.

DB 설계에서는 단순히 “값이 없을 수 있으니까 NULL”이라고 판단하기보다 **업무 의미가 있는지**를 먼저 확인해야 합니다.

---

## STEP 9. 미확정 요구사항을 따로 적습니다

요구사항에 없는 내용을 임의로 확정하면 안 됩니다.

예를 들어 다음 질문은 현재 요구사항만으로는 답할 수 없습니다.

```text
회원 이메일은 반드시 고유한가?
ISBN은 반드시 고유한가?
ISBN이 없는 책도 등록할 수 있는가?
회원 한 명이 동시에 최대 몇 권까지 빌릴 수 있는가?
같은 도서를 동시에 두 명이 빌릴 수 있는가?
회원 삭제 후 대여 이력을 유지할 것인가?
실제반납일이 대여일보다 빠르면 막아야 하는가?
```

이런 질문은 설계 실패가 아니라 오히려 좋은 설계 과정의 결과물입니다.

**모르는 것을 모른다고 표시하는 것**이 중요합니다.

---

## STEP 10. ERD 초안을 그려 봅니다

이번 예제의 기본 ERD는 다음 구조입니다.

```text
members
   1
   |
   N
 loans
   N
   |
   1
 books
```

텍스트로 표현하면 다음과 같습니다.

```text
members
- id PK
- name
- email
- joined_at

loans
- id PK
- member_id FK → members.id
- book_id FK → books.id
- borrowed_at
- due_at
- returned_at

books
- id PK
- title
- author
- published_year
- isbn
```

ERD를 그릴 때는 다음을 확인합니다.

```text
PK가 있는가?
FK 연결 방향이 맞는가?
관계 수가 요구사항과 맞는가?
선택 관계인지 필수 관계인지 구분했는가?
속성이 올바른 엔터티에 들어갔는가?
```

## STEP 11. 작은 시나리오로 설계를 검증합니다

ERD만 보고 끝내지 말고 실제 데이터를 상상해 봅니다.

예를 들어 회원 김민지가 책 두 권을 빌렸다고 가정합니다.

```text
members
1 | 김민지

books
10 | 데이터베이스 입문
11 | SQL 기초

loans
100 | member_id=1 | book_id=10
101 | member_id=1 | book_id=11
```

이 구조에서 다음 질문에 답할 수 있어야 합니다.

```text
김민지가 빌린 책은 무엇인가?
책 10번은 누가 빌렸는가?
아직 반납되지 않은 대여는 무엇인가?
회원 한 명의 과거 대여 이력을 조회할 수 있는가?
```

작은 샘플 데이터를 넣어 보는 것만으로도 설계 오류를 많이 발견할 수 있습니다.

---

## STEP 12. 요구사항 추적표를 만들어 봅니다

좋은 설계는 각 구조가 어떤 요구사항에서 나왔는지 추적할 수 있어야 합니다.

| 요구사항 | 반영 구조 |
| --- | --- |
| 회원 관리 | `members` |
| 회원 이름·이메일·가입일 | `members` 속성 |
| 도서 관리 | `books` |
| 대여 가능 | `loans` |
| 대여일·반납예정일 | `loans` 속성 |
| 미반납 상태 | `returned_at NULL` 허용 |

이 표를 만들면 요구사항 누락 여부를 확인하기 쉬워집니다.

---

## STEP 13. ERD를 PostgreSQL 테이블 구조로 바꿔 봅니다

논리 구조가 정해졌다면 PostgreSQL DDL 초안을 만들 수 있습니다.

```sql
CREATE TABLE members (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255),
    joined_at DATE NOT NULL
);

CREATE TABLE books (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    author VARCHAR(100),
    published_year INTEGER,
    isbn VARCHAR(30)
);

CREATE TABLE loans (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    member_id INTEGER NOT NULL,
    book_id INTEGER NOT NULL,
    borrowed_at DATE NOT NULL,
    due_at DATE NOT NULL,
    returned_at DATE,
    FOREIGN KEY (member_id) REFERENCES members(id),
    FOREIGN KEY (book_id) REFERENCES books(id)
);
```

이 코드는 설계 초안입니다.

`UNIQUE`, `CHECK`, 삭제 정책 같은 세부 규칙은 요구사항이 확정된 뒤 추가해야 합니다.

## STEP 14. AI에게 ERD 초안을 요청해 봅니다

ChatGPT나 Codex에 다음처럼 요청할 수 있습니다.

```text
다음 도서 대여 시스템 요구사항을 분석해서
엔터티, 속성, PK, FK, 관계를 정리하고 ERD 초안을 만들어 주세요.

요구사항:
- 회원을 관리한다.
- 회원은 이름, 이메일, 가입일을 가진다.
- 도서는 제목, 저자, 출판연도, ISBN을 가진다.
- 회원은 여러 권의 책을 대여할 수 있다.
- 책은 시간에 따라 여러 번 대여될 수 있다.
- 대여에는 대여일, 반납예정일, 실제반납일을 저장한다.
- 아직 반납하지 않았다면 실제반납일은 NULL일 수 있다.

확정되지 않은 업무 규칙은 임의로 만들지 말고
'추가 확인 필요' 항목으로 따로 정리해 주세요.
```

AI가 설계를 빠르게 만들어 줄 수 있지만 그대로 정답으로 사용하면 안 됩니다.

## STEP 15. AI가 만든 설계를 검증합니다

다음 질문으로 AI 결과를 검토합니다.

```text
1. 각 테이블의 한 행은 무엇을 의미하는가?
2. 각 PK는 왜 필요한가?
3. FK 방향은 올바른가?
4. N:M 관계가 연결 테이블로 풀렸는가?
5. 대여일과 반납일은 왜 loans에 있어야 하는가?
6. NULL 허용 여부가 요구사항과 맞는가?
7. 요구사항에 없는 UNIQUE나 CHECK를 임의로 추가하지 않았는가?
8. 미확정 정책을 별도 질문으로 정리했는가?
```

AI 시대에는 ERD를 직접 손으로만 그리는 능력보다 **AI가 만든 ERD가 실제 업무 요구사항에 맞는지 검증하는 능력**이 더 중요해지고 있습니다.

## AI 활용 실습 2. ERD 검토 요청하기

직접 만든 ERD를 텍스트로 정리한 뒤 다음 프롬프트를 사용해 봅니다.

```text

- FK
- 관계 수
```

이렇게 요청하면 AI를 설계 정답 생성기가 아니라 **설계 리뷰어**로 사용할 수 있습니다.

```text

```

```text
테이블 이름보다 한 행의 의미가 먼저다.
관계는 양방향 문장으로 확인한다.
요구사항에 없는 정책은 임의로 확정하지 않는다.
ERD는 그림이 아니라 요구사항을 구조로 표현한 결과물이다.
```
