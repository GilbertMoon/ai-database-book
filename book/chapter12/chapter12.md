# Chapter 12. NoSQL 이해와 선택 기준

이 장에서는 관계형 데이터베이스와 다른 방식으로 데이터를 저장하는 NoSQL 계열을 살펴봅니다. 목표는 특정 제품 이름을 많이 외우는 것이 아니라, 온라인 강의 서비스의 데이터 성격과 조회 패턴에 맞게 저장 방식을 판단하는 것입니다.

온라인 강의 서비스에는 `students`, `instructors`, `courses`, `enrollments`처럼 정합성이 중요한 데이터가 있습니다. 동시에 학생 로그인 세션, 인기 강의 캐시, 강의별 유연한 메타데이터, 학습 행동 이벤트, 학생-강의-주제 추천 관계처럼 관계형 테이블만으로는 설계가 번거로운 데이터도 있습니다.

이 장에서 다룰 내용은 다음과 같습니다.

- RDBMS와 NoSQL의 역할 차이
- NoSQL의 의미와 자주 하는 오해
- Key-Value DB
- Document DB
- Column-Family DB
- Graph DB
- PostgreSQL JSONB 실습
- 데이터 저장 방식 선택 기준
- AI 추천 결과 검토 방법

## 1. NoSQL을 왜 배우는가

관계형 데이터베이스는 구조가 명확하고 정합성이 중요한 데이터에 강합니다. 예를 들어 학생이 강의를 수강 신청하고 결제하는 흐름은 `students`, `courses`, `enrollments`, `payments` 같은 테이블과 제약 조건, 트랜잭션으로 관리하는 편이 안전합니다.

하지만 모든 데이터가 같은 성격을 갖지는 않습니다.

- 로그인 세션은 `student:1001:session` 같은 키로 빠르게 읽고 만료할 수 있어야 합니다.
- 인기 강의 목록은 `course:popular:top3`처럼 원본 데이터에서 계산한 캐시로 둘 수 있습니다.
- 강의의 옵션, 태그, 강사 소개는 강의마다 구조가 조금씩 다를 수 있습니다.
- 학습 행동 이벤트는 학생과 날짜 기준으로 대량 저장하고 시간순으로 읽을 수 있어야 합니다.
- 추천 기능은 학생, 강의, 주제 사이의 관계를 여러 단계 따라가야 할 수 있습니다.

이처럼 데이터 구조와 조회 패턴이 달라지면 저장 방식도 달라질 수 있습니다.

## 2. RDBMS와 NoSQL의 역할 나누기

NoSQL을 관계형 데이터베이스보다 좋은 기술로 이해하면 안 됩니다. 두 방식은 우열 관계가 아니라 역할이 다릅니다.

![RDBMS와 NoSQL 역할 나누기](../../images/chapter12/ch12_01_rdbms_vs_nosql_overview.svg)

그림 12-1 RDBMS와 NoSQL 역할 나누기

| 구분 | RDBMS에 적합한 경우 | NoSQL을 고려할 수 있는 경우 |
|---|---|---|
| 데이터 구조 | 테이블, 컬럼, 관계가 비교적 명확함 | 문서, 키-값, 이벤트, 그래프처럼 구조가 다양함 |
| 정합성 | 제약 조건과 트랜잭션이 중요함 | 일부 데이터는 최종 일관성이나 비동기 갱신을 허용할 수 있음 |
| 조회 패턴 | JOIN, 집계, 조건 검색이 중요함 | 키 조회, 문서 단위 조회, 특정 파티션 조회, 관계 탐색이 중요함 |
| 운영 관점 | 이미 익숙한 백업, 권한, SQL 운영 체계가 있음 | 별도 제품 운영, 모니터링, 백업, 장애 대응이 필요할 수 있음 |

온라인 강의 서비스에서 수강 신청의 원본 데이터는 RDBMS가 적합합니다. 반면 인기 강의 캐시는 원본 데이터를 빠르게 보여 주기 위한 파생 데이터이므로 Key-Value 저장소를 고려할 수 있습니다.

## 3. NoSQL의 의미와 오해 정리

NoSQL은 관계형 테이블 모델만 사용하지 않는 여러 데이터베이스 접근 방식의 계열입니다. 흔히 “Not Only SQL”이라고 해석하기도 하지만, 이것을 고정된 공식처럼 외우기보다 관계형 모델 밖의 다양한 저장 모델을 묶어 부르는 말로 이해하는 편이 안전합니다.

NoSQL에 대해 자주 생기는 오해는 다음과 같습니다.

- NoSQL이라고 해서 항상 SQL을 전혀 쓰지 않는 것은 아닙니다.
- NoSQL이라고 해서 스키마나 설계 규칙이 필요 없는 것은 아닙니다.
- NoSQL이라고 해서 트랜잭션이 항상 없는 것은 아닙니다. 제품과 설정에 따라 범위가 다릅니다.
- NoSQL이라고 해서 항상 더 빠른 것은 아닙니다. 조회 패턴에 맞게 설계했을 때 장점이 납니다.
- 모든 NoSQL이 같은 방식으로 확장되는 것은 아닙니다.

따라서 NoSQL 선택은 “새 기술을 쓰고 싶다”가 아니라 “이 데이터는 어떤 구조이고, 어떤 방식으로 읽고 쓰는가”에서 출발해야 합니다.

이 장에서는 다음 네 가지 유형만 다룹니다.

![NoSQL 유형 정리](../../images/chapter12/ch12_02_nosql_types_map.svg)

그림 12-2 NoSQL 유형 정리

## 5. Key-Value DB: 세션과 캐시

Key-Value DB는 키로 값을 바로 찾는 저장 방식입니다. 값은 문자열, 숫자, JSON, 바이너리 등 제품이 지원하는 형태가 될 수 있습니다.

![Key-Value 조회와 캐시 미스](../../images/chapter12/ch12_03_key_value_lookup.svg)

그림 12-3 Key-Value 조회와 캐시 미스

예를 들어 다음과 같은 키를 사용할 수 있습니다.

| 키 | 의미 |
|---|---|
| `student:1001:session` | 학생 1001번의 로그인 세션 |
| `course:popular:top3` | 인기 강의 상위 3개 캐시 |
| `feature:recommendation:v1` | 추천 기능 활성화 여부 |

Key-Value 저장소는 정확한 키를 알고 있을 때 빠르게 읽는 상황에 적합합니다. 다만 캐시는 원본 데이터가 아니라 원본에서 계산하거나 복사한 파생 데이터입니다. 원본은 여전히 RDBMS에 있고, 캐시는 빠른 응답을 위해 별도로 둔다고 이해해야 합니다.

캐시 미스가 발생하면 보통 다음 흐름을 사용합니다.

1. 키로 캐시를 조회합니다.
2. 값이 없거나 만료되었으면 원본 RDBMS에서 읽습니다.
3. 캐시를 다시 저장합니다.
4. 사용자에게 결과를 반환합니다.

TTL이나 만료 정책은 제품마다 다릅니다. 이 장의 SQL 실습에서 사용하는 `key_value_cache_examples` 테이블은 Key-Value 개념을 흉내 낸 예시일 뿐입니다. 메모리 저장, 분산, 자동 TTL 삭제, 복제, 고성능 조회를 구현하지 않습니다. `expired_at` 컬럼도 만료 기준 시각을 저장할 뿐이며 행을 자동 삭제하지 않습니다.

## 6. Document DB: 강의 문서와 유연한 메타데이터

Document DB는 데이터를 문서 단위로 저장합니다. 문서는 보통 JSON과 비슷한 구조를 갖습니다. 하나의 강의 문서를 만들고, 조회하고, 수정하는 작업이 함께 일어나는 경우에 적합할 수 있습니다.

![Document JSON 구조](../../images/chapter12/ch12_04_document_json_structure.svg)

그림 12-4 Document JSON 구조

강의 문서 예시는 다음과 같습니다.

```json
{
  "course_code": "DB-101",
  "title": "데이터베이스 입문",
  "level": "basic",
  "tags": ["SQL", "PostgreSQL", "DB"],
  "instructor": {"name": "김강사", "specialty": "Database"},
  "options": {"online": true, "certificate": true}
}
```

Document DB는 유연한 구조가 장점이지만 아무 규칙 없이 저장해도 된다는 뜻은 아닙니다. 문서 크기, 반복 저장되는 값, 깊은 중첩, 자주 바뀌는 구조를 검토해야 합니다. 같은 의미의 필드가 어떤 문서에는 `level`, 어떤 문서에는 `difficulty`로 저장된다면 조회와 분석이 어려워집니다.

## 7. Column-Family DB: 학습 이벤트 조회 패턴

와이드 컬럼(Column-Family) DB는 대량 쓰기와 특정 조회 패턴에 맞춘 읽기에 강점을 갖는 NoSQL 유형입니다. 이 장에서는 이후부터 Column-Family DB라고 부르겠습니다.

![Column-Family 조회 패턴](../../images/chapter12/ch12_05_column_family_log_flow.svg)

그림 12-5 Column-Family 조회 패턴

중요한 점은 Column-Family DB 설계가 조회 패턴에서 출발한다는 것입니다. 예를 들어 목표 조회가 “학생 한 명의 특정 날짜 학습 이벤트를 시간순으로 읽기”라면 다음처럼 설계할 수 있습니다.

| 설계 요소 | 예시 |
|---|---|
| partition key | `student_id + event_date` |
| sort key | `event_time` |
| target query | 특정 학생의 특정 날짜 학습 이벤트 조회 |

이 구조는 “아무 조건으로나 자유롭게 분석하는 저장소”가 아닙니다. JOIN을 자유롭게 대체하는 도구도 아닙니다. 특정 조회를 빠르게 만들기 위해 데이터를 중복 저장하거나 비정규화할 수 있으며, 그만큼 설계와 운영 책임이 커집니다.

## 8. Graph DB: 학생-강의-주제 관계 탐색

Graph DB는 데이터를 노드와 엣지로 표현합니다. 관계를 여러 단계 따라가며 탐색하는 문제가 많을 때 적합할 수 있습니다.

![Graph 관계 탐색](../../images/chapter12/ch12_06_graph_relationship_search.svg)

그림 12-6 Graph 관계 탐색

온라인 강의 서비스에서는 다음과 같은 그래프를 생각할 수 있습니다.

| 요소 | 예시 |
|---|---|
| 노드 | `Student`, `Course`, `Topic` |
| 엣지 | `ENROLLED`, `INTERESTED_IN`, `RELATED_TO` |
| 질문 | “Topic X와 연결된 학생에게 추천할 강의는 무엇인가?” |

관계가 있다고 해서 항상 Graph DB가 필요한 것은 아닙니다. 단순한 수강 목록이나 강의별 학생 목록은 RDBMS JOIN으로 충분할 수 있습니다. Graph DB는 관계를 여러 단계 확장하며 탐색하거나 추천 후보를 찾는 일이 핵심일 때 검토합니다.

## 9. PostgreSQL JSONB로 문서형 데이터 맛보기

PostgreSQL의 JSONB는 관계형 데이터베이스 안에서 JSON 형태 데이터를 저장하고 조회할 수 있게 해 주는 타입입니다. 하지만 JSONB를 사용한다고 PostgreSQL이 Document DB가 되는 것은 아닙니다. JSONB는 문서형 데이터의 일부 요구를 RDBMS 안에서 처리하는 선택지입니다.

![JSONB 실습 흐름](../../images/chapter12/ch12_07_jsonb_practice_flow.svg)

그림 12-7 PostgreSQL JSONB 실습 흐름

실습에서는 `course_documents` 테이블을 사용합니다.

```sql
CREATE TABLE course_documents (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    course_code TEXT NOT NULL UNIQUE,
    title TEXT NOT NULL,
    metadata JSONB NOT NULL
);
```

주요 JSONB 연산자는 다음과 같습니다.

| 연산자 | 의미 |
|---|---|
| `->` | JSON/JSONB 값을 반환 |
| `->>` | text 값을 반환 |
| `?` | 최상위 키 존재 여부 확인 |
| `@>` | JSONB 포함 조건 확인 |

예상 조회 결과는 다음과 같습니다.

| course_code | title | level | online |
|---|---|---|---|
| DB-101 | 데이터베이스 입문 | basic | true |
| AI-201 | AI 데이터 분석 | intermediate | true |
| GRAPH-301 | 그래프 데이터 이해 | advanced | false |

JSONB 인덱스는 필요할 때만 추가합니다. 전체 문서 포함 검색에는 GIN 인덱스를 고려할 수 있고, 특정 필드를 자주 조건으로 쓰면 표현식 인덱스를 고려할 수 있습니다. 표본이 작으면 인덱스를 만들어도 `Seq Scan`이 나올 수 있습니다.

## 10. 저장 방식 선택 기준

NoSQL 선택은 다음 질문으로 검토합니다.

- 이 데이터가 원본인가, 원본에서 만든 파생 데이터인가?
- 강한 정합성과 트랜잭션이 필요한가?
- 주된 조회 패턴은 키 조회, 문서 조회, 파티션 조회, 관계 탐색 중 무엇인가?
- 데이터 구조가 자주 바뀌는가?
- 별도 저장소를 운영하고 백업, 복구, 모니터링할 역량이 있는가?
- 장애가 났을 때 RDBMS와 NoSQL 사이의 동기화 문제를 감당할 수 있는가?

온라인 강의 서비스에서는 보통 수강 신청과 결제는 RDBMS에 둡니다. 세션과 인기 강의 캐시는 Key-Value 저장소를 검토할 수 있고, 강의 메타데이터는 Document DB나 PostgreSQL JSONB를 검토할 수 있습니다. 학습 이벤트는 조회 패턴이 명확할 때 Column-Family DB를 검토하고, 추천 관계 탐색은 Graph DB를 검토할 수 있습니다.

## 11. AI가 추천한 NoSQL 선택 결과 검토하기

AI에게 저장 방식 추천을 요청할 수는 있지만, 결과를 그대로 적용하면 위험합니다. AI 추천은 검토할 초안입니다.

![AI 추천 NoSQL 선택 검토 흐름](../../images/chapter12/ch12_08_ai_nosql_choice_review.svg)

그림 12-8 AI 추천 NoSQL 선택 검토 흐름

검토 질문은 다음과 같습니다.

- AI가 원본 데이터와 캐시 데이터를 구분했는가?
- 조회 패턴을 구체적으로 확인했는가?
- 정합성과 트랜잭션 요구사항을 확인했는가?
- PostgreSQL JSONB로 충분한 문제를 별도 Document DB로 과장하지 않았는가?
- Column-Family DB를 단순 로그 저장소처럼만 설명하지 않았는가?
- Graph DB가 필요한 관계 탐색인지, RDBMS JOIN으로 충분한지 검토했는가?
- 운영 복잡도와 장애 대응 계획을 고려했는가?

## 12. 마무리

NoSQL은 관계형 데이터베이스를 버리기 위한 기술이 아닙니다. 데이터 구조와 조회 패턴에 따라 RDBMS와 함께 선택할 수 있는 저장 방식의 계열입니다.

Chapter 12의 핵심은 다음과 같습니다.

- RDBMS는 정합성, 제약 조건, 트랜잭션이 중요한 원본 데이터에 강합니다.
- Key-Value DB는 정확한 키 조회와 캐시에 적합할 수 있습니다.
- Document DB는 문서 단위로 함께 생성, 조회, 수정되는 데이터에 적합할 수 있습니다.
- Column-Family DB는 조회 패턴을 먼저 정하고 파티션 키와 정렬 키를 설계합니다.
- Graph DB는 관계를 여러 단계 탐색하는 문제에 적합할 수 있습니다.
- PostgreSQL JSONB는 문서형 데이터 요구 일부를 RDBMS 안에서 처리하는 방법입니다.
- AI 추천은 데이터 구조, 조회 패턴, 정합성, 운영 난이도 기준으로 검증해야 합니다.
