## 5. 첫 테이블과 최소 설계 범위

Chapter 04의 실습 테이블은 다음 하나입니다.

```sql
CREATE TABLE public.students (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    major VARCHAR(100),
    grade INTEGER,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

```text
한 행 = 학생 한 명
id = 내부 식별자

created_at = 기본 등록 시각
```

학년 범위, 전공 표준화, 이메일 업무 규칙과 삭제 정책을 이 장에서 과도하게 확정하지 않고 Chapter 06으로 연결합니다.

## 6. CRUD와 CREATE TABLE 구분

CRUD의 Create와 DDL의 `CREATE TABLE`을 구분했습니다.

| CRUD | SQL | 역할 |
| --- | --- | --- |
| Create | `INSERT` | 새 데이터 행 추가 |
| Read | `SELECT` | 저장된 데이터 조회 |
| Update | `UPDATE` | 기존 데이터 수정 |
| Delete | `DELETE` | 기존 데이터 삭제 |

`CREATE TABLE`은 데이터를 추가하는 CRUD Create가 아니라 데이터를 저장할 구조를 생성하는 명령입니다.

## 7. DISTINCT·NULL·정렬 보강

`DISTINCT`를 핵심 조회 흐름에 추가했습니다.

```sql
SELECT DISTINCT major
FROM public.students
WHERE major IS NOT NULL
ORDER BY major;
```

원본 데이터를 지우는 기능이 아니라 조회 결과의 중복만 제거한다는 점을 명시했습니다.

NULL은 다음 기준으로 정리했습니다.

```text
NULL ≠ 0
NULL ≠ 빈 문자열
= NULL 사용 금지
IS NULL / IS NOT NULL 사용
<> 비교에서 NULL 행이 빠질 수 있음
IS DISTINCT FROM은 선택·심화 학습
```

`ORDER BY`가 없으면 행 순서를 보장하지 않고, `LIMIT`을 사용할 때는 안정적인 정렬 기준과 동률 보조 기준을 함께 사용하도록 했습니다.

## 11. INSERT 부분 입력 방지 보강

이번 전체 점검에서 `02_insert_students.sql`의 중요한 안전성 문제를 보완했습니다.

기존에는 학생 데이터를 세 번의 독립 `INSERT`로 실행했기 때문에 중간 문장이 실패하면 앞 문장만 입력된 부분 상태가 남을 수 있었습니다.

현재 파일은 다음 순서로 동작합니다.

```text
현재 DB·public·쓰기 가능 상태 확인
→ public.students 존재 확인
→ 시작 행 수 0 확인
→ BEGIN
→ 학생 1명 INSERT
→ 학생 4명 INSERT
→ NULL 학생 1명 INSERT
→ COMMIT 전 초기 데이터 상태 자동 판정
→ COMMIT
```

COMMIT 전 판정:

```text
학생 수 = 6
이준호 grade = 3
박서연 = 1행
윤서진 major·grade = NULL
```

따라서 세 입력 중 하나 또는 최종 판정이 실패하면 정상 완료된 초기 상태로 간주하지 않습니다.

## 14. 안전한 UPDATE·DELETE와 위험 SQL 표현

핵심 안전 흐름은 다음으로 통일했습니다.

```text
SELECT
→ UPDATE/DELETE RETURNING
→ 영향 행 수 확인
→ SELECT 재확인
```

발표 화면의 WHERE 없는 위험 SQL은 이번 점검에서 복사·실행 가능한 예처럼 보이지 않도록 주석 형태로 보정했습니다.

```sql
-- 실행하지 않습니다.
-- UPDATE public.students
-- SET grade = 1;

-- 실행하지 않습니다.
-- DELETE FROM public.students;
```

실습 코드 파일에서도 동일하게 주석 상태를 유지합니다.

본문과 워크북의 위험 SQL은 설명용 예시라는 문맥이 존재하지만, 최종 출판 렌더링 단계에서 실행 금지 표시가 충분히 눈에 띄는지 별도 확인합니다.

## 15. AI SQL 검토 기준

AI SQL 검토를 다음 여섯 질문으로 단순화했습니다.

```text
1. 현재 연결과 테이블이 맞는가?
2. 사용하는 열과 데이터 타입이 맞는가?
3. WHERE 조건과 NULL 처리가 요구사항과 맞는가?
4. 예상 반환 행 또는 영향받는 행 수는 몇 개인가?
5. UPDATE·DELETE 전에 같은 조건으로 SELECT했는가?
6. 실행 결과가 예상과 일치하는가?
```

발표자료의 “현재 체크포인트는 어디인가?” 표현도 “현재 데이터 상태는 무엇인가?”로 보정했습니다.

## 16. 워크북 동기화

워크북은 핵심·선택·심화 활동으로 재구성되어 있습니다.

```text
핵심
→ 연결, 작성 규칙, 테이블, 타입, 입력, 조회, NULL, DISTINCT, 정렬, 수정·삭제, AI 검토

선택
→ RETURNING, ILIKE, NULLS LAST, 형 변환, 여러 열 UPDATE

심화
→ IDENTITY, CURRENT_TIMESTAMP, UNKNOWN, IS DISTINCT FROM
```

주요 SQL마다 예상과 실제 결과를 기록하도록 구성해 자율 학습에서 실행 성공 여부만 확인하지 않도록 했습니다.


내부 `k` 값은 기존 의미 단위 수동 매핑과 호환하기 위해 유지하고, 최종 화면 내용은 `chapter04_content_patch.js`에서 보정합니다.
