# Chapter 05. 요구사항에서 데이터 모델과 ERD 만들기

---

## 이 장에서 살펴볼 내용

Chapter 04에서는 이미 정해진 `students` 테이블을 만들고 기본 SQL을 실행했습니다. 실제 프로젝트에서는 테이블이 먼저 주어지지 않습니다. 사용자의 업무 요구사항을 읽고 무엇을 저장해야 하는지, 데이터가 어떻게 연결되는지, 아직 결정되지 않은 정책은 무엇인지부터 판단해야 합니다.

이 장의 학습 흐름은 다음과 같습니다.

```text
요구사항 읽기
→ 업무 사실과 규칙 구분
→ 확정·미확정 규칙 분리
→ 엔터티와 속성 찾기
→ 관계를 양방향 문장으로 표현
→ 카디널리티와 선택성 결정
→ PK·FK 후보 정리
→ ERD 작성
→ 요구사항 추적표로 누락 확인
→ PostgreSQL 구조로 변환
→ 작은 데이터로 구조 확인
```

이 장에서는 다음 내용을 살펴봅니다.

- 요구사항에서 업무 사실과 업무 규칙 찾기
- 확정된 규칙과 미확정 규칙 구분하기
- 엔터티와 속성 판단하기
- 식별자와 기본키 후보 정하기
- 1:1, 1:N, N:M 관계 이해하기
- 필수 관계와 선택 관계 표현하기
- N:M 관계를 사건·업무 테이블로 풀기
- 개념 모델과 PostgreSQL 테이블 구조의 차이 이해하기
- 요구사항 추적표로 설계 누락 확인하기
- ERD를 PostgreSQL 테이블로 변환하기
- AI가 만든 ERD의 가정과 누락 검토하기

이 장의 목표는 ERD 도구 사용법을 외우는 것이 아닙니다. 요구사항의 각 문장을 어떤 테이블, 열, 관계와 규칙으로 표현했는지 설명할 수 있는 데이터 모델을 만드는 것입니다.

> **핵심 원칙**
>
> 좋은 데이터 모델은 명사만 찾아 만든 테이블이 아니라, 요구사항의 업무 규칙과 관계를 근거와 함께 설명할 수 있는 구조입니다.

## 1. 이미 있는 테이블과 직접 설계하는 것의 차이

Chapter 04에서는 `students` 테이블의 구조가 이미 정해져 있었습니다. 따라서 열의 의미를 이해하고 SQL을 실행하는 데 집중할 수 있었습니다.

실제 시스템 개발에서는 먼저 다음 질문에 답해야 합니다.

```text
무엇을 독립적으로 관리해야 하는가?
각 대상은 어떤 정보를 가지는가?
대상들은 어떻게 연결되는가?
한 대상이 다른 대상을 몇 개까지 가질 수 있는가?
값이 반드시 있어야 하는가, 비어 있어도 되는가?
시간에 따라 반복되는 사건을 별도로 기록해야 하는가?
어떤 정책이 확정되었고 어떤 정책이 아직 미정인가?
```

예를 들어 다음과 같은 하나의 큰 표가 있다고 가정해 보겠습니다.

| member_name | member_email | book_title | author | borrowed_at | due_at |
| --- | --- | --- | --- | --- | --- |
| 김민지 | minji@example.com | 데이터베이스 입문 | 문길래 | 2026-04-01 | 2026-04-15 |
| 김민지 | minji@example.com | SQL 기초 | 홍길동 | 2026-04-02 | 2026-04-16 |

회원 정보와 책 정보가 대여 기록마다 반복됩니다. 이메일이나 책 제목이 바뀌면 여러 행을 수정해야 합니다. 또한 한 행이 회원을 나타내는지, 책을 나타내는지, 대여 사건을 나타내는지 분명하지 않습니다.

데이터 모델링은 이런 문제를 줄이기 위해 현실의 업무를 데이터 구조로 정리하는 과정입니다.

```text
현실의 업무
→ 관리 대상과 사건
→ 속성
→ 관계
→ 업무 규칙
→ 관계형 데이터베이스 구조
```

반복되는 정보는 테이블 분리가 필요한 신호일 수 있습니다. 구체적인 정규화 판단 기준은 Chapter 06에서 자세히 다룹니다.

## 2. 개념 모델과 PostgreSQL 구조를 구분한다

데이터 모델링에는 서로 다른 수준이 있습니다.

```text
현실의 대상과 사건
→ 개념 모델의 엔터티와 관계
→ 논리 모델의 엔터티·속성·키
→ PostgreSQL 물리 모델의 테이블·열·데이터 타입·제약조건
```

엔터티와 속성은 업무 대상을 개념적으로 표현하는 요소입니다. 이를 관계형 데이터베이스의 논리·물리 구조로 변환하면 엔터티는 주로 테이블이 되고 속성은 열이 됩니다.

이 책에서는 초보자가 설계와 SQL을 연결해 이해할 수 있도록 **개념·논리 모델을 PostgreSQL 테이블 구조와 가깝게 표현한 실무형 ERD**를 사용합니다. 따라서 ERD의 엔터티 이름과 실제 테이블 이름이 유사하지만, 두 개념이 완전히 같은 것은 아닙니다.

| 모델 수준 | 주요 질문 | 대표 결과 |
| --- | --- | --- |
| 개념 모델 | 어떤 업무 대상과 사건이 있는가? | 회원, 도서, 대여 관계 |
| 논리 모델 | 어떤 속성·키·카디널리티가 필요한가? | `members`, `books`, `loans` 구조 초안 |
| 물리 모델 | PostgreSQL에서 어떤 타입과 제약조건으로 구현하는가? | `CREATE TABLE`, 데이터 타입, PK·FK |

## 3. 데이터 모델링의 전체 흐름

데이터 모델링은 한 번에 완성되는 작업이 아닙니다. 요구사항과 설계 결과를 반복해서 비교하는 과정입니다.

| 단계 | 핵심 질문 | 주요 산출물 |
| --- | --- | --- |
| 요구사항 분석 | 무엇을 관리하고 어떤 규칙이 있는가? | 업무 사실·규칙 목록 |
| 미확정 사항 분리 | 추가 확인이 필요한 정책은 무엇인가? | 질문 목록 |
| 엔터티 찾기 | 독립적으로 관리할 대상은 무엇인가? | 엔터티 후보 |
| 속성 정리 | 각 대상은 어떤 정보를 가지는가? | 속성 후보 |
| 관계 문장 작성 | 대상들은 두 방향에서 어떻게 연결되는가? | 관계 문장 |
| 카디널리티 결정 | 한쪽 행이 다른 쪽 행과 몇 개 연결되는가? | 1:1, 1:N, N:M |
| 선택성 결정 | 관계가 반드시 필요한가? 없어도 되는가? | 0..1, 1, 0..N, 1..N |
| 키 설계 | 행과 관계를 어떻게 식별하는가? | PK·FK 후보 |
| ERD 작성 | 구조를 한눈에 어떻게 표현하는가? | ERD 초안 |
| 추적 검토 | 모든 요구사항이 반영되었는가? | 요구사항 추적표 |
| SQL 변환 | PostgreSQL에서 어떻게 구현하는가? | DDL 초안 |
| 구조 검증 | 작은 데이터로 관계를 표현할 수 있는가? | 샘플 데이터·검증 결과 |

![요구사항에서 데이터베이스 구조까지의 모델링 흐름](../../images/chapter05/ch05_01_modeling_process.svg)

그림 5-1 요구사항에서 데이터베이스 구조까지의 모델링 흐름

초급 단계에서는 완벽한 ERD보다 다음 질문에 답할 수 있는지가 더 중요합니다.

```text
이 테이블은 어떤 요구사항에서 나왔는가?
한 행은 무엇을 의미하는가?
이 열은 왜 이 테이블에 들어갔는가?
이 외래키는 어떤 관계를 표현하는가?
이 관계는 필수인가 선택인가?
설계자가 임의로 추가한 가정은 없는가?
```

## 4. 요구사항에서 업무 사실과 업무 규칙 찾기

이 장에서는 단순한 도서 대여 시스템을 예제로 사용합니다.

```text
R-01. 도서관은 회원을 관리한다.
R-02. 회원은 이름, 이메일, 가입일을 가진다.
R-03. 도서는 제목, 저자, 출판연도, ISBN을 가진다.
R-04. 회원은 여러 권의 책을 대여할 수 있다.
R-05. 책은 시간에 따라 여러 번 대여될 수 있다.
R-06. 대여 기록에는 대여일, 반납예정일, 실제반납일을 저장한다.
R-07. 아직 반납되지 않은 대여 기록은 실제반납일이 비어 있을 수 있다.
```

요구사항에서는 단순히 명사만 찾지 않고 세 가지를 구분합니다.

| 구분 | 예 | 데이터 모델에서의 역할 |
| --- | --- | --- |
| 관리 대상 | 회원, 도서, 대여 기록 | 엔터티 후보 |
| 설명 값 | 이름, ISBN, 대여일 | 속성 후보 |
| 업무 규칙 | 회원은 여러 권을 대여할 수 있음 | 관계·제약조건 후보 |

요구사항 문장을 다음처럼 분석할 수 있습니다.

| 요구사항 | 데이터 요소 | 관계·규칙 |
| --- | --- | --- |
| R-01 | 회원 | 독립적으로 관리 |
| R-02 | 이름, 이메일, 가입일 | 회원의 속성 |
| R-04 | 회원, 도서, 대여 | 회원과 대여 기록의 1:N 후보 |
| R-07 | `returned_at` | NULL 허용 후보 |

명사를 찾는 작업은 출발점일 뿐입니다. 문장의 동사와 수량 표현에서 관계와 업무 규칙을 찾아야 합니다.

## 5. 확정 규칙과 미확정 규칙 구분하기

요구사항 문서에는 필요한 모든 정책이 적혀 있지 않은 경우가 많습니다. 설계자는 빠진 내용을 임의로 확정하지 않고 질문 목록으로 분리해야 합니다.

### 확정된 규칙

현재 요구사항에서 명확하게 알 수 있는 내용입니다.

```text
회원과 도서를 관리한다.
대여 기록은 회원과 도서를 연결한다.
대여일과 반납예정일을 저장한다.
실제반납일은 비어 있을 수 있다.
한 회원과 한 도서는 시간에 따라 여러 대여 기록을 가질 수 있다.
```

### 미확정 규칙

현재 문장만으로 결정할 수 없는 내용입니다.

```text
회원 이메일은 시스템 안에서 반드시 고유한가?
이메일 대소문자를 같은 값으로 취급하는가?
ISBN은 시스템 안에서 반드시 고유한가?
ISBN이 없는 도서도 등록할 수 있는가?
동일한 ISBN의 실제 복본을 어떻게 구분하는가?
한 도서에 여러 저자를 저장해야 하는가?
회원 한 명이 동시에 빌릴 수 있는 최대 권수는 몇 권인가?
연체 회원도 새 책을 대여할 수 있는가?
한 대여 기록의 반납예정일은 어떻게 계산하는가?
대여일보다 반납예정일이 앞설 수 있는가?
실제반납일이 대여일보다 앞설 수 있는가?
같은 한 권의 동시 활성 대여를 어떻게 차단하는가?
회원 탈퇴 후 과거 대여 기록을 유지하는가?
```

| 구분 | 처리 방법 |
| --- | --- |
| 확정된 규칙 | ERD와 열·관계에 반영 |
| 미확정 규칙 | 질문 목록으로 관리 |
| 임시 가정 | 가정이라고 명시하고 검토 요청 |
| 범위 제외 | 이번 모델에서 다루지 않는다고 기록 |

### 이 장의 범위 가정

이 장에서는 모델링 흐름에 집중하기 위해 다음 범위를 사용합니다.

```text
books의 한 행을 하나의 대여 대상 도서로 취급한다.
동일 ISBN의 여러 복본은 별도 행이나 별도 테이블로 구분하지 않는다.
샘플 데이터에서는 같은 한 권이 동시에 두 미반납 대여에 속하지 않도록 한다.
동시 대여를 데이터베이스 제약조건으로 차단하는 구현은 Chapter 06으로 미룬다.
최대 대여 권수, 연체 정책과 삭제 정책은 범위에서 제외한다.
회원 이메일과 ISBN의 고유성은 아직 확정하지 않는다.
```

확장 모델에서는 다음처럼 나눌 수 있습니다.

```text
books: 제목, 저자, ISBN과 같은 서지 정보
book_copies: 실제 대여 가능한 복본
loans: 복본별 대여 기록
```

지금은 `members`, `books`, `loans` 세 테이블만 사용합니다.

## 6. 엔터티 후보 찾기

엔터티는 데이터베이스에서 독립적으로 관리해야 할 대상이나 사건입니다. 관계형 데이터베이스로 구현할 때 보통 테이블 후보가 됩니다.

엔터티 후보를 판단할 때 다음 질문을 사용합니다.

```text
독립적인 식별자가 필요한가?
여러 속성을 가지는가?
여러 건의 데이터가 저장되는가?
다른 대상과 관계를 가지는가?
시간에 따라 생성되는 사건이나 이력인가?
```

도서 대여 요구사항에서 후보를 분류하면 다음과 같습니다.

| 후보 | 엔터티 여부 | 판단 근거 |
| --- | --- | --- |
| 회원 | 엔터티 | 독립적으로 식별·관리하며 여러 속성을 가짐 |
| 도서 | 엔터티 | 독립적으로 식별·관리하며 여러 속성을 가짐 |
| 대여 기록 | 사건 엔터티 | 회원과 책 사이에서 반복 발생하며 날짜와 상태를 가짐 |
| 이메일 | 속성 | 회원을 설명하는 값 |
| ISBN | 속성 | 도서를 설명하는 값 |
| 반납예정일 | 속성 | 대여 사건을 설명하는 값 |

따라서 이 장의 엔터티 후보는 다음 세 가지입니다.

```text
members
books
loans
```

`loans`처럼 시간에 따라 발생하는 행위나 이력을 저장하는 대상을 **사건 엔터티** 또는 **업무 엔터티**라고 볼 수 있습니다.

그림 5-2 엔터티와 속성 구분하기

도서 대여 시스템의 속성을 정리하면 다음과 같습니다.

| 엔터티 | 속성 후보 |
| --- | --- |
| 회원 | 회원ID, 이름, 이메일, 가입일 |
| 도서 | 도서ID, 제목, 저자, 출판연도, ISBN |
| 대여 기록 | 대여ID, 회원ID, 도서ID, 대여일, 반납예정일, 실제반납일 |

영문 테이블과 열 이름으로 바꾸면 다음과 같습니다.

| 테이블 | 열 |
| --- | --- |
| `members` | `id`, `name`, `email`, `joined_at` |
| `books` | `id`, `title`, `author`, `published_year`, `isbn` |
| `loans` | `id`, `member_id`, `book_id`, `borrowed_at`, `due_at`, `returned_at` |

이 책에서는 다음 이름 규칙을 사용합니다.

```text
테이블 이름은 복수형을 사용한다.
열 이름은 snake_case를 사용한다.
기본키 열은 id를 사용한다.
외래키 열은 참조 대상의 단수형 + _id를 사용한다.
날짜·시간 열은 의미가 드러나는 이름을 사용한다.
```

이름 규칙은 절대적인 법칙이 아니라 프로젝트 안에서 일관성을 유지하기 위한 약속입니다.

## 8. 식별자와 기본키 후보 정하기

각 테이블의 행은 서로 구분할 수 있어야 합니다.

| 테이블 | 기본키 후보 | 업무상 고유값 후보 | 현재 상태 |
| --- | --- | --- | --- |
| `members` | `id` | `email` | 고유성 미확정 |
| `books` | `id` | `isbn` | 고유성·복본 정책 미확정 |
| `loans` | `id` | 별도 정책 필요 | 단일 대여 사건 식별 |

이 장에서는 모든 테이블에 숫자형 `id`를 기본키로 사용합니다.

```text
기본키: 데이터베이스 내부에서 행을 안정적으로 식별
업무상 고유값 후보: 업무 정책 확인 후 중복 금지 여부를 결정할 값
```

이메일이나 ISBN을 기본키로 직접 사용할 수도 있지만, 값의 형식이나 정책이 바뀔 수 있으므로 별도 숫자 ID를 기본키로 사용합니다. 이메일과 ISBN의 고유성은 요구사항에서 아직 확정되지 않았으므로 Chapter 05의 DDL에서는 `UNIQUE`를 적용하지 않습니다. Chapter 06에서 정책을 확인하고 제약조건 후보로 다시 검토합니다.

## 9. 관계를 문장으로 표현하기

ERD를 그리기 전에 관계를 자연어 문장으로 작성합니다.

```text
한 회원은 0개 이상의 대여 기록을 가질 수 있다.
하나의 대여 기록은 정확히 한 회원을 참조한다.

한 도서는 0개 이상의 대여 기록을 가질 수 있다.
하나의 대여 기록은 정확히 한 도서를 참조한다.
```

관계를 양방향 문장으로 작성하면 다음을 확인하기 쉽습니다.

- 어느 쪽이 1이고 어느 쪽이 N인지
- 외래키가 어느 테이블에 들어가야 하는지
- 관계가 필수인지 선택인지
- 요구사항에 모순이 없는지

관계 문장이 모호하다면 ERD를 먼저 그리지 말고 업무 담당자에게 질문해야 합니다.

## 10. 1:1, 1:N, N:M 관계

테이블 사이의 관계는 보통 다음 세 유형으로 설명합니다.

| 관계 | 의미 | 예 |
| --- | --- | --- |
| 1:1 | 한 행이 다른 쪽에서 최대 한 행과 연결 | 회원과 회원 상세정보 |
| 1:N | 한 행이 다른 쪽의 여러 행과 연결 | 회원과 대여 기록 |
| N:M | 양쪽의 여러 행이 서로 여러 행과 연결 | 회원과 도서의 대여 이력 |

### 1:1 관계

1:1 관계는 그림의 표기만으로 보장되지 않습니다. 자식 테이블에 일반 외래키만 두면 여러 자식 행이 같은 부모를 참조할 수 있어 1:N이 됩니다.

구현할 때는 다음 방식 중 하나를 사용할 수 있습니다.

```text
자식 외래키에 UNIQUE를 적용한다.
부모의 기본키를 자식의 기본키이자 외래키로 사용한다.
```

구체적인 제약조건 구현은 Chapter 06에서 다룹니다.

### 1:N 관계

`members`와 `loans`는 1:N 관계입니다.

```text
members 1 ─── N loans
```

1:N 관계에서는 보통 N쪽 테이블에 외래키를 둡니다.

```text
loans.member_id → members.id
```

![1:N 관계와 외래키 위치](../../images/chapter05/ch05_04_one_to_many_relationship.svg)

그림 5-3 1:N 관계와 외래키 위치

같은 `member_id`가 여러 대여 행에 나타나는 것은 중복 오류가 아니라 1:N 관계의 정상적인 표현입니다.

## 11. 필수 관계와 선택 관계

관계에는 최대 개수뿐 아니라 최소 개수도 중요합니다.

| 표기 | 의미 |
| --- | --- |
| `1` | 정확히 하나 |
| `0..1` | 없거나 하나 |
| `0..N` | 없거나 여러 개 |
| `1..N` | 하나 이상 |

도서 대여 관계를 표현하면 다음과 같습니다.

```text
회원 → 대여 기록: 0..N
도서 → 대여 기록: 0..N
대여 기록 → 회원: 1
대여 기록 → 도서: 1
```

회원은 가입 직후 대여 기록이 없을 수 있습니다. 도서도 아직 대여된 적이 없을 수 있습니다. 따라서 부모에서 대여 기록으로 향하는 관계는 선택적입니다.

반면 대여 기록은 반드시 특정 회원과 특정 도서를 가리켜야 합니다. 따라서 `loans.member_id`와 `loans.book_id`는 `NOT NULL` 외래키 후보입니다.

필수·선택 관계는 이후 `NOT NULL`, 외래키와 NULL 허용 여부를 결정할 때 근거가 됩니다.

---

## 12. N:M 관계와 사건·업무 테이블

회원과 도서를 직접 보면 N:M 관계입니다.

```text
한 회원은 여러 도서를 대여할 수 있다.
한 도서는 시간에 따라 여러 회원에게 대여될 수 있다.
```

정규화된 관계형 데이터 모델에서는 N:M 관계를 한쪽 테이블의 외래키 한 열로 표현하지 않고, 중간 테이블이나 사건 테이블을 두 개의 1:N 관계로 구성합니다.

```text
members 1 ─── N loans N ─── 1 books
```

![N:M 관계를 연결 테이블로 풀기](../../images/chapter05/ch05_05_many_to_many_bridge_table.svg)

그림 5-4 N:M 관계를 사건 테이블로 풀기

배열이나 JSON에 여러 ID를 저장하는 방식도 기술적으로 가능하지만, 일반적인 관계형 설계에서는 외래키, 조회와 무결성 관리가 어려워 이 장의 기본 원칙으로 사용하지 않습니다.

`loans`는 두 외래키만 저장하는 단순 연결 테이블이 아닙니다.

```text
borrowed_at
 due_at
returned_at
```

이처럼 관계가 발생한 시점, 상태와 이력을 함께 저장하므로 `loans`는 **대여 사건을 기록하는 업무 테이블**입니다.

```text
단순 연결 테이블: 두 대상의 연결만 저장
사건·업무 테이블: 연결이 발생한 시점과 추가 업무 정보를 함께 저장
```

## 13. 기본키와 외래키로 관계 표현하기

각 테이블의 키를 정리하면 다음과 같습니다.

| 테이블 | 기본키 | 외래키 |
| --- | --- | --- |
| `members` | `id` | 없음 |
| `books` | `id` | 없음 |
| `loans` | `id` | `member_id`, `book_id` |

```text
members.id ← loans.member_id
books.id   ← loans.book_id
```

![기본키와 외래키로 테이블 연결하기](../../images/chapter05/ch05_03_primary_foreign_key_relationship.svg)

그림 5-5 기본키와 외래키로 테이블 연결하기

외래키의 위치는 관계 문장에서 결정됩니다.

```text
하나의 대여 기록은 정확히 한 회원에 속한다.
→ loans에 member_id가 필요하다.

하나의 대여 기록은 정확히 한 도서에 속한다.
→ loans에 book_id가 필요하다.
```

외래키는 이름을 반복 저장하는 대신 안정적인 식별자를 참조합니다.

## 14. ERD의 기본 구성 요소

ERD는 Entity Relationship Diagram의 약자로 엔터티, 속성과 관계를 그림으로 표현한 것입니다. 이 책의 실무형 ERD에는 PostgreSQL 테이블 설계와 연결하기 위해 다음 정보도 함께 표시합니다.

```text
테이블 또는 엔터티 이름
열 또는 속성 이름
기본키
외래키
테이블 사이의 관계
카디널리티
필수·선택 여부
```

도서 대여 구조를 텍스트로 먼저 작성할 수 있습니다.

```text
members
- id PK
- name
- email
- joined_at

books
- id PK
- title
- author
- published_year
- isbn

loans
- id PK
- member_id FK -> members.id
- book_id FK -> books.id
- borrowed_at
- due_at
- returned_at

관계
members 1 : 0..N loans
books   1 : 0..N loans
```

그림 도구를 사용하기 전 텍스트로 구조를 작성하면 관계와 열을 검토하기 쉽습니다.

## 16. 요구사항 추적표로 누락 확인하기

요구사항 추적표는 요구사항, 가정과 범위 제외 항목이 어느 구조에 반영되었는지 확인하는 문서입니다.

| ID | 요구사항·가정 | 상태 | 반영 구조 | 확인 방법 |
| --- | --- | --- | --- | --- |
| R-01 | 회원을 관리한다 | 확정 | `members` | 회원 행 입력·조회 |
| R-02 | 회원 이메일을 저장한다 | 확정 | `members.email` | 이메일 값 조회 |
| R-03 | 도서와 ISBN을 저장한다 | 확정 | `books`, `books.isbn` | 도서 행 입력·조회 |
| R-04 | 회원은 여러 책을 대여할 수 있다 | 확정 | `loans.member_id` | 한 회원의 여러 대여 행 |
| R-05 | 책은 시간에 따라 여러 번 대여될 수 있다 | 확정 | `loans.book_id` | 한 도서의 여러 시점 행 |
| R-06 | 대여·반납예정·실제반납일 저장 | 확정 | `loans`의 날짜 열 | 날짜 값 확인 |
| R-07 | 미반납 상태를 표현한다 | 확정 | `returned_at` NULL 허용 | NULL 행 입력 |
| Q-01 | 이메일은 중복되지 않는다 | 미확정 | 아직 `UNIQUE` 미적용 | 정책 확인 필요 |
| Q-02 | ISBN은 중복되지 않는다 | 미확정 | 아직 `UNIQUE` 미적용 | 복본 정책 확인 필요 |
| O-01 | 동일 ISBN 복본을 별도 관리한다 | 범위 제외 | 미반영 | 확장 모델에서 검토 |
| A-01 | 책 한 행을 대여 대상 한 권으로 본다 | 임시 가정 | `books` | 샘플 동시 대여 없음 확인 |

추적표를 사용하면 다음 문제를 찾을 수 있습니다.

```text
요구사항은 있는데 대응하는 열이 없음
열은 있는데 근거가 되는 요구사항이 없음
하나의 요구사항이 잘못된 테이블에 반영됨
미확정 정책을 제약조건으로 임의 확정함
AI가 요구사항에 없는 정책을 추가함
범위 제외 항목이 구현된 것처럼 설명됨
```

요구사항 ID를 사용하면 Chapter 13과 Chapter 15에서 AI 결과와 실행 증거를 같은 항목에 연결하기 쉽습니다.

## 17. ERD를 PostgreSQL 테이블로 변환하기

ERD 요소를 PostgreSQL 구조로 바꾸면 다음과 같습니다.

| ERD 요소 | PostgreSQL 구현 |
| --- | --- |
| 엔터티 | `CREATE TABLE` 후보 |
| 속성 | 열 이름과 데이터 타입 |
| 식별자 | `PRIMARY KEY` |
| 1:N 관계 | N쪽 테이블의 외래키 |
| 필수 속성 | `NOT NULL` 후보 |
| 확정된 업무상 고유값 | `UNIQUE` 후보 |
| 선택 속성 | NULL 허용 후보 |
| 부모·자식 순서 | 부모 테이블 생성 후 자식 테이블 생성 |

![ERD를 PostgreSQL 테이블로 변환하기](../../images/chapter05/ch05_07_erd_to_sql_flow.svg)

그림 5-7 ERD를 PostgreSQL 테이블로 변환하기

실행 전 Chapter 04와 같은 기준으로 현재 위치를 확인합니다.

```sql
SELECT current_database();
SELECT current_schema();
SHOW search_path;
```

이 책에서는 Chapter 04와 동일하게 `IDENTITY` 방식을 사용하며, 스키마를 명시합니다.

```sql
CREATE TABLE public.members (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    joined_at DATE NOT NULL
);

CREATE TABLE public.books (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    author VARCHAR(100) NOT NULL,
    published_year INTEGER,
    isbn VARCHAR(20) NOT NULL
);

CREATE TABLE public.loans (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    member_id INTEGER NOT NULL REFERENCES public.members(id),
    book_id INTEGER NOT NULL REFERENCES public.books(id),
    borrowed_at DATE NOT NULL,
    due_at DATE NOT NULL,
    returned_at DATE
);
```

이메일과 ISBN에는 아직 `UNIQUE`를 적용하지 않았습니다. 이는 중복을 허용한다고 확정한 것이 아니라, 고유성 정책이 미확정이므로 제약조건 적용을 보류한 것입니다.

생성 순서는 다음과 같습니다.

```text
public.members 생성
→ public.books 생성
→ public.loans 생성
```

`loans`가 `members`와 `books`를 참조하므로 부모 테이블을 먼저 생성합니다.

실제 실행 파일은 다음과 같이 역할을 분리합니다.

```text
code/chapter05/library_schema.sql
code/chapter05/library_seed.sql
code/chapter05/library_validation.sql
code/chapter05/reset_library.sql
```

`library_schema.sql`은 기존 테이블을 자동으로 삭제하지 않습니다. 처음부터 다시 시작해야 할 때만 보호 구문이 있는 `reset_library.sql`을 별도로 사용합니다.

> **자동 커밋 주의**
>
> 자동 커밋 상태에서는 앞 테이블이나 일부 샘플 데이터가 반영된 뒤 뒤 문장에서 오류가 날 수 있습니다. 실행 전에 현재 위치와 기존 테이블 여부를 확인하고, 실행 후 `library_validation.sql`의 행 수와 관계 결과로 전체 상태를 검증합니다.

## 18. 작은 샘플 데이터로 구조 확인하기

모델은 실제 사례를 표현할 수 있어야 합니다. 이 장의 샘플 데이터는 관계가 분명하도록 ID를 명시적으로 사용합니다.

```text
회원 ID: 101, 102, 103
도서 ID: 201, 202, 203
대여 ID: 1001~1004
```

`GENERATED BY DEFAULT AS IDENTITY`는 명시적인 ID 입력을 허용합니다. 그러나 명시적 ID는 연결된 IDENTITY의 다음 값을 자동으로 변경하지 않습니다. 따라서 샘플 입력 뒤 다음 자동 값이 샘플 ID와 충돌하지 않도록 시작값을 조정합니다.

```sql
ALTER TABLE public.members
    ALTER COLUMN id RESTART WITH 104;

ALTER TABLE public.books
    ALTER COLUMN id RESTART WITH 204;

ALTER TABLE public.loans
    ALTER COLUMN id RESTART WITH 1005;
```

샘플 데이터는 다음과 같습니다.

```sql
INSERT INTO public.members (id, name, email, joined_at)
VALUES
    (101, '김민지', 'minji@example.com', '2026-03-01'),
    (102, '이준호', 'junho@example.com', '2026-03-05'),
    (103, '박서연', 'seoyeon@example.com', '2026-03-10');

INSERT INTO public.books (id, title, author, published_year, isbn)
VALUES
    (201, '데이터베이스 입문', '문길래', 2026, 'ISBN-001'),
    (202, 'SQL 기초', '홍길동', 2025, 'ISBN-002'),
    (203, 'ERD 설계 연습', '이몽룡', 2024, 'ISBN-003');

INSERT INTO public.loans (id, member_id, book_id, borrowed_at, due_at, returned_at)
VALUES
    (1001, 101, 201, '2026-04-01', '2026-04-15', '2026-04-02'),
    (1002, 101, 202, '2026-04-02', '2026-04-16', NULL),
    (1003, 102, 201, '2026-04-03', '2026-04-17', NULL),
    (1004, 103, 203, '2026-04-05', '2026-04-19', NULL);
```

이 데이터는 다음 관계를 확인할 수 있게 합니다.

```text
김민지 회원은 여러 대여 기록을 가진다.
데이터베이스 입문 도서는 시간에 따라 여러 대여 기록을 가진다.
도서 201의 첫 대여는 4월 2일 반납된 뒤 4월 3일 다시 시작된다.
같은 한 권이 동시에 두 미반납 대여에 속하지 않는다.
반납되지 않은 기록 3건은 returned_at이 NULL이다.
모든 대여 기록은 존재하는 회원과 도서를 참조한다.
```

설계 검증용 파일에서는 각 테이블의 행 수를 확인합니다.

```sql
SELECT COUNT(*) AS member_count FROM public.members;
SELECT COUNT(*) AS book_count FROM public.books;
SELECT COUNT(*) AS loan_count FROM public.loans;
```

관계가 실제로 연결되는지 확인하기 위한 최소 JOIN도 사용할 수 있습니다.

```sql
SELECT
    loans.id,
    members.name AS member_name,
    books.title AS book_title,
    loans.returned_at
FROM public.loans AS loans
JOIN public.members AS members
    ON loans.member_id = members.id
JOIN public.books AS books
    ON loans.book_id = books.id
ORDER BY loans.id;
```

JOIN 문법과 다양한 결합 방식은 Chapter 08에서 자세히 다룹니다. 이 장에서는 ERD의 관계가 실제 조회로 연결 가능한지만 확인합니다.

외래키 오류, 참조 무결성, 날짜 선후 관계, 고유성 제약조건과 동시 대여 차단은 Chapter 06에서 다룹니다.

## 20. AI가 만든 ERD와 가정 검토하기

![AI 생성 ERD 검토 흐름](../../images/chapter05/ch05_08_ai_erd_review_flow.svg)

그림 5-8 AI 생성 ERD 검토 흐름

AI가 만든 모델은 다음 기준으로 검토합니다.

| 검토 항목 | 확인 질문 |
| --- | --- |
| 요구사항 추적 | 각 테이블과 열의 근거가 요구사항 ID에 있는가? |
| 모델 수준 | 개념 엔터티와 실제 테이블 정의를 구분했는가? |
| 엔터티 | 독립적으로 관리할 대상이 적절히 분리되었는가? |
| 속성 | 속성이 올바른 엔터티와 테이블에 들어갔는가? |
| 기본키 | 각 행을 안정적으로 식별할 수 있는가? |
| 외래키 | 관계를 표현할 외래키가 N쪽에 있는가? |
| 관계 문장 | 양방향으로 읽었을 때 요구사항과 일치하는가? |
| 선택성 | 관계가 필수인지 선택인지 구분했는가? |
| 1:1 구현 | 필요하다면 UNIQUE 또는 공유 PK 방식이 있는가? |
| N:M 관계 | 중간 테이블 또는 사건 테이블로 풀었는가? |
| 임의 가정 | 요구사항에 없는 고유성·삭제 정책을 확정하지 않았는가? |
| 미확정 규칙 | 추가 확인이 필요한 정책을 질문으로 분리했는가? |
| 시간 변화 | 현재 상태와 반복되는 사건·이력을 구분했는가? |
| 샘플 정합성 | 범위 가정과 모순되는 샘플 상태가 없는가? |
| 구현 가능성 | PostgreSQL 테이블로 변환 가능한가? |

예를 들어 AI가 `members` 테이블에 `book_id` 하나만 추가했다면 한 회원이 여러 도서를 대여하는 요구사항과 반복 이력을 표현할 수 없습니다. `loans` 같은 사건 테이블이 필요합니다.

AI가 이메일 고유성, 최대 대여 권수나 삭제 정책을 요구사항 없이 추가했다면 해당 내용은 확정 규칙이 아니라 미확정 질문이나 명시적 가정으로 옮겨야 합니다.

## 21. 자주 하는 실수

### 실수 1. 중요한 명사를 모두 테이블로 만든다

제목, 이메일과 대여일은 독립 관리 대상이 아니라 다른 엔터티나 사건을 설명하는 속성입니다.

### 실수 2. 엔터티와 테이블을 완전히 같은 개념으로 생각한다

엔터티는 업무의 개념적 대상이고 테이블은 이를 관계형 DBMS에서 구현한 구조입니다.

### 실수 3. 동사와 수량 표현을 무시한다

“회원은 여러 책을 대여할 수 있다”에서 `여러`와 `대여한다`는 관계와 사건 테이블을 결정하는 핵심 단서입니다.

### 실수 4. 요구사항에 없는 정책을 임의로 확정한다

이메일 고유성, 최대 대여 권수와 삭제 정책이 없으면 미확정 규칙으로 분리해야 합니다.

### 실수 5. 관계를 한 방향으로만 읽는다

`회원 → 대여`뿐 아니라 `대여 → 회원`도 문장으로 확인해야 외래키 위치와 필수 관계를 정확히 정할 수 있습니다.

### 실수 6. 1:1을 외래키 하나만으로 보장할 수 있다고 생각한다

일반 외래키만 두면 같은 부모를 여러 행이 참조할 수 있습니다. 1:1에는 추가 고유성 제약이 필요합니다.

### 실수 7. N:M 관계를 한쪽 테이블의 외래키 하나나 문자열 목록으로 표현한다

여러 건의 관계와 이력을 안정적으로 저장하려면 중간 테이블 또는 사건 테이블이 필요합니다.

### 실수 8. 관계 테이블을 단순 연결로만 생각한다

`loans`에는 대여일과 반납 상태가 있으므로 독립적인 업무 의미를 가진 사건 테이블입니다.

### 실수 9. 명시적 ID를 입력하면 IDENTITY 다음 값도 자동으로 바뀐다고 생각한다

명시적 ID 입력 후 다음 자동 값을 별도로 조정하지 않으면 샘플 ID 범위와 혼재하거나 나중에 충돌할 수 있습니다.

### 실수 10. 현재 스키마와 `search_path`를 확인하지 않는다

스키마를 생략하면 다른 위치에 테이블을 만들거나 동명 객체를 사용할 수 있습니다.

### 실수 11. 위치 조회문이 DROP을 자동으로 막는다고 생각한다

조회 결과만 출력하고 이어서 `DROP TABLE`을 실행하면 잘못된 위치에서도 삭제될 수 있습니다. 초기화는 검증과 삭제를 하나의 보호 구문 안에서 수행합니다.

### 실수 12. ERD를 그린 뒤 요구사항과 다시 비교하지 않는다

ERD는 산출물일 뿐입니다. 추적표와 작은 샘플 데이터로 누락과 모순을 확인해야 합니다.

### 실수 13. AI가 만든 ERD를 그대로 확정한다

AI는 누락된 정책을 임의로 가정하거나 관계의 필수성과 샘플 상태를 잘못 표현할 수 있습니다.

## 23. 권장 해설

### 23.1 개념 확인

1. 업무 사실은 관리할 대상과 발생한 사건이고, 업무 규칙은 대상 사이의 관계·수량·필수 여부와 허용 조건입니다.
2. 미확정 정책을 임의로 구조에 반영하면 실제 업무와 다른 제약조건이나 삭제 정책이 만들어질 수 있습니다.
3. 엔터티는 업무의 개념적 대상이며, 관계형 데이터베이스로 구현할 때 주로 테이블로 변환됩니다.
4. 독립 식별자, 여러 속성, 반복 저장, 다른 대상과의 관계, 시간에 따른 사건 여부를 확인할 수 있습니다.
5. 일반적으로 N쪽 테이블에 부모의 기본키를 참조하는 외래키를 둡니다.
6. `0..N`은 연결이 없어도 되지만 `1..N`은 최소 한 개의 연결이 필요합니다.
7. 자식 외래키에 `UNIQUE`를 적용하거나 부모 PK를 자식의 PK이자 FK로 사용하는 방식이 필요합니다.
8. 사건·업무 테이블은 연결뿐 아니라 발생 시점, 수량, 가격과 상태 같은 정보를 함께 저장합니다.
9. 명시적 ID는 IDENTITY 시퀀스를 소비하지 않으므로 다음 자동 값이 샘플 ID와 충돌하지 않게 조정해야 합니다.
10. 누락된 요구사항, 근거 없는 열, 잘못된 위치, 임의 가정과 범위 제외 항목의 오해를 찾는 데 도움이 됩니다.

### 23.2 쇼핑몰 권장 모델

```text
customers
orders
products
order_items
```

관계는 다음과 같습니다.

```text
customers 1 : 0..N orders
orders    1 : 1..N order_items
products  1 : 0..N order_items
```

구조 후보는 다음과 같습니다.

```text
customers
- id
- name
- email

orders
- id
- customer_id
- ordered_at
- status

products
- id
- name
- current_price

order_items
- id 또는 (order_id, product_id)
- order_id
- product_id
- quantity
- unit_price
```

`unit_price`는 현재 상품 가격이 아니라 **주문 당시 가격**입니다. 상품 가격이 나중에 바뀌어도 과거 주문 금액을 재현해야 하기 때문입니다.

미확정 규칙에는 고객 이메일 고유성, 한 주문의 최소 상품 수, 주문상태 목록, 같은 상품의 중복 행 허용 여부와 삭제 정책 등이 포함될 수 있습니다.

### 23.3 AI 제안의 문제점

```text
고객 행에 주문과 상품 정보가 섞여 있다.
주문 엔터티가 없다.
한 고객의 여러 주문을 독립적으로 식별할 수 없다.
한 주문에 여러 상품을 표현할 수 없다.
주문일과 주문상태의 위치가 잘못되었다.
수량과 주문 당시 가격을 저장할 위치가 없다.
고객과 상품을 product_id 하나로 직접 연결해 N:M 관계와 이력을 표현하지 못한다.
```

따라서 `orders`와 `order_items` 사건·업무 테이블이 필요합니다.

## 24. 핵심 정리

| 검토 영역 | 핵심 질문 |
| --- | --- |
| 요구사항 | 무엇을 관리하며 어떤 규칙이 있는가? |
| 미확정 사항 | 추가 확인이 필요한 정책은 무엇인가? |
| 모델 수준 | 엔터티·속성과 테이블·열을 구분했는가? |
| 엔터티 | 독립적으로 식별·관리할 대상이나 사건인가? |
| 속성 | 어떤 엔터티를 설명하는 값인가? |
| 관계 문장 | 두 방향으로 읽었을 때 의미가 맞는가? |
| 카디널리티 | 하나와 여러 개 중 어떤 관계인가? |
| 선택성 | 관계가 없어도 되는가, 반드시 있어야 하는가? |
| PK·FK | 행과 관계를 안정적으로 식별하는가? |
| N:M 관계 | 사건 또는 중간 테이블로 풀었는가? |
| 추적표 | 모든 요구사항·가정·범위가 연결되었는가? |
| 구현 | 스키마·IDENTITY·생성 순서가 일관적인가? |
| 샘플 데이터 | 범위 가정과 모순되지 않는가? |
| AI 초안 | 임의 가정과 누락을 사람이 다시 확인했는가? |

핵심 내용을 문장으로 정리하면 다음과 같습니다.

```text
1. 데이터 모델링은 요구사항을 엔터티, 속성, 관계와 규칙으로 바꾸는 과정이다.
2. 개념 엔터티와 PostgreSQL 테이블은 연결되지만 같은 수준의 개념은 아니다.
3. 명사는 엔터티와 속성 후보를 찾는 출발점일 뿐이다.
4. 동사와 수량 표현에서 관계와 카디널리티를 찾는다.
5. 요구사항에 없는 고유성·삭제 정책은 임의로 확정하지 않는다.
6. 관계는 양방향 문장으로 작성한다.
7. 1:N 관계에서는 보통 N쪽에 외래키를 둔다.
8. N:M 관계는 중간 테이블이나 사건 테이블로 풀어낸다.
9. 필수·선택 관계는 NULL 허용과 외래키 설계의 근거가 된다.
10. 요구사항 추적표와 작은 데이터로 누락과 모순을 검증한다.
11. 명시적 ID를 사용하면 IDENTITY 다음 값을 조정한다.
12. AI가 만든 ERD는 가정과 근거를 검토해야 하는 초안이다.
```

이 장에서 가장 중요한 문장은 다음입니다.

```text
좋은 데이터베이스는 SQL을 작성하기 전에
요구사항의 업무 규칙과 관계를 근거와 함께 구조화하는 것에서 시작된다.
```
