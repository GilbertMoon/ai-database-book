# Chapter 15. 실전 프로젝트 2: AI 기반 데이터베이스 서비스 완성하기

지금까지 관계형 데이터베이스, SQL, ERD, 정규화, JOIN, 집계, 트랜잭션, 인덱스, 보안과 백업, NoSQL, AI 설계 검토, Vector DB와 RAG를 배웠습니다. Chapter 15는 이 내용을 하나의 작은 프로젝트로 묶어 “다른 사람이 다시 실행할 수 있는 데이터베이스 프로젝트”를 완성하는 장입니다.

이 장에서 말하는 AI 기반 프로젝트는 모든 서비스에 RAG나 생성형 AI 기능을 넣는다는 뜻이 아닙니다. 기본 경로에서는 AI를 요구사항 정리, ERD와 DDL 초안 작성, SQL 오류 분석을 돕는 개발 보조 도구로 사용합니다. 서비스 자체에 RAG, NoSQL, 웹 CRUD, 배포를 넣는 것은 요구사항이 있을 때 선택적으로 확장합니다.

## 1. 완성형 데이터베이스 프로젝트란 무엇인가

완성형 프로젝트는 기능 수가 많은 프로젝트가 아닙니다. 작은 범위라도 다음 근거가 맞물려 있으면 완성도가 높습니다.

- 해결하려는 문제와 사용자
- 필수 범위와 제외 범위
- 요구사항 ID
- ERD와 관계 설명
- 반복 실행 가능한 `schema.sql`
- 정상, 경계, 오류 상황을 담은 `seed.sql`
- 요구사항을 증명하는 `queries.sql`
- AI 제안과 사람의 수정 근거
- 최종 보고서와 재현 가능한 README

SQL 실행 성공만으로 프로젝트가 끝난 것은 아닙니다. 요구사항을 실제 데이터와 쿼리로 증명해야 합니다.

## 2. 필수 범위와 선택 확장을 구분한다

처음부터 웹, NoSQL, RAG, 배포를 모두 넣으면 핵심 DB 설계가 흐려질 수 있습니다. 필수 프로젝트와 선택 확장을 분리합니다.

그림 15-2 필수 범위와 선택 확장 결정하기

| 구분 | 기본 여부 | 예 |
|---|---|---|
| AI를 이용한 설계·SQL 검토 | 기본 | 요구사항 정리, DDL 초안, 오류 분석 |
| 웹 CRUD/API | 선택 | 데이터 입력과 조회 흐름 확인 |

## 4. 프로젝트 주제를 선택한다

이 장의 기준 예제는 **AI 튜터링 질문 관리 서비스**입니다.

주요 테이블은 다음과 같습니다.

- `students`
- `tutors`
- `questions`
- `answers`
- `learning_materials`
- `question_materials`

관계는 다음과 같습니다.

```text
students 1:N questions
questions 1:N answers
tutors 1:N answers
questions N:M learning_materials
questions 1:N question_materials N:1 learning_materials
```

독자는 이 구조를 자신의 주제에 맞게 바꿀 수 있습니다. 중요한 것은 이름을 바꾸더라도 요구사항, ERD, DDL, seed, queries가 함께 바뀌어야 한다는 점입니다.

## 5. 요구사항과 미확정 업무 규칙을 작성한다

요구사항에는 ID를 붙입니다. 나중에 SQL 검증 결과와 연결하기 위해서입니다.

| ID | 요구사항 | DB 반영 | 검증 방법 |
|---|---|---|---|
| REQ-01 | 학생은 질문을 등록할 수 있다 | `questions.student_id` FK | JOIN |
| REQ-02 | 학생 이메일은 중복될 수 없다 | `students.email` UNIQUE | 중복 INSERT |
| REQ-03 | 튜터 이메일은 중복될 수 없다 | `tutors.email` UNIQUE | 중복 INSERT |
| REQ-04 | 질문 상태는 허용 값만 사용한다 | `questions.status` CHECK | 잘못된 상태 INSERT |
| REQ-05 | 질문에는 여러 답변이 가능하다 | `questions` 1:N `answers` | 답변 집계 |
| REQ-06 | 답변은 튜터와 연결된다 | `answers.tutor_id` FK | JOIN/FK 확인 |
| REQ-07 | 질문과 학습 자료는 N:M이다 | `question_materials` | 관계 조회 |
| REQ-08 | 질문이 없는 학생도 조회할 수 있다 | LEFT JOIN | 0건 집계 |
| REQ-09 | 연결되지 않은 자료를 찾을 수 있다 | LEFT JOIN | 누락 조회 |
| REQ-10 | 실제 개인정보를 사용하지 않는다 | 가상 seed 데이터 | 샘플 검토 |

미확정 규칙은 제약 조건으로 고정하지 않습니다. 예를 들어 “같은 튜터가 한 질문에 여러 답변을 작성할 수 있는가?”가 미확정이면 `UNIQUE(question_id, tutor_id)`를 추가하지 않습니다.

## 6. ERD와 DDL이 일치하는지 확인한다

DDL은 ERD를 구현한 결과입니다. 관계 설명과 SQL이 다르면 프로젝트 신뢰도가 떨어집니다.

![요구사항부터 실행 결과까지 검증하기](../../images/chapter15/ch15_04_db_design_validation.svg)

그림 15-4 요구사항부터 실행 결과까지 검증하기

기준 DDL은 `code/chapter15/templates/schema.sql`에 있습니다. 핵심은 다음과 같습니다.

- 부모 테이블을 먼저 만들고 자식 테이블을 나중에 만듭니다.
- 삭제는 자식 테이블부터 부모 테이블 순서로 합니다.
- 요구사항이 없으므로 `ON DELETE CASCADE`를 쓰지 않습니다.
- FK는 5개입니다.
- 이메일에는 UNIQUE 제약을 둡니다.
- `questions.status`, `learning_materials.material_type`, `question_materials.display_order`에는 CHECK 제약을 둡니다.

## 7. 검증 시나리오 데이터를 설계한다

샘플 데이터는 단순히 채우는 것이 아니라 검증 목적을 가져야 합니다.

| 테이블 | 기대 행 수 |
|---|---:|
| `students` | 4 |
| `tutors` | 3 |
| `questions` | 5 |
| `answers` | 5 |
| `learning_materials` | 6 |
| `question_materials` | 7 |

경계 상황도 포함합니다.

- 질문이 없는 학생 1명
- 연결되지 않은 학습 자료 1건
- 답변이 없는 open 질문
- 한 질문에 여러 답변이 있는 사례

`seed.sql`은 고정 PK 숫자에 의존하지 않고 `RETURNING`과 자연키 역할의 이메일/제목으로 연결합니다.

## 8. 필수 SQL과 검증 쿼리로 요구사항을 증명한다

`queries.sql`은 다음을 확인합니다.

- 학생과 질문 JOIN
- 질문별 답변 수 집계
- 답변과 튜터 연결
- 질문과 학습 자료 N:M 조회
- 질문이 없는 학생 LEFT JOIN
- 연결되지 않은 학습 자료 LEFT JOIN
- 정합성 이상 0행 확인
- FK 개수 5개 확인
- 트랜잭션 ROLLBACK 예시

정상 테스트와 오류 테스트는 분리합니다. 오류 테스트는 기본 실행 흐름을 깨지 않도록 주석 상태로 두고, 필요할 때 하나씩 실행합니다.

## 9. 데이터 변경과 트랜잭션을 검토한다

트랜잭션은 여러 변경을 하나의 단위로 묶습니다. 실습에서는 답변 INSERT를 트랜잭션 안에서 실행한 뒤 `ROLLBACK`하여 원래 상태로 돌아오는지 확인합니다.

이 확인은 “SQL이 실행된다”와 “요구사항이 충족된다”가 다르다는 점을 보여 줍니다. 실행 결과가 예상값과 일치해야 검증 근거가 됩니다.

## 10. 실제 조회 패턴과 인덱스를 검토한다

모든 테이블에 인덱스를 추가하지 않습니다. 실제 조회 패턴을 근거로 후보를 검토합니다.

| 인덱스 후보 | 근거 | 상태 |
|---|---|---|
| `questions(student_id, status, created_at)` | 학생별 질문 목록 | 후보 |
| `answers(question_id)` | 질문별 답변 조회 | 후보 |
| `question_materials(material_id)` | 자료별 연결 질문 조회 | 후보 |

PostgreSQL은 PK와 UNIQUE에는 인덱스를 자동으로 만들지만, FK 컬럼 인덱스를 항상 자동으로 만들지는 않습니다. 실제 조회와 실행 계획을 보고 결정합니다.

## 11. 보안, 개인정보, 백업과 복구를 검토한다

프로젝트가 작아도 운영 안전성은 기록해야 합니다.

- 실제 개인정보를 seed에 넣지 않았는가?
- DB 비밀번호나 API 키가 문서에 포함되지 않았는가?
- 권한이 필요한 테이블과 작업을 구분했는가?
- 백업과 복구 방법을 설명했는가?
- 운영 DB에서 DROP 스크립트를 실행하지 않도록 경고했는가?

## 14. 필요한 선택 확장을 판단한다

기본 DB가 완성된 뒤에 선택 확장을 판단합니다.

| 선택 확장 | 판단 기준 |
|---|---|
| 웹 CRUD/API | 데이터 입력과 조회를 화면이나 API로 확인해야 할 때 |
| NoSQL | 캐시, 문서, 이벤트 저장 특성이 필요할 때 |
| Vector DB/RAG | 학습 자료 의미 검색과 근거 기반 답변이 필요할 때 |
| 배포 | 다른 사람이 접속해 검증해야 할 때 |

모든 프로젝트에 RAG가 필요한 것은 아닙니다. AI 기능을 넣었다는 사실보다 요구사항을 정확히 해결했는지가 더 중요합니다.
