# Chapter 15 프로젝트 실행 가이드

## AI 기반 데이터베이스 서비스 완성하기

> 이 문서는 Chapter 15의 프로젝트를 실제 파일과 실행 결과로 정리하기 위한 보조 가이드입니다. 정해진 형식을 모두 따라야 하는 것은 아니며, 프로젝트의 규모와 목적에 맞게 필요한 부분만 사용하면 됩니다.

## 1. 프로젝트의 완성 기준

프로젝트가 완성되었다고 판단하려면 다음 흐름이 서로 연결되어야 합니다.

```text
문제 정의
→ 요구사항
→ ERD
→ DDL
→ 샘플 데이터
→ 핵심 SQL
→ 실행 결과
→ 검토와 개선 기록
```

화면이나 기능 수보다 중요한 것은 다음 세 가지입니다.

```text
1. 왜 이런 데이터 구조를 선택했는지 설명할 수 있다.
2. PostgreSQL에서 같은 결과를 다시 실행할 수 있다.
3. AI가 만든 결과를 무엇을 기준으로 수정했는지 기록되어 있다.
```

## 2. 추천 프로젝트 구조

```text
project/
├── README.md
├── requirements.md
├── erd.md 또는 erd.png
├── schema.sql
├── seed.sql
├── queries.sql
├── ai_review.md
├── project_notes.md
└── screenshots/
```

| 파일 | 역할 |
| --- | --- |
| `README.md` | 프로젝트 목적, 환경, 실행 순서 |
| `requirements.md` | 사용자, 기능, 데이터, 업무 규칙과 제외 범위 |
| `erd.md` 또는 `erd.png` | 테이블, 컬럼과 관계 설명 |
| `schema.sql` | 테이블과 제약조건 생성 |
| `seed.sql` | 핵심 상황을 재현하는 샘플 데이터 |
| `queries.sql` | 조회, JOIN, 집계와 검증 SQL |
| `ai_review.md` | AI 제안, 발견한 문제와 수정 근거 |
| `project_notes.md` | 한계, 성능·보안 검토와 다음 버전 계획 |
| `screenshots/` | 필요한 경우 실행 결과를 보조하는 이미지 |

파일은 `schema.sql → seed.sql → queries.sql` 순서로 실행할 수 있게 정리합니다.

## 3. 주제 선택 기준

주제는 다음 조건을 만족하면 데이터베이스 프로젝트로 적합합니다.

```text
저장해야 할 데이터가 두 종류 이상 있다.
데이터 사이에 관계가 있다.
등록과 조회뿐 아니라 상태 변화가 있다.
중복이나 잘못된 참조를 막아야 한다.
JOIN 또는 집계로 유용한 결과를 만들 수 있다.
```

### 주제 후보

| 주제 | 핵심 테이블 예시 | 검증할 핵심 문제 |
| --- | --- | --- |
| AI 튜터링 | students, tutors, questions, answers | 질문 상태와 답변 관계 |
| 온라인 강의 | students, instructors, courses, enrollments | 학생과 강의의 N:M 관계 |
| 문서 검색 | documents, chunks, questions, search_logs | 문서 출처와 검색 기록 |
| 쇼핑몰 | users, products, orders, order_items, inventory | 주문과 재고의 일관성 |
| 예약 | users, resources, reservations | 시간 중복과 취소 정책 |
| 도서 대여 | members, books, loans | 대여 상태와 반납 이력 |
| 출석 관리 | members, meetings, attendances | 회차별 중복 출석과 통계 |

## 4. 요구사항 점검

`requirements.md`에는 다음 내용을 기록합니다.

```text
프로젝트가 해결하는 문제
주요 사용자
핵심 기능
저장할 데이터
데이터 사이의 관계
허용할 상태값
중복을 막아야 할 값
삭제하거나 보존해야 할 이력
이번 버전에서 제외할 기능
```

요구사항은 다음 형식으로 쓰면 데이터 구조로 연결하기 쉽습니다.

```text
[주체]는 [대상]을 [동작]할 수 있다.
[데이터]는 [허용된 값 또는 규칙]을 따라야 한다.
[하나의 데이터]는 [다른 데이터] 여러 개와 연결될 수 있다.
```

## 5. ERD와 DDL 점검

### ERD

```text
핵심 엔터티가 모두 있는가?
각 테이블의 역할을 한 문장으로 설명할 수 있는가?
모든 핵심 테이블에 기본키가 있는가?
외래키의 방향이 요구사항과 맞는가?
N:M 관계를 중간 테이블로 처리했는가?
같은 사실을 여러 곳에 반복 저장하지 않는가?
```

### DDL

```text
데이터 타입이 실제 값의 의미와 맞는가?
필수 값에 NOT NULL이 있는가?
중복 금지 값에 UNIQUE가 있는가?
상태·금액·수량에 CHECK가 필요한가?
DEFAULT가 숨은 오류를 만들지는 않는가?
참조 데이터 삭제 시 동작을 검토했는가?
```

ERD와 `schema.sql`은 같은 테이블명, 컬럼명과 관계를 사용해야 합니다.

## 6. 샘플 데이터 점검

샘플 데이터는 다음 상황을 확인할 수 있게 구성합니다.

```text
정상적인 기본 데이터
한 부모에 여러 자식이 연결된 데이터
서로 다른 상태값을 가진 데이터
JOIN에 포함되지 않는 데이터
집계 결과에 차이를 만드는 데이터
검증 쿼리로 찾을 수 있는 경계 상황
```

실제 개인정보, 비밀번호, API 키, 운영 DB에서 가져온 값은 사용하지 않습니다.

## 7. 핵심 SQL 점검

`queries.sql`에는 프로젝트에 필요한 SQL만 선별해 넣습니다.

| SQL 유형 | 확인할 내용 |
| --- | --- |
| 기본 조회 | 주요 테이블의 데이터 확인 |
| 조건 조회 | 실제 검색·필터 기능 재현 |
| JOIN | 사용자에게 필요한 이름과 상세 정보 연결 |
| 집계 | 수량, 금액, 상태별 통계 |
| 정렬·제한 | 최근 또는 상위 데이터 조회 |
| 검증 쿼리 | 누락, 모순, 연결되지 않은 데이터 확인 |

각 SQL 아래에는 결과가 어떤 요구사항을 증명하는지 주석으로 남기는 것이 좋습니다.

## 8. 운영 관점 점검

### 트랜잭션

```text
여러 테이블 변경이 함께 성공하거나 실패해야 하는가?
중간에 오류가 나면 어떤 상태가 남는가?
```

### 인덱스

```text
가장 자주 실행하는 WHERE, JOIN, ORDER BY는 무엇인가?
인덱스 후보를 EXPLAIN으로 검토했는가?
```

### 보안

```text
애플리케이션이 과도한 권한으로 접속하지 않는가?
사용자 입력값을 파라미터로 전달하는가?
접속 정보가 코드와 저장소에 노출되지 않는가?
실제 개인정보가 샘플과 화면에 포함되지 않는가?
```

### 복구

```text
무엇을 백업해야 하는가?
백업을 별도 환경에서 복구할 수 있는가?
복구 후 어떤 SQL로 상태를 확인할 것인가?
```

## 10. 선택 확장

다음 항목은 핵심 데이터베이스가 완성된 뒤 필요에 따라 추가합니다.

| 확장 | 적합한 상황 |
| --- | --- |
| 웹 CRUD | 데이터 입력과 조회 흐름을 화면에서 확인할 때 |
| API | 다른 클라이언트나 서비스와 연결할 때 |
| NoSQL | 관계형 구조와 다른 저장 특성이 필요한 데이터가 있을 때 |
| Vector DB·RAG | 문서의 의미 검색과 근거 기반 답변이 필요할 때 |
| 테스트 자동화 | 스키마와 핵심 기능을 반복 검증할 때 |
| 클라우드 배포 | 외부에서 실행 환경을 공유해야 할 때 |

기술을 추가하기 전에는 해결하려는 문제와 운영 비용을 함께 기록합니다.
