## 4. 클라이언트 설명 확장

DBeaver를 유일한 접근 도구처럼 설명하지 않도록 수정했다.

```text
DBeaver
psql
Python 프로그램
웹 애플리케이션
기타 개발 도구
```

이들은 모두 PostgreSQL에 명령을 보내는 클라이언트가 될 수 있다. DBeaver는 DBMS나 데이터베이스 자체가 아님을 유지했다.

---

## 5. PostgreSQL 계층과 데이터베이스 객체

기존의 서버·데이터베이스·스키마·테이블 구조에 데이터베이스 객체 개념을 추가했다.

```text
PostgreSQL 서버
└── 데이터베이스
    └── 스키마
        └── 데이터베이스 객체
            ├── 테이블
            ├── 뷰
            ├── 시퀀스
            └── 함수
```

Chapter 02에서는 테이블만 자세히 다루고 뷰와 다른 객체의 생성·사용은 후속 장으로 이동했다.

---

## 6. 테이블과 조회 결과 구분 추가

초보자가 DBeaver의 결과 화면을 원본 테이블로 오해하지 않도록 다음 구분을 추가했다.

```text
테이블
→ 데이터를 저장하는 구조

조회 결과
→ SQL의 조건·연결·계산으로 만들어진 결과 집합
```

`ORDER BY`가 없으면 조회 결과의 행 순서가 보장되지 않는다는 설명도 유지했다.

## 7. 내부 식별자와 업무 식별자 강화

기존 `id`와 학번 예제를 별도 절로 분리했다.

```text
내부 식별자
→ DB 내부에서 행을 안정적으로 구분

업무 식별자
→ 학번, 회원번호, 주문번호처럼 업무에서 사용
```

자연키·대체키와 복합 키의 상세 설계는 Chapter 05~06으로 이동했다.

## 9. 기본키와 외래키 범위 유지

다음 핵심 경계는 유지했다.

```text
기본키는 자신의 테이블에서 행을 구분한다.
외래키는 다른 행을 참조한다.
외래키 값은 반복될 수 있다.
외래키는 자동으로 UNIQUE가 아니다.
외래키는 별도 NOT NULL이 없으면 NULL을 허용할 수 있다.
```

외래키 위치, 필수 관계, 복합 키와 삭제 정책은 Chapter 05~06으로 이동했다.

## 15. AI 구조 검토를 다섯 질문으로 압축

기존 8단계 검토 흐름을 다음 질문으로 단순화했다.

```text
1. 이 테이블의 한 행은 무엇을 나타내는가?
2. 각 행을 구분할 기본키가 있는가?
3. 다른 테이블을 참조해야 할 값은 무엇인가?
4. 서로 다른 성격의 데이터가 한 테이블에 섞이지 않았는가?
5. 데이터 타입과 필수 여부가 값의 의미에 맞는가?
```
