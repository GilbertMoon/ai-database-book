## 1. 데이터베이스 안에는 무엇이 있을까

온라인 강의 서비스를 생각해 보겠습니다. 기본 서비스에는 학생, 강사, 강의와 수강신청 데이터가 필요합니다. 각 수강신청에는 신청일, 상태와 신청 당시 기록 금액이 포함될 수 있습니다.

```text
학생
강사
강의
수강신청
신청 당시 기록 금액
```

실제 결제 성공·실패와 환불까지 운영하려면 별도의 결제 구조와 상태가 필요합니다. 신청 당시 기록 금액은 결제 완료 금액, 환불 반영 순금액이나 회계 매출과 같은 의미가 아닙니다.

관계형 데이터베이스는 관련 데이터를 테이블에 나누어 저장하고 키와 제약조건을 사용해 데이터의 의미와 연결을 관리합니다.

```text
테이블의 한 행은 하나의 기록을 나타낸다.
열은 기록을 구성하는 항목을 나타낸다.
기본키는 자신의 테이블에서 행을 구분한다.
외래키는 다른 행을 참조한다.
DBMS는 데이터를 저장·조회하고 설정된 규칙을 적용한다.
```

이 흐름을 이해하면 SQL을 읽을 때 명령어만 보는 것이 아니라 어떤 구조의 데이터를 대상으로 무엇을 처리하는지 함께 판단할 수 있습니다.

## 2. 데이터, 데이터베이스와 DBMS

### 2.1 데이터란 무엇인가

데이터는 관찰하거나 기록한 값이나 사실입니다.

| 데이터 예시 | 나타내는 의미 |
| --- | --- |
| 김민지 | 학생 이름 |
| 1 | 데이터베이스 내부에서 학생 행을 구분하는 `id` |
| 20260001 | 학교 업무에서 사용하는 학번 `student_number` |
| 데이터베이스 입문 | 강의 제목 |
| 2026-03-02 | 수강신청일 |
| 50000 | 신청 당시 기록 금액 |
| 신청 | 수강신청 상태 |

`id`와 학번은 모두 학생을 식별하는 데 사용할 수 있지만 역할이 다릅니다.

```text
id = 1
→ 데이터베이스 내부에서 학생 행을 안정적으로 구분하는 식별자

student_number = 20260001
→ 학교 업무에서 부여한 업무 식별자
```

학번은 정책에 따라 형식이나 재발급 규칙이 바뀔 수 있습니다. 이 책에서는 데이터베이스 내부 식별자인 `id`와 업무 식별자인 `student_number`를 구분합니다.

여러 값이 연결되면 하나의 업무 사실을 표현합니다.

```text
학번 20260001인 김민지 학생이
2026년 3월 2일에
데이터베이스 입문 강의를 신청했고
신청 상태는 신청이다.
```

### 2.2 데이터베이스란 무엇인가

데이터베이스(Database)는 관련 데이터를 일정한 구조로 저장하고 관리하는 논리적 공간입니다.

이 책에서는 Chapter 03에서 `ai_database_book` 데이터베이스를 만듭니다. Chapter 04에서는 `public.students` 테이블을 생성하고, Chapter 07에서는 `course_project` 스키마에 학생·강사·강의·수강신청 테이블을 구성합니다.

### 2.3 DBMS란 무엇인가

DBMS(Database Management System)는 데이터베이스를 생성하고 관리하며 사용할 수 있게 해 주는 소프트웨어입니다.

| 역할 | 설명 |
| --- | --- |
| 저장 | 데이터를 일정한 구조로 보관 |
| 조회 | 조건에 맞는 데이터를 검색 |
| 규칙 적용 | 제약조건에 따라 잘못된 값과 참조를 제한 |
| 동시 처리 | 여러 사용자의 작업을 트랜잭션과 동시성 제어로 조정 |
| 보호 | 사용자와 역할별 접근 권한 관리 |
| 복구 지원 | 백업과 장애 복구에 필요한 기능 제공 |

대표적인 관계형 DBMS에는 PostgreSQL, MySQL, MariaDB, Oracle Database, SQL Server와 SQLite가 있습니다. 이 책에서는 PostgreSQL을 기본 환경으로 사용합니다.

SQLite도 관계형 DBMS이지만 PostgreSQL과 운영 방식이 다릅니다. PostgreSQL은 일반적으로 별도의 서버 프로세스에 접속해 사용하고, SQLite는 애플리케이션이 데이터베이스 파일을 직접 사용하는 임베디드 방식으로 많이 사용합니다.

### 2.4 세 용어의 차이

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 데이터 | 기록된 개별 값이나 사실 | 학생 이름, 학번, 신청일 |
| 데이터베이스 | 관련 데이터가 저장되는 논리적 공간 | `ai_database_book` |
| DBMS | 데이터베이스를 관리하고 SQL을 실행하는 소프트웨어 | PostgreSQL |

일상에서는 데이터베이스와 DBMS를 모두 ‘DB’라고 부르기도 합니다. 그러나 설치, 연결과 오류를 이해하려면 두 개념을 구분해야 합니다.

## 3. 클라이언트와 DBMS는 어떻게 연결되는가

DBeaver를 설치하면 데이터베이스가 설치되는 것으로 오해하기 쉽습니다. DBeaver와 PostgreSQL은 역할이 다릅니다.

| 구성 요소 | 역할 |
| --- | --- |
| 사용자 | 질문과 SQL을 작성하고 결과를 판단 |
| DBeaver | PostgreSQL에 접속해 SQL을 보내고 결과를 보여 주는 클라이언트 |
| PostgreSQL | 데이터를 저장하고 SQL을 실행하는 DBMS |
| SQL | 클라이언트가 DBMS에 전달하는 명령 언어 |

```text
사용자가 DBeaver에서 SQL 작성
→ DBeaver가 SQL을 PostgreSQL에 전달
→ PostgreSQL이 SQL 실행
→ PostgreSQL이 결과 또는 오류 반환
→ DBeaver가 결과를 화면에 표시
```

DBeaver를 종료해도 PostgreSQL 서버와 데이터 저장소가 정상이라면 데이터는 유지됩니다. 반대로 DBeaver가 실행 중이어도 PostgreSQL 서버가 중지되어 있거나 연결 정보가 잘못되면 접속할 수 없습니다.

이 장의 클라이언트–서버 구조는 PostgreSQL을 기준으로 설명합니다. SQLite처럼 별도의 서버 없이 사용하는 DBMS는 연결 방식이 다릅니다.

## 4. PostgreSQL의 기본 구조

PostgreSQL에서 데이터를 탐색할 때는 다음 계층을 이해해야 합니다.

```text
PostgreSQL 서버
└── 데이터베이스
    └── 스키마
        └── 테이블
            ├── 행
            └── 열
```

이 책에서 구조가 만들어지는 순서는 다음과 같습니다.

```text
PostgreSQL 서버
└── ai_database_book                 Chapter 03
    ├── public
    │   └── students                 Chapter 04
    └── course_project               Chapter 07
        ├── students
        ├── instructors
        ├── courses
        └── enrollments
```

Chapter 02에서 사용하는 학생·강의·수강신청 표는 개념을 설명하기 위한 축약 예제입니다. 실제 객체는 각 장의 실습 순서에 따라 단계적으로 생성합니다.

### 4.1 서버

PostgreSQL DBMS가 실행되는 환경입니다. 한 서버에서 여러 데이터베이스를 관리할 수 있습니다.

### 4.2 데이터베이스

업무나 프로젝트별 데이터를 분리하는 논리적 공간입니다. 한 PostgreSQL 서버에 `ai_database_book`과 `shop_db`를 서로 다른 데이터베이스로 구성할 수 있습니다.

### 4.3 스키마

스키마(Schema)는 데이터베이스 안에서 테이블, 뷰와 같은 객체를 이름으로 구분해 관리하는 이름 공간입니다.

PostgreSQL은 스키마 이름을 생략한 객체를 `search_path`에 정의된 순서대로 찾습니다. 현재 스키마가 `public`이고 앞선 검색 경로에 같은 이름의 객체가 없다면 다음 두 이름은 같은 테이블을 가리킬 수 있습니다.

```text
students
public.students
```

현재 데이터베이스, 스키마와 검색 경로는 다음 SQL로 확인합니다.

```sql
SELECT current_database();
SELECT current_schema();
SHOW search_path;
```

스키마 이름을 명시한 `public.students`는 대상을 분명하게 지정합니다. `students`가 실제로 어느 테이블을 가리키는지는 현재 `search_path`와 같은 이름의 객체 존재 여부에 따라 달라질 수 있습니다.

### 4.4 테이블

테이블은 같은 성격의 데이터를 행과 열로 정리한 구조입니다. DBeaver에서는 일반적으로 다음 순서로 찾습니다.

```text
Databases
→ ai_database_book
→ Schemas
→ public
→ Tables
```

DBeaver 버전과 연결 설정에 따라 일부 중간 항목의 표시 방식은 달라질 수 있습니다.

## 5. 테이블, 행, 열과 셀

학생 정보를 저장하는 `students` 테이블을 살펴보겠습니다.

| id | name | email | major |
| ---: | --- | --- | --- |
| 1 | 김민지 | minji@example.com | 컴퓨터공학 |
| 2 | 이준호 | junho@example.com | 데이터사이언스 |
| 3 | 박서연 | seoyeon@example.com | 경영학 |

![테이블, 행, 열과 셀의 구조](../../images/chapter02/ch02_02_table_row_column.svg)

그림 2-1 테이블, 행, 열과 셀의 구조

### 5.1 테이블과 한 행의 의미

표 전체가 하나의 테이블입니다. `students` 테이블의 한 행은 학생 한 명을 나타냅니다.

```text
students 한 행 = 학생 한 명
```

한 행이 무엇을 의미하는지 명확하게 정하는 것이 좋은 데이터 구조의 출발점입니다.

### 5.2 행

행(Row)은 하나의 기록입니다. 행은 레코드(Record) 또는 튜플(Tuple)이라고도 부르지만 이 책에서는 주로 `행`이라는 표현을 사용합니다.

표에 표시된 첫째·둘째·셋째 행의 순서는 설명을 위한 예시입니다. 관계형 데이터베이스의 조회 결과는 `ORDER BY`로 정렬 기준을 지정하지 않으면 순서가 보장되지 않습니다. 화면에 보이는 위치나 `id` 값만으로 항상 같은 표시 순서를 기대해서는 안 됩니다.

### 5.3 열

열(Column)은 기록을 구성하는 데이터 항목입니다.

```text
id
name
email
major
```

모든 행은 같은 열 구조를 사용하지만 각 행에 저장된 값은 다릅니다.

### 5.4 셀

셀(Cell)은 표를 이해하기 위한 편의적 표현으로 특정 행과 열이 만나는 하나의 값을 뜻합니다. 예제 표에서 `id = 1`인 행의 `major` 값은 `컴퓨터공학`입니다.

SQL에서는 화면상의 ‘첫 번째 셀’ 위치로 값을 찾지 않습니다. 행을 찾는 조건과 열 이름을 사용해 조회하거나 변경합니다.

### 5.5 데이터 타입

각 열은 저장할 값의 종류를 나타내는 데이터 타입을 가집니다.

| 데이터 종류 | 예시 |
| --- | --- |
| 정수 | 내부 `id`, 수량 |
| 문자열 | 이름, 이메일, 상태, 학번 |
| 날짜·시간 | 가입일, 신청일 |
| 불리언 | 활성 여부, 완료 여부 |

학번은 숫자로만 보이더라도 계산을 위한 값이 아니며 앞자리 0이 필요할 수도 있으므로 문자열로 저장하는 경우가 많습니다. 데이터 타입은 값의 모양뿐 아니라 업무에서 어떻게 사용하는지도 고려해 선택합니다.

PostgreSQL의 구체적인 데이터 타입과 테이블 생성 문법은 Chapter 04에서 다룹니다.

## 6. 관계 모델과 업무 관계

‘관계형 데이터베이스’의 관계와 ‘학생이 강의를 신청한다’의 관계는 비슷하게 들리지만 구분해서 이해하는 것이 좋습니다.

| 용어 | 의미 |
| --- | --- |
| 릴레이션(Relation) | 관계 모델에서 행과 열로 구성된 테이블에 가까운 구조 |
| 업무 관계(Relationship) | 학생·강의·주문처럼 업무 대상이 서로 연결되는 규칙 |
| 카디널리티(Cardinality) | 1:1, 1:N, N:M처럼 최대 연결 개수를 표현하는 방식 |

관계형 데이터베이스가 단순히 테이블끼리 연결할 수 있어서 ‘관계형’이라고 불리는 것은 아닙니다. 관계 모델을 바탕으로 데이터를 행과 열의 구조로 다루며, 실무에서는 기본키와 외래키로 업무 관계도 함께 표현합니다.

온라인 강의 서비스는 다음처럼 나눌 수 있습니다.

| 테이블 | 한 행이 나타내는 것 |
| --- | --- |
| `students` | 학생 한 명 |
| `courses` | 강의 한 개 |
| `enrollments` | 학생 한 명의 강의 신청 한 건 |

```text
students ← enrollments → courses
```

```text
enrollments.student_id → students.id
enrollments.course_id  → courses.id
```

업무 관계의 카디널리티는 다음처럼 표현합니다.

| 관계 유형 | 간단한 의미 | 예시 |
| --- | --- | --- |
| 1:1 | 한 행이 상대편의 최대 한 행과 연결 | 사용자와 하나의 상세 프로필 |
| 1:N | 한 행이 상대편의 여러 행과 연결 | 학생과 질문 |
| N:M | 양쪽의 여러 행이 서로 연결 | 학생과 강의 |

![1:1, 1:N, N:M 관계 유형](../../images/chapter02/ch02_05_relationship_types.svg)

그림 2-2 업무 관계의 카디널리티 미리보기

`1`과 `N`은 주로 연결 가능한 최대 개수를 나타냅니다. 실제 업무에서는 0개를 허용하는 선택 관계인지, 하나 이상이 필요한 필수 관계인지도 결정해야 합니다. 가입 직후 학생의 질문은 0개일 수 있습니다.

N:M 관계는 일반적으로 `enrollments` 같은 연결 테이블을 두어 두 개의 1:N 관계로 구현합니다.

```text
students 1 ── N enrollments N ── 1 courses
```

외래키 위치, 선택·필수 관계와 연결 테이블 설계는 Chapter 05에서 자세히 다룹니다.

## 7. 기본키와 외래키 미리보기

### 7.1 기본키

기본키(Primary Key, PK)는 한 테이블 안에서 각 행을 고유하게 구분하는 하나 이상의 열입니다. 초반 실습에서는 이해하기 쉬운 단일 `id` 열을 기본키로 사용합니다.

| id | name | email |
| ---: | --- | --- |
| 1 | 김민지 | minji@example.com |
| 2 | 김민지 | minji2@example.com |

두 학생의 이름은 같지만 `id`가 다르므로 서로 다른 행으로 구분할 수 있습니다.

![기본키가 행을 구분하는 방식](../../images/chapter02/ch02_03_primary_key_concept.svg)

그림 2-3 기본키가 행을 구분하는 방식

```text
기본키 값 또는 값의 조합은 중복되지 않는다.
기본키를 구성하는 열은 NULL일 수 없다.
각 행을 안정적으로 구분한다.
가능하면 자주 바뀌지 않는 값을 사용한다.
```

여러 열을 묶어 행을 구분하는 복합 기본키는 Chapter 06에서 다룹니다.

### 7.2 외래키

외래키(Foreign Key, FK)는 다른 행을 참조하는 하나 이상의 열입니다. 일반적으로 다른 테이블의 기본키나 고유성이 보장된 열 또는 열 조합을 참조합니다.

| id | student_id | course_id | status |
| ---: | ---: | ---: | --- |
| 1 | 1 | 10 | 신청 |
| 2 | 1 | 20 | 수강중 |
| 3 | 2 | 10 | 완료 |

`student_id`는 `students.id`를 참조하고 `course_id`는 `courses.id`를 참조합니다.

![외래키로 연결되는 학생·강의·수강신청 관계](../../images/chapter02/ch02_04_foreign_key_relationship.svg)

그림 2-4 외래키로 연결되는 학생·강의·수강신청 관계

> 기본키는 자신의 테이블에서 각 행을 고유하게 구분합니다.
>
> 외래키는 참조 대상 행이 존재하는지 확인하고 업무 관계를 표현합니다.

외래키와 관련해 다음 차이를 기억해야 합니다.

```text
외래키 값은 여러 행에서 반복될 수 있다.
외래키는 기본적으로 UNIQUE가 아니다.
외래키 열은 별도의 NOT NULL 규칙이 없으면 NULL을 허용할 수 있다.
외래키만 정의한다고 필수 관계나 1:1 관계가 자동으로 완성되지는 않는다.
```

예제에서 학생 1은 두 강의를 신청하므로 `student_id = 1`이 반복됩니다. 이는 1:N 관계에서는 정상입니다.

외래키는 같은 테이블의 다른 행을 참조할 수도 있지만 초반 실습에서는 서로 다른 테이블을 연결하는 사례를 중심으로 사용합니다. 실제 SQL 정의, 복합 키와 삭제 정책은 Chapter 05~06에서 다룹니다.

## 8. DBMS가 데이터를 지키는 방법

DBMS는 데이터를 저장하는 기능뿐 아니라 잘못된 상태를 줄이고 안전하게 운영하기 위한 기능도 제공합니다.

### 8.1 제약조건

제약조건(Constraint)은 저장할 수 있는 값과 참조에 대한 규칙입니다.

```text
학생 이름은 비어 있을 수 없다.
이메일은 중복될 수 없다.
존재하지 않는 학생의 수강신청은 저장할 수 없다.
상품 가격은 0보다 작을 수 없다.
```

대표적인 제약조건에는 `PRIMARY KEY`, `FOREIGN KEY`, `NOT NULL`, `UNIQUE`, `CHECK`가 있습니다. `DEFAULT`는 값을 생략했을 때 사용할 기본값을 정하는 설정이며, 잘못된 값을 직접 차단하는 제약조건과 역할이 다릅니다.

### 8.2 동시 처리

여러 사용자가 동시에 같은 좌석이나 재고를 변경할 때는 작업이 충돌할 수 있습니다. DBMS는 트랜잭션과 동시성 제어 기능으로 여러 작업을 조정합니다. 자세한 내용은 Chapter 09에서 다룹니다.

### 8.3 권한

모든 사용자가 모든 데이터를 읽고 수정할 수 있어서는 안 됩니다. DBMS는 사용자와 역할에 따라 조회·입력·수정 권한을 구분할 수 있습니다.

### 8.4 백업과 복구

DBMS는 백업과 복구 기능을 제공하지만 데이터가 자동으로 안전해지는 것은 아닙니다. 백업 주기, 보관 위치, 권한과 복구 절차를 구성하고 실제 복구 가능 여부를 점검해야 합니다.

권한, 보안, 백업과 복구는 Chapter 11에서 자세히 살펴봅니다.

## 9. SQL과 CRUD 미리보기

SQL(Structured Query Language)은 관계형 DBMS에 명령을 전달하는 언어입니다.

```sql
SELECT *
FROM students;
```

이 SQL은 `students` 테이블의 모든 행과 열을 조회하라는 의미입니다. 결과 순서는 `ORDER BY`가 없으면 보장되지 않습니다.

CRUD는 애플리케이션에서 반복되는 네 가지 기본 데이터 작업입니다.

| CRUD | 의미 | 대표 SQL |
| --- | --- | --- |
| Create | 새로운 데이터 행 추가 | `INSERT` |
| Read | 저장된 데이터 조회 | `SELECT` |
| Update | 기존 데이터 수정 | `UPDATE` |
| Delete | 데이터 삭제 기능 | `DELETE` 또는 상태 변경 |

CRUD의 Create는 새로운 데이터 행을 추가하는 작업이므로 일반적으로 `INSERT`에 해당합니다. SQL의 `CREATE TABLE`은 데이터 행이 아니라 테이블 구조를 만드는 DDL 명령입니다.

```text
CRUD Create → INSERT로 데이터 행 추가
CREATE TABLE → 테이블 구조 생성
```

CRUD의 Delete도 반드시 물리적인 `DELETE`만 뜻하지는 않습니다. 실제 업무에서는 거래·신청 이력을 보존하기 위해 `status = '취소'` 또는 `deleted_at`을 변경하는 방식으로 삭제 기능을 구현할 수 있습니다.

```text
물리 삭제
→ DELETE로 행 제거

상태 기반 삭제
→ 행은 남기고 상태나 삭제 시각 변경
```

테이블 생성과 데이터 입력·조회·수정·삭제 SQL은 Chapter 04에서 직접 실행합니다.

## 10. 데이터의 구조 유형과 저장 방식

데이터는 구조의 명확성에 따라 다음처럼 구분할 수 있습니다.

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| 정형 데이터 | 열과 데이터 타입이 명확한 데이터 | 학생·주문 테이블 |
| 반정형 데이터 | 고정된 표는 아니지만 키와 계층 구조가 있는 데이터 | JSON, XML, JSON 이벤트 로그 |
| 비정형 데이터 | 고정된 행과 열로 표현하기 어려운 데이터 | 문서, 이미지, 음성, 영상 |

로그라고 해서 모두 반정형 데이터인 것은 아닙니다. 정해진 열의 로그 테이블은 정형 데이터이고, JSON 로그는 반정형 데이터이며, 형식이 일정하지 않은 텍스트 로그는 비정형에 가까울 수 있습니다.

다음 두 기준을 같은 것으로 보지 않습니다.

```text
정형·반정형·비정형
→ 데이터 자체의 구조적 특성

RDBMS·문서형 DB·객체 저장소·파일
→ 데이터를 저장하고 사용하는 방식
```

PostgreSQL도 `JSONB`를 사용해 반정형 데이터를 저장할 수 있습니다. 반대로 정형 데이터가 CSV나 스프레드시트로 전달될 수도 있습니다. 데이터 구조만 보고 저장소를 자동으로 결정하지 않습니다. 조회 패턴과 저장소 선택은 Chapter 12에서 다룹니다.

## 11. 기준 데이터, 결정적 파생 데이터와 AI 생성 결과

Chapter 01에서 구분한 세 범주를 데이터 구조 관점에서 다시 살펴보겠습니다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 기준 데이터<br>(Source of Truth) | 업무에서 직접 발생하고 판단의 기준이 되는 데이터 | 학생 가입, 신청, 결제 원장, 출석 기록 |
| 결정적 파생 데이터<br>(Derived Data) | 정해진 계산식으로 기준 데이터를 가공한 결과 | 학생별 질문 수, 월별 집계, 대시보드 지표 |
| AI 생성 결과 | 모델·입력·지시문과 실행 조건으로 생성한 결과 | 요약, 분류, 추천, 생성 답변 |

결정적 파생 데이터는 같은 기준 데이터, 계산식과 기준 시점이 있으면 다시 만들 수 있는 경우가 많습니다. 기준 데이터가 변경되면 파생 결과의 최신성을 확인해야 합니다.

```text
기준 데이터 변경
→ 파생 결과 최신성 확인
→ 필요한 집계·캐시 재생성
```

AI 생성 결과는 모델, 입력 데이터 기준 시점, 프롬프트 템플릿, 생성 조건과 외부 도구 결과가 달라지면 바뀔 수 있습니다. 완전히 같은 문장이 다시 생성된다고 보장할 수 없으며, 승인된 결과가 업무 기록이 되었다면 별도로 보존해야 합니다.

파생 결과를 다루는 방법도 구분해야 합니다.

```text
실행할 때 계산
→ SELECT
→ 일반 VIEW: 조회 정의를 저장하고 호출할 때 원본 조회

결과를 별도로 저장
→ 집계 테이블
→ Materialized View
→ 캐시
```

일반 VIEW는 조회 결과 자체를 저장하지 않습니다. 결과를 별도로 보관하는 객체와 혼동하지 않아야 합니다. VIEW와 집계는 Chapter 08과 Chapter 14에서 다시 다룹니다.

## 12. 하나의 사례로 구조 읽기

앞의 개념을 학생·강의·수강신청 축약 사례에 연결해 보겠습니다.

### students

| id | name |
| ---: | --- |
| 1 | 김민지 |
| 2 | 이준호 |

### courses

| id | title |
| ---: | --- |
| 10 | 데이터베이스 입문 |
| 20 | 파이썬 기초 |

### enrollments

| id | student_id | course_id | status | recorded_amount |
| ---: | ---: | ---: | --- | ---: |
| 1 | 1 | 10 | 신청 | 50000 |
| 2 | 1 | 20 | 수강중 | 40000 |
| 3 | 2 | 10 | 완료 | 50000 |

`enrollments`의 한 행은 학생 한 명이 강의 한 개를 신청한 한 건을 나타냅니다. `recorded_amount`는 신청 당시 기록한 금액이며 실제 결제 완료나 매출을 자동으로 의미하지 않습니다.

| 개념 | 사례에서의 의미 |
| --- | --- |
| DBMS | PostgreSQL |
| 데이터베이스 | `ai_database_book` |
| 스키마 | 개념 예제에서는 생략, 실제 프로젝트는 `course_project` |
| 테이블 | `students`, `courses`, `enrollments` |
| 행 | 학생 한 명 또는 수강신청 한 건 |
| 열 | `id`, `name`, `student_id`, `course_id`, `status` |
| 기본키 | 각 테이블의 `id` |
| 외래키 | `enrollments.student_id`, `enrollments.course_id` |
| 1:N 업무 관계 | 학생 한 명과 여러 신청, 강의 한 개와 여러 신청 |
| N:M 업무 관계 | 연결 테이블을 통해 표현된 학생과 강의 |

```text
students.id ← enrollments.student_id
enrollments.course_id → courses.id
```

지금 단계에서 중요한 것은 전체 설계를 직접 만드는 것이 아니라 주어진 구조를 정확한 용어로 읽는 것입니다.

## 13. AI가 만든 구조를 기본 용어로 검토하기

AI가 다음 테이블을 제안했다고 가정하겠습니다.

```sql
CREATE TABLE student_courses (
    student_name VARCHAR(50),
    student_email VARCHAR(100),
    course_title VARCHAR(100),
    instructor_name VARCHAR(50)
);
```

문법적으로 실행될 수 있지만 기본 구조를 확인하면 여러 질문이 생깁니다.

```text
한 행은 학생을 나타내는가, 수강신청을 나타내는가?
각 행을 구분할 기본키가 있는가?
학생·강의·강사 정보가 한 테이블에 섞이지 않았는가?
같은 학생 이름과 강의 제목이 반복되지 않는가?
다른 테이블을 참조해야 할 정보가 문자열로 반복되지 않는가?
각 열의 데이터 타입이 값의 의미와 맞는가?
필수값과 선택값을 구분할 수 있는가?
```

검토 순서는 다음과 같습니다.

```text
1. 한 행이 무엇을 나타내는지 확인한다.
2. 테이블과 열 이름이 의미를 정확히 표현하는지 확인한다.
3. 각 행을 구분할 기본키가 있는지 확인한다.
4. 다른 테이블을 참조해야 할 값이 있는지 확인한다.
5. 서로 다른 종류의 데이터가 한 테이블에 섞였는지 확인한다.
6. 데이터 타입이 값의 의미와 맞는지 확인한다.
7. 필수값과 선택값을 구분했는지 확인한다.
8. 상세 설계가 필요한 문제는 후속 장의 기준으로 다시 검토한다.
```

그림 2-5 AI 생성 테이블 구조 검토 흐름

## 14. 자주 하는 오해

### 오해 1. DBeaver가 데이터베이스이다

DBeaver는 PostgreSQL 같은 DBMS에 접속하는 클라이언트 도구입니다. 데이터를 저장하고 SQL을 실행하는 시스템은 PostgreSQL입니다.

### 오해 2. DBMS와 데이터베이스는 같은 것이다

PostgreSQL은 DBMS이고 그 안에 만든 `ai_database_book`은 데이터베이스입니다.

### 오해 3. 스키마와 데이터베이스는 같은 것이다

PostgreSQL에서 스키마는 데이터베이스 안에 있으며 테이블과 뷰 같은 객체를 이름으로 구분합니다.

### 오해 4. 테이블의 행은 항상 같은 순서로 보인다

`ORDER BY`가 없으면 조회 결과의 행 순서는 보장되지 않습니다.

### 오해 5. 외래키는 중복될 수 없고 항상 값이 있어야 한다

외래키 값은 1:N 관계에서 반복될 수 있으며, 별도의 `NOT NULL`과 `UNIQUE` 규칙이 있는지에 따라 NULL과 중복 허용 여부가 달라집니다.

### 오해 6. CRUD의 Delete는 항상 SQL DELETE이다

업무 이력을 보존해야 하면 상태나 삭제 시각을 변경하는 방식으로 삭제 기능을 구현할 수 있습니다.

### 오해 7. 일반 VIEW는 조회 결과를 저장한다

일반 VIEW는 조회 정의를 저장하고 호출할 때 원본 데이터를 조회합니다. 결과를 저장하는 Materialized View나 집계 테이블과 구분해야 합니다.

### 오해 8. SQL이 실행되면 데이터 구조도 올바르다

DBMS는 문법적으로 유효한 SQL을 실행할 수 있지만 한 행의 의미와 업무 규칙까지 자동으로 판단하지는 않습니다.

### 권장 해설

- 데이터는 기록된 값이나 사실입니다.
- 데이터베이스는 관련 데이터가 저장되는 논리적 공간입니다.
- DBMS는 데이터베이스를 관리하고 SQL을 실행하는 소프트웨어입니다.
- 내부 `id`는 행을 안정적으로 구분하는 값이고 학번은 업무 식별자입니다.
- 기본키는 자신의 테이블에서 행을 고유하게 구분합니다.
- 외래키는 참조 대상의 존재를 확인하며 값이 반복될 수 있습니다.
- 일반 VIEW는 조회 정의를 저장하고, Materialized View·집계 테이블·캐시는 결과를 별도로 보관할 수 있습니다.
- 신청 당시 기록 금액은 결제 완료 금액이나 회계 매출과 같은 의미가 아닙니다.

## 16. 핵심 정리

| 용어 | 한 줄 설명 | 예시 |
| --- | --- | --- |
| 데이터 | 기록된 값이나 사실 | 학생 이름, 신청일 |
| DBMS | 데이터베이스를 관리하고 SQL을 실행하는 소프트웨어 | PostgreSQL |
| 데이터베이스 | 관련 데이터가 저장되는 논리적 공간 | `ai_database_book` |
| 클라이언트 | DBMS에 명령을 보내고 결과를 보여 주는 도구 | DBeaver |
| 스키마 | 데이터베이스 안의 객체를 구분하는 이름 공간 | `public`, `course_project` |
| 테이블 | 같은 성격의 데이터를 행과 열로 정리한 구조 | `students` |
| 행 | 하나의 데이터 기록 | 학생 한 명 |
| 열 | 기록을 구성하는 데이터 항목 | `id`, `name` |
| 기본키 | 자신의 테이블에서 행을 고유하게 구분하는 열 조합 | `students.id` |
| 외래키 | 다른 행을 참조하는 열 조합 | `enrollments.student_id` |
| 업무 관계 | 업무 대상 사이의 연결 규칙 | 학생과 질문 |
| 카디널리티 | 연결 가능한 최대 개수 | 1:1, 1:N, N:M |
| SQL | 관계형 DBMS에 명령을 전달하는 언어 | `SELECT` |
| CRUD | 데이터 행의 생성·조회·수정·삭제 기능 | `INSERT`, `SELECT`, `UPDATE`, `DELETE` |
| 제약조건 | 잘못된 값과 참조를 제한하는 규칙 | `NOT NULL`, `FOREIGN KEY` |
| 기준 데이터 | 업무 판단의 기준이 되는 데이터 | 신청, 결제 원장 |
| 결정적 파생 데이터 | 정해진 계산식으로 만든 결과 | 월별 집계 |
| AI 생성 결과 | 모델과 실행 조건으로 생성한 결과 | 요약, 추천 |

이번 장에서 기억해야 할 흐름은 다음과 같습니다.

```text
DBeaver에서 SQL 작성
→ PostgreSQL이 SQL 실행
→ 데이터베이스의 스키마와 테이블에 접근
→ 조건과 열 이름으로 행의 값을 조회·변경
→ 키와 제약조건으로 구조와 정확성을 관리
→ 기준 데이터와 파생·AI 결과를 구분
```

```text
데이터베이스를 이해한다는 것은
DBMS, 데이터베이스, 스키마, 테이블과 키가
어떤 역할로 연결되는지 설명할 수 있다는 뜻이다.
```
