## 2. 프로젝트 시나리오

온라인 강의 서비스에는 학생, 강사, 강의, 수강신청 정보가 필요합니다.

1. 학생은 이름, 이메일, 가입일을 가진다.
2. 강사는 이름, 이메일, 전문 분야를 가진다.
3. 강의는 제목, 설명, 레벨, 수강료, 개설일을 가진다.
4. 하나의 강의에는 한 명의 강사가 배정된다.
5. 한 명의 강사는 여러 강의를 개설할 수 있다.
6. 학생은 여러 강의를 수강신청할 수 있다.
7. 하나의 강의에는 여러 학생이 수강신청할 수 있다.
8. 수강신청에는 신청일, 수강 상태, 결제 금액을 저장한다.
9. 수강 상태는 신청, 수강중, 완료, 취소 중 하나로 관리한다.
10. 학생 이메일과 강사 이메일은 각각 중복될 수 없다.

### 먼저 정할 범위

| 질문 | 나의 결정 | 이유 |
| --- | --- | --- |
| 결제를 별도 테이블로 분리할 것인가? |  |  |
| 학생과 강사를 하나의 users 테이블로 합칠 것인가? |  |  |
| 같은 학생의 같은 강의 재신청을 허용할 것인가? |  |  |
| 취소된 수강신청을 삭제할 것인가, 상태로 남길 것인가? |  |  |
| 수강 상태는 CHECK, ENUM, 별도 코드 테이블 중 무엇으로 관리할 것인가? |  |  |

초기 버전에서는 `students`, `instructors`, `courses`, `enrollments` 네 테이블로 시작합니다. 더 복잡한 구조를 선택한다면 그 이유를 함께 기록합니다.

## 6. 관계 분석

| 관계 | 유형 | 설명 |
| --- | --- | --- |
| instructors - courses | 1:N | 한 강사는 여러 강의를 개설할 수 있다. |
| students - enrollments | 1:N | 한 학생은 여러 수강신청을 남길 수 있다. |
| courses - enrollments | 1:N | 한 강의에는 여러 수강신청이 연결될 수 있다. |
| students - courses | N:M | `enrollments`로 해소한다. |

### N:M 관계 설명

- `students`와 `courses`는 왜 N:M 관계인가?
- `enrollments`가 이 관계를 어떻게 두 개의 1:N 관계로 바꾸는가?
- 수강 상태와 결제 금액이 `students`나 `courses`가 아니라 `enrollments`에 있어야 하는 이유는 무엇인가?

|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |

전체 SQL 파일을 끝까지 실행하면 신규 신청 1건이 추가되어 최종 JOIN은 5건을 반환해야 합니다. 이 상태가 Chapter 08에서 JOIN과 집계 실습의 기준이 됩니다.

|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  | 취소 |  |  |
|  | 이준호 | 정규화 실습 |  | 신청 | 120000 |  |

### 결과 해석

- JOIN 결과가 요구사항을 어떤 방식으로 검증하는가?

## 11. CRUD와 안전한 데이터 변경

| 작업 | 목적 | 실행 전 SELECT | 실행 결과 |
| --- | --- | --- | --- |
| SELECT | 특정 학생의 수강 목록 조회 | 해당 없음 |  |
| INSERT | 새로운 수강신청 추가 | 참조 대상 확인 |  |
| UPDATE | 수강 상태 변경 | 변경 대상 확인 |  |
| DELETE | 실제 삭제가 필요한 경우의 선택 예시 | 같은 WHERE 조건 확인 | 기본 파일에서는 주석 상태 |

### UPDATE와 DELETE 전 확인

1. 같은 WHERE 조건으로 SELECT를 실행한다.
2. 변경 대상 행 수와 내용을 확인한다.
3. UPDATE를 실행한다.
4. 같은 조건으로 결과를 다시 확인한다.
5. DELETE는 상태 변경으로 충분하지 않을 때만 별도 정책에 따라 검토한다.

기본 흐름에서는 수강신청을 물리적으로 삭제하지 않고 `status = '취소'`로 남깁니다.

## 16. 핵심 정리

- 요구사항은 엔터티, 속성, 관계로 바뀐다.
- 엔터티는 테이블이 되고 속성은 열이 된다.
- 기본키는 행을 구분하고 외래키는 테이블을 연결한다.
- N:M 관계는 연결 테이블로 표현한다.
- 샘플 데이터와 JOIN은 설계가 실제로 동작하는지 검증한다.
- 정규화는 중복과 이상 현상을 줄이기 위한 판단 기준이다.
- AI는 초안을 만들 수 있지만 최종 구조는 실행 결과와 사람이 확인한 근거로 결정한다.
