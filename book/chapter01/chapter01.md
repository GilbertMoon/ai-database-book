# Chapter 01. AI 시대에 데이터베이스를 왜 배우는가

> 상태: 원고 1차 확장 완료

---

## 이 장에서 배울 내용

이 장에서는 데이터베이스를 왜 배우는지, 그리고 ChatGPT와 Codex 같은 AI 도구가 등장한 이후 데이터베이스 학습의 방향이 어떻게 달라져야 하는지 살펴봅니다.

이 장에서 다룰 내용은 다음과 같습니다.

- 데이터와 데이터베이스의 차이
- 파일, 엑셀, 데이터베이스의 차이
- 데이터베이스가 필요한 상황과 필요하지 않은 상황
- AI 시대에도 DBMS와 SQL을 배워야 하는 이유
- ChatGPT와 Codex를 활용한 데이터베이스 학습 흐름
- AI가 만든 DB 설계와 SQL을 검증하는 기본 관점

이 장은 본격적인 SQL 실습에 들어가기 전에, 데이터베이스를 바라보는 기본 관점을 잡기 위한 장입니다. 아직 SQL 문법을 자세히 알 필요는 없습니다. 대신 앞으로 데이터베이스를 배울 때 계속 사용하게 될 핵심 질문을 먼저 익힙니다.

```text
이 데이터는 어디에 저장해야 하는가?
이 데이터는 어떻게 연결되는가?
이 구조는 나중에 문제가 되지 않는가?
AI가 만든 설계는 정말 맞는가?
```

---

## 1. 왜 이 내용을 먼저 배우는가

데이터베이스를 처음 배우는 학습자는 보통 SQL 문법부터 시작합니다.

```sql
SELECT * FROM students;
```

이런 쿼리를 보고 “학생 정보를 조회하는 명령어구나”라고 이해하는 것은 중요합니다. 하지만 SQL 문법만 배우면 더 중요한 질문을 놓치기 쉽습니다.

```text
students 테이블은 왜 필요한가?
students 테이블에는 어떤 컬럼이 있어야 하는가?
학생 이름을 기본키로 써도 되는가?
학생과 수강신청은 어떻게 연결해야 하는가?
AI가 만든 테이블 구조를 그대로 사용해도 되는가?
```

AI 도구가 발전하면서 SQL 작성 자체는 점점 쉬워지고 있습니다. ChatGPT에게 “학생 테이블을 만들어 줘”라고 요청하면 몇 초 만에 SQL을 만들어 줍니다. Codex에게 “학생 등록 기능을 구현해 줘”라고 요청하면 웹 코드 초안까지 만들 수 있습니다.

하지만 AI가 만들어 준 결과가 항상 좋은 설계라는 뜻은 아닙니다.

예를 들어 AI가 다음과 같은 테이블을 제안했다고 가정해 보겠습니다.

```sql
CREATE TABLE enrollments (
    id SERIAL PRIMARY KEY,
    student_name VARCHAR(50),
    course_title VARCHAR(100),
    instructor_name VARCHAR(50),
    payment_amount INT
);
```

겉으로 보면 학생, 강의, 강사, 결제 금액이 모두 들어 있으므로 괜찮아 보입니다. 그러나 데이터베이스 관점에서는 여러 문제가 있습니다.

- 학생 이름이 바뀌면 여러 행을 수정해야 할 수 있습니다.
- 강의 제목이 바뀌면 여러 행에 중복된 제목을 모두 수정해야 합니다.
- 같은 강사가 여러 강의를 담당하면 강사 이름이 반복 저장됩니다.
- 학생, 강의, 강사, 결제 정보가 하나의 테이블에 섞여 있습니다.
- 나중에 학생의 이메일이나 연락처를 관리하기 어렵습니다.

즉, AI가 SQL을 만들 수는 있지만, 그 SQL이 좋은 구조인지 판단하는 일은 여전히 사람의 역할입니다.

이 책은 바로 그 능력을 기르는 것을 목표로 합니다.

---

## 2. 데이터란 무엇인가

데이터는 의미를 가질 수 있는 기록입니다.

예를 들어 다음은 모두 데이터입니다.

| 데이터 예시 | 의미 |
| --- | --- |
| 홍길동 | 학생 이름 |
| 20260001 | 학번 |
| 데이터베이스 입문 | 강의명 |
| 2026-03-02 | 수강신청일 |
| 35000 | 결제 금액 |
| 완료 | 결제 상태 |

데이터는 그 자체로도 기록이지만, 여러 데이터가 연결되면 더 큰 의미를 가집니다.

예를 들어 “홍길동”이라는 이름만 있으면 단순한 문자열입니다. 하지만 다음과 같이 연결되면 하나의 수강 기록이 됩니다.

```text
홍길동 학생이
2026년 3월 2일에
데이터베이스 입문 강의를
수강신청했고
결제 상태는 완료이다.
```

데이터베이스는 이런 데이터를 체계적으로 저장하고, 필요할 때 정확하게 조회하고, 잘못된 데이터가 들어가지 않도록 관리하기 위해 사용합니다.

---

## 3. 데이터 저장 방식은 여러 가지다

데이터를 저장하는 방법은 데이터베이스만 있는 것이 아닙니다. 작은 데이터는 파일이나 엑셀로도 충분히 관리할 수 있습니다.

대표적인 저장 방식은 다음과 같습니다.

| 저장 방식 | 예시 | 적합한 상황 |
| --- | --- | --- |
| 텍스트 파일 | `.txt`, `.md` | 간단한 메모, 설정 기록 |
| JSON 파일 | `.json` | 작은 구조화 데이터, 설정값 |
| CSV 파일 | `.csv` | 표 형태 데이터, 엑셀 교환용 |
| 엑셀 | `.xlsx` | 소규모 명단, 수작업 정리 |
| 데이터베이스 | PostgreSQL, MySQL | 다중 사용자, 검색, 수정, 관계 관리 |

중요한 점은 “무조건 데이터베이스가 좋다”가 아니라는 것입니다. 데이터가 작고, 거의 바뀌지 않고, 한 사람이 관리한다면 파일이나 엑셀이 더 간단할 수 있습니다.

반대로 데이터가 많아지고, 여러 사용자가 동시에 접근하고, 데이터 사이의 관계가 중요해지면 데이터베이스가 필요합니다.

---

## 4. 파일로 충분한 경우

먼저 데이터베이스가 필요하지 않은 상황을 생각해 보겠습니다.

### 4.1 개인 메모

개인이 학습 내용을 정리하는 정도라면 Markdown 파일로 충분합니다.

```text
2026-03-01
오늘은 데이터베이스의 기본 개념을 학습했다.
테이블, 행, 열, 기본키라는 용어가 중요하다.
```

이런 데이터는 검색과 관계 관리가 복잡하지 않습니다. 작성자도 한 명입니다. 굳이 PostgreSQL을 설치하고 테이블을 만들 필요가 없습니다.

### 4.2 작은 설정값

프로그램의 설정값도 파일로 충분한 경우가 많습니다.

```json
{
  "theme": "dark",
  "language": "ko",
  "page_size": 20
}
```

이 정도 설정값은 JSON 파일에 저장해도 문제가 없습니다. 데이터가 많지 않고, 동시에 여러 사용자가 수정하지도 않습니다.

### 4.3 고정된 메뉴판

카페 메뉴가 10개이고 가격이 거의 바뀌지 않는다면 데이터베이스보다 JSON이나 CSV가 간단할 수 있습니다.

```csv
name,price
아메리카노,4000
카페라떼,4500
바닐라라떼,5000
```

이처럼 데이터가 작고 단순하면 데이터베이스는 오히려 과한 선택일 수 있습니다.

---

## 5. 데이터베이스가 필요한 경우

이제 데이터베이스가 필요한 상황을 살펴보겠습니다.

### 5.1 여러 사용자가 동시에 접근하는 경우

온라인 강의 서비스를 생각해 보겠습니다. 여러 학생이 동시에 강의를 신청합니다. 어떤 학생은 결제를 하고, 어떤 학생은 수강을 취소합니다. 관리자는 강의 정보를 수정하고, 강사는 수강생 목록을 확인합니다.

이 상황에서 엑셀 파일 하나를 여러 사람이 동시에 수정한다면 어떻게 될까요?

- 누가 어떤 데이터를 수정했는지 추적하기 어렵습니다.
- 동시에 수정하다가 데이터가 덮어써질 수 있습니다.
- 잘못된 값이 들어가도 막기 어렵습니다.
- 학생과 강의 사이의 관계를 안정적으로 관리하기 어렵습니다.

데이터베이스는 이런 상황에서 데이터를 안전하게 관리할 수 있도록 도와줍니다.

### 5.2 데이터 사이의 관계가 중요한 경우

온라인 강의 서비스에는 여러 데이터가 연결되어 있습니다.

```text
학생 → 수강신청 → 강의 → 강사
```

학생 한 명은 여러 강의를 신청할 수 있습니다. 강의 하나에는 여러 학생이 등록할 수 있습니다. 강사 한 명은 여러 강의를 담당할 수 있습니다.

이런 관계를 파일이나 엑셀로 관리하면 점점 복잡해집니다. 반면 관계형 데이터베이스는 테이블 간 관계를 기본 구조로 다룹니다.

### 5.3 데이터 정확성이 중요한 경우

결제 금액, 재고 수량, 출석 기록, 성적 같은 데이터는 정확성이 중요합니다.

예를 들어 수강신청 시스템에서 결제는 실패했는데 수강신청은 완료 처리되면 문제가 됩니다. 반대로 결제는 완료되었는데 수강신청 기록이 없으면 더 큰 문제가 됩니다.

이런 경우에는 여러 작업을 하나의 단위로 처리하는 트랜잭션이 필요합니다. 트랜잭션은 뒤쪽 Chapter에서 자세히 학습합니다.

### 5.4 검색과 집계가 필요한 경우

데이터가 많아지면 단순히 저장하는 것보다 찾고 분석하는 일이 중요해집니다.

예를 들어 다음 질문에 답해야 할 수 있습니다.

```text
이번 학기에 가장 많이 신청된 강의는 무엇인가?
수강신청 후 결제하지 않은 학생은 누구인가?
강사별 개설 강의 수는 몇 개인가?
최근 한 달간 신규 가입자는 몇 명인가?
```

이런 질문에 답하려면 SQL을 사용해 데이터를 조회하고 집계해야 합니다.

## 6. 파일, 엑셀, 데이터베이스 비교

다음 표는 세 가지 방식을 비교한 것입니다.

| 구분 | 파일 | 엑셀 | 데이터베이스 |
| --- | --- | --- | --- |
| 사용 난이도 | 쉬움 | 쉬움 | 처음에는 다소 어려움 |
| 데이터 구조 | 단순 | 표 형태 | 테이블과 관계 |
| 동시 사용 | 약함 | 제한적 | 강함 |
| 검색/집계 | 직접 구현 필요 | 기본 기능 제공 | SQL로 강력하게 처리 |
| 데이터 검증 | 약함 | 일부 가능 | 제약조건으로 관리 가능 |
| 대용량 처리 | 약함 | 제한적 | 상대적으로 강함 |
| 서비스 연동 | 불편 | 제한적 | 적합 |

이 표에서 알 수 있듯이 데이터베이스는 처음에는 조금 어렵지만, 데이터가 많아지고 관계가 복잡해질수록 강력해집니다.

---

## 7. 데이터베이스가 필요하지 않은데 사용하는 사례

실무나 학습 과정에서는 데이터베이스가 굳이 필요하지 않은데도 사용하는 경우가 있습니다.

| 사례 | DB를 사용하는 경우 | 더 단순한 대안 |
| --- | --- | --- |
| 개인 메모 앱 | 메모 몇 개를 DB에 저장 | Markdown, txt |
| 작은 설정값 | 다크모드 여부를 DB에 저장 | JSON, `.env` |
| 고정 공지사항 | 거의 안 바뀌는 문구를 DB에서 조회 | HTML, Markdown |
| 학생 10명 명단 | 실습용 명단을 DB에 저장 | CSV, 엑셀 |
| 메뉴 5개 카페 사이트 | 메뉴를 DB에 저장 | JSON, CSV |

이런 예시는 데이터베이스가 나쁘다는 뜻이 아닙니다. 중요한 것은 상황에 맞는 도구를 선택하는 것입니다.

초급 학습자는 “데이터를 저장한다”는 말만 들으면 바로 데이터베이스를 떠올리기 쉽습니다. 하지만 실제 설계에서는 다음 질문을 먼저 해야 합니다.

```text
데이터가 자주 바뀌는가?
여러 사용자가 동시에 접근하는가?
데이터 간 관계가 중요한가?
검색과 집계가 필요한가?
정확성과 복구가 중요한가?
서비스와 연결되어야 하는가?
```

이 질문에 대부분 “아니오”라면 파일이나 엑셀이 더 적절할 수 있습니다.

## 8. AI 시대에는 데이터베이스 학습이 덜 중요해졌을까

ChatGPT나 Codex를 사용하면 SQL을 빠르게 만들 수 있습니다.

예를 들어 다음처럼 요청할 수 있습니다.

```text
학생 정보를 저장하는 PostgreSQL 테이블을 만들어 주세요.
```

그러면 AI는 다음과 비슷한 SQL을 만들어 줄 수 있습니다.

```sql
CREATE TABLE students (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

겉으로 보면 좋아 보입니다. 실제로 간단한 실습에는 충분히 쓸 수 있습니다.

하지만 여기서 학습자가 해야 할 일은 “AI가 만들어 줬으니 끝”이 아닙니다. 다음 질문을 할 수 있어야 합니다.

```text
id는 왜 필요한가?
email에 UNIQUE가 필요한가?
name은 NOT NULL이어야 하는가?
created_at은 어떤 용도로 쓰는가?
학번이 있다면 id와 학번 중 무엇을 기본키로 쓸 것인가?
학생이 탈퇴하면 데이터를 삭제할 것인가, 상태값을 바꿀 것인가?
```

AI가 코드를 만들어 줄수록, 사람은 더 높은 수준의 판단을 해야 합니다.

---

## 9. AI가 잘하는 일과 사람이 해야 하는 일

AI 도구는 데이터베이스 학습에서 매우 유용합니다. 하지만 역할을 구분해야 합니다.

| 구분 | AI가 잘하는 일 | 사람이 해야 하는 일 |
| --- | --- | --- |
| 요구사항 정리 | 설명을 표로 정리 | 실제 요구사항과 맞는지 판단 |
| ERD 초안 | 테이블 후보 제안 | 관계와 정규화 검토 |
| SQL 작성 | DDL, SELECT 초안 생성 | 실행 결과와 위험성 검토 |
| 오류 해결 | 오류 메시지 원인 추정 | 실제 환경과 비교해 해결 |
| 코드 생성 | CRUD 코드 초안 작성 | 보안, 예외, 구조 검토 |
| 문서화 | 설명 초안 작성 | 부정확한 내용 수정 |

AI는 빠른 초안을 만드는 데 강합니다. 하지만 데이터베이스 설계는 업무 규칙, 데이터 관계, 장기 운영을 고려해야 합니다. 이런 판단은 사람이 해야 합니다.

## 10. 이 책에서 사용하는 AI 학습 흐름

이 책에서는 ChatGPT와 Codex를 다음처럼 활용합니다.

```text
ChatGPT: 개념 이해, 요구사항 정리, 설계 초안, 검토 질문
Codex: SQL 파일 작성, 웹 CRUD 코드 생성, 리팩토링, 테스트 보조
GitHub: 원고, 코드, 실습 자료, 프로젝트 결과 관리
PostgreSQL: 로컬 및 배포용 관계형 데이터베이스
DBeaver: 테이블과 데이터를 직접 확인하는 도구
```

전체 흐름은 다음과 같습니다.

```text
요구사항을 읽는다.
→ ChatGPT로 요구사항을 정리한다.
→ 테이블 후보를 만든다.
→ ERD를 작성한다.
→ Codex로 DDL과 SQL 초안을 만든다.
→ PostgreSQL에서 실행한다.
→ DBeaver로 결과를 확인한다.
→ 문제를 찾아 수정한다.
→ GitHub에 기록한다.
```

이 흐름에서 가장 중요한 단계는 “문제를 찾아 수정한다”입니다.

AI가 만든 결과를 실행하는 것만으로는 충분하지 않습니다. 결과가 맞는지 확인하고, 왜 그렇게 설계했는지 설명할 수 있어야 합니다.

## 11. 데이터베이스 학습의 방향이 달라지는 이유

전통적인 데이터베이스 입문 수업은 보통 다음 순서로 진행됩니다.

```text
DBMS 개념
→ SQL 문법
→ ERD
→ 정규화
→ 트랜잭션
→ 인덱스
```

이 순서 자체는 여전히 중요합니다. 이 책도 이 내용을 다룹니다. 하지만 AI 시대에는 하나가 더 필요합니다.

```text
AI 생성 결과 검증
```

따라서 이 책의 흐름은 다음과 같습니다.

```text
DBMS 개념
→ SQL 기초
→ ERD와 정규화
→ 중간 프로젝트
→ JOIN, 트랜잭션, 인덱스, 보안
→ NoSQL
→ AI 생성 결과 검증
→ Vector DB와 RAG
→ 최종 프로젝트
```

단순히 SQL을 작성하는 능력뿐 아니라, 다음 능력을 함께 기릅니다.

```text
- 좋은 설계와 나쁜 설계를 구분하는 능력
- AI가 만든 테이블 구조를 검토하는 능력
- 위험한 SQL을 찾아내는 능력
- 데이터베이스 선택 기준을 설명하는 능력
- DB 설계를 웹 기능으로 연결하는 능력
```

## 12. 작은 사례: 학생 명단 관리

학생 20명의 이름과 이메일만 관리한다고 가정해 보겠습니다.

| 학번 | 이름 | 이메일 |
| --- | --- | --- |
| 20260001 | 김민지 | minji@example.com |
| 20260002 | 이준호 | junho@example.com |
| 20260003 | 박서연 | seoyeon@example.com |

이 정도라면 엑셀이나 CSV로 충분할 수 있습니다.

하지만 다음 요구사항이 추가되면 상황이 달라집니다.

```text
- 학생은 여러 강의를 수강할 수 있다.
- 강의별 출석을 기록해야 한다.
- 과제 제출 여부를 관리해야 한다.
- 성적을 계산해야 한다.
- 학생별 수강 이력을 조회해야 한다.
- 여러 조교가 동시에 데이터를 입력한다.
```

이제는 단순 명단이 아닙니다. 학생, 강의, 출석, 과제, 성적이 서로 연결됩니다. 이때는 데이터베이스가 필요합니다.

이 사례는 앞으로 이 책에서 반복해서 사용될 기본 사고방식입니다.

```text
데이터가 단순하면 파일로 충분할 수 있다.
데이터가 연결되고 변하면 데이터베이스가 필요하다.
```

## 13. 작은 사례: 온라인 강의 서비스

온라인 강의 서비스를 생각해 보겠습니다.

처음에는 강의 목록만 보여 주는 사이트일 수 있습니다.

```text
강의명
강사명
강의 소개
가격
```

이 정도는 JSON 파일로도 만들 수 있습니다.

하지만 실제 서비스가 되면 요구사항이 늘어납니다.

```text
- 사용자가 회원가입을 한다.
- 학생이 강의를 수강신청한다.
- 결제를 처리한다.
- 강의별 수강생 목록을 확인한다.
- 강사가 공지사항을 등록한다.
- 학생이 강의평을 남긴다.
- 관리자가 매출을 집계한다.
```

이제 데이터는 단순 목록이 아니라 서비스의 핵심 자산이 됩니다. 이때 데이터베이스 설계가 중요해집니다.

잘못 설계하면 다음 문제가 생깁니다.

```text
- 같은 학생 정보가 여러 곳에 중복된다.
- 강의명이 바뀌면 여러 데이터를 수정해야 한다.
- 결제 상태와 수강 상태가 맞지 않는다.
- 수강생 수를 정확히 계산하기 어렵다.
- 삭제하면 안 되는 결제 기록이 사라진다.
```

데이터베이스를 배우는 이유는 바로 이런 문제를 예방하기 위해서입니다.

## 14. 실습 활동 1: 저장 방식 선택하기

다음 사례를 보고 어떤 저장 방식이 적합한지 판단해 보세요.

| 사례 | 추천 저장 방식 | 이유 |
| --- | --- | --- |
| 개인 학습 메모 10개 | Markdown 파일 | 단순하고 개인용 |
| 카페 메뉴 8개 | JSON 또는 CSV | 데이터가 적고 거의 고정 |
| 학생 20명 명단 | 엑셀 또는 CSV | 소규모 표 데이터 |
| 온라인 강의 수강신청 | 데이터베이스 | 학생, 강의, 수강신청 관계 필요 |
| 쇼핑몰 주문/결제/재고 | 데이터베이스 | 정합성, 트랜잭션 필요 |

이 표는 정답을 외우기 위한 것이 아닙니다. 중요한 것은 판단 기준입니다.

다음 질문으로 스스로 판단해 보세요.

```text
1. 데이터 양이 많은가?
2. 데이터가 자주 바뀌는가?
3. 여러 사용자가 동시에 접근하는가?
4. 데이터 사이에 관계가 있는가?
5. 검색과 집계가 필요한가?
6. 잘못된 데이터가 들어가면 큰 문제가 되는가?
7. 나중에 웹 서비스와 연결해야 하는가?
```

## 15. 실습 활동 2: ChatGPT에게 물어보고 검토하기

이제 ChatGPT를 활용해 저장 방식을 추천받아 보겠습니다.

다음 프롬프트를 입력해 보세요.

```text
작은 온라인 강의 서비스를 만든다고 가정하겠습니다.
처음에는 강의 목록 10개만 보여 주지만,
나중에는 회원가입, 수강신청, 결제, 강의평 기능을 추가할 수 있습니다.
파일, 엑셀, 데이터베이스 중 어떤 저장 방식을 선택해야 하는지 비교해 주세요.
초급자가 이해할 수 있도록 표로 정리해 주세요.
```

AI가 답변을 생성하면 다음 기준으로 검토합니다.

| 검토 항목 | 확인 질문 |
| --- | --- |
| 현재 규모 | 지금 당장 DB가 꼭 필요한가? |
| 확장 가능성 | 기능이 늘어나면 DB가 필요한가? |
| 데이터 관계 | 회원, 강의, 수강신청 사이 관계가 있는가? |
| 정합성 | 결제와 수강 상태가 정확히 맞아야 하는가? |
| 운영 편의성 | 관리자 페이지나 검색 기능이 필요한가? |

AI 답변을 그대로 복사하지 말고, 본인의 판단을 한 문단으로 정리해 보세요.

예시:

```text
초기에는 강의 목록만 관리하므로 JSON 파일도 가능하다.
하지만 회원가입, 수강신청, 결제, 강의평이 추가될 가능성이 높기 때문에
처음부터 PostgreSQL 같은 관계형 데이터베이스를 고려하는 것이 좋다.
다만 학습 초기에는 JSON과 DB를 비교해 보며 단계적으로 전환하는 방식도 가능하다.
```

## 16. 실습 활동 3: AI 답변의 문제 찾기

다음은 AI가 생성했다고 가정한 답변입니다.

```text
온라인 강의 서비스는 데이터가 많지 않으므로 엑셀로 관리하면 됩니다.
학생 이름, 강의명, 결제 금액을 한 시트에 저장하면 충분합니다.
나중에 기능이 늘어나도 엑셀에 열을 추가하면 됩니다.
```

이 답변은 초급자가 보기에는 그럴듯할 수 있습니다. 하지만 여러 문제가 있습니다.

검토해 봅시다.

| 문제 | 설명 |
| --- | --- |
| 확장성 부족 | 회원가입, 결제, 강의평이 추가되면 엑셀 관리가 어려워짐 |
| 관계 관리 어려움 | 학생과 강의의 N:M 관계를 안정적으로 표현하기 어려움 |
| 동시 수정 문제 | 여러 관리자가 동시에 수정하면 충돌 가능 |
| 정합성 부족 | 결제 상태와 수강신청 상태를 안전하게 연결하기 어려움 |
| 보안 문제 | 개인정보와 결제 관련 데이터를 엑셀로 관리하면 위험 |

이 활동의 목적은 AI를 믿지 말라는 것이 아닙니다. AI 답변을 더 좋은 답변으로 다듬는 능력을 기르는 것입니다.

수정된 답변은 다음처럼 작성할 수 있습니다.

```text
강의 목록만 보여 주는 초기 단계라면 JSON이나 CSV로도 충분할 수 있다.
그러나 회원, 수강신청, 결제, 강의평 기능이 추가되면 데이터 간 관계와 정합성이 중요해진다.
따라서 확장 가능성이 있는 온라인 강의 서비스라면 PostgreSQL 같은 관계형 데이터베이스를 사용하는 것이 적절하다.
```

## 18. AI 시대의 데이터베이스 학습 원칙

이 책에서 계속 사용할 학습 원칙은 다음과 같습니다.

### 원칙 1. SQL을 외우기보다 구조를 이해한다

SQL 문법은 AI가 도와줄 수 있습니다. 하지만 테이블 구조를 이해하지 못하면 좋은 SQL을 판단할 수 없습니다.

### 원칙 2. 작은 실습부터 시작한다

처음부터 복잡한 쇼핑몰이나 병원 시스템을 만들지 않습니다. 학생 테이블처럼 작은 구조에서 시작해 점차 확장합니다.

### 원칙 3. AI가 만든 결과를 검증한다

AI가 만든 SQL, ERD, 코드에는 오류가 있을 수 있습니다. 항상 다음 관점으로 검토합니다.

```text
- 요구사항과 맞는가?
- 중복이 많지 않은가?
- 기본키와 외래키가 적절한가?
- 위험한 SQL은 없는가?
- 나중에 확장 가능한가?
```

### 원칙 4. 실행 결과를 직접 확인한다

AI 설명만 읽고 끝내지 않습니다. PostgreSQL에서 직접 실행하고, DBeaver에서 결과를 확인합니다.

### 원칙 5. 설계와 구현을 연결한다

테이블 설계가 끝이 아닙니다. 최종적으로는 웹 CRUD 형태로 데이터를 입력하고 조회해 보면서 설계가 실제로 동작하는지 확인합니다.

## 19. 이 장의 핵심 판단표

데이터베이스가 필요한지 판단할 때 다음 표를 사용할 수 있습니다.

| 질문 | 예 | DB 필요 가능성 |
| --- | --- | --- |
| 데이터가 많아질 가능성이 있는가? | 회원 수 증가 | 높음 |
| 여러 사용자가 동시에 접근하는가? | 학생, 관리자, 강사 | 높음 |
| 데이터 간 관계가 있는가? | 학생-강의-수강신청 | 높음 |
| 데이터 정확성이 중요한가? | 결제, 성적, 재고 | 높음 |
| 검색과 집계가 필요한가? | 강의별 수강생 수 | 높음 |
| 데이터가 거의 고정되어 있는가? | 카페 메뉴 5개 | 낮음 |
| 개인만 사용하는가? | 개인 메모 | 낮음 |

이 표에서 높은 항목이 많을수록 데이터베이스를 사용하는 것이 적절합니다.

## 20. 자주 하는 실수

### 실수 1. 데이터를 저장하면 무조건 DB가 필요하다고 생각한다

데이터베이스는 강력하지만 모든 상황에 필요한 것은 아닙니다. 작은 설정값이나 개인 메모는 파일이 더 단순합니다.

### 실수 2. 엑셀로 충분한 상황과 DB가 필요한 상황을 구분하지 못한다

엑셀은 소규모 데이터를 사람이 직접 관리할 때 유용합니다. 하지만 여러 사용자가 동시에 접근하거나 관계가 복잡해지면 DB가 필요합니다.

### 실수 3. AI가 만든 설계를 그대로 사용한다

AI가 만든 테이블은 초안입니다. 기본키, 외래키, 정규화, 보안, 성능 관점에서 검토해야 합니다.

### 실수 4. SQL 실행만 되면 맞다고 생각한다

SQL이 실행된다고 해서 좋은 설계라는 뜻은 아닙니다. 잘못된 설계도 실행은 될 수 있습니다.

### 실수 5. 처음부터 너무 복잡한 시스템을 만들려고 한다

초급자는 작은 테이블 하나에서 시작해야 합니다. 학생 테이블, 강의 테이블, 수강신청 테이블처럼 단계적으로 확장하는 것이 좋습니다.

## 23. 정리

이번 장에서는 데이터베이스를 왜 배우는지, 그리고 AI 시대에 데이터베이스 학습 방향이 어떻게 달라져야 하는지 살펴보았습니다.

핵심 내용을 정리하면 다음과 같습니다.

```text
1. 데이터는 의미를 가진 기록이다.
2. 데이터베이스는 데이터를 체계적으로 저장하고 관리하는 공간이다.
3. DBMS는 데이터베이스를 관리하는 소프트웨어이다.
4. 파일, 엑셀, 데이터베이스는 각각 적합한 상황이 다르다.
5. 데이터가 단순하고 작으면 파일이나 엑셀로 충분할 수 있다.
6. 데이터가 많고, 관계가 있고, 여러 사용자가 접근하고, 정합성이 중요하면 데이터베이스가 필요하다.
7. AI는 SQL과 설계 초안을 빠르게 만들 수 있지만, 최종 검증은 사람이 해야 한다.
8. 이 책은 ChatGPT로 설계하고, Codex로 구현하고, PostgreSQL과 DBeaver로 검증하는 흐름을 따른다.
```

이 장에서 가장 중요한 문장은 다음입니다.

```text
AI가 데이터베이스 작업을 도와줄수록,
사람은 데이터 구조를 이해하고 검증하는 능력을 더 중요하게 가져야 한다.
```
