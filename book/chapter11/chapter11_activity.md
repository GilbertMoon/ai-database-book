# Chapter 11 독자 워크북

## 데이터베이스를 안전하게 지키고 복구하는 방법

> 이 워크북은 `security_lab`을 기준으로 최소 권한, PUBLIC·멤버십·소유권, 비밀 정보 보호, 백업·복원 검증 결과를 기록하기 위한 자료입니다. 역할 변경은 관리자 권한이 있는 테스트 환경에서, 복원 검증은 별도 DB에서 진행합니다.

---

## 1. 실습 파일과 순서

```text
01_security_lab_schema.sql
02_security_lab_seed.sql
03_role_permission_plan.sql
04_permission_checks.sql
05_permission_behavior_tests.sql
06_restore_validation.sql
BACKUP_RESTORE_RUNBOOK.md
reset_security_lab.sql
```

권장 순서:

```text
01 → 02
→ 03에서 필요한 역할·권한 문장만 검토·선택 실행
→ 04 유효 권한과 PUBLIC·ACL 확인
→ 05 허용·차단 동작 선택 실습
→ 터미널 백업·별도 DB 복원
→ 복원 DB에서 06 실행
→ 역할 재적용 후 04·05 재검증
→ RUNBOOK 기록
```

`05_restore_validation.sql`은 기존 링크 안내 파일이며 최종 복원 검증에는 `06_restore_validation.sql`을 사용합니다.

## 26. 권장 해설

### 역할과 권한

```text
인증은 접속 주체 확인, 권한은 객체 작업 허용, 소유권은 객체 관리 책임이다.
LOGIN 역할은 접속에 사용하고 NOLOGIN 역할은 권한 묶음과 소유 책임에 사용한다.
```

### 권한 경로

```text
has_*_privilege는 최종 유효 권한을 본다.
ACL·PUBLIC·직접 GRANT·멤버십·소유권은 그 권한이 생긴 경로를 설명한다.
MEMBER는 멤버십 존재, USAGE는 권한 사용 가능성을 확인한다.
```

### 시퀀스

```text
ID 생략 INSERT에는 테이블 INSERT와 시퀀스 USAGE가 필요하다.
일반 앱에 시퀀스 SELECT를 관성적으로 부여할 필요는 없다.
ROLLBACK 후에도 자동 번호는 회수되지 않을 수 있다.
```

### 백업과 복원

```text
스키마 덤프는 외부 의존성을 자동으로 모두 포함하지 않는다.
백업 계정은 대상 데이터를 읽을 권한과 RLS 영향을 확인해야 한다.
해시는 파일 변경 검증이고 별도 DB 복원은 복구 가능성 검증이다.
--no-owner --no-privileges 뒤에는 owner와 ACL을 별도로 검증한다.
```

### RPO·RTO

```text
RPO는 허용 가능한 데이터 손실 시점이고,
RTO는 서비스 재개까지 허용되는 시간이다.
```

```text
안전한 데이터베이스 운영은 ________________________________________이다.
```
