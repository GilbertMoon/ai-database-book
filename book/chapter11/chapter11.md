## 1. 왜 데이터베이스 보안과 백업을 배워야 하는가

데이터베이스에는 서비스의 핵심 데이터가 저장됩니다.

온라인 강의 수강신청 시스템을 예로 들면 다음과 같은 데이터가 들어 있습니다.

```text
- 학생 이름과 이메일
- 강사 정보
- 강의 정보
- 수강신청 상태
- 결제금액
- 수강 이력
```

이 데이터가 외부에 노출되거나, 잘못 변경되거나, 삭제되면 서비스 신뢰도가 크게 떨어집니다.

![보안과 백업이 필요한 이유](../../images/chapter11/ch11_01_security_backup_overview.svg)

그림 11-1 보안과 백업이 필요한 이유

데이터베이스 운영에서 중요한 질문은 다음과 같습니다.

```text
누가 데이터베이스에 접속할 수 있는가?
어떤 사용자가 어떤 테이블을 읽을 수 있는가?
누가 데이터를 수정할 수 있는가?
실수로 삭제되었을 때 복구할 수 있는가?
백업 파일은 안전하게 보관되고 있는가?
AI가 만든 SQL이나 설정을 그대로 적용해도 안전한가?
```

이 장의 핵심은 다음 문장으로 정리할 수 있습니다.

```text
데이터베이스 보안은 접근을 통제하는 것이고, 백업은 문제가 생겼을 때 되돌아갈 수 있는 안전망이다.
```

## 2. 데이터베이스 보안의 기본 관점

데이터베이스 보안은 단순히 비밀번호를 어렵게 만드는 것만 의미하지 않습니다.

기본 관점은 다음과 같습니다.

| 관점 | 설명 | 예시 |
| --- | --- | --- |
| 접근 통제 | 허용된 사용자만 접속하도록 제한 | 계정, 비밀번호, 접속 IP 제한 |
| 권한 통제 | 필요한 작업만 할 수 있도록 제한 | 읽기 전용 계정, 관리자 계정 분리 |
| 입력값 검증 | 사용자 입력이 SQL 구조를 바꾸지 못하게 함 | 파라미터 바인딩 사용 |
| 데이터 보호 | 개인정보와 민감 정보를 안전하게 관리 | 이메일, 결제정보 보호 |
| 백업과 복구 | 장애나 실수에 대비 | 정기 백업, 복구 테스트 |

초급 단계에서는 모든 보안 기술을 깊게 다루기보다, 위험한 습관을 피하고 기본 원칙을 지키는 것이 중요합니다.

## 3. 계정과 권한 관리

데이터베이스에는 여러 사용자가 접속할 수 있습니다. 이때 모든 사용자에게 관리자 권한을 주면 위험합니다.

![계정과 권한 구조](../../images/chapter11/ch11_02_account_permission_model.svg)

그림 11-2 계정과 권한 구조

예를 들어 다음과 같은 계정을 구분할 수 있습니다.

| 계정 유형 | 목적 | 권장 권한 |
| --- | --- | --- |
| 관리자 계정 | DB 생성, 권한 관리, 운영 관리 | 높은 권한 |
| 애플리케이션 계정 | 서비스에서 DB에 접속 | 필요한 테이블에 대한 제한된 권한 |
| 읽기 전용 계정 | 조회, 분석, 리포트 | SELECT 권한 중심 |
| 실습 계정 | 교육용 실습 | 별도 실습 DB에 제한된 권한 |

가장 중요한 원칙은 **최소 권한 원칙**입니다.

![최소 권한 원칙](../../images/chapter11/ch11_03_least_privilege_principle.svg)

그림 11-3 최소 권한 원칙

```text
최소 권한 원칙 = 사용자가 자기 역할을 수행하는 데 필요한 권한만 부여하는 것
```

예를 들어 리포트만 조회하는 사용자에게 `INSERT`, `UPDATE`, `DELETE` 권한이 필요하지 않습니다.

## 4. PostgreSQL 사용자와 권한 맛보기

PostgreSQL에서는 사용자 또는 역할을 만들고 권한을 부여할 수 있습니다.

교육용 예시는 다음과 같습니다.

```sql
CREATE ROLE readonly_user LOGIN PASSWORD 'change_this_password';
```

위 SQL은 로그인 가능한 역할을 만드는 예시입니다. 실제 환경에서는 예시 비밀번호를 그대로 사용하면 안 됩니다.

특정 데이터베이스에 접속할 수 있도록 권한을 부여할 수 있습니다.

```sql
GRANT CONNECT ON DATABASE ai_database_book TO readonly_user;
```

특정 스키마를 사용할 수 있게 할 수 있습니다.

```sql
GRANT USAGE ON SCHEMA public TO readonly_user;
```

특정 테이블을 읽을 수 있도록 할 수 있습니다.

```sql
GRANT SELECT ON students TO readonly_user;
GRANT SELECT ON courses TO readonly_user;
GRANT SELECT ON enrollments TO readonly_user;
```

이렇게 하면 `readonly_user`는 지정된 테이블을 조회할 수 있지만, 데이터를 수정할 수는 없습니다.

## 5. GRANT와 REVOKE

`GRANT`는 권한을 부여할 때 사용합니다. `REVOKE`는 권한을 회수할 때 사용합니다.

![GRANT와 REVOKE 흐름](../../images/chapter11/ch11_04_grant_revoke_flow.svg)

그림 11-4 GRANT와 REVOKE 흐름

| 명령 | 의미 |
| --- | --- |
| GRANT | 권한 부여 |
| REVOKE | 권한 회수 |

예를 들어 읽기 권한을 부여하려면 다음처럼 작성할 수 있습니다.

```sql
GRANT SELECT ON courses TO readonly_user;
```

반대로 권한을 회수하려면 다음처럼 작성합니다.

```sql
REVOKE SELECT ON courses FROM readonly_user;
```

쓰기 권한이 필요한 경우에도 권한을 세분화해서 부여할 수 있습니다.

```sql
GRANT INSERT, UPDATE ON enrollments TO app_user;
```

다만 초급 단계에서는 다음 원칙을 먼저 기억하는 것이 좋습니다.

```text
관리자 권한을 기본값으로 주지 않는다.
읽기만 필요한 계정에는 SELECT만 부여한다.
서비스 계정에는 실제 기능에 필요한 권한만 부여한다.
권한을 부여한 뒤에는 반드시 확인한다.
```

## 6. 개발용 계정과 운영용 계정 구분

실무에서는 개발 환경과 운영 환경을 구분해야 합니다.

![개발용 계정과 운영용 계정 분리](../../images/chapter11/ch11_05_dev_prod_account_separation.svg)

그림 11-5 개발용 계정과 운영용 계정 분리

| 구분 | 설명 |
| --- | --- |
| 개발 환경 | 개발자와 테스트용 데이터가 있는 환경 |
| 운영 환경 | 실제 사용자의 데이터가 있는 환경 |

개발 환경에서 사용하는 계정과 운영 환경에서 사용하는 계정은 분리해야 합니다.

좋지 않은 방식은 다음과 같습니다.

```text
- 개발용 관리자 계정을 운영 서비스에서도 그대로 사용한다.
- 모든 개발자가 운영 DB 관리자 비밀번호를 공유한다.
- 테스트용 SQL을 운영 DB에서 그대로 실행한다.
```

좋은 방식은 다음과 같습니다.

```text
- 개발 DB와 운영 DB를 분리한다.
- 운영 DB 접속 권한은 필요한 사람에게만 부여한다.
- 서비스용 계정은 필요한 테이블과 작업에만 접근한다.
- 실습이나 테스트는 별도 DB에서 수행한다.
```

## 7. 비밀번호와 접속 정보 관리

데이터베이스 접속 정보는 매우 민감한 정보입니다.

다음 정보는 코드에 직접 작성하지 않는 것이 좋습니다.

```text
- DB_HOST
- DB_PORT
- DB_NAME
- DB_USER
- DB_PASSWORD
```

특히 다음과 같은 방식은 피해야 합니다.

```text
- 소스코드에 DB 비밀번호를 직접 작성한다.
- GitHub 공개 저장소에 .env 파일을 올린다.
- 팀 채팅방에 운영 DB 비밀번호를 평문으로 공유한다.
- 여러 사람이 하나의 관리자 계정을 공유한다.
```

일반적으로는 `.env` 파일이나 클라우드의 Secret 관리 기능을 사용합니다. 단, `.env` 파일은 `.gitignore`에 포함해 저장소에 올라가지 않도록 해야 합니다.

예시는 다음과 같습니다.

```text
.env
.env.local
```

`.gitignore`에는 다음처럼 추가할 수 있습니다.

```text
.env
.env.*
```

## 8. SQL Injection 개념

SQL Injection은 사용자 입력값이 SQL 문장의 구조에 영향을 주어, 의도하지 않은 조회나 변경이 발생할 수 있는 보안 취약점입니다.

![SQL Injection 위험과 안전한 쿼리](../../images/chapter11/ch11_06_sql_injection_safe_query.svg)

그림 11-6 SQL Injection 위험과 안전한 쿼리

초급자는 다음 원칙만 먼저 기억해도 좋습니다.

```text
사용자 입력값을 SQL 문자열에 직접 이어 붙이지 않는다.
입력값은 파라미터로 전달한다.
AI가 만든 로그인 SQL도 문자열 결합 방식이면 반드시 검토한다.
```

위험한 패턴은 다음과 같이 표현할 수 있습니다.

```text
SQL 문자열 + 사용자 입력값 + SQL 문자열
```

안전한 방향은 다음과 같습니다.

```text
SQL 문장 구조와 사용자 입력값을 분리한다.
```

예를 들어 애플리케이션 코드에서는 보통 다음과 같은 파라미터 바인딩 방식을 사용합니다.

```text
SELECT id, email
FROM users
WHERE email = ?
```

또는 사용하는 라이브러리에 따라 `$1`, `:email` 같은 placeholder를 사용합니다.

핵심은 입력값을 SQL 명령처럼 해석하지 않도록 분리하는 것입니다.

## 9. 개인정보 보호 기본 원칙

데이터베이스에는 개인정보가 들어갈 수 있습니다.

온라인 강의 시스템에서는 다음 정보가 개인정보에 해당할 수 있습니다.

```text
- 이름
- 이메일
- 전화번호
- 결제 관련 정보
- 수강 이력
```

개인정보를 다룰 때는 다음 원칙을 지켜야 합니다.

| 원칙 | 설명 |
| --- | --- |
| 최소 수집 | 필요한 정보만 저장한다 |
| 최소 접근 | 필요한 사람만 접근한다 |
| 목적 제한 | 수집 목적에 맞게만 사용한다 |
| 보관 기간 관리 | 불필요하게 오래 보관하지 않는다 |
| 로그 주의 | 민감 정보가 로그에 남지 않게 한다 |

수업 예제에서는 실제 개인정보를 사용하지 않고 가상의 샘플 데이터를 사용해야 합니다.

## 10. 백업이란 무엇인가

백업은 데이터 손실에 대비해 데이터를 별도로 복사해 두는 작업입니다.

![백업과 복구 테스트 흐름](../../images/chapter11/ch11_07_backup_restore_flow.svg)

그림 11-7 백업과 복구 테스트 흐름

데이터가 손실될 수 있는 상황은 다양합니다.

```text
- 사용자가 실수로 데이터를 삭제했다.
- 잘못된 UPDATE가 많은 행에 적용되었다.
- 서버 장애가 발생했다.
- 저장장치 문제가 발생했다.
- 배포 중 예상치 못한 오류가 발생했다.
```

백업은 이런 상황에서 되돌아갈 수 있는 안전망입니다.

하지만 백업 파일만 있다고 충분한 것은 아닙니다. 실제로 복구할 수 있는지 테스트해야 합니다.

```text
백업의 완성은 백업 파일 생성이 아니라 복구 테스트이다.
```

## 11. 백업 종류 맛보기

백업은 목적에 따라 여러 방식으로 나눌 수 있습니다.

| 종류 | 설명 | 예시 |
| --- | --- | --- |
| 논리 백업 | SQL 또는 덤프 형태로 데이터와 구조를 저장 | pg_dump |
| 물리 백업 | 데이터 파일 자체를 복사 | 서버 파일 백업 |
| 전체 백업 | 전체 데이터베이스를 백업 | 매일 새벽 전체 백업 |
| 부분 백업 | 특정 테이블 또는 스키마만 백업 | 특정 테이블만 백업 |
| 정기 백업 | 일정 주기로 자동 백업 | 매일/매주 백업 |

초급 단계에서는 `pg_dump`를 사용한 논리 백업 개념을 이해하면 충분합니다.

## 12. pg_dump 백업 맛보기

PostgreSQL에서는 `pg_dump` 명령으로 데이터베이스를 백업할 수 있습니다.

기본 형식은 다음과 같습니다.

```bash
pg_dump -U postgres -d ai_database_book -f ai_database_book_backup.sql
```

이 명령의 의미는 다음과 같습니다.

| 구성 | 의미 |
| --- | --- |
| pg_dump | PostgreSQL 백업 도구 |
| -U postgres | 접속 사용자 |
| -d ai_database_book | 백업할 데이터베이스 이름 |
| -f ai_database_book_backup.sql | 저장할 백업 파일 |

운영 환경에서는 다음 사항도 함께 검토해야 합니다.

```text
- 백업 파일 저장 위치
- 백업 파일 접근 권한
- 백업 파일 암호화 여부
- 백업 주기
- 백업 보관 기간
- 복구 테스트 일정
```

## 13. 복구 맛보기

백업 파일은 복구할 수 있어야 의미가 있습니다.

SQL 파일 형태의 백업은 `psql`로 복구할 수 있습니다.

```bash
psql -U postgres -d ai_database_book_restore -f ai_database_book_backup.sql
```

여기서 중요한 점은 운영 데이터베이스에 바로 복구 테스트를 하지 않는 것입니다.

복구 테스트는 보통 별도의 테스트용 데이터베이스에서 수행합니다.

```text
1. 테스트용 복구 DB를 만든다.
2. 백업 파일을 복구 DB에 적용한다.
3. 테이블 수와 주요 데이터 수를 확인한다.
4. 서비스에 필요한 핵심 조회가 되는지 확인한다.
5. 문제가 있으면 백업 절차를 수정한다.
```

## 14. 백업 운영 체크리스트

백업을 운영할 때는 다음 질문을 확인해야 합니다.

| 질문 | 확인 |
| --- | --- |
| 백업 주기가 정해져 있는가? |  |
| 백업 파일이 안전한 위치에 저장되는가? |  |
| 백업 파일 접근 권한이 제한되어 있는가? |  |
| 백업 파일이 암호화되어야 하는가? |  |
| 복구 테스트를 정기적으로 하는가? |  |
| 오래된 백업 파일 삭제 정책이 있는가? |  |
| 장애 발생 시 누가 복구를 수행하는가? |  |
| 복구 절차가 문서화되어 있는가? |  |

이 표는 작은 프로젝트에서도 사용할 수 있습니다.

## 15. AI가 제안한 보안 설정과 백업 명령 검토하기

AI에게 다음처럼 요청할 수 있습니다.

```text
PostgreSQL 데이터베이스의 보안 설정과 백업 명령을 추천해 주세요.
초급자가 이해할 수 있도록 설명해 주세요.
```

AI는 계정 생성, 권한 부여, 백업 명령을 제안할 수 있습니다. 하지만 이를 그대로 실행해서는 안 됩니다.

![AI 보안·백업 명령 검토 흐름](../../images/chapter11/ch11_08_ai_security_review_flow.svg)

그림 11-8 AI 보안·백업 명령 검토 흐름

다음 기준으로 검토해야 합니다.

| 검토 항목 | 확인 질문 |
| --- | --- |
| 계정 권한 | 관리자 권한을 과도하게 주고 있지 않은가? |
| 최소 권한 | 필요한 권한만 부여하는가? |
| 비밀번호 | 예시 비밀번호를 그대로 사용하지 않는가? |
| 접속 정보 | 비밀번호가 코드나 문서에 노출되지 않는가? |
| 대상 DB | 운영 DB와 실습 DB를 혼동하지 않았는가? |
| 위험 명령 | 삭제, 덮어쓰기, 권한 확대 명령이 포함되어 있지 않은가? |
| 백업 파일 | 저장 위치와 접근 권한이 안전한가? |
| 복구 테스트 | 별도 테스트 DB에서 검증하는가? |

AI가 만든 명령은 편리한 초안입니다. 최종 적용 여부는 사람이 환경과 위험성을 검토한 뒤 결정해야 합니다.

## 16. 자주 하는 실수

### 실수 1. 개발용 관리자 계정을 운영에서 그대로 사용한다

운영 서비스에는 필요한 권한만 가진 계정을 사용해야 합니다.

### 실수 2. 모든 계정에 모든 권한을 준다

권한이 많을수록 실수나 공격의 피해도 커질 수 있습니다.

### 실수 3. 비밀번호를 코드에 직접 작성한다

DB 접속 정보는 환경 변수나 Secret 관리 기능을 사용해 관리해야 합니다.

### 실수 4. 백업만 하고 복구 테스트를 하지 않는다

복구할 수 없는 백업은 실제 장애 상황에서 도움이 되지 않습니다.

### 실수 5. AI가 만든 보안 설정을 그대로 적용한다

AI가 만든 SQL이나 명령은 환경을 모르는 상태에서 작성된 초안일 수 있습니다.

## 17. 연습 문제

### 17.1 개념 확인

1. 최소 권한 원칙이 무엇인지 설명하세요.
2. 읽기 전용 계정이 필요한 상황을 예로 들어 보세요.
3. GRANT와 REVOKE의 차이를 설명하세요.
4. SQL Injection을 막기 위한 기본 원칙을 설명하세요.
5. 백업 후 복구 테스트가 필요한 이유를 설명하세요.

### 17.2 SQL 작성 문제

다음 요구사항에 맞는 SQL을 작성하세요.

```text
1. 읽기 전용 계정 readonly_user를 생성한다.
2. readonly_user에게 데이터베이스 접속 권한을 부여한다.
3. readonly_user에게 students, courses 테이블 SELECT 권한을 부여한다.
4. courses 테이블 SELECT 권한을 회수한다.
```

### 17.3 검토 문제

다음 상황에서 문제가 될 수 있는 부분을 설명하세요.

```text
- 운영 DB 관리자 비밀번호를 소스코드에 직접 작성했다.
- 리포트 조회 계정에 INSERT, UPDATE, DELETE 권한까지 부여했다.
- 매일 백업 파일은 만들지만 복구 테스트를 한 적이 없다.
- AI가 만든 백업 명령을 운영 DB에서 바로 실행했다.
```

## 18. 정리

이번 장에서는 데이터베이스 보안과 백업의 기본을 학습했습니다.

핵심 내용을 정리하면 다음과 같습니다.

```text
1. 데이터베이스 보안은 중요한 데이터를 보호하기 위한 기본 조건이다.
2. 모든 사용자에게 관리자 권한을 주면 위험하다.
3. 최소 권한 원칙에 따라 필요한 권한만 부여해야 한다.
4. GRANT는 권한 부여, REVOKE는 권한 회수에 사용한다.
5. DB 비밀번호와 접속 정보는 코드에 직접 작성하지 않는다.
6. 사용자 입력값은 SQL 문자열에 직접 결합하지 않는다.
7. 백업은 데이터 손실에 대비한 안전망이다.
8. 백업은 복구 테스트까지 해야 의미가 있다.
9. AI가 만든 보안 설정과 백업 명령도 사람이 검토해야 한다.
```

이 장에서 가장 중요한 문장은 다음입니다.

```text
데이터베이스는 빠르게 조회되는 것만큼 안전하게 보호되고 복구 가능해야 한다.
```
