# Chapter 11 구성안

## 제목

데이터베이스를 안전하게 지키고 복구하는 방법

## 권장 분량

20~24페이지

## 이 장의 역할

데이터베이스를 만드는 방법에서 한 단계 더 나아가, 데이터를 안전하게 사용하고 문제가 발생했을 때 복구할 수 있는 기본 운영 원칙을 설명한다.

보안 기술을 나열하기보다 다음 질문에 답하는 흐름으로 구성한다.

```text
누가 데이터베이스에 접속할 수 있는가?
접속한 사용자는 무엇을 할 수 있는가?
사용자 입력이 SQL 구조를 바꾸지 못하게 하려면 어떻게 해야 하는가?
접속 정보와 개인정보는 어디에 보관해야 하는가?
데이터가 삭제되거나 손상되었을 때 되돌릴 수 있는가?
백업 파일이 실제로 복구 가능한지 어떻게 확인하는가?
AI가 만든 보안 설정과 명령을 그대로 실행해도 되는가?
```

## 독자가 얻게 될 것

- 데이터베이스 보안을 접근 통제, 권한 통제, 입력값 처리, 데이터 보호 관점에서 설명할 수 있다.
- 관리자 계정, 애플리케이션 계정, 읽기 전용 계정의 역할을 구분할 수 있다.
- 최소 권한 원칙에 따라 필요한 권한만 설계할 수 있다.
- PostgreSQL의 `GRANT`, `REVOKE`, 권한 확인 명령을 읽을 수 있다.
- SQL Injection이 발생하는 구조와 파라미터 바인딩의 필요성을 이해할 수 있다.
- 비밀번호, 접속 URL, 환경 변수와 저장소를 안전하게 관리할 수 있다.
- `pg_dump`와 `psql`을 이용한 논리 백업·복구 흐름을 이해할 수 있다.
- 백업 주기보다 복구 가능성 검증이 더 중요할 수 있음을 설명할 수 있다.
- AI가 제안한 권한과 백업 명령의 위험 요소를 점검할 수 있다.

## 주요 개념

- 접근 통제
- 인증과 권한
- 최소 권한 원칙
- 역할과 계정 분리
- `GRANT`와 `REVOKE`
- 파라미터 바인딩
- SQL Injection
- 비밀정보와 환경 변수
- 개인정보 최소 수집과 최소 접근
- 논리 백업과 복구
- 복구 테스트
- RPO와 RTO의 기초 개념

## 본문 구성

1. 빠른 데이터베이스보다 안전한 데이터베이스가 먼저인 이유
2. 데이터베이스 보안을 바라보는 네 가지 관점
3. 계정과 역할을 분리하는 이유
4. 최소 권한 원칙과 권한 설계
5. PostgreSQL의 `GRANT`, `REVOKE`, 권한 확인
6. 개발 환경과 운영 환경 분리
7. 비밀번호와 접속 정보 관리
8. SQL Injection과 파라미터 바인딩
9. 개인정보와 로그를 다루는 기본 원칙
10. 백업이 필요한 장애 시나리오
11. 논리 백업과 복구 명령 이해
12. 백업 주기, 보관 위치, RPO와 RTO
13. 별도 데이터베이스에서 복구 검증하기
14. AI가 생성한 보안·백업 명령 검토하기
15. 운영 전 최종 점검표

## 독자 참여 요소

- 읽기 전용 계정과 서비스 계정의 권한 비교
- 위험한 문자열 결합 방식과 파라미터 바인딩 비교
- 공개 저장소에 포함하면 안 되는 정보 찾기
- 소규모 서비스의 백업·복구 계획 작성
- AI가 제안한 과도한 권한과 위험한 복구 명령 수정

## 편집 원칙

- 특정 수업, 학생, 제출 기한, 배점, 평가 표현을 본문에 넣지 않는다.
- 실제 운영 데이터베이스에서 위험한 명령을 따라 하도록 유도하지 않는다.
- 역할 생성과 권한 변경 명령은 기본적으로 주석 처리된 예제로 제시한다.
- 예시 비밀번호는 실제 환경에서 사용할 수 없음을 명확히 밝힌다.
- 백업 파일 생성과 복구 성공을 별개의 단계로 설명한다.
- 특정 조직의 보안 정책이나 법률 요구사항을 일반화하지 않는다.
