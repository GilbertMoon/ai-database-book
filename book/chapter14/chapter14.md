# Chapter 14. Vector DB와 RAG 기초

이 장에서는 Vector DB와 RAG를 입문 관점에서 정리합니다. 핵심은 “SQL 검색을 버리고 벡터 검색으로 바꾼다”가 아닙니다. PostgreSQL에서도 벡터 검색은 SQL로 실행할 수 있습니다. 비교해야 할 것은 SQL이라는 질의 언어와 벡터 검색의 대립이 아니라, 정확한 조건이나 키워드로 찾는 방식과 임베딩 거리로 의미가 가까운 문서를 찾는 방식의 차이입니다.

## 1. 왜 Vector DB와 RAG를 배우는가

일반적인 데이터베이스 검색은 명확한 조건에 강합니다.

- 상태가 `active`인 사용자 찾기
- 특정 날짜 이후에 작성된 공지 찾기
- 제목에 `환불`이라는 단어가 포함된 문서 찾기

하지만 사용자는 항상 같은 단어를 쓰지 않습니다. “환불 기준이 궁금해요”라는 질문은 “결제 취소”, “구독 취소”, “돈을 돌려받는 조건” 같은 문서와 관련될 수 있습니다. 이때 임베딩과 벡터 검색은 단어가 완전히 일치하지 않아도 의미가 가까운 문서를 후보로 찾는 데 도움을 줍니다.

RAG는 검색된 문서를 LLM에게 근거로 제공해 답변하게 하는 방식입니다. 모델 가중치를 다시 학습하는 과정이 아니라, 질문 시점에 관련 문서를 찾아 컨텍스트로 넣는 방식입니다.

## 2. 구조화 조건 검색, 키워드 검색, 의미 기반 검색

검색 방식은 하나가 아닙니다.

![구조화·키워드 검색과 벡터 의미 검색](../../images/chapter14/ch14_01_sql_vs_semantic_search.svg)

그림 14-1 구조화·키워드 검색과 벡터 의미 검색

| 검색 방식 | 기준 | 예시 |
|---|---|---|
| 구조화 조건 검색 | 정확한 컬럼 값과 범위 | 공개 문서, 최신 버전, 접근 권한 있음 |
| 키워드 검색 | 문자열 포함 | 제목에 `환불` 포함 |
| 벡터 의미 검색 | 임베딩 벡터 간 거리 | “돈을 돌려받는다”와 가까운 환불 문서 |
| 혼합 검색 | 구조화 필터 + 의미 순위 | 공개 문서 중 환불 관련 Top-3 |

구조화 조건 검색과 키워드 검색은 정확한 조건에 강합니다. 벡터 의미 검색은 표현이 달라도 의미가 가까운 문서를 찾는 데 유용합니다. 실무에서는 두 방식을 함께 쓰는 혼합 검색이 자주 필요합니다.

## 3. 임베딩이란 무엇인가

임베딩은 모델이 텍스트를 고정 길이 숫자 벡터로 변환한 결과입니다.

![텍스트를 같은 벡터 공간으로 변환하기](../../images/chapter14/ch14_02_embedding_vector_conversion.svg)

그림 14-2 텍스트를 같은 벡터 공간으로 변환하기

벡터의 각 숫자를 사람이 개별적으로 해석하기는 어렵습니다. 중요한 것은 같은 임베딩 모델이 비슷한 의미의 텍스트를 가까운 위치에 놓도록 학습되어 있다는 점입니다. 다만 가까운 위치가 항상 인간의 기대와 완전히 일치하는 것은 아닙니다.

임베딩 비교에는 조건이 있습니다.

| 확인 항목 | 이유 |
|---|---|
| 같은 모델 | 서로 같은 벡터 공간이어야 합니다. |
| 같은 모델 버전 | 모델 업데이트로 벡터 분포가 달라질 수 있습니다. |
| 같은 차원 | 거리 계산을 하려면 길이가 같아야 합니다. |
| 같은 전처리 기준 | 문서와 질문 처리 방식이 달라지면 결과가 흔들릴 수 있습니다. |
| 같은 거리 함수 | 점수 방향과 의미를 일관되게 해석해야 합니다. |

이 장의 수동 3차원 벡터는 실제 임베딩 모델 결과가 아닙니다. 거리 계산 원리를 설명하기 위해 사람이 만든 `manual-demo-3d` 예시입니다.

## 4. 벡터 거리와 Top-k 검색

벡터 검색은 질문 벡터와 문서 벡터 사이의 거리를 계산하고 가까운 후보를 정렬합니다.

![L2 거리, Top-k, 임계값으로 근거 후보 선택](../../images/chapter14/ch14_03_vector_similarity_topk.svg)

그림 14-3 L2 거리, Top-k, 임계값으로 근거 후보 선택

| 표현 | 의미 |
|---|---|
| L2 거리 | 작을수록 가깝습니다. |
| 코사인 거리 | 작을수록 방향이 유사합니다. |
| 코사인 유사도 | 일반적으로 클수록 유사합니다. |
| Top-k | 가장 가까운 후보 k개입니다. |
| 임계값 | 관련성이 부족한 후보를 제외하는 기준입니다. |

pgvector에서 `<->`는 L2 거리이고, `<=>`는 코사인 거리입니다. 코사인 유사도는 `1 - (embedding <=> query)`처럼 계산할 수 있습니다. 이 장의 기본 SQL 실습은 L2 거리만 사용합니다.

Top-k에 포함되었다는 것은 다른 문서보다 상대적으로 가깝다는 뜻입니다. 질문에 답할 만큼 충분히 관련 있다는 뜻은 아닙니다. 따라서 Top-k 결과 뒤에는 사람이 정한 평가 기준이나 검증 절차가 필요합니다.

## 5. Vector DB와 벡터 검색 기능의 역할

Vector DB는 임베딩 벡터와 메타데이터를 저장하고, 가까운 벡터를 검색하는 기능을 중심으로 설계된 저장소 또는 기능입니다. Vector DB가 임베딩을 직접 생성한다고 설명하면 안 됩니다. 임베딩은 임베딩 모델이 만들고, Vector DB나 pgvector는 그 벡터를 저장하고 검색합니다.

Vector DB라는 말은 여러 형태로 쓰입니다.

- 벡터 검색을 중심으로 설계된 전용 제품
- PostgreSQL + pgvector처럼 기존 DB에 벡터 검색을 추가한 방식
- 검색 엔진이나 데이터 플랫폼 안의 벡터 검색 기능

제품 형태는 달라도 핵심 역할은 같습니다. 벡터와 메타데이터를 저장하고 가까운 벡터를 찾습니다. 검색 결과가 실제 질문과 관련 있는지는 별도로 평가해야 합니다.

## 6. 문서 청킹과 메타데이터

RAG는 긴 문서를 그대로 넣기보다 적당한 단위로 나누어 검색합니다. 이 과정을 청킹이라고 합니다.

![원문을 의미 단위 청크로 나누기](../../images/chapter14/ch14_04_document_chunking.svg)

그림 14-4 원문을 의미 단위 청크로 나누기

청크에는 본문뿐 아니라 메타데이터가 함께 필요합니다.

- 문서명
- 청크 번호
- 문서 버전
- 업데이트 시각
- 접근 권한
- 임베딩 모델과 버전

문서가 변경되면 기존 벡터는 낡은 파생 데이터가 됩니다. 원문을 다시 청킹하고 재임베딩하거나, 삭제된 문서의 벡터를 검색 대상에서 제거해야 합니다.

## 7. RAG의 기본 흐름

RAG는 색인 단계와 질문 처리 단계로 나눌 수 있습니다.

![RAG의 색인, 검색, 답변, 검토 흐름](../../images/chapter14/ch14_05_rag_pipeline.svg)

그림 14-5 RAG의 색인, 검색, 답변, 검토 흐름

1. 원문 문서를 수집합니다.
2. 문서를 청크로 나눕니다.
3. 청크를 임베딩합니다.
4. 원문 메타데이터와 벡터를 저장합니다.
5. 질문을 임베딩합니다.
6. 접근 권한과 최신성 필터를 먼저 적용합니다.
7. 관련 청크를 Top-k로 검색합니다.
8. 근거가 충분한지 확인합니다.
9. 검색된 청크를 LLM 컨텍스트로 전달합니다.
10. 답변과 출처를 검토합니다.

근거가 부족하면 답변을 억지로 만들지 않아야 합니다. 질문 표현, 필터, Top-k, 임계값, 청킹 방식을 조정하거나 답변을 보류해야 합니다.

## 8. PostgreSQL과 pgvector

pgvector는 PostgreSQL에서 벡터 타입과 벡터 거리 검색을 사용할 수 있게 하는 확장입니다. pgvector는 텍스트를 임베딩하지 않습니다. 임베딩 모델이 만든 벡터를 PostgreSQL에 저장하고 SQL로 검색할 수 있게 해 줍니다.

![pgvector와 수동 3차원 벡터 실습 비교](../../images/chapter14/ch14_06_pgvector_practice_flow.svg)

그림 14-6 pgvector와 수동 3차원 벡터 실습 비교

실습 파일에는 pgvector 확인 쿼리가 포함되어 있습니다.

```sql
SELECT name, default_version, installed_version
FROM pg_available_extensions
WHERE name = 'vector';

SELECT to_regtype('vector') AS vector_type_in_current_database;
```

`CREATE EXTENSION`은 운영체제에 pgvector를 설치하는 명령이 아닙니다. 서버에 확장 파일이 준비되어 있고 현재 DB에 확장을 생성할 권한이 있을 때 활성화하는 명령입니다. 운영 DB에서는 임의로 실행하지 않습니다.

pgvector 공식 문서 기준으로 기본 검색은 정확 최근접 검색입니다. HNSW와 IVFFlat은 근사 최근접 검색 인덱스입니다. 근사 검색은 속도를 얻는 대신 일부 결과 재현율을 희생할 수 있습니다. 이 장의 기본 실습은 7개 문서만 사용하므로 HNSW나 IVFFlat 인덱스를 만들지 않습니다.

## 10. 일반 LLM 답변과 RAG 답변 비교

일반 LLM 답변은 모델 내부 지식과 입력 프롬프트에 의존합니다. RAG 답변은 검색된 문서를 근거로 답변하도록 설계합니다.

| 구분 | 일반 LLM 답변 | RAG 답변 |
|---|---|---|
| 근거 | 모델 내부 지식 중심 | 검색 문서 중심 |
| 최신 문서 반영 | 제한적일 수 있음 | 문서 업데이트와 재임베딩 필요 |
| 내부 문서 활용 | 프롬프트에 넣어야 함 | 검색으로 관련 청크 제공 |
| 검토 기준 | 답변 자체의 그럴듯함 | 검색 적합성 + 답변 근거성 |

RAG도 환각을 완전히 제거하지 않습니다. 검색 문서가 틀리거나, 검색은 맞았지만 답변이 문서에 없는 주장을 추가할 수 있습니다.

## 11. 작은 예제: 서비스 공지 RAG

질문: “환불은 언제까지 가능한가요?”

검색 결과 후보:

1. `구독 취소`: 취소 절차와 환불 기준 참조
2. `환불 기준`: 결제 후 7일 이내 전액 환불 가능
3. `이용권 변경`: 다음 결제일부터 적용

좋은 RAG 답변은 `환불 기준` 문서를 핵심 근거로 사용하고, `구독 취소` 문서는 보조 근거로 해석합니다. “30일 이내 언제든 환불”처럼 검색 문서에 없는 내용을 만들면 unsupported claim입니다.

## 12. 검색 적합성과 답변 근거성 평가

검색 적합성과 답변 근거성은 다른 평가 항목입니다.

![검색 적합성과 답변 근거성 분리 검토](../../images/chapter14/ch14_07_rag_answer_grounding_review.svg)

그림 14-7 검색 적합성과 답변 근거성 분리 검토

| 사례 | 검색 적합 | 답변 근거 | unsupported claim | 해석 |
|---|---|---|---|---|
| 정상 답변 | TRUE | TRUE | FALSE | 검색과 답변이 모두 적절함 |
| 근거 없는 주장 | TRUE | FALSE | TRUE | 검색은 맞지만 답변이 문서 밖 내용을 추가함 |
| 부적합 검색 | FALSE | TRUE | FALSE | 답변은 선택 문서에 근거하지만 질문과 문서가 맞지 않음 |

근거가 부족하면 답변을 보류하거나 “제공된 문서만으로는 확인할 수 없습니다”라고 안내해야 합니다.

## 13. 문서 업데이트와 재임베딩

RAG 시스템은 문서 변경에 민감합니다.

- 원문이 변경되면 청크를 다시 만들어야 할 수 있습니다.
- 청크가 바뀌면 임베딩도 다시 만들어야 합니다.
- 문서가 삭제되면 벡터 검색 대상에서도 제외해야 합니다.
- 접근 권한이 바뀌면 검색 전에 필터가 적용되어야 합니다.
- 임베딩 모델이 바뀌면 기존 문서를 같은 모델로 재임베딩해야 합니다.

벡터 인덱스는 원문에서 다시 만들 수 있는 파생 데이터입니다. 원문과 출처, 버전, 권한 정보가 기준 데이터입니다.

## 14. Vector DB와 기존 저장소의 역할

RAG 시스템에서는 저장소마다 역할이 다릅니다.

![RAG 저장소 역할 분리](../../images/chapter14/ch14_08_db_role_separation.svg)

그림 14-8 RAG 저장소 역할 분리

| 저장소 | 역할 |
|---|---|
| 업무 RDBMS | 사용자, 권한, 로그, 설정 같은 구조화 데이터 관리 |
| 문서 저장소 | 원문 문서, 버전, 파일, 작성자 관리 |
| 벡터 인덱스 | 청크 임베딩과 메타데이터를 이용한 의미 검색 |
| 검색 로그 | 질문, 검색 결과, 거리, 답변 검토 기록 관리 |

역할 분리는 논리적 개념입니다. 반드시 제품을 네 개 써야 한다는 뜻은 아닙니다. PostgreSQL과 pgvector처럼 한 시스템 안에서도 역할을 나누어 설계할 수 있습니다.

## 15. AI 활용 실습: RAG 설계 검토

AI에게 RAG 설계를 검토하게 할 때는 다음 질문을 포함합니다.

- 문서 원본과 벡터 파생 데이터의 역할이 구분되어 있는가?
- 질문과 문서가 같은 임베딩 모델, 버전, 차원을 쓰는가?
- 접근 권한 필터가 검색 전에 적용되는가?
- Top-k와 임계값을 어떤 데이터로 검증했는가?
- 검색 적합성과 답변 근거성을 분리해 평가하는가?
- 근거가 부족할 때 답변을 보류하는 흐름이 있는가?
- 문서 업데이트와 재임베딩 절차가 있는가?

## 16. 자주 하는 실수

- Vector DB가 임베딩을 자동으로 만든다고 생각한다.
- SQL 검색과 벡터 검색을 대립 관계로 설명한다.
- `<->`를 코사인 유사도처럼 설명한다.
- Top-k 결과를 모두 정답 문서로 간주한다.
- 문서와 질문의 임베딩 모델, 버전, 차원을 확인하지 않는다.
- 검색 적합성과 답변 근거성을 하나로 평가한다.
- 접근 권한 필터를 검색 뒤에만 처리한다.
- 문서 변경 후 재임베딩을 하지 않는다.
- RAG가 환각을 완전히 제거한다고 설명한다.

## 18. 정리

Vector DB와 RAG는 기존 데이터베이스를 대체하는 기술이 아닙니다. 구조화 데이터, 문서 원문, 벡터 인덱스, 검색 로그가 각자의 역할을 하며 함께 작동합니다.

이 장의 핵심은 다음과 같습니다.

- 벡터 검색도 PostgreSQL에서는 SQL로 실행할 수 있습니다.
- 임베딩 모델이 텍스트를 벡터로 변환하고, Vector DB는 벡터 저장과 검색을 담당합니다.
- 질문과 문서는 같은 임베딩 모델, 버전, 차원, 전처리 기준을 사용해야 합니다.
- pgvector의 `<->`는 L2 거리, `<=>`는 코사인 거리입니다.
- 기본 검색은 정확 검색이고 HNSW/IVFFlat은 근사 검색 인덱스입니다.
- Top-k는 상대적 순위이며 충분한 관련성을 보장하지 않습니다.
- RAG는 검색 문서를 근거로 답변하지만 환각을 완전히 제거하지 않습니다.
- 검색 적합성과 답변 근거성은 분리해서 평가해야 합니다.
